# 10 随机读瓶颈定位与提升计划（2026-06-19）

> 本文聚焦下一阶段的唯一目标——**纯随机读**。包含两部分:
> （A）对当前认识的两点关键澄清/纠错（"124 线速"的来历、"2.5× 放大"的归因存疑）;
> （B）后续行动计划（先分层定位、再据层优化）。
>
> 背景:在 256K 卷 + 直连 RADOS 的全链路优化下,单客户端测试结果已分化为两类——
> **顺序读写 + 随机写已到网卡/后端裸能力天花板（瓶颈=网卡,无需也无法再调）**;
> **唯独随机读 45.9 MB/s 未达标,且原因不同**（网卡 RX 已到 113,但有效读只有 45.9,被 ~2.5× 吃掉）。
> 故下一阶段**只聚焦随机读：先确认放大在哪一层,再决定如何提升。**

---

## 一、目标重定义（用户口径）

- **目标**:有效数据带宽 ≥ **网卡带宽的一半**。
  - 单客户端:单张千兆网卡半速 ≈ **59 MB/s**。
  - 多客户端聚合:集群多网卡半速之和 = 节点数 × 59（3 节点 → **177 MB/s**）。
- 这是一个**相对比例目标（半速）**,不是固定数值;**若千兆换万兆、或客户端数变化,验收线同步缩放**
  （万兆 → 单客户端目标 ~590;N 客户端 → N×单网卡半速）。

### 主攻方向：优先定位单客户端瓶颈（用户拍板）

> 多客户端聚合带宽虽更大,但**验收线也按客户端数同步抬高**（N 客户端 → N×59）,聚合涨多少、
> 验收线就抬多少,**治标不治本**。故调优**优先攻单客户端**:把单客户端从 ~45.9 推向 59。
> `10_2` 的多客户端数据**降级为旁证**（证明后端/网络有横向扩展空间）,不作单客户端达标依据。

---

## 二、概念澄清一：59 / 177 的物理基准 "124" 从哪来

千兆网卡 = 1 Gbps = 10⁹ bit/s。带宽标称用 bit,吞吐用 Byte（1 Byte = 8 bit）:

```
1 Gbit/s ÷ 8 = 125,000,000 Byte/s = 125 MB/s   （单网卡 · 单方向 · 理论线速）
扣以太网/IP/TCP 协议开销后实际可用 ≈ 117–124 MB/s
```

由此派生:

| 量 | 算法 | 含义 |
|----|------|------|
| 单网卡单方向线速 | 125 ≈ **124**（实际 117–124） | 每个测点头顶的硬天花板 |
| 单网卡半速 = **59** | 124 ÷ 2 | 单客户端验收目标 |
| **177** | 3 × 59 | 多客户端聚合验收目标 |

**实测都在往 124 顶**:单客户端 randread 时网卡 RX=113（91%）、rados bench 单点=118（95%）。
即每个**单一测点（单网卡单方向）**都被 124 封顶,这是后面所有分析的物理基准单位。

> ⚠️ **177 与"千兆"内在不自洽**:177 = 3×单网卡半速,但要真跑出 177 的聚合,
> 总流量必须摊到 ≥2 张网卡、每张单方向 < 124。在千兆 + EC 4+2 + FUSE 组合下,
> 后端 EC 聚合 ~145 ÷ 放大 ~2.5 ≈ **58 端到端上限**,先一步卡死,摸不到 177。
> → **177 这条线实质隐含"万兆网络"前提。** 千兆下随机读聚合的物理上限约 ~58。

## 三、概念澄清二："2.5× 放大"不是"FUSE 放大",归因仍存疑

### 1. 先纠正用词

- **块级放大（16×,已消灭）**:4M block 下读 256K 却取回整 4M。256K 卷已使 block=256K,不再多读。✅
- **残余 2.5×**:deepseek 在 `09_1` 7.5 笼统称"FUSE 放大",**此命名误导**。逐项看:

| 来源 | 是否产生额外网卡 RX 字节 | 量级 |
|------|------------------------|------|
| **EC 4+2 取片（256K=4×64K shard,跨 3 节点 6 OSD）** | **是,且大概率是大头** | 大 |
| TiKV 查元数据（读 chunk 前查位置） | 是（额外 TCP 往返） | 小 |
| librados / TCP 包头 | 是 | ~2% |
| **FUSE 上下文切换（内核↔用户态）** | **否——纯 CPU 开销,不上网卡** | ~0 字节 |

→ **真正让网卡 RX = 2.5× 有效读的,是网络层的协议封装 + EC 取片传输冗余,不是 FUSE。**
用户"不理解 FUSE 怎么放大网卡流量"的疑问是对的:**FUSE 切换确实不放大网卡流量。**

### 2. 归因为什么仍未被干净证实

deepseek 的现有证据链:
1. 网卡监控 randread 45.9 时 RX=113 → RX/有效读 ≈ 2.5×（✅ 测量可信）。
2. rados bench（无 FUSE）145 ÷ 端到端 55.6 ≈ 2.6×,与 2.5× 自洽。
3. `09_1` 第四节 EC vs 副本(size=3) 对照:换池后 RX/有效读仍 2.5×,据此判"EC 取片非主因,是 FUSE"。

**漏洞**:
- 第 3 步逻辑不严:副本只需从 1 个 OSD 读完整对象,EC 要从 4 个 OSD 取片,机制天差地别,
  RX 却"完全相同 2.5×"——这要么支持"与池类型无关"（FUSE 论）,**要么存在共同上游瓶颈
  （如客户端串行、固定 per-IO 开销）把两者都压在同一数上,掩盖了差异**。仅凭"两者相等"无法区分。
- **"FUSE"从未被单独剥离测过**:`09_1` 的 rados bench 是 4M 大对象 rand,口径与"256K 小对象随机读 +
  同并发模型"对不齐,不能据此证实/证伪 FUSE。

> **结论:方向（瓶颈在"客户端到后端的取片/协议链 + 单网卡"）大概率对,
> 但"具体是 FUSE 这一层"证据不足。后续不得直接采信"是 FUSE"。**

## 四、后续计划：只聚焦随机读,两步走

### 步骤 A（必做 · 定位）：用同口径 256K 随机读,分三层量"有效读带宽 + 网卡 RX/有效读比"

| 层 | 路径 | 回答 |
|----|------|------|
| **L1 裸 librados / rados** | 256K **随机读**（绕 FUSE、绕 CephFS） | 网络 + EC 取片本身的放大 |
| **L2 内核态 CephFS** | 同 fio 256K randread | 去掉 FUSE、保留网络/EC,看 RX 比降不降 |
| **L3 JuiceFS FUSE** | 现状（基线） | 全链路 2.5× |

判读:
- **L1 就已 2.5×** → 放大在**网络/EC**,与 FUSE 无关 → 优化走"升万兆 / 改 EC 分片 / 加节点"。
- **L1≈1、L2≈1、L3 才 2.5×** → **确是 FUSE** → 优化走 JuiceFS 读路径（但 v1.4 已显退化,空间存疑）。
- **L2 已 2.5×（但 L1 不是）** → 放大在**网络 + 访问模式**,CephFS 也救不了。

> 关键纪律:三层必须**同口径**（同 256K 随机读、同并发模型、同冷态 cache=0、同时采单方向网卡 RX/TX）,
> 否则不可比。这一步成本低、可一锤定音,是后续任何"提升"动作的前提——**不先定位,提升即猜测。**

#### L1 具体跑法（GLM 建议 + 必要补全）

GLM 建议用 `rados bench -p juicefs-data 60 rand -b 262144` 把放大切第一刀
（"JuiceFS 内部" vs "librados/EC/网络层"）——方向对、成本低,**已采纳为 L1**。
但裸命令只产出一个带宽数,无法直接得出"2.5×",必须配套三点(否则白跑):

1. **`-b 262144`(=256K) 不可省**:`rados bench` 默认 `-b 4M`,`09_1` 的 118/145 都是 **4M 大对象**,
   与 JuiceFS 256K 卷口径错位。换 256K 小对象后裸带宽**很可能明显低于 118**（小对象 IOPS 受限、
   每对象协议开销占比飙升）——这个新数才是与 JuiceFS 256K 真正可比的后端基准,顺带**修正"后端裸上限"本身**。
2. **同时采网卡 RX**（`/proc/net/dev` 跑前跑后取差）,才能算 `放大 = RX ÷ rados有效读带宽`,与 JuiceFS 的 2.5× 对照。
3. **口径对齐 + 单点干净发起**:并发扫 `-t 16 128`（逼近 JuiceFS iodepth/numjobs=128）;
   **从干净客户端 tikv-node 发起**（OSD 主机发起会 RX/TX 混算）;跑前 `write --no-cleanup` 垫够对象保证读冷数据。

**封装脚本**:[`tests/bench-rados-256k-rand.sh`](../../tests/bench-rados-256k-rand.sh)
（`-b 262144` + 跑前后 `/proc/net/dev` 差值算 RX/有效读比 + `-t` 并发扫 + write 垫数据/cleanup;不依赖 JuiceFS、不动任何卷）。
```bash
# 在干净客户端(tikv-node)上,环境空闲时:
CEPH_POOL=juicefs-data THREADS="16 128" RUNTIME=60 \
  setsid bash tests/bench-rados-256k-rand.sh l1-probe < /dev/null & disown
```

判读（L1 第一刀）:
- **L1 RX/有效读 ≈ 2.5×** → 放大在 **librados/EC/网络层**,JuiceFS 无辜 → 直接走步骤 B 的"网络/EC"行。
- **L1 ≈ 1.x** → 放大在 **JuiceFS 内部** → 再跑 **L2 CephFS** 切第二刀,区分是 FUSE 还是访问模式。

> L1 是二分定位的**第一刀**（JuiceFS 内部 vs 网络/EC）,不是终点;落在"JuiceFS 内部"时仍需 L2。

### 步骤 B（据 A 结果 · 优化）

| 若瓶颈落在 | 提升路线 | 备注 |
|-----------|----------|------|
| 网络 / EC 取片 | 升万兆;调 EC 分片策略;加节点（node3 .14 当前 SSH 不通） | 最可能命中,需硬件/架构动作 |
| FUSE 层 | JuiceFS 版本/参数、FUSE 读路径调优 | 软件层;v1.4 默认已证退化（见五）,空间可能有限 |
| 访问模式 | iodepth / numjobs / 预读模型 | `08_2` A/B 已大量试过无效,可能性低 |

> ⚠️ rados-4M 的 120/154（`10_2` 五）是 **4M 对象**,口径错位,**不作随机读后端基准**;
> 正确基准由 L1（`bench-rados-256k-rand.sh`,256K）现测——L1 直接替代这个废弃数。

### 前提提醒

千兆集群上,随机读聚合的物理上限约 **后端 145 ÷ 放大 2.5 ≈ 58**,而聚合目标 177 隐含万兆。
故步骤 A 很可能得出"要达标必须升万兆"——**这不是失败,而是关闭'软件能否解决'、给出明确架构结论**,
对决策同样有价值。

## 五、1.3 vs 1.4 基线已完成（结论：单客户端保 v1.3.1）

> 详见 [`10_1`](./10_1-v1.4-upgrade-test.md)、[`10_2`](./10_2-multiclient-aggregation-results.md)。本轮已对账核验（见六）。

| 场景 | v1.4 vs v1.3.1 | 含义 |
|------|---------------|------|
| **单客户端 randread** | **−3.3%**（45.7→44.2,逐 run 均低,非波动） | `--max-downloads` 引入调度开销,对单客户端**净损** |
| 多客户端 randread 聚合 | **+36~38%**（2cl 55→76、4cl 67→92） | 打破并发连接瓶颈,数量级增益（但属聚合,见下） |

- **本主线优先攻单客户端 → 生产保持 v1.3.1**;v1.4 仅在确定走多客户端架构时才考虑。
- **关键洞察(强化单客户端主线)**:多客户端 randread 涨,是靠**每台客户端各自的网卡 RX** 叠加
  （v1.4 2cl 76.5 = 两台各 ~38;4cl 92 = 四台各 ~23）。**任何单台都从未突破单网卡半速对应的有效读。**
  → 多客户端聚合**帮不上单客户端达标**,反证"单客户端的墙 = 单网卡 RX ÷ 放大",L1/L2/L3 定位仍是正解。

## 七、一句话总结

- 单客户端:顺序读写 + 随机写已到网卡天花板（无需调）;**唯随机读 45.9 未达标,因网卡 RX 被 ~2.5× 非有效流量占用。**
- 这 2.5× **大概率是网络/EC 取片 + 协议封装,而非 FUSE**;但归因未干净证实。
- 1.3-vs-1.4 基线已完成:**单客户端保 v1.3.1**（v1.4 单客户端 −3%,只利好多客户端聚合）。
- **优先攻单客户端**:下一步做 **L1/L2/L3 同口径分层定位** 找出放大所在层,再 **据层选择优化**（很可能指向万兆/架构）。
- 三类无效数据（randrw[analysis] / rados-4M / 不完整顺序）**弃用且不重测**,不作任何结论依据。
