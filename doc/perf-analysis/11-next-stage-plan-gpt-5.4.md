# 11 下一阶段计划（gpt-5.4，2026-06-24）

> 操作节点固定为 `tikv-node`（`192.168.11.12`，`turboai/TurboAi@303`）。
> 本文承接 `10_1` / `10_2`，只保留后续决策真正需要的结论，重点回答两件事：
> 1. 下一阶段到底是围绕“关闭预读后的副作用修复”继续做，还是继续追随机读根因。
> 2. `10` 阶段里未闭环的项，还有哪些值得继续做，哪些可以停。

## 一、当前阶段已收敛的最小结论

### 1. 单客户端主线没有变

- 验收口径是：**单项带宽达到当前网卡带宽的 50%**。
- 因此判断标准始终是“有效带宽占链路带宽的比例”，不是绝对 MB/s。
- 顺序读写、纯随机写已不是主矛盾；**单客户端随机读**仍是主矛盾。

### 2. `10` 阶段给出的关键信息

- `10_1`：v1.3.1 与 v1.4 单客户端基本持平，v1.4 没有把单客户端随机读拉上去。
- `10_1`：`--max-downloads` 只有 v1.4 有，且 **100 以上已饱和**；它不是当前单客户端瓶颈突破口。
- `10_2`：多客户端聚合能提升，但**不能当作单客户端达标依据**。
- `10_2`：多客户端目标也是 `N x 59`，不是固定 59；因此多客户端结果主要用于旁证“后端和系统还有横向扩展空间”。

### 3. 这一阶段新增的关键认识

- 当前最值得重视的新现象，不是“新版本更快”，而是：
  **预读行为会明显影响随机读有效带宽，但关闭预读又会拖累其他指标。**
- 这说明后续不该再泛泛地重复 `08/09` 已证无效的客户端参数 sweep，而应把问题收敛成：
  **哪些预读必须关，关到什么程度，以及关掉后损失的是哪一层能力。**

## 二、关于下一阶段主线的判断

### 结论

**下一阶段不建议在“完全放弃预读”和“只修关闭预读后的副作用”之间二选一。**

更合理的主线是：

1. **先把“预读影响”拆清楚，确认到底是哪一层预读在伤随机读。**
2. **以“随机读达标”为第一优先级，允许牺牲仍然高于验收线的非主矛盾指标。**
3. **一旦证明某层预读确实伤随机读，就在该层关闭，再只补真正被拉到验收线以下的指标。**

换句话说：

- 不是先假设“预读必须保留”，然后绕开它继续找别的瓶颈；
- 也不是先武断地“全关预读”，再盲目修副作用；
- 而是先把预读分层，找出**该关的是 JuiceFS 预读、FUSE readahead，还是两者都不是根因**。

### 原因

- 当前不达标的是随机读，所以优先级必须服从随机读。
- 但 `08_2` 已经证明：`--prefetch 0/16` 在当时的 4M/早期场景里基本无效，说明“预读”不能只理解为 JuiceFS 的 `--prefetch` 一个参数。
- 你现在明确说“经过 10 文档相关调优，基本确认预读是重要因素”，那就更说明：
  **最新问题很可能已经从早期 `--prefetch` 参数 sweep，转向了更具体的预读路径，例如 FUSE/VFS readahead 或特定访问模式触发的额外拉取。**
- 所以下一阶段最重要的不是重复测 `--prefetch`，而是把“预读”拆成可定位、可关闭、可复测的具体层次。

## 三、`10` 阶段里哪些未闭环项还值得继续做

### 值得继续做

#### 1. 预读分层定位

这是下一阶段第一优先级，理由是它直接决定主线。

至少要区分三种状态：

1. 默认挂载
2. 关闭 JuiceFS 侧预读
3. 关闭 FUSE/VFS 侧 readahead

如果条件允许，再补第四种：

4. JuiceFS 预读关闭 + FUSE readahead 关闭

这组测试的价值不在于“调参”，而在于回答：

- 随机读到底是被哪一层预读拉低的
- 顺序读/混合读写的损失来自哪一层
- 是否存在“只关一层就能保住随机读收益，同时把副作用压到最小”的折中点

#### 2. 随机读期间的真实流量画像

如果已经怀疑预读，就不能只看 fio 带宽，必须补**随机读时的真实拉取量**。

建议在 randread 期间同时记录：

- `sar -n DEV 1`
- `juicefs stats`
- 如可行，再抓客户端侧流量样本

要回答的问题是：

- 有效 randread 提升时，NIC RX 是下降了还是上升了
- object 层读流量与 fio 有效读之间的倍数关系是否变化
- 关闭某层预读后，是“少读了无效数据”，还是“总并发也被一起打掉了”

如果关闭预读后：

- fio randread 上升
- NIC RX 下降或持平

那就说明你拿到的是**真实效率提升**；这类改动值得继续推。

#### 3. FUSE 限流是否参与了“关闭预读后的副作用”

这一项值得做，但前提是要放在“预读分层测试”后面。

原因不是它一定是主因，而是：

- 关闭预读后，可能会让 I/O 更碎、更依赖请求数；
- 如果这时 FUSE `max_background` / `congestion_threshold` 成为限制，就会把本来能拿到的收益吞掉。

因此建议把它作为**第二层验证项**，不是第一主线。

#### 4. 仅保留与当前问题直接相关的 `10` 补测

还值得补的，只应保留这类问题：

- 能解释“为什么关闭预读会伤其他指标”
- 能解释“为什么随机读有效带宽占比上升/不上升”
- 能帮助判断正式生产配置到底选哪档

### 不值得继续做

#### 1. 再做版本主线扩展

`10_1` 已经足够说明：

- v1.4 对单客户端不是突破口
- `--max-downloads` 也不是单客户端当前主突破口

所以这条线现在不应再扩。

#### 2. 再拿多客户端结果替代单客户端判断

`10_2` 的价值已经够了：

- 它证明系统能横向扩展
- 但它不能回答单客户端为何达不到目标比例

所以这条线也不应继续消耗主线时间。

#### 3. 重复早已证伪的客户端参数 sweep

以下方向除非和“预读分层定位”直接绑定，否则都不建议重开：

- `--buffer-size`
- 早期意义上的 `--prefetch 0/16` 重复扫档
- `--max-readahead` 泛化扫档
- 元数据/TiKV 主因怀疑
- RGW 是否是当前随机读根因

这些在现有文档里已经有足够结论，重做只会让 11 文档再次发散。

## 四、下一阶段建议的工作计划

### P0：先把 11 文档的定位收紧

`11` 文档不再承担“完整回顾所有调优历史”的职责，只保留三部分：

1. `10` 阶段已固化的结论
2. 本阶段待回答的问题
3. 下一阶段的执行计划与判据

### P1：先回答“该不该关预读”

目标不是一句“关”或“不关”，而是输出正式判据：

- 关哪一层预读
- 关掉后哪些指标下降
- 哪些下降仍在验收线之上，可接受
- 哪些下降不可接受，需要补救

建议最少形成如下结果表：

| 档位 | randread | seq-read | seq-write | randwrite | 备注 |
|------|----------|----------|-----------|-----------|------|
| 默认 |  |  |  |  | 基线 |
| 关 JuiceFS 预读 |  |  |  |  |  |
| 关 FUSE readahead |  |  |  |  |  |
| 两层都关 |  |  |  |  |  |

### P2：若“关某层预读”对随机读明显有利，就转入“副作用最小化”

这时才进入“基于关闭预读，修复被拉低指标”的路线。

修复顺序建议是：

1. 先看是否只是顺序读下降，但仍高于验收线
2. 再看是否 randwrite / randrw 被一起拉低
3. 最后才看是否需要补 FUSE 并发或其他局部参数

原则是：

- **只修掉到验收线以下的项**
- 不为已经明显高于验收线的项做过度优化

### P3：若“关预读”并没有带来明确收益，就停止围绕预读投入

判据建议直接一点：

- 如果随机读提升不明显，且其他指标还下降，那么预读不是下一阶段主抓手。
- 这时应切回“继续分析随机读瓶颈”的路线，并聚焦：
  - FUSE 请求节流
  - 读路径固定开销
  - 有效带宽与实际拉取流量的比例

也就是说：

- **预读必须先被证实为“可兑现的收益来源”，才值得进入副作用修复阶段。**
- 否则就不要让它继续占据主线。

## 五、我对下一阶段的最终建议

### 主判断

**下一阶段建议先走“预读分层定位”，而不是直接进入“全面关闭预读后的补洞”。**

### 原因压缩成一句话

因为你们现在已经知道“预读相关”，但还不知道：

- 伤随机读的是哪一层预读
- 关闭后损失的是不是验收真正关心的指标
- 有没有只关局部、就能拿到主要收益的配置点

### 因此，11 文档里建议明确写成下面这个决策顺序

1. 先确认预读影响来自哪一层
2. 再判断关闭该层后，随机读是否得到可兑现收益
3. 若收益成立，再只修被拖到验收线以下的指标
4. 若收益不成立，停止围绕预读投入，回到随机读根因定位

## 六、建议写进 11 文档的阶段计划

### 阶段目标

在不重复 `08`~`10` 已证无效方向的前提下，确定单客户端随机读的下一阶段主线，并给出正式生产配置的决策依据。

### 本阶段只做三件事

1. **做预读分层对照测试**
2. **同步采集随机读时的有效带宽与实际拉取流量**
3. **根据结果二选一**

二选一的分叉：

- 若关闭某层预读能明显提高随机读有效带宽占比：
  进入“关闭该层预读后的副作用最小化”阶段。
- 若关闭预读收益不明显或副作用不可接受：
  放弃把预读作为主线，继续做随机读瓶颈定位。

### 本阶段不再继续的方向

1. 版本主线扩展
2. 多客户端作为主论据
3. 已证无效的通用客户端参数 sweep
4. 已排除的元数据/RGW/BlueStore 主因怀疑

---

## 七、一句话结论

**11 阶段不该直接选“关预读后补洞”或“完全放弃预读”其中之一；正确做法是先把预读分层定位，证明哪一层预读在伤随机读，再决定是否进入“关闭该层预读后的副作用修复”路线。**
