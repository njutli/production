## 〇、重大更新（2026-07-03）：随机读 2.5× 放大根因确认，推翻 10 阶段归因

> 本节是本文最新、优先级最高的结论，覆盖下面 §二 路A 的旧归因（EC 取片/messenger）。

- **根因 = JuiceFS v1.3.1 客户端 `loadRange` bug**（`cached_store.go:153` 条件 `len(p)<=blockSize/4`(=64K) 挡住 128K FUSE 半块 → 客户端把整块 256K 全量读回 → ~2×），**不是** EC 取片、不是 messenger、不是网络、不是加密。
  - 四重证据：①副本池(非EC)随机读也 3.2× → 排除 EC；②同口径 strace 顺序/随机 read 分布相同 → 排除 messenger 碎读；③L1 裸 RADOS 256K=1.04× → 放大在客户端不在后端；④源码定位到 commit `eaf3d21f`(main)，patch 该行后放大 2.17→1.11、纯随机读 51.8→98.3、每 op 吐出 127K→67K（行为证据）。
- **patched v1.3.1 全量重测（cold/warm-mu150，已对账原始 fio）**：
  - 纯随机读：冷态 r1=**38.6**、暖态自我预热爬升 36→69→96→(125/146=缓存命中，越 124 红线不计)；ra=0 专项单测曾达 98。→ **升级修复后纯随机读可达标**。
  - **randrw：冷态 13.8–19.4、暖态最高 24.6（全口径 14–25），patch 也救不了**，差目标 2.4–4×。
- **落地路径**：**首选 1.3.1 release + 单行 patch 自编译**（变更面窄、基座稳定，风险小于升 v1.4 beta/rc）；v1.4 仅待正式版发布后再评估。见 §五 步骤 0。

## 一、两个已定的大方向（用户拍板）

### 1.1 调优基于「单客户端」展开
- **理由（修正版）**：验收口径按客户端数缩放（N 客户端 → 目标 N×59）。多客户端聚合涨多少、
  验收线就抬多少，**治标不治本**。单客户端是"每客户端达标"的基本单元，打通它多客户端自然按
  `min(单客户端能力, 后端÷N)` 推。
- ⚠️ 注意区分：08_2 多客户端"平均带宽下降"**不是**多客户端无用的证据，而是**后端总能力被 N 个
  客户端平分**（后端有共享瓶颈）。所以"基于单客户端"的理由是**验收缩放**，不是"多客户端没用"。

### 1.2 主攻方向「重测后重新决定」，不再预设任何项已达标
- 此前 all-in 随机读，是基于"顺序读写 + 纯随机写已达标"——该前提**已知不可靠**（09 基线口径有问题：
  原始日志丢失、randwrite=124 超物理上限、误标 cache=0）。
- **GLM 干净重测出来后，按"哪些项真不达标"重新排主攻方向**（决策矩阵见 §四）。

## 二、随机读提升的两条路（用户提问的拆解）

随机读有效带宽 ≈ `min(网卡线速, 后端裸能力 ÷ 读放大)`。当前真冷态单客户端 ~45–52，三者同时顶住：
- 网卡侧：`124 ÷ 2.5 ≈ 50`，且实测 tikv RX=91.5≈线速 → **网卡 RX 已被放大打满**；
- 后端侧：`后端 ÷ 2.5 ≈ 45` → 后端也接近。

所以提升随机读理论上两条路，但**优先级不同**：

### 路 A：减少前端读放大（2.5×）—— 单客户端千兆下的**主路**
> 因为单网卡千兆是死的，网卡 RX 已被放大打满；不减放大，提后端也出不来更多有效读。

| 方向 | 说明 | 现状/可行性 |
|------|------|-----------|
| **放大来源已定位（订正）** | ~~EC 4+2 取片 + messenger~~ → **实为 v1.3.1 `loadRange` bug（客户端全量读半块），见 §〇** | ✅ 已定位，**打单行 patch 即可修**（非结构性） |
| 修复落地（**最高杠杆**） | 1.3.1 release + patch `eaf3d21f`（一行）→ 纯随机读放大 2×→1.1×、带宽翻倍 | ✅ 见 §五 步骤 0；v1.4 beta/rc 风险大，仅待正式版评估 |
| 缓存绕过（暖态命中） | 命中本地缓存不走后端 → 放大消失 | ⚠️ 有效但**暖态高值多为自我预热/缓存命中(越124红线)**，仅定性，不能报为后端能力 |
| ~~EC 分片数↓（EC 2+1）~~ | ❌ **划掉**：副本池对照已证明放大与 EC 无关，减分片无用 | ❌ 排除 |
| 源码级减每读往返 | patch 已把每 op 吐出 127K→67K；残余空间小 | 视升级后剩余放大再评估 |

### 路 B：提升后端裸能力 —— **次路**（放大降下来 / 换万兆后才显效）
> 单客户端千兆下后端不是首要瓶颈；但若走暖态/多客户端/万兆，后端裸能力会成为新天花板。

| 方向 | 说明 | 现状/可行性 |
|------|------|-----------|
| **先测准 256K 冷态后端裸能力** | 现无干净数：4M 口径 145（错位弃用）、256K 口径 112.7（工作集 6.4G 内存命中、偏高） | 🔴 **缺基准，需补测**：128G 工作集 + 测前清 OSD 缓存 |
| 加 OSD / 节点 | 横向扩后端总吞吐 | 硬件动作 |
| PG primary 均衡 | 6 OSD 小集群，PG 不均致热点 OSD | 低成本可查 |
| BlueStore 读缓存 `bluestore_cache_size_ssd` | 09_1 只测了写路径参数，读缓存未测 | 待测 |
| 升万兆 | 后端节点也是千兆，单节点 rados bench 已近线速 118 | 架构动作，验收线同步抬 |

### 关键结论
**单客户端千兆下，随机读放大根因已确认 = `loadRange` bug（非 EC），最高杠杆是打单行 patch（路 A，1.3 release 上，非升 1.4 beta），可让纯随机读翻倍达标。
但升级只解决纯随机读——验收口径 randrw 仍全口径不达标（14–25，patch 也无效），是独立的读写竞争瓶颈，才是决定验收的硬骨头。**

## 四、方向决策矩阵（2026-06-28 最新干净数据，含调参效果）

> 口径：256K block、单客户端、目标 59。数据源：`results/results-table-20260628.md` + 各 `full-bs256k-*` 目录（双轮、单变量、可追溯）。
> ⚠️ **数据可信度注记（已核测试方法）**：
> - 随机项（randread/write/randrw）口径正确（bs=256k、direct=1、单变量），**可信、可用**。

### 关键发现（基于最新数据）
0. **（2026-07-03 补，最高优先）下表是 default(未patch) 二进制数据。patched v1.3.1 重测后**：纯随机读那行显著抬升（冷 r1=38.6，专项 ra0 达 98），**但 randrw 那行不变（冷 13.8–19.4 / 暖最高 24.6，patch 全无效）**。暖态纯随机读的 100+/174 等高值是**自我预热爬升 + 越 124MB/s 红线的缓存命中**，仅定性，不能当后端能力报。
1. **ra=0 是写类的最优解，但砸 randrw 和顺序读**：
   - ra=0 让 顺序写 +47%、随机写 +18%、随机读 +39%（暖态）、layout +39% —— **写类和纯随机读全面受益**。
   - 但 ra=0 让 **randrw −55%（跌到 8）**、顺序读 −37%。**ra=0 不能全局开，是"按负载选"的参数**。
2. **mu=150 这次有效了（与早前冷态结论相反）**：暖态下 顺序写 +38%、顺序读 +18%、layout +39%、随机写 +14%。
   - 早前 `maxuploads150` 冷态测无效，**是因为冷态 cache=0 关了 writeback**；暖态(有 writeback 缓冲)下 mu=150 才发挥作用。
3. **randrw 是唯一怎么都救不了的项**：冷 10–16、暖默认 17–19、ra=0 反而更差(8)、mu150 也降、**patched 二进制也只 14–25**。所有缓存/调参/patch 手段对 randrw 无效或有害，是**独立于放大 bug 的读写竞争瓶颈**（待步骤 3 诊断）。
4. **顺序读"达标"存疑**：78–80 可能是 page cache 命中虚高（顺序测试无 direct），需 direct=1 重测确认真实后端顺序读。

## 五、下一阶段工作计划（明确、可行，2026-07-03 更新）

> 现状小结（冷态口径，patched v1.3.1 + cache=0 + mu=150 + default ra）：
> - **已达标 2 项**：顺序读 80.1、多线程读 109。
> - **贴线 3 项（即将达标，本阶段主攻）**：顺序写 57.0(差3%)、随机写 55.7(差6%)、多线程写 43.7(差26%)——三项写类天花板都 ~79(千兆118÷EC写放大1.5) > 59，**物理上都能过**。
> - **硬骨头 2 项**：randrw R/W 26.6/26.3(差55%)，读写竞争，patch/调参全无效。
> - 随机读 52.0(差12%，patch 后天花板 ~106)：有空间但杠杆不如写侧明确，列第二优先。
>
> **本阶段策略：先集中把"贴线的写侧三项"用纯后端手段推过 59（达标数 2→有望 5），randrw 单独攻，随机读补一枪。**

### 步骤 0（最高杠杆，1 天）：随机读修复正规落地 —— 首选「1.3 release + 单行 patch」，非升 1.4
- **背景**：随机读放大是 v1.3.1 `loadRange` bug（`cached_store.go:153`），修复 commit `eaf3d21f` 在 main 分支，**未 backport 到 release-1.3**；含此修复的 v1.4 目前**只有 beta/rc（我们测的是 v1.4.0-rc1），尚无正式版**。
- **风险权衡（用户提出）**：
  | 方案 | 变更面 | 风险 |
  |------|--------|------|
  | **1.3.1 release + 单行 patch（首选）** | 仅改 `cached_store.go:153` 一行，基座是稳定 release；已验证放大 2.17→1.11、纯随机读翻倍、每 op 吐出 127K→67K | **小**，面窄可控 |
  | 升 v1.4 beta/rc | 整版跳级，rc 版单客户端还 -3%，回归面广，beta 上生产不合规 | **大** |
- **做法**：以 **1.3.1 release 打这一行 patch、自编译**为落地首选，走内部代码评审 + 回归测试；v1.4 仅作"等**正式版**发布后再评估"的备选（届时重测单客户端净收益 vs 早前 rc -3.3%）。
- **产出**：patched 1.3.1 的正规构建/评审/回归方案；v1.4 正式版跟踪项（不阻塞本阶段）。

### 步骤 1（半天）：修复顺序读口径 + 锁定真实顺序能力
- **问题**：现有顺序测试无 `--direct=1`，seqread 走 page cache，77–80 可能虚高；results-table 标 "bs=4M" 实为 256K。
- **做法**：顺序四项补 `--direct=1` 重测（冷态 cache=0 + 客户端&OSD drop），bs 同时测 256K 和 4M 两档对照。
- **产出**：真实后端顺序读/写能力（确认 90/62 是否站得住）；修正 results-table 口径标注。
- **意义**：你已向领导承诺顺序读写——必须用干净口径坐实，避免 page cache 虚高数字被拆穿。

### 步骤 2（本阶段主攻·性价比最高，1 天）：写侧冲线 —— 把贴线的写类三项推过 59
> 用户决策：**冷态口径、只用纯后端手段（mu/buffer），不开 writeback**（保证是真实后端能力，非异步落盘虚高）。
> 目标把达标数从 2 项拉到 5 项。

- **对象**：顺序写(57.0,差2)、随机写(55.7,差3.3)、多线程写(43.7,差15.3)。三项天花板 ~79 > 59，都够得着。
- **做法**（patched v1.3.1 + cache=0 冷态，单变量扫，只测这三项）：
  1. **max-uploads**：150(基线)→ 200 → 300。依据：20→150 已让顺序写+12%、randrw+86%，128 job 争 slot 仍未喂饱，**最可能奏效的杠杆**。
  2. **buffer-size**：300M(默认)→ 1G。128 并发写下 flush buffer 可能不足；旧"buffer 反降"是旧配置，patched+高 mu 下重验。
  3. **组合**：取 1、2 各自最优值组合再测一轮，确认是否叠加。
- **口径红线**：只认 **r1**（不取 MAX，避免 OSD cache 预热虚高）；每格采 **NIC_RX（必须 <118，任何写值 >79 立即回查 writeback 泄漏/缓存命中）** + OSD op_w perf；结论对账原始 fio。
- **产出**：写类达标交付配置（mu/buffer 组合）+ 达标情况；更新报告 §5.1/5.2。
- **预案**：多线程写缺口大(15.3)，若 mu/buffer 到顶仍卡在 ~79 附近过不了 59 → 如实标"EC 写放大+网络物理受限"，转多客户端聚合口径；某项 mu 越大反降则取拐点。

### 步骤 2b（第二优先·随机读补一枪，半天）：随机读 52.0 → 59
- **对象**：冷态随机读 52.0(差12%，7.0)，patched default-ra 稳态；天花板 ~106（千兆÷1.11 放大），有空间。
- **注意**：patch 后 **ra 对 randread 已无影响**（sweep 51–53），别再指望 ra=0。剩余瓶颈是残余 1.11× 放大 + 客户端并发调度。
- **做法**：冷态 r1，扫 fio iodepth/numjobs 有效并发、复核 EC 读粒度对齐；若纯软件调不动到 59 → 归为"随机读靠 patch 落地(步骤0)后再评估 + 多客户端聚合"。
- **产出**：随机读能否单客户端过 59 的结论；不能则明确差距归属。

### 步骤 3（核心攻坚，2–3 天）：randrw 根因诊断 —— **唯一硬骨头（差55%）**
- **唯一全口径不达标项**，ra=0/mu150/缓存/**patch 全无效甚至有害**（patched 重测 randrw 仍 14–25）→ 纯随机读的放大 bug 已修，randrw 是独立问题，必须从根因下手。
- **前提**：在 **patched 二进制**下诊断（纯读放大已消除，能干净看到读写竞争本身），暖态默认配置跑 randrw 60s，同步采集：
  1. **pprof CPU**：定位 CPU 热点（FUSE dispatch / librados / 锁竞争）。
  2. **strace 读写 syscall 交错**：看写是否阻塞读的调度。
  3. **FUSE waiting**：读写请求是否互相阻塞在 FUSE 队列。
  4. **OSD perf dump**：写触发的 EC RMW 是否与读争抢 OSD（op_r vs op_w 延迟）。
  5. **关键量化**：`randrw读 vs 纯随机读`、`randrw写 vs 纯随机写` 的差值 → 读写干扰吃掉多少。
- **产出**：randrw 慢的根因归属（FUSE 队列串行 / EC RMW 争抢 / 写阻塞读），决定能否软件解。
- **预案**：若根因是 EC RMW 或 FUSE 单队列等结构性限制（软件难解）→ 评估 ① 多客户端聚合是否满足业务、
  ② 向领导用 weka 数据说明真实负载（混合读写本就难）、③ 副本池对照（牺牲容量换 randrw）。
