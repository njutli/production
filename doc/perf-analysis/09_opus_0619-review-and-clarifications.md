## 二、bench-juicefs.sh 的 layout 复用改造（deepseek 改 / 本轮校验）

**痛点**:每次测试都要重铺 layout（~20min）极耗时。deepseek 加了三个开关解决:

| 开关 | 作用 |
|------|------|
| `DO_LAYOUT_ONLY=1` | 仅建卷 + 布局后退出、不下卷不销毁（建一个可复用的卷） |
| `SKIP_LAYOUT=1` | 跳过 destroy/format/mount/layout,直接在已挂载已布局的卷上跑随机读/分析写/混合（结束不销毁） |
| `SKIP_RANDWRITE=1` | 跳过随机写/混合项,只跑纯 randread |

**典型工作流**:`DO_LAYOUT_ONLY=1` 建一次卷（~20min）→ 反复 `SKIP_LAYOUT=1` 测（~3min/次）。

### 校验结论:可行、逻辑正确、且已被实测验证

- `bash -n` 语法通过;gate 边界划得干净;`do_mount` 无下游依赖变量,跳过安全。
- `SKIP_LAYOUT=1` 正确跳过 spec randwrite/randrw（需 fresh volume 会毁布局）+ 跳过 cleanup（保卷）。
- **实测自洽（最关键）**:`DO_LAYOUT_ONLY` 建卷 → `SKIP_LAYOUT` 复用,复用跑出 **45.9 MB/s**,
  与全量 layout 跑的 45.5–45.9 **完全一致** → 复用未引入缓存/数据偏差,数值可信。
  （证据:`results/20260618-155446`=layout-only、`-170938`=reuse 三次均 ~45.9、`-152323`=全量对照）

### 必须遵守的纪律（deepseek 文档已写明,确认无误）

1. **spec 口径必须用独立池**（如 `CEPH_POOL=juicefs-spec`）,否则 `do_fresh_volume` 会销毁 layout 数据。
2. **`SKIP_LAYOUT=1` 不做 cleanup,需手动 `juicefs destroy` 收尾**,否则池一直占着 128G。

### 一个未采纳的小建议（非阻塞）

`SKIP_LAYOUT=1` 假设卷已挂载在 `/mnt/juicefs`,脚本未校验挂载点就直接 fio。
若卷被卸载/重启丢失,fio 会写到本地根盘空目录、跑出**假高带宽**。
建议在 SKIP_LAYOUT 分支加 `mountpoint -q "${JUICEFS_MOUNT_POINT}" || fail "volume not mounted"`。
（本轮未改脚本,记此备忘。）

## 三、C 测试结论的纠错：OSD 主机兼客户端"收发互抢网卡"是误判

### 背景

C 测试（多客户端聚合 randread）做过两次:
- **第一次同机**：tikv-node 起 2 个挂载点,聚合 ≈1×（无提升）。
- **第二次跨机（`08_2` 四之二）**：tikv-node(.12) + ceph-node1(.11) 两台,聚合 **54.8 MB/s ≈ 1.54×**（有提升,但不到 2×）。

旧结论把"不到 2×"归因为 **ceph-node1 同时承载 OSD 服务 + 客户端读 → 收发互抢网卡**
（`RX 86.1 + TX 56.4 = 142 > 千兆线速 124`）。

### 用户质疑（正确）

OSD/RGW 服务读请求走网卡**出向(TX)**,客户端读数据进来走**入向(RX)**;
千兆是**全双工**,RX 和 TX 各一条独立 ~124 MB/s 通道,**不互相影响**。

### 校验结论:用户对,deepseek 的修正在物理 + 数据两方面都成立

1. **物理**:全双工下 RX/TX 独立。旧判据 `RX+TX=142>124` 是错误——
   不能把两个方向相加再跟单方向线速比。正确看:RX 86<124 ✓、TX 56<124 ✓,**两方向各自都没满**。

2. **数据自证伪（更关键）**:Phase2 实测
   - ceph-node1（OSD 主机兼客户端）randread = **28.1**
   - tikv-node（干净客户端）randread = **26.7**

   若真互抢,OSD 主机当客户端应**明显更低**;结果它**反而略高 1.4**。
   旧文档写"28.1 比干净客户端低",跟同表里唯一的同期干净客户端数（26.7）**自相矛盾**——本就该改。

3. **两客户端各 ~27 的真因**:不是单机 NIC 竞争,而是**后端裸能力 ~118 被两客户端平分**
   （读放大后每客户端有效读 ≈ 总量/N）。数值自洽:26.7+28.1=54.8 = 聚合值。

### 下游影响（修正后两处结论方向正确）

- **解锁硬件路线**:无需另找/加"网卡干净的独立客户端机",**现有 3 台 OSD 主机可直接当多客户端用**,
  2B 多客户端聚合门槛与成本大幅下降。
- **2A（单客户端）确认死路**:单客户端被自身千兆 RX 卡死（91% 线速）,降放大已榨干 → 只剩升万兆。

### 已补的护栏（写进 09 步骤 2B）

全双工只保证 RX/TX 各自独立,**不保证某一单方向不被打满**。
正式跑 2B 时须逐节点采单方向 RX/TX（`/proc/net/dev`）,判据 **任一节点任一方向 < ~110 MB/s（线速 88%）**;
某方向触线则该节点不能再加负载。**不再用"RX+TX 之和"对比线速（已被推翻的错误判据）。**

## 四、沉淀的测量纪律（写进 09 顶部「〇、测量纪律」）

由这次"收发互抢"误判复盘而来,作为后续定位通用铁律:

1. **网卡分方向看（RX/TX 各自比线速）,严禁求和。** 判据:任一单方向 < ~110 MB/s。
   一台机器身兼数职未必互相拖累,关键看各角色压哪个方向、是否撞同一方向。
2. **任何因果结论落地前,先用现有实测数自检能否解释;自相矛盾的解释一律推翻重来。**
3. **只认 cache=0 冷态真值**（读缓存命中是热态幻觉）。
4. **横向对比必须同口径同工作集**（randrw 用 [analysis] 复用布局口径;正式结论 128G 全口径）。

## 五、口径澄清：为什么不能"按 3 个 ceph 节点 × 59 = 177"（写进 09「七」）

### 用户设想

集群有 3 个 ceph 节点,半速指标 59 是否该 ×3 到 **177**?那当前裸能力 118 岂不是只到集群 1/3,差距很大?

### 校验结论:不能 ×3;177 无对应物理实体;118 不是 1/3 而是 3/3

1. **118 已是"3 节点 6 OSD 合力"的总数**。`rados bench -p juicefs-data rand` 打的是整个 EC 4+2 池,
   数据摊在全部节点/OSD 上,118 就是三节点一起干出来的聚合总能力,**不能再 ×3**。
   类比:118 是"一个水池 3 个进水口一起放水的总流量",3 个口已都算进 118。

2. **唯一能 ×3 的是客户端网卡管子**:3 台客户端 × ~113 RX ≈ 340 入口管子。但管子粗 ≠ 能灌满:

   ```
   聚合有效读 ≈ min( Σ各客户端RX ,  后端裸读 ÷ 读放大 )
               = min( ~340 ,  118 ÷ 2.5 ≈ 47 )  ≈ 47
   ```

   后端 118 经 256K 卷残余 ~2.5× 放大后,**有效读上限仅 ~47**,远低于管子 340。
   → 瓶颈卡在后端 118,加客户端只能逼近 47~55,**到不了 177**。
   实测自洽:跨机 2 客户端聚合 54.8（1.54× 而非 2×）,边际已在掉。

3. **真实差距在读放大,不在节点数**:
   - 放大 2.5× → 有效 47;若压到 1.2× → 有效 ~98。**该追的增量在 FUSE 读路径,不在堆节点。**
   - 后端 118 本身能否再抬（EC 协议/BlueStore/网络往返）属动架构,收益存疑、低优先级。

4. **对验收口径的含义**:
   - 单客户端口径:目标固定 59,与节点数无关;乘 3 无物理意义（单客户端收不进 177）。
   - 多客户端聚合口径:天花板 ≈ `min(Σ客户端RX, 后端118÷放大)` ≈ 47~55,**仍不是 节点数×59**。
