# 路线A：LDAP统一用户管理实施与注意事项

> 建立及更新日期：2026-09-22。
> 状态：身份路线A及新建身份服务产品389 Directory Server（389 DS）已确定；部署配置及Portal集成待核对和实施。本文不是环境已完成部署或验收的证明，也不构成执行授权。
> 用途：持续记录路线A的决定、实施注意点和待确认事项，作为后续Portal用户管理开发的主要依据；不为每次讨论另建一份重复方案。

## 一、已确定的范围

**业务用户统一由双节点389 DS管理，同一用户在所有获准客户端使用相同UID/GID，通过JuiceFS原生POSIX权限访问文件；不在各客户端重复创建本地业务账号，不修改JuiceFS源码增加身份映射。** 具体节点和配置尚待核对；产品取舍见[选型调研](LDAP-PRODUCT-SELECTION-RESEARCH-20260923.md)。

| 事项 | 当前决定 |
|---|---|
| 业务身份 | 采用路线A。本期无需兼容已有业务账号，统一通过LDAP开户 |
| 客户端组件 | 使用现有NSS/PAM/SSSD等标准能力；暂不开发客户端助手或本地账号远程管理服务 |
| root及系统账号 | 保留各主机本地root和必要服务账号；业务挂载基线启用`root-squash`，独立管理挂载保留UID 0管理能力。客户端root仍属于可信运维范围，因为它能控制本机挂载和凭据 |
| 历史路线B/C | 保留开发计划，当前不实施；以后需要兼容已有账号时再评估 |
| 配额 | 沿用独立配额开发计划，管理目录容量及inode限额；身份统一不替代配额管理 |
| Portal | 先区分“登记已有LDAP身份”和“直接管理LDAP账号”；后者作为后续集成方向，接口及权限尚未冻结 |

“不新增代码即可实现路线A”指通过成熟目录服务和客户端配置即可实现身份统一，不需自研认证系统或修改JuiceFS数据路径；**不代表现有Portal已经能创建LDAP用户**。如果要求在Portal直接开户、停用、改组，仍需开发相应页面和受限管理接口。

## 二、各组件负责什么

| 组件或数据 | 职责与边界 |
|---|---|
| 双节点389 DS及统一开户流程 | 保存并复制业务账号、UID/GID和组关系，执行受控ID分配、密码策略和账号停用；两节点复制是异步的，管理变更传播需要验收 |
| 客户端NSS/PAM/SSSD | 查询账号和组信息，参与登录认证及访问控制，缓存查询结果；不是把LDAP账号复制成一套本地账号文件 |
| 客户端进程及JuiceFS | 进程以解析出的UID/GID运行，JuiceFS按数字身份、权限和ACL检查访问；不根据Portal登录名判断文件权限 |
| Portal及存储管理库 | 展示或管理已获授权的业务身份、登记目录及网页查看权、记录任务和审计；不分配另一套存储UID/GID，不保存LDAP用户密码副本 |
| TiKV/Ceph | 分别保存文件元数据和内容。后端凭据、认证与访问限制单独部署，LDAP不会自动替它们启用认证 |

SSSD通过目录查询为Linux提供身份、认证和授权能力，支持身份缓存；部署后无需为每名LDAP用户在每台机器重复执行`useradd`。[SSSD介绍](https://sssd.io/docs/introduction.html)、[LDAP接入说明](https://sssd.io/docs/ldap/ldap-introduction.html)

LDAP查询主要发生在身份解析、登录、组查询及缓存刷新等环节，不新增文件内容转发节点。仍需验证实际JuiceFS版本的组查询路径、缓存未命中和目录故障时的表现，不能承诺所有操作都绝无额外延时。

## 三、实施前必须确定的配置

### 3.1 UID/GID、用户名和组

- 为业务账号保留明确的非零UID/GID范围，避开root、系统服务账号及实际使用的容器映射范围；`50001:50001`仅作本文示例，不是已批准分配。
- 用户UID不得分给不同人员；组GID不得代表不同的组，但多个用户可以属于同一个组，主GID也可以相同。
- 使用389 DS的受控开户流程及经核验的两节点ID号段分配，必要时配置DNA插件；限制手工指定UID/GID的管理入口，并检查重复值。DNA自动分号不保证手工指定值唯一，两个节点各自开户的并发与复制延迟也须验收；不把客户端root的自觉当作LDAP数字ID唯一性的保障。[389 DS DNA说明](https://www.port389.org/docs/389ds/design/dna-plugin.html)。
- 检查用户名和组名冲突，也检查数字冲突。NSS先查本地还是先查LDAP，只决定解析顺序，不能修复两个不同身份共用同一数字的问题。
- 所有客户端后续本地开户都必须避开业务保留范围；即使本期没有旧业务账号，仍需核对本地系统账号。LDAP不会自动扫描所有客户端。
- 同一UID跨客户端、跨JuiceFS卷保持同一身份。改名或改密码不改数字ID；UID/GID变更另行处理，停用或删除账号后不立即回收仍关联文件、ACL或任务的ID。

### 3.2 客户端登录与业务运行

- 统一客户端NSS、PAM和SSSD配置，核验`id alice`、`getent passwd alice`、组查询以及登录后的实际进程身份；“能查到账号”不等于“允许登录”。
- 明确哪些用户/组允许登录哪些客户端及使用哪些登录方式。LDAP中存在账号不自动表示获准登录所有机器，主机登录授权也不代替文件权限。
- 若业务使用SSH公钥，停用策略必须覆盖公钥登录的账号检查链；只锁定密码不等于撤销所有登录方式。
- 确定身份缓存、离线登录、缓存有效期及停用传播要求。具体值待验证，不默认承诺立即生效。
- 训练任务、推理服务、调度器和容器均须使用正确的业务UID/GID和附加组；不能只验证交互式Shell。
- 确定本地home目录的创建方式及容量限制。可复用受控预配置或系统已有的登录时创建机制，不为此开发客户端助手；本地home与JuiceFS用户存储目录是两类资源，路径需明确。

客户端认证、缓存及停用机制的详细解释沿用[用户ID映射子调研第三节](USER-ID-MAPPING-SUBRESEARCH-20260920.md#三ldapad--sssd统一身份来源)；其中旧的路线选择建议不再作为本期实施结论。

### 3.3 root和后端安全

- 每台客户端保留本地root（UID 0）。它们的密码和SSH授权分别管理，不要求一致，也不因都是UID 0就自动获得彼此主机的SSH登录权或LDAP管理权。
- 本期信任所有获准客户端root，不通过LDAP为它们改号或映射。日常运维可用个人账号加受控sudo留痕，普通业务用户不得拥有完整sudo、Docker管理或其他宿主机root等价权限。
- 所有业务挂载按下节基线启用`root-squash`；通过这些挂载访问时，root按专用低权限身份检查，不能仅凭UID 0进入root拥有的0700待交付目录。
- 只保留独立受控管理挂载的UID 0文件管理能力，用于创建一级用户目录、`chown`和应急修复。持有有效TiKV凭据或能控制挂载配置的root仍可绕过客户端squash，因此客户端root继续属于可信管理范围。
- 挂载进程持有的TiKV/Ceph凭据必须保护，普通用户不得直接读取。上线前另行完成PD/TiKV强制认证或已验证的等效接入隔离，LDAP登录管理不能代替这一措施。
- 不给业务客户端分发LDAP最高管理凭据；LDAP连接保护与PD/TiKV连接保护是两项独立配置。不能因为一侧已启用TLS，就认为另一侧也已受保护。

389 DS连接暂按单向TLS加LDAP账号密码规划，客户端须验证服务器证书；查询身份与开户管理身份分离，普通客户端不得持有LDAP最高管理凭据或读取敏感属性。两节点的服务器证书分别导入NSS证书库，签发、到期预警和续证由本项目负责；LDAP是否升级为双向TLS留待安全要求核对，与PD/TiKV mTLS分别配置。证书角色和连接流程见3.4节。[选型调研](LDAP-PRODUCT-SELECTION-RESEARCH-20260923.md#45-ldap连接管理身份与tls边界)。

#### 业务挂载基线：JuiceFS `root-squash`

交付版本JuiceFS支持在挂载时使用`--root-squash=<uid>:<gid>`，将**经该FUSE挂载发出的UID 0请求**改为指定的普通UID/GID，再按普通权限检查。该参数固化为所有业务挂载的基线要求。普通LDAP用户的UID/GID不会被改变。不要改用`--all-squash`，它会把所有用户合并成同一身份，破坏路线A的多用户隔离；同时配置时，`all-squash`优先。[JuiceFS v1.4.1挂载选项实现](https://github.com/juicedata/juicefs/blob/v1.4.1/cmd/mount_unix.go)、[FUSE请求身份转换](https://github.com/juicedata/juicefs/blob/v1.4.1/pkg/fuse/context.go)

基线模板为：

```text
juicefs mount <其余已批准参数> \
  --root-squash=${JFS_ROOT_SQUASH_UID}:${JFS_ROOT_SQUASH_GID} \
  <META> <业务挂载点>
```

`JFS_ROOT_SQUASH_UID/GID`必须在部署前冻结为全局一致的非零数字ID。可以在统一身份规划阶段提前预留该UID/GID，也可以在实际挂载前检查所有客户端、LDAP及既有文件owner后选择未占用值；无论采用哪种方式，正式挂载前都要确认它未被业务用户或组占用。为它建立专用技术身份，例如`jfsanon`：禁止交互登录，不属于业务组或运维组，不拥有业务目录，也不用于Portal人员身份。JuiceFS参数只接受数字值，不能依赖客户端分别解析用户名；不得省略数字而隐式采用各主机可能不同的`nobody/nogroup`。该ID应纳入LDAP/全局ID台账和冲突检查，但不作为可登录业务用户。

部署配置和安装文档必须明确区分：

| 挂载类型 | `root-squash` | 使用者与用途 |
|---|---|---|
| 业务挂载 | **必须启用**，使用冻结的同一匿名UID/GID | LDAP普通用户执行业务IO；客户端root经此入口也只能按低权限身份访问 |
| 管理挂载 | 不启用 | 仅可信运维在受控节点创建一级目录、`chown`和应急修复；不得向业务用户暴露或复用为业务挂载 |
| 152统计挂载 | 独立配置，不承担目录交付 | 只用于统计/控制功能，不因本决定自动变成管理挂载 |

该基线用于减少客户端root误读待交付0700目录、创建UID 0文件或误改权限，但存在明确边界：

- 它不修改Linux的root账号，只转换通过该挂载进入JuiceFS的请求；不影响root管理本机、读取挂载配置或控制挂载进程。
- root可卸载后去掉该选项重新挂载、另启一个JuiceFS客户端，也可让进程以Alice等非零UID发起访问；还可能直接使用本机可读取的TiKV/Ceph凭据。因此它不能把不可信客户端root变成普通用户，也不能作为配额防绕过的安全边界。
- v1.4.1实现改写请求的主UID/GID，但权限检查还会读取请求进程的附加组。目标身份必须使用最小组权限，并验证root进程的实际附加组；业务目录不应通过`root`组或其他运维组授予访问。
- 经squash的root不能再执行原先依赖UID 0的任意`chown`、权限修复和用户目录交付，创建的文件也会显示为映射后的owner。若所有挂载都启用，当前“root创建目录、设置owner后交付”的流程将失去管理入口。

因此，本方案固定在业务挂载启用，并保留与业务挂载分离、由可信运维控制的管理入口处理建目录、`chown`和应急修复；管理入口的凭据和访问权限必须严于业务挂载。该配置仍须先在测试挂载完成最小权限和业务兼容验证，验证失败时停止上线并修正配置，而不是静默取消基线。

### 3.4 LDAP CA、证书和连接流程

以下按**一个受控根CA、两个389 DS服务节点A/B、客户端使用单向TLS**说明设计；尚未签发证书或部署。这里的CA是证书签发方，可以离线完成签发，不要求有长期在线的CA服务。签发环境及私钥备份位置须在S2-0确定，不把CA私钥留在业务客户端或长期在线的LDAP节点。

| 角色 | 长期持有的身份材料 | 分发和用途 |
|---|---|---|
| CA签发环境 | 一对CA公私钥；CA证书包含CA公钥 | CA私钥只用于签发和续签，绝不分发；CA证书可分发给LDAP节点与客户端作为信任依据 |
| 389 DS节点A | A自己的私钥、包含A公钥和连接名称的服务器证书 | 私钥只留在A的NSS证书库；连接A时向客户端出示证书A |
| 389 DS节点B | B自己的私钥、包含B公钥和连接名称的服务器证书 | 私钥只留在B的NSS证书库；连接B时向客户端出示证书B |
| 每台获准客户端 | 信任的CA证书；LDAP查询或登录所需凭据另行管理 | 单向TLS不要求客户端证书或长期TLS私钥；客户端无需另存A/B公钥，它们已分别包含在服务器证书中 |

在这个**单根CA、没有中间CA**的示例中，共有三对长期身份公私钥、三张证书；文件被复制到多个节点不产生新的密钥或证书种类。两条TLS连接会各自协商临时会话密钥，不计入上述长期身份材料。[TLS 1.3握手规范](https://www.rfc-editor.org/info/rfc8446/)。

1. CA在受控环境生成CA密钥对及CA证书；分别在A、B本机生成各自的私钥和证书签名请求（CSR）。CSR携带该节点公钥及连接名称，不包含私钥。389 DS可在本机NSS证书库中生成私钥与CSR。[389 DS TLS配置](https://docs.redhat.com/en/documentation/red_hat_directory_server/12/html/securing_red_hat_directory_server/assembly_enabling-tls-encrypted-connections-to-directory-server_securing-rhds)。
2. CA核对申请的节点名称后，用**CA私钥对证书内容生成数字签名**，分别签发证书A/B。证书包含对应节点的公钥、名称、有效期、签发者及签名，**不包含CA私钥或服务器私钥**。签好的证书导入各自节点NSS证书库；客户端预先信任CA证书，连接名称与证书中的名称须一致。
3. 客户端连接A时，A在TLS握手中出示证书A；客户端用本地CA证书里的CA公钥验签，并检查有效期和服务器名称；A通过握手证明持有与证书A公钥对应的私钥。验证通过后建立加密通道，再进行LDAP账号密码认证。连接B时按同一流程使用证书B，客户端仍信任同一CA证书。CA不参与每次在线连接。[TLS 1.3握手规范](https://www.rfc-editor.org/info/rfc8446/)、[SSSD LDAP配置](https://sssd.io/docs/quick-start.html)。

后续如果要求LDAP**双向TLS**，客户端才需另有自己的证书和私钥，由服务器校验；这属于待决定的安全要求，不因PD/TiKV采用双向TLS而自动启用。证书到期预警、两节点轮流续证、客户端信任更新及故障切换须在获准环境验收；服务器私钥、CA私钥、LDAP密码不得写入报告或结果包。

## 四、用户开通、使用与停用

以Alice需要使用两台已获准客户端A、B，LDAP账号为`alice`、UID/GID为`50001:50001`为例。这是目标部署形态的说明：第二阶段只在一台获准客户端验证两个LDAP用户；A、B跨客户端一致性在第三阶段另备两台客户端后实测，不意味着第二阶段必须改动正在运行业务的157。

### 4.1 开通

1. 目录管理员通过389 DS的受控管理入口创建Alice、设置组关系和登录范围；UID/GID由已核验的统一规则分配。只创建一份LDAP身份，不逐台创建同名本地账号。
2. 运维在目标客户端核验身份解析、实际登录及进程UID/GID。检查未通过时记录原因，不把“中心创建成功”写成“所有客户端均已可用”。
3. 可信运维准备JuiceFS私有目录；需要初始配额时，按配额计划先设定并确认，再改为Alice拥有。新目录在交付前为root拥有、0700，父目录由运维控制。
4. 按需在Portal登记身份和目录并授予网页查看权；暂时不限额的目录仍可登记，没有Portal账号也不影响文件访问。

后续Portal开户功能实现后，可由Portal代替第1步的单独管理工具；第2步不因页面提交成功而自动完成，也不要求开发客户端执行服务。

### 4.2 使用及改组

Alice从两台客户端启动的业务均使用UID 50001。共享模型目录按预定组权限只读，私有目录按owner和权限读写；权限与配额均由JuiceFS按原生机制处理。

修改LDAP组关系后，既有进程的附加组不会自动整体重建。涉及新增或撤销权限时，要核验新会话和运行任务；要求收回既有任务权限时，由运维按业务窗口处理，不能只等待Portal页面刷新。

### 4.3 停用与删除

1. 通过389 DS禁用账号或撤销登录许可，覆盖实际启用的密码、公钥等方式；核对停用操作在两个节点间的传播。
2. 核验客户端缓存、新登录和已有会话。账号被禁用不使运行中的训练任务或打开的文件立即失效；由运维确认需要停止的会话及任务，不由Portal自动远程杀进程。
3. 按需另外禁用Portal账号或撤销网页授权，保留目录、数据、配额及审计，不用“配额设0”代替停用。
4. 数据移交和ID回收单独确认；不能删除LDAP条目后立即把旧UID分给新人。

新客户端按第三节完成一次标准LDAP接入和核验即可。若以后出现必须保留的旧业务账号冲突，不擅自改其UID/GID，也不悄悄切换映射路线，重新评估历史B/C方案。

## 五、对后续Portal开发的要求

### 5.1 分清两个交付层次

| 层次 | Portal能做什么 | 需要完成的工作 |
|---|---|---|
| 当前配额计划中的身份登记 | 查询并登记已存在的LDAP用户，关联受管目录和网页查看权 | 只读LDAP查询适配及身份核验；不负责LDAP开户 |
| 后续统一账号管理入口 | 由获授权的ADMIN创建业务账号、管理业务组、停用及按需重置凭据 | 新增页面、受限写接口、目录产品适配和操作审计；具体范围另行确认 |

未来新增写管理能力，不应悄悄把现有“登记身份”接口改成“开户”。页面区分“创建LDAP账号”和“登记已有账号”，接口也要明确副作用；若决定由Portal直接开户，再单独设计对389 DS的受限管理调用，不把Directory Manager凭据交给Web进程。本期不开发此写入能力。

### 5.2 权限和数据来源

- Portal账号与LDAP业务账号仍是两类账号，角色独立；本期不顺带把Portal登录改成LDAP单点登录。
- 写LDAP时使用限定业务对象、字段及操作的委派权限，不给Web进程或普通客户端LDAP超级管理员凭据；不允许创建UID 0业务账号或授予主机管理组权限。具体由哪个受控后端组件承载，在详细设计时确定。
- 即使采用受限接口，被攻陷的Portal仍可能滥用其获准管理范围，应保留操作人、目标、前后值和结果；不能把“分进程”当作请求天然可信的证明。
- 身份与组以LDAP为准，文件owner/权限及配额以JuiceFS元数据为准。SQLite保存LDAP引用、管理记录、网页授权和审计，不成为第二套业务ID或密码分配系统。
- 不把原始密码写入管理库、日志或报告；初始凭据交付和重置流程沿用选定身份系统的安全机制，另行确认。
- 开户超时后先查询真实目录状态，不盲目重建账号；ID仍由统一开户流程维护。LDAP创建成功、目录交付、配额确认是不同步骤，失败时保留明确状态，不做自动级联删除。

### 5.3 明确不做

不开发客户端助手，不向Portal开放客户端任意命令执行、本地root/系统账号管理、UID迁移、递归改owner或自动结束任务。标准客户端安装配置仍由可信运维完成。以后确有必要增加这些功能时，另行评估授权和业务影响，不作为路线A的隐含依赖。

## 六、部署、故障和最小验证

### 6.1 尚待确定的实施项

| 待确定项 | 要确认的内容 |
|---|---|
| 389 DS双节点部署 | 具体两个节点、OS/版本、资源预算、DNS/时间、复制拓扑、备份及恢复方式；150～152只是现有资源范围，不据此默认批准在某节点安装服务 |
| LDAP连接与证书 | 两节点服务器证书的CA、连接名称、NSS导入、到期预警和轮流续证；单向TLS与LDAP绑定的配置及客户端校验；是否要求客户端证书待安全要求核对 |
| 业务ID和命名规则 | UID/GID保留范围、用户名/组名、附加组、两节点分号与手工值约束、客户端本地账号排重及ID回收规则 |
| 客户端模板 | 目标发行版、SSSD/NSS/PAM配置、SSH方式、登录范围、home创建、容器及调度器身份 |
| 缓存与停用 | 是否允许离线登录、缓存期限、撤权预期时延及已有会话处理流程 |
| Portal集成范围 | [第二阶段总计划](../../USER-AND-QUOTA-MANAGEMENT-DEVELOPMENT-PLAN-20260922.md)按查询并登记已有LDAP用户实施；若后续增加开户/停用，再确认写权限范围及身份管理后端接口 |

LDAP不可用可能影响新登录、身份查询和缓存未命中的组查询；已有会话可能继续，但不能承诺所有文件操作都完全不受影响。root及必要系统服务账号保留本地，应急入口需实际验证。389 DS双节点复制是异步的，须分别验证SSSD切换、两个节点开户的ID唯一性及管理变更传播；不能把“两个可查询地址”视为写管理天然高可用。[SSSD缓存机制](https://sssd.io/docs/introduction.html)、[389 DS功能](https://www.port389.org/docs/389ds/FAQ/features.html)。

### 6.2 最小实施与验收顺序

1. 核对389 DS两个节点、证书来源与续期、ID范围及测试客户端，形成一份配置与恢复清单；不先编写大套自动化脚本。
2. 在批准的隔离范围完成双节点389 DS、服务器TLS、复制及标准客户端接入，先保留可用运维会话，确认应急登录，不直接覆盖业务主机PAM/SSH配置。
3. 第二阶段用两个普通LDAP用户、一台获准客户端和少量文件完成下列单客户端用例；跨客户端用例移交第三阶段，不重跑全量性能矩阵。
4. 根据结果冻结客户端配置、389 DS部署参数及身份登记接口；本期Portal只查询和登记已有LDAP用户，不开发Portal直接开户。以后若决定由Portal创建、停用LDAP账号，再单独确定范围和授权。部署、账号、服务、认证及挂载变更仍需单独授权，不影响157正在运行的业务。

| 验收项 | 最小通过条件 |
|---|---|
| 身份一致 | 第二阶段核对Alice、Bob在一台客户端的NSS查询、实际业务进程UID/GID及附加组；第三阶段在两台客户端核对同一用户数字身份一致 |
| 普通用户隔离 | Alice可用自己的目录，Bob不能访问；共享模型可读不可写；容器/调度任务用正确身份 |
| root及凭据 | 业务挂载含冻结的`root-squash`参数，root不能经该入口访问用户0700目录或创建UID 0文件；独立管理挂载仍可完成建目录和`chown`。普通用户拿不到后端或目录管理凭据，不能提高配额 |
| 登录与停用 | 核验实际使用的密码/公钥登录、缓存和禁用传播；记录旧会话、旧进程的处理方式 |
| 双节点ID分配 | 分别经两个节点受控开户，不重复分配UID/GID；限制或拒绝手工指定重复数字ID；客户端本地账号与预留号段排重 |
| TLS与故障恢复 | 客户端校验两节点服务器证书；在隔离环境验证一节点故障后的在线新登录、复制传播、服务器证书续期及恢复，区分冷缓存、热缓存和运行任务；不在业务环境制造认证故障 |
| 配额衔接 | 第二阶段验证单客户端的目录交付及配额生效；普通用户Portal个人查看授权已后置，不以网页记录代替真实读写结果。第三阶段在两台客户端核对同一配额共同生效 |

当前无客户端助手，核验由运维完成并登记结果；页面不能据此声称具有实时、自动的逐客户端用户同步证明。必要结果保存至`/mnt/c/SunRise/test/`，文档引用索引，不保存账号密码或私钥。
