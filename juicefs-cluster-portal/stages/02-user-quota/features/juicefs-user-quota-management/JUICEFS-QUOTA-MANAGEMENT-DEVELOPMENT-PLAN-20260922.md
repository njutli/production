## 一、交付目标与范围

**管理员在现有Portal登记已有LDAP用户及其目录，为目录设置或调整容量、inode限额并查看结果。配额使用JuiceFS原生机制，Portal不参与业务文件读写。普通用户的Portal个人额度页、目录查看授权和个人三级统计留待后续。**

目录登记与配额设置独立：`/users/alice`可以先加入Portal管理列表而不设限额，之后再设置配额。不需要Portal管理的目录无需登记，仍可正常使用。存储管理库保存受管目录、LDAP身份引用及审计，不替代POSIX权限，也不复制所有文件的归属关系。

| 第一期交付 | 本期不做 |
|---|---|
| 固定JuiceFS卷、指定管理根下的用户目录登记；独立“存储用户”页用于选择和核对已有LDAP账号 | 普通用户个人目录查看授权；任意卷、任意路径的开放式管理，以及自动创建或迁移业务目录 |
| 原生目录容量与inode硬限额的查询、首次设置、增额和受控降额 | 新增UID/GID配额、卷级配额、软配额、自动清理和取消已有配额 |
| ADMIN管理页面和变更记录；第一阶段既有只读监控保持可用 | USER个人额度页面、多租户角色体系、自动化管理员写Token、完整文件浏览器 |
| 独立配额服务、存储管理SQLite、操作恢复及必要权限调整 | 高可用管理服务、自研元数据网关和自研配额执行引擎 |
| 第一阶段已有目录统计继续运行，不为本功能重做监控平台 | 普通用户个人目录三级统计；为采集放宽0700权限；全量性能调优矩阵 |

inode限额按JuiceFS原生口径计量，包含文件和目录，不等同于仅限制普通文件数量。目录配额限制的是该目录子树，而不是某个UID在全卷写入的数据量；用户绑定用于管理和展示，两者不能混淆。

### 与LDAP身份管理的关系

路线A的配置前提、root边界、生命周期及后续Portal开户需求集中记录在[LDAP统一用户管理实施与注意事项](JUICEFS-LDAP-USER-MANAGEMENT-IMPLEMENTATION-NOTES-20260922.md)。本文当前仍按“查询和登记已有LDAP身份”开发；未来增加开户/停用等写接口时，另行同步接口及授权设计，不默认为本计划已包含，也不增加客户端助手。

会议已选定路线A：运维通过LDAP管理工具创建业务账号，各客户端接入NSS/SSSD，同一用户使用统一UID/GID；无需修改JuiceFS源码增加身份映射。

- LDAP及统一开户流程负责UID/GID分配和组关系。本功能通过受控只读LDAP查询核对身份，只保存引用，不另建ID分配器，不通过Portal创建LDAP/Linux业务账号。
- 同一LDAP UID跨客户端、跨卷代表同一用户。卷UUID只标识目录所属文件系统，不改变用户身份。
- 可用模拟身份先完成离线开发；本阶段在一台获准客户端上用两个真实LDAP账号验证身份、权限及配额。另一客户端上的身份一致性和配额共同生效在第三阶段新环境验收。LDAP部署和客户端配置另列实施工作，不将其扩成配额服务的开户功能。
- [显式映射计划（C）](../juicefs-user-id-mapping/JUICEFS-USER-ID-MAPPING-DEVELOPMENT-PLAN-20260921.md)与[名称自动映射计划（B）](../juicefs-user-id-mapping/JUICEFS-NAME-AUTO-MAPPING-DEVELOPMENT-PLAN-20260922.md)仅作历史保留；本期不开发映射核心、client_id认证、映射版本或发布工具。

## 二、部署结构与权限

```text
浏览器 → 152 Portal（Linux账号 jfsweb）
           ├─ 第一阶段目录展示：只读现有统计SQLite
           └─ 用户/目录登记、配额查询及ADMIN管理请求
                        ↓ 本机Unix Socket
              quota-controller（Linux账号 jfsquota）
                 ├─ 存储管理SQLite：登记、授权、任务、审计
                 └─ JuiceFS原生元数据接口 → PD/TiKV

业务客户端 → JuiceFS挂载 → TiKV元数据 + Ceph文件内容
               （基线启用root-squash）
                           按原生配额限制超额写入

受控管理挂载（不启用root-squash）
           → 仅供建目录、chown和应急修复
```

| 主体 | 职责 |
|---|---|
| 可信运维人员 | 经LDAP管理工具创建业务账号、接入客户端并准备目录；管理挂载、凭据及本地root/服务账号；通过受控工具管理Portal登录账号 |
| Portal ADMIN | 通过独立“存储用户”页选择并核对已有LDAP身份、登记目录、设置或调整额度、处理异常任务 |
| Portal USER | 保留第一阶段既有只读监控权限；本期不开放个人配额或目录明细，不得访问新增管理接口 |
| `jfsweb` | 运行网页后端；不持有TiKV/Ceph凭据，不直接打开存储管理数据库 |
| `jfsquota` | 运行常驻配额服务，直接调用JuiceFS元数据接口；不挂载文件系统，不持有Ceph keyring |
| `jfsstats` | 运行原有专用统计挂载和collector，更新目录统计库 |

这些服务账号是Linux账号，与人员登录Portal所用的ADMIN/USER账号分开。Prometheus/Grafana暂保留原服务账号，不顺带改造。157不增加配额服务。

Unix Socket通过文件权限和对端UID限定调用者为专用的`jfsweb`进程。Portal验证个人ADMIN会话，控制器再次检查固定操作、资源范围和参数；控制器仍信任Portal转交的人员身份，不能宣称能抵御已经被控制的Portal后端。

**安全前提：客户端root及运维人员可信，普通业务用户没有root等价权限，也不能取得后端凭据。** 所有业务挂载必须启用JuiceFS `--root-squash=<冻结UID>:<冻结GID>`，把经业务挂载发出的UID 0请求映射为统一的专用低权限身份；独立受控管理挂载不启用该参数，仅用于建目录、`chown`和应急修复。持有TiKV有效访问凭据的可信root仍可以直接修改配额；本功能不阻止这种管理能力。要承诺“普通用户不能自行提高限额”，必须在上线前完成第七节的后端接入隔离。

各客户端保留本地root（UID 0）及系统服务账号，不把它们作为LDAP业务用户。root的密码、SSH授权分别管理，日常可用个人运维账号加受控sudo留痕。`root-squash`使用的非零数字UID/GID必须在所有客户端和LDAP目录完成冲突检查后冻结，对应账号禁止登录、不加入业务或管理组、不拥有业务目录；不得依赖各主机可能不同的`nobody/nogroup`默认值，也不得改用会破坏LDAP多用户隔离的`all-squash`。该参数只能降低正常业务挂载上的误操作风险，不能限制能够控制挂载配置及后端凭据的恶意root，本期不承诺这种隔离。

## 三、用户实际如何操作

### 3.1 登记目录，不要求同时设置配额

1. 运维在LDAP创建并核验业务账号，例如`alice=50001:50001`。准备新目录时，在独立、未启用`root-squash`的受控管理挂载上用root创建尚不存在的`/users/alice`，创建即为root拥有、0700；父目录由运维控制。业务挂载上的root已被映射为低权限身份，不能经正常业务入口误操作该目录。已有目录只核对，不自动修改owner或搬数据。
2. ADMIN在“存储用户”页选择LDAP中的Alice，控制器经只读LDAP查询核对UID/GID及组关系后登记；在“目录与配额”页选择已配置的卷并填写目录路径。Portal不能另填一套不同的存储ID。
3. 控制器读取真实卷UUID、目录inode和实际owner，保存目录管理记录。新空目录记录实际root owner及拟交付的LDAP用户，不能提前将实际owner记成Alice；正常使用的目录则核对实际LDAP owner。
4. ADMIN可暂不设置配额，也可进入3.2流程。需要首次使用即受限的目录，配额确认前不交付；无需配额的目录核对后可直接交付。本期不授予Portal USER个人目录查看权。

目录资源状态与配额状态分开。没有目录配额的资源仍可正常登记、授权和查询；页面显示“未设置目录配额”，不意味着卷级或其他配额也不存在。此时目录统计可用于展示空间占用，但不能冒充原生配额计数或“剩余额度”。

### 3.2 首次设置与调整配额

1. ADMIN输入容量（GiB）、inode数及修改理由，点击预览；控制器读取现有限额、最新用量和分配预算。
2. 确认后提交任务。控制器重新核对资源、旧限额及预算，调用JuiceFS接口，再读取实际规则。
3. 回读一致且审计记录持久化后，页面显示“配置已确认”；客户端实际感知新限额可能稍有延迟，验收时记录这一时间。
4. 新目录由可信运维将owner改为LDAP用户`50001:50001`并保持0700；控制器回读同一卷、inode及新owner，更新登记记录并确认交付。已有目录保留经核对的权限和数据。真正开放访问的是POSIX权限变更，Portal的“已登记”或“已确认”状态本身不是文件访问开关；配额结果不明时，不交付要求初始限额的新目录。

首次为有数据目录设置配额可能需要初始化统计，按后台任务执行，不占用一次网页请求等待。若要求初始化期间没有不受配额约束的写入，由运维暂停该目录写任务后操作。

### 3.3 查询、撤权与停用

- ADMIN可查看所有受管资源及审计；USER仍只使用第一阶段既有只读监控，不查询新增受管资源或配额。拥有Linux账号不必同时拥有Portal账号。
- 禁用Portal账号只撤销网页访问；不删除目录、不取消配额，也不自动终止Linux进程或文件访问。个人目录查看授权和撤权流程留待后续。
- 停止业务使用时，LDAP管理员禁用账号，运维核对登录缓存并停止已有会话/任务；LDAP禁用不使正在运行的进程立即失效。保留目录、原配额和历史记录，不自动回收仍关联数据的UID，不用额度0代替禁用账号。

## 四、必须明确的配额规则

| 规则 | 实现方式 |
|---|---|
| 管理对象 | 初期仅配置卷内的`/users/<name>`目录；卷和允许根由受保护的服务配置给出，浏览器不提交META URL或后端凭据 |
| 容量单位 | 页面显示GiB，接口及数据库保存整数bytes；按交付版本支持的最小粒度检查输入，不静默四舍五入。inode使用整数 |
| 修改字段 | 修改请求中缺省字段表示保持原值；首期新增或修改的上限必须为正数，不能把0、空值或缺字段解释为取消配额 |
| 已有规则 | 导入和调整时保留未修改的限制；无法识别的现有规则转人工核对，不按页面默认值覆盖 |
| 降低额度 | 执行前刷新用量，拒绝低于当前观测用量的新上限；业务继续写入时仍可能出现设置后用量超过新上限，不承诺跨客户端原子切换。要求精确切换时暂停写入 |
| 叠加限制 | 核对并展示卷级、祖先目录等相关限制；若owner存在UID/GID配额，明确这是针对该身份的约束，不能将其剩余额度当成整个目录剩余额度 |
| 用量与剩余额度 | 原生quota接口读取额度及对应计数；剩余额度为`max(上限－同口径已用量, 0)`，同时显示超额量及采集时间。不是Ceph物理可用空间保证 |
| 管理预算 | 管理员设置每卷逻辑分配预算，串行检查已分配额度及尚未确认的增额任务；预算不代表预留Ceph空间。不限额目录及未纳管数据单独提示，不把它们算成零风险 |
| 后端容量 | 复用已有Ceph容量采集，结合副本开销、存量数据和安全余量制定预算；后端容量不足或观测过期时暂停新增及增额。不能用JuiceFS的`df`显示值自动推导预算 |

目录配额设置成功不表示字节级零超额。并发写入、计数刷新、删除、回收站及移动的实际表现以固定交付版本的隔离测试为准，测试结果写入使用说明，不通过长时间反复跑带宽来证明功能正确。

## 五、实现工作清单

### 5.1 原生配额适配器与控制服务

- 基于既定JuiceFS版本的元数据接口封装读取目录、查询和设置配额等固定操作，验证返回的规则、计数、单位及错误。不自行拼写TiKV Key/Value；本期不重建JuiceFS二进制。
- 优先独立构建薄适配层，避免将JuiceFS全部依赖引入现有Portal网页进程。先验证构建兼容性和精确整数输出，不假定现有CLI提供JSON，也不解析经过取整的人类可读容量作为真实值。
- `quota-controller`通过Unix Socket提供固定接口，一个worker串行执行变更；周期读取用量，不做每次页面请求触发的递归扫描。
- 执行前检查卷UUID、目录类型、inode、owner及路径范围，拒绝符号链接和路径逃逸。目录删除重建、改名或owner变化时标记待核对，暂停该资源的修改及管理员页面中不确定的展示。
- 待交付空目录允许已登记的root owner，交付时验证其变为指定LDAP用户；这一预期变更单独确认，不能与正常使用后意外改owner混为一谈。
- 管理根由运维控制，业务用户不能替换其他人的顶层目录；不能只靠执行前后两次路径检查承诺消除目录替换竞争。

### 5.2 数据库与可靠性

本功能使用**现有目录统计SQLite＋新增存储管理SQLite**，不再增加配额展示用数据库副本。

存储管理库为每个纳管目录生成一个**受管目录记录ID（resource ID）**，用作配额任务和审计记录的内部引用。它关联卷UUID、路径、inode和owner，但不是文件系统inode、用户UID/GID或访问凭据；目录删除重建、inode或owner异常变化时，必须暂停操作并重新核对，不能仅凭resource ID继续管理。

| 存储管理库记录 | 最小内容 |
|---|---|
| LDAP用户/组引用 | 内部ID、LDAP目录及条目引用、用户名、核对后的UID/GID和组关系、核验时间及状态；引用LDAP现有身份，不另分配ID，GID可共享 |
| 客户端身份核验 | 客户端名称、关联LDAP用户、实际解析UID/GID及组关系、核验人/时间/结果；不包含B/C映射配置或发布状态 |
| 卷与目录资源 | 卷UUID及配置引用、管理根、预算；受管目录记录ID（resource ID）、路径、inode、实际owner、可关联的LDAP身份和资源状态。待交付目录另记目标用户，交付时更新实际owner；同卷活动路径/inode不得重复登记 |
| 配额观测 | 每资源仅保留最近一次成功的实际上限、已用容量/inode及时间，另记最近错误/过期状态；拟修改值另存于任务，不逐次追加历史 |
| 任务与审计 | 同表保存控制器生成的操作编号（兼作幂等键）、操作者、服务身份、目标摘要、修改前后值、管理版本、理由、请求摘要、执行及回读结果；另记预览有效期、受理/终态时间、详情清理状态 |

数据库只由`jfsquota`读写；Portal经Socket查询。账号密码仍放在受保护的Portal账号配置中，后端私钥单独保存，均不复制进管理库。真正的配额规则和计数保存在TiKV，SQLite只记录管理关系、流程及观测。

业务账号及组关系保存在LDAP，存储管理库只记录核验结果；只读LDAP连接凭据与后端凭据一样由受保护配置提供。LDAP不可用时暂停新增或更换身份登记，不接受未经核实的网页UID/GID输入；不自动删除既有目录、撤销配额或改写owner。

变更流程：`保存24小时有效的预览操作 → 确认已有编号并持久化受理状态 → 检查真实值及版本 → 调用后端 → 回读 → 持久化审计 → 返回确认`。

- 已受理的同编号、相同内容返回原任务；同编号不同内容拒绝。未知、过期或已清理的编号不能补建为新任务。管理版本用于防止Portal中的旧请求覆盖，不宣称是TiKV的原子CAS。
- 超时或服务重启后无法确定是否提交时，标记“结果待确认”，优先回读，不盲目重试、解除限额或回滚。
- 日常变更统一经控制器。可信root需用CLI应急处理时先暂停相关管理任务，事后核对；发现外部更改只告警，不自动覆盖。
- SQLite或审计不能写入时拒绝新变更；未决任务保留预算占用。按下节实现保留、清理和一致性备份，禁止直接复制运行中的裸数据库/WAL作为完整备份。

#### 5.2.1 过期记录清理与备份实施要求

策略依据为[方案11.8.5](USER-AND-QUOTA-MANAGEMENT-RESEARCH-20260914.md#1185-过期数据清理空间与备份)，在Q1实现、Q3验收；复用控制器和操作表，不新增常驻维护服务或审计归档库。

**操作编号与清理资格：**

- `quota-preview`生成随机且不复用的operation ID，写入`awaiting_confirmation`记录，绑定原操作者、资源、规范化请求/理由、预期版本和24小时有效期；未确认预览不占预算。
- 提交只确认这一已有编号。在同一SQLite事务内校验当前权限、原操作者、内容、状态、期限和管理版本，转为`queued`并预留预算。两个同时到达的确认请求仅受理一次；后续worker仍检查真实配额。已受理编号的合法重试先查原记录并返回状态，不重新入队、不延长期限。
- 过期/未知/已清理编号返回同一“不可再次提交”错误（建议HTTP 410）；变更内容返回409。前端重新预览必须由管理员再次确认，不能自动替用户重做。操作查询仍按当前授权，不把随机编号当凭据。
- `queued/running/result_unknown`不自动删除。确认成功、确认无副作用的失败/取消才写`terminal_at`；服务重启、读取记录和重试不改该时间。调用后端后的超时或审计落盘失败，不能直接变成可清理的`failed`。
- 终态详情从`terminal_at`起保留180天；清空详情后仍保留请求摘要及去重信息。审计摘要和该编号保留730天再删除。资源当前管理版本独立保存；不永久保留每资源最后一条操作，也不设级联删除审计的外键。

**有界维护：**

- 定时器每24小时触发；启动时如上次运行已过期，补一轮即可。每批最多1000条，每轮最多10批/30秒，以先达到者为准；提交变更优先，遇锁忙结束本轮。批内重新校验状态、到期时间和引用，清理中断后可重入；时钟不可靠时跳过年龄清理。
- 为预览到期、终态时间及状态建立适用索引，按“过期未提交预览→过期详情→过期审计→无依赖停用记录”处理。停用资源先撤销授权、停止采集并阻止旧采集发布；摘要保存必要操作者/目标字段，不依赖永远保留活跃用户对象。
- 预览上限1000条、未决上限100条，未决超24小时提示；详情上限16 KiB、审计及请求摘要上限4 KiB。超长请求拒绝，错误输出脱敏截断。到达上限停止受理新建，不删未决记录解锁队列；配额刷新仅更新最新观测。
- 数据库及WAL/SHM默认规划2 GiB，80%告警、90%停止新增；系统盘空闲低于`max(5 GiB, 5%)`同样保护。检查预计写入/备份增量，留出确认已有任务、清理及恢复余量；这是应用阈值，不宣称硬限制。容量恢复且数据库可用后再受理新变更。
- 删除页允许复用，检查点有界，监测WAL和长读事务；不直接删除WAL/SHM，不每天整库VACUUM。必要的缩库安排维护窗口并核对临时空间；本阶段不调整其他服务的数据保留策略。

**备份与恢复：**

- 每天最多一份一致性备份；最近7份、7天、合计8 GiB（含临时文件）任一限制先到即轮换旧副本。只允许一份在建备份；生成前允许删除多余旧副本腾出预计所需空间，始终保护最后一份有效备份，待新副本验证并原子发布后再淘汰此前最后有效的副本。仍无法满足容量时跳过并告警，不删唯一有效副本冒险生成新备份。
- Portal账号配置和会话签名密钥分别受保护保存，备份时记录其版本与管理库备份的对应关系；恢复时核对管理员稳定账号ID和审计归属，不匹配就先关闭新增管理写入口、人工核对。密钥不写入管理库或公开结果包，恢复后旧会话失效。
- 只删除本服务已登记且创建进程停止、超24小时的失败备份临时文件。独立诊断文件如有，按7天/256 MiB轮换；配置、私钥及其他服务数据不属于清理对象。
- 恢复先关闭新增管理写入口；作废全部未确认预览，逐项核对未决，不自动重放。开写前回读所有恢复的活动资源身份/额度，更新观测、重算预算，人工核对并补齐备份后的纳管差异，不仅检查未决任务；未核实范围暂停，丢失审计标明缺口。恢复账号配置时一并作废旧会话。保留原事件时间，不能恢复后重新计算180/730天。
- 默认审计到期直接清理，无自动长期归档。额外人工导出另定存放范围和期限；备份有自己的轮换周期，不作为永久审计。最后有效备份超期保留属于有告警的例外。
- 记录最近维护时间、清理数量、过期积压、未决数量/年龄及占用，无每条删除的永久审计流水。页面说明可查询的730天范围和已清理状态。

### 5.3 Portal接口与页面

复用现有Go API和网页，不重新建设前端框架。以下接口以`/api/v1`为前缀，实施时同步更新[OpenAPI](../../../../api/openapi-v1.yaml)。

| 接口 | 用途与权限 |
|---|---|
| `GET /admin/ldap-users?query=&cursor=` | 仅个人ADMIN会话可用；控制器向389 DS只读查询已有账号，空筛选返回首批、输入部分用户名后重新筛选，按需分页供下拉框浏览；不周期性同步全部LDAP账号，不返回密码等敏感属性 |
| `GET /admin/storage-users` | ADMIN查看管理库中**已登记**的用户及最近核验时间；这是登记记录，不冒充实时LDAP全量列表 |
| `POST /admin/storage-users` | ADMIN选择LDAP账号后登记；控制器再次向389 DS核对条目、UID/GID及组，不信任浏览结果或网页提交的数字ID；LDAP不可用或身份变化时拒绝登记，不创建LDAP/Linux用户 |
| `PUT /admin/storage-users/{id}/identity-status` | ADMIN记录客户端LDAP/NSS身份核验结果，不执行远程开户或映射发布 |
| `GET/POST /admin/storage-resources` | ADMIN查询或登记已存在目录及实际owner，待交付目录另记目标LDAP用户；不改变文件权限，允许不设配额 |
| `POST /admin/storage-resources/{id}/quota-preview` | ADMIN提交拟变更值和理由，返回真实用量、预算检查结果及24小时有效的待确认操作编号，不修改配额 |
| `PUT /admin/storage-resources/{id}/quota` | ADMIN确认已有操作编号及绑定内容；受理时复核权限、版本和真实规则，返回原编号/状态，重复提交不重复执行 |
| `GET /admin/storage-operations`及`GET /admin/storage-operations/{id}` | ADMIN查看变更列表及单项结果 |
| `GET /admin/storage-quotas` | ADMIN查询所有受管资源的原生配额额度与用量；本期不新增USER个人额度接口 |
| 现有`GET /usage/roots`、`GET /usage/tree` | 保持第一阶段既有只读监控行为并做回归，不把整卷root及其top 100聚合结果当作普通用户个人目录快照 |

新增的身份、目录、配额、任务和审计接口（包括只读查询）只接受个人ADMIN登录会话。现有`automation-admin`和`automation-user` Bearer凭据仅保留既有监控读取用途，不因旧代码把前者映射成ADMIN而获得新增管理数据的读取权。实施时按路由来源区分个人会话与自动化凭据，不能只判断角色字符串。

ADMIN增加“存储用户”“目录与配额”“变更记录”。“存储用户”登记表单使用可搜索下拉框：进入页面先加载一页LDAP账号，点击可直接选择或继续翻页；输入几个字母时按用户名筛选，大小写输入不应妨碍找到原始用户名（例如输入`Alice`仍显示`alice`）。只向浏览器返回选择所需的用户名、UID/GID及必要状态，不一次取回全部用户。显示目录、上限、用量、剩余额度、更新时间及状态；USER“我的额度”后置。管理员页面区分“未设置”“处理中”“已确认”“待核对”“数据过期”，不能把失败或未采集显示为0。

用量初始刷新安排为控制器每60秒采集一次、页面每30秒查询一次，修改后立即回读；超过180秒未成功采集则标记过期。**这一周期只针对配额用量，不是LDAP账号同步周期**：LDAP浏览按用户操作实时查询所连接节点，页面提示双节点异步复制可能造成短时差异；管理库仅保存已登记身份的最近核验结果。授权检查每次请求使用当前管理记录，不等待用量刷新。

2. **安全改造未就绪时不上线写入口。** 可在隔离环境完成开发、演示及功能测试，但不能声称普通用户无法绕过。若采用其他隔离方式，须单独审查并验证所有真实后端端点，不以“放行客户端IP”代替用户隔离。
3. **执行前列精确变更。** 新建Linux服务账号、修改文件权限/unit、专用统计挂载切换、业务/管理挂载的`root-squash`变更、网络/TLS变更及服务启停，另列命令、对象和恢复方式供审批；本计划不是sudo授权。业务客户端挂载变更必须安排窗口，不中断157业务。
4. **先只读核对，再开放管理。** 试点环境安装服务后先验证查询、权限和旧功能；完成普通用户防绕过测试后，才允许试点目录修改。若另行批准复用152，先核对业务窗口及原有监控，再按批准范围操作；保持现有不开机自启的约定。
5. **回退不删除已有配额。** 关闭新写入口、保留TiKV真实规则、备份管理库和审计；按已确认的真实配额核对未决任务。回退不得扩大旧USER的整卷查看范围，也不得把新业务用户直接绑定整卷root。涉及凭据或TLS的回退另按对应维护方案执行。

普通用户不能通过修改配额逃避限制，是本功能的验收要求；防御持有后端凭据的恶意客户端root不在本期范围。两者在交付说明中分开写清楚。
