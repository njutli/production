# JuiceFS按用户名与组名自动映射开发计划（路线B）

> 日期：2026-09-22。
> 状态更新（2026-09-22）：历史备选，尚未实现。本期会议决定采用路线A，业务账号统一通过LDAP管理，不执行本文计划；仅在后续需要兼容已有账号时重新评估。下文保留原设计，不作为本期开发或验收要求。
> 适用架构：JuiceFS社区版＋TiKV＋Ceph，客户端root及部署运维可信。
> 关联：[路线C——多客户端显式账号映射计划](JUICEFS-USER-ID-MAPPING-DEVELOPMENT-PLAN-20260921.md)、[配额管理开发计划](../juicefs-user-quota-management/JUICEFS-QUOTA-MANAGEMENT-DEVELOPMENT-PLAN-20260922.md)。

## 一、目标与方案定位

**保留各客户端现有Linux账号及UID/GID；对已经确认属于同一身份的同名用户、同名组，自动生成统一存储ID映射，省去管理员逐台填写数字对应关系。**

例如Alice在A上为`alice=10001`，在B上为`alice=20001`：管理员登记一次`alice → 存储UID 50001`并批准使用范围，工具分别解析两台机器，生成`10001 → 50001`与`20001 → 50001`。两端仍以原账号运行应用，卷内文件owner统一为50001；在各客户端查看时再显示为本机UID。

### 1.1 借鉴什么，不照搬什么

JuiceFS商业版公开文档介绍了按用户/组名称映射内部ID、再在各主机转换为本地数字ID的行为，也说明了本机缺少账号和关闭映射时的限制。[官方UID/GID Auto Map说明](https://juicefs.com/docs/cloud/guide/guid_auto_map/)

本计划借鉴上述使用效果，**不是复刻商业版内部算法，也不承诺与其内部ID、协议或数据格式兼容**。本项目自行实现“受控名称登记＋本机身份解析＋JuiceFS双向转换”，不要求替换TiKV/Ceph，也不增加NFS/SMB或第二层FUSE。

### 1.2 与路线A、C的区别

| 路线 | 管理员主要维护什么 | 客户端要不要改原UID/GID | 是否改JuiceFS |
|---|---|---|---|
| A：统一存储账号 | 集中账号及统一UID/GID，业务用该身份运行 | 冲突账号需要迁移，或改用新建存储账号 | 不需要映射补丁 |
| B：本计划 | 同名身份确认、名称与存储ID、获准客户端范围；本地数字自动解析 | 不需要 | 需要共用的双向映射核心 |
| C：显式映射 | 各客户端本地UID/GID与存储ID的对应关系 | 不需要，用户名也可不同 | 同一套双向映射核心 |

**B、C只是映射配置的生成方式不同，不开发两套文件权限引擎。** B自动生成C核心可加载的数字映射；共同处理请求身份、属性返回、附加组、缓存及异常路径。路线C目前也只有计划，尚无已验收代码；可以直接从B开始开发共用核心，不必先完整交付C的管理流程。

首期选择B或C生成一个挂载使用的完整配置，不在请求处理中遇到B失败就自动切换C，也不让两种配置争抢同一个本地UID。

## 二、“自动”的范围与身份规则

### 2.1 谁确认身份，谁转换数字

管理员确认“各台机器上的alice确属同一人”，工具负责把名称解析成数字。**程序不能从同名推断真实人员归属，也不能因为某人自行创建同名账号就自动授予存储访问。**

| 情况 | 首期处理 |
|---|---|
| 同名、同一人、本地UID不同 | 确认并纳入允许范围后，自动生成同一存储UID映射 |
| 同名、不同人 | 不自动合并；在相应客户端禁用该名称的自动接入，改走C显式映射或先整理名称 |
| 不同名、同一人 | B不猜测别名关系；采用C显式映射。首期不额外开发别名系统 |
| 同名组、不同成员或用途 | 先确认是否确属同一共享业务组；不能按同名自动扩大成员权限 |
| 新客户端或新账号 | 先确认该客户端上的人员/组归属及允许范围，再自动解析数字；不扫描后自动开通所有账号 |
| 本地或目录服务重复、遮蔽同名记录 | 明确实际NSS解析来源及歧义，未解决前不发布该客户端配置 |

名称登记初期限定在一个受管身份域内。“身份域”只是共同遵守同名身份规则的一组受管账号和客户端，不要求部署LDAP域，不是JuiceFS卷，也不是客户端IP。不同组织的同名人员不能随意放入同一域；以后增加多域时，名称键必须带域且存储数字仍不得冲突。

### 2.2 名称、数字和组的约定

- 用户和组分开登记，名称键包含类型：`用户 alice`和`组 alice`不是同一条记录。UID不必等于主GID，用户名不必等于主组名。
- 首期名称精确匹配，保留大小写和域后缀，不自动把`alice`、`Alice`、`alice@example`合并。解析结果不能稳定对应时交由管理员处理。
- 统一登记处持久分配存储UID/GID，不由客户端按发现顺序独立分配，也不使用未处理碰撞的名称哈希直接决定文件owner。
- 一个存储UID在受管范围内只对应一个用户；同一用户可在多个客户端和多个卷复用。同一存储GID可由多个用户共享。卷UUID只标识挂载、目录、配额等资源，不参与身份映射键。
- 存储ID范围先核对已有文件owner、现有登记及保留值，不能照搬商业版示例中的数字区间。已有用户已分配过存储ID时沿用原值，不因选择B重新分配。

## 三、实现方式与请求流向

```text
管理员确认获准的用户/组名称及客户端范围
    ↓
集中登记：用户名/组名 → 固定存储UID/GID
    ↓ 由运维通过受控连接传递配置及解析结果
各客户端定向查询本机NSS：名称 → 本地UID/GID
    ↓
配置工具校验并生成：本地数字 ↔ 存储数字
    ↓
定制JuiceFS挂载时加载本机映射
    ↓
业务IO：实际进程身份 → 内存映射 → 原生文件权限及元数据操作
属性返回：存储owner → 本机UID/GID
```

### 3.1 集中登记与本机配置

首期使用一份受保护的集中登记文件及单写者工具，保存已分配ID；工具加锁、检查唯一性并原子更新。后续Portal集成时迁入已规划的存储管理SQLite，保持原ID，不再创建独立身份数据库或两份可同时分配ID的权威记录。

| 数据 | 最小字段 |
|---|---|
| 名称登记 | 用户/组类型、准确名称、存储ID、状态、获准客户端范围、版本；停用记录保留 |
| 客户端记录 | 持久`client_id`、联系地址、身份域、核验记录；IP变化不重新分配ID |
| 本机解析结果 | client_id、名称、本地UID/GID、解析时间、来源配置摘要、冲突检查结果 |
| 最终配置 | client_id、名称登记版本、数字双向映射、配置哈希；不含密码、TiKV私钥或Ceph密钥 |
| 加载记录 | 实际挂载实例、卷UUID、二进制及配置版本、验收状态；与“文件已复制”区分 |

这些是拟开发的字段，不是当前JuiceFS已支持的参数或配置。注册文件、生成配置和运行记录分别表达期望值、部署值与实际加载值，不能因Portal中记录存在就宣称已经生效。

### 3.2 本机NSS解析

NSS是Linux查询本地文件、SSSD等身份源的接口。工具按获准名单定向查询，例如核对`getent passwd alice`及相关组，而不是只读`/etc/passwd`，也不依赖不带参数的全量`getent`枚举。SSSD可能关闭枚举，因此枚举不到不等于账号不存在。[SSSD身份查询说明](https://sssd.io/troubleshooting/basics.html)

开发要求：

1. 核验名称查数字、数字反查名称的对应关系；同一客户端不能把一个本地UID识别为两个可隔离用户，也不能存在不可逆的多对一映射。
2. 对缺少的获准账号、重复ID、来源歧义、超时或变化中的结果明确报错，不生成半套可用配置。获准名单本身可以只覆盖该客户端需要使用的用户，不要求每台机器创建所有人的账号。
3. 生成时记录快照，挂载前复核。发现本地UID或组记录变化时重新生成并确认，不能静默用旧数字代表新账号。
4. NSS调用使用实际系统解析链；原型核对Go构建方式和查询实现是否覆盖现场身份源，不能假定静态构建的账号查询天然等价于NSS。
5. **不在每次IO中查询名称、LDAP、Portal或集中登记。** 已加载挂载使用内存数字表；名称解析成本放在配置生成和挂载前。

### 3.3 复用JuiceFS映射核心

代码范围沿用[路线C的客户端边界设计](JUICEFS-USER-ID-MAPPING-DEVELOPMENT-PLAN-20260921.md#32-代码改动集中在客户端边界)：内部元数据和共享缓存保持存储ID，输入身份和返回属性在JuiceFS中转换。FUSE负责传递请求，不是FUSE自身维护本项目的映射规则。

必须共同覆盖以下路径：

- 实际请求UID、主GID和参与权限检查的附加组；创建、chown/setattr、setgid继承；lookup/getattr/readdirplus的owner返回。
- **附加组只转换请求进程实际持有的组。** NSS解析用于建立组ID对照，不把目录服务中新增加的组成员资格直接补给已有进程，更不能把本地组与存储组取并集。
- 内核权限检查和JuiceFS用户态检查的一致性，以及属性、目录、页缓存和已打开文件路径。不能只修改请求头两个字段后就宣称权限正确。
- 缺失映射不得原样透传本地数字；远端owner在本机没有反向映射时，也不能直接返回可能碰撞本地账号的存储数字。安全的未知owner展示/拒绝策略必须在最小原型验证，不默认`nobody/65534`天然安全。
- 首期可信root保留显式`0 → 0`管理语义，禁止普通名称映射到UID/GID 0；root、内部管理及释放/清理请求单独测试，不因拒绝未知用户破坏排空和卸载。需要把各客户端root降权为不同存储身份时另行定义，不由名称B自动合并或自动降权。

原型审计以实际交付源码为准，可参考上游[身份上下文](https://github.com/juicedata/juicefs/blob/v1.4.1/pkg/fuse/context.go)、[FUSE操作入口](https://github.com/juicedata/juicefs/blob/v1.4.1/pkg/fuse/fuse.go)及[Linux FUSE权限说明](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html)。若公共核心尚不能安全处理未知owner、缓存或组权限，应先解决这些问题，不用B的自动配置掩盖它们。

## 四、操作示例与生命周期

### 4.1 Alice从两个客户端使用原账号

以下名称及数字均为例子：

| 对象 | 客户端A | 客户端B | 统一存储记录 |
|---|---|---|---|
| 用户alice | UID 10001 | UID 20001 | UID 50001 |
| Alice的主组research | GID 11001 | GID 21001 | GID 51001 |
| 附加共享组model-readers | GID 12000 | GID 22000 | GID 52000 |
| 用户charlie | 无需开通 | UID 10001 | UID 60001 |

1. 运维确认两台的alice属于同一人、两个同名组含义一致，并确认B的charlie是另一人；批准各自使用范围。
2. 集中工具为名称分配上述存储ID。管理员不填写A、B每个本地数字；工具从两台机器采集并校验后自动生成映射。
3. 运维部署同一版本的定制JuiceFS及各自配置，挂载前复核本机身份；在受控入口完成读写、拒绝越权和owner检查后开放业务。
4. A的alice创建文件时记录owner `50001:51001`；B的alice使用同一存储身份访问，在B上查看owner为`20001:21001`。
5. B的charlie即使本地UID与A的alice相同，也转换为60001，不能读取Alice的0700私有目录。共享模型文件的目录和文件权限单独设置为获准用户可读、不可改；映射本身不自动授予共享权限。

若进程没有model-readers附加组，即使账号数据库已经加入该组，本功能也不能替进程补上权限；需按Linux账号和任务流程启动具有正确组身份的进程。

### 4.2 新增、改名、停用及重连

| 场景 | 规定动作 |
|---|---|
| 新增获准用户/客户端 | 确认同名身份，更新允许名单，定向解析并生成配置；不逐台手填UID映射 |
| 用户或组改名 | 经确认更新名称记录并保留原存储ID；多客户端过渡期间采用受控窗口或C，不自动按新名字分配新身份 |
| 本地UID/GID改变 | 重新解析、核验并部署新配置，存储ID及文件owner不变；不替用户修改Linux账号 |
| 同名账号删除后分给新人 | 先撤销旧访问并处理旧任务，旧名称保留历史记录，不自动继承原存储ID或文件。数字和名称都相同也无法自动证明还是原人 |
| 正常断线、重启、IP变化 | 复用原client_id、已批准存储ID及配置；挂载前核验身份漂移，不自动分配新ID |
| NSS暂不可用 | 不生成新配置，不绕过新挂载的身份复核；已有挂载继续使用已加载映射，不把一次查询失败当成自动撤权 |
| 全局停用 | 撤销各获准客户端配置，停止相关存储任务并完成正常卸载、重挂载及拒绝访问验证；保留文件、存储ID和配额 |

首期映射在挂载生命周期内固定：新增、修改、撤销均需停止受影响任务、排空写入、正常卸载后重挂载，可能影响同一挂载的其他用户。不能用lazy unmount、仅更新磁盘配置或Portal状态代替实际生效；旧句柄、旧FUSE连接及缓存需按共用验收处理。

运行期间不得擅自把获准账号的UID或名称交给另一个人。静态映射不会持续监控账号数据库，这一限制必须写入客户端账号管理流程；如果业务要求无窗口动态变更，再单独开发热更新和撤权机制。

## 五、数据兼容、配额与Portal

- **已有数据不自动转换。** 启用B后，原来保存本地UID的文件不会自动变为新存储ID。先在独立测试卷验证；需要接入已有卷时另做owner盘点、备份和迁移计划，不能直接开启后批量chown。
- **回退也有身份语义。** 关闭映射或换回原版JuiceFS后，应用可能直接看到存储ID，不能当作无影响回退。恢复旧配置也不得重新授权刚被撤销的用户。
- **配额独立。** 目录配额仍针对原目录，使用原生计数；配额服务核对存储owner。Portal用户/目录绑定不要求先设置额度，也不因文件用户名相同而自动绑定Portal账号。
- **目标管理入口是Portal ADMIN，首期先用工具。** 后续在既有存储管理库增加名称、允许客户端范围、解析差异及配置加载记录；网页负责登记、预览、批准和导出。运维部署及核验，不让Portal按每次文件IO参与映射。
- **身份登记不等于后端授权。** 客户端仍需TiKV/Ceph接入能力、受控挂载及POSIX文件权限；名称表不会替代后端认证，也不防范持有凭据的恶意root。普通用户凭据隔离依照配额计划和总体安全方案单独验收。

## 六、开发阶段与验收

### 6.1 先做最小原型，再补齐工程化

| 阶段 | 工作 | 完成条件 | 状态 |
|---|---|---|---|
| B0：名称原型与公共核心核验 | 固定源码/构建；实现最小名称登记、NSS定向解析及数字配置；联调两个隔离客户端视图。公共映射核心尚未实现时同步完成其最小原型 | 同名不同UID跨机共享；同号不同人隔离；名称冲突拒绝；owner双向返回、组权限及未知owner策略可验证 | 待开始 |
| B1：配置生成与公共核心完整实现 | 名称/存储ID持久分配、允许范围、NSS校验、版本及加载记录；复用或补齐C的请求/属性/缓存处理 | 配置错误不启动为无映射挂载；重复执行不重新分配ID；不增加每IO网络查名 | 待B0 |
| B2：正确性与异常回归 | 补名称、组、改名/回收、NSS失败、撤销及存量兼容用例，共用C的权限与文件操作回归 | 无已知越权、错误owner或错误授权生效报告；不支持的功能明确拒绝 | 待B1 |
| B3：实际后端受控试点 | 经授权的独立TiKV/Ceph测试卷，训练典型操作及小范围映射开/关对照；发布使用和回退说明 | 原生配额及业务操作正常，性能开销有数据，业务挂载未受影响 | 待B2及环境授权 |

首期不做：别名自动合并、映射热更新、即时撤权、完整ACL/SELinux/file capability映射、自动证书平台或常驻配置分发代理。若实际业务依赖这些能力，在试点前扩展范围并重新估算，不能静默忽略已有权限规则。

### 6.2 最小测试清单

复用路线C公共测试，不另跑一套长时间调优矩阵；B0先跑前四项及公共权限核心。

| 场景 | 核验重点 |
|---|---|
| 同名不同本地ID | 同一存储owner，各机显示自己的UID/GID；跨客户端访问正常 |
| 不同名却相同本地ID | 不会合并为同一用户；私有目录拒绝越权 |
| 同名不同人、缺少名称、重复ID | 管理端不自动合并；编译失败明确，不输出部分生效配置 |
| 主组/附加组 | 主组名与用户名不同、setgid继承、进程组与最新NSS组不同，均不额外授予权限 |
| 未知owner及共享模型 | 反向显示不碰撞本地用户；属性和缓存路径不越权；获准模型可读不可写 |
| 名称规则与身份源 | 大小写、域后缀、NSS优先级、查询超时和关闭枚举时行为确定；不临时开启全量枚举 |
| 新增、改名、同名重建 | 原存储ID稳定，账号换人不自动继承；旧名称和旧配置不造成隐式重新授权 |
| 重启、管理不可用及撤销 | 重连不换身份；已加载与已部署区分；所有相关旧连接处理后才确认撤销 |
| 文件操作与配额 | 共用C的创建、属性修改、rename/link、缓存与目录配额回归；不改变TiKV元数据格式 |
| 开销 | 对照映射开/关的元数据操作及代表性读写；记录挂载前解析耗时和内存，异常下降再做定向复测 |

不存在已经测得的“零延迟开销”结论。设计只保证不主动新增每IO的名称服务网络往返；实际CPU、查表和权限检查开销在B3确认。
