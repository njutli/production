## 一、目标与选择依据

**保留各客户端已有Linux账号、UID/GID及业务运行方式，通过修改JuiceFS客户端，在访问共享文件系统时进行用户与组ID转换，解决跨客户端数字身份冲突。**

业务特点是：多个客户端只读共享模型相关文件，各客户端写入自己的业务文件；同一客户端存在多个用户，仍需区分文件所有权并隔离私有文件。因此，不能将整台客户端的所有用户用`all-squash`合并为一个身份。

当前三条候选路线的取舍是：

| 路线 | 用户如何使用 | 主要代价 |
|---|---|---|
| A：统一存储账号 | 通过LDAP/AD或受控账号表管理不冲突的存储账号，业务以这些账号运行 | 需要统一规划ID，并调整部分业务的运行身份 |
| B：按名称自动生成映射 | 管理员确认同名身份后，自动解析各机UID/GID，用户继续使用原账号 | 需要同名身份规则、名称解析工具及共用映射核心 |
| C：本计划的显式逐用户映射 | 管理员登记数字对应关系，用户继续使用原账号和原UID/GID访问挂载点 | 需要研发和长期维护权限相关补丁 |

本计划承载路线C；[路线B开发计划](JUICEFS-NAME-AUTO-MAPPING-DEVELOPMENT-PLAN-20260922.md)单独说明名称登记与配置生成，两者共用本文的双向数字映射核心和公共权限回归，不重复开发或计算公共工作量。可从B或C开始实现共用核心，不要求先完整交付C才能做B。各路线仍待验证，不预先宣布替代A。客户端root和部署运维人员仍然可信；不解决恶意root更换程序、映射配置或利用后端凭据绕过限制的问题。

## 二、身份与权限模型

### 2.1 映射的含义

“存储UID/GID”是JuiceFS元数据中保存的统一数字身份，不是新增的Linux登录账号，也不是TiKV或Ceph的账号。各客户端的映射表由运维配置，不根据用户名或当前IP自动推断。

以下均为示例数字，不可直接用于部署：

| 客户端与本地账号 | 本地UID/GID | 存储UID/GID | 预期 |
|---|---|---|---|
| A：Alice | `10001:10001` | `50001:50001` | 拥有Alice的私有文件 |
| A：Bob | `10002:10002` | `50002:50002` | 与Alice隔离 |
| B：Charlie | `10001:10001` | `60001:60001` | 虽与A的Alice本地ID相同，仍是不同身份 |
| B：Alice（确有跨客户端使用需要时） | `20001:20001` | `50001:50001` | 经明确登记后访问同一个人的文件 |

访问请求中的本地身份转为存储身份；向应用返回的文件属主则转回本机身份。例如B上的Alice创建文件，卷内owner是50001，在B上查看owner应是20001。

UID与GID分别维护映射。不同用户可以属于同一个共享组；共享组不是用户身份冲突。首期同一挂载内不允许多个本地UID合并为同一个存储UID，避免反向显示和权限判断存在歧义。

Alice从A换到B使用原文件时，由运维先确认两端账号确实属于同一业务用户，再登记两端分别映射到存储50001。A创建文件后卷内owner保持50001；B上的20001经映射后使用同一存储身份。用户名相同、数字UID相同或持有同一客户端证书，都不能代替这一步人员与账号核对。

### 2.2 文件、配额与管理边界

- 共享模型目录由受控管理身份持有，业务用户仅能读取；文件及父目录都不能被业务用户修改，防止删除或替换模型。
- 私有目录按映射后的存储身份设置owner、权限，允许所属用户读写；客户端内部与跨客户端的其他用户都必须经过相同权限检查。
- 首期配额使用JuiceFS原生目录配额，不重新开发配额引擎。若后续使用UID/GID配额，配置和计费必须以存储ID为准。
- 普通用户不能修改映射配置，也不能取得TiKV/Ceph凭据或绕过受控挂载。root仍属于可信运维，不把映射当作防范root的安全机制。
- 配额管理权限、TiKV认证改造及Portal权限控制属于其他特性；本补丁不会自动把普通IO与配额设置划分成不同后端权限。

### 2.3 管理端与客户端各自负责什么

| 位置 | 职责 |
|---|---|
| 集中登记与配置工具；后续可由Portal提供入口 | 分配存储UID/GID，登记每台客户端的本地账号对应关系，检查冲突，生成配置并记录部署结果 |
| 每台客户端上的定制JuiceFS | 加载本机专属配置，在接收FUSE请求、返回FUSE属性时转换身份，执行映射准入及对应权限检查；FUSE本身不保存或执行本方案的映射表 |
| 客户端Linux内核 | 提供进程身份，并按实际挂载选项参与本地权限检查；实现必须让其与JuiceFS的身份视图一致 |
| TiKV与Ceph | TiKV保存JuiceFS元数据中的存储UID/GID等记录，Ceph保存内容对象；两者不执行本方案的逐用户映射 |

配置管理关系为：`集中台账 → 每客户端配置 → 本机JuiceFS加载`。实际访问关系为：`本地进程 → 内核/FUSE → 本机JuiceFS映射与文件权限处理 → TiKV/Ceph读写`。Portal不进入数据IO链路，也不要求修改TiKV协议传入客户端ID。

不能把过程描述为“TiKV发现请求UID等于文件owner，所以允许访问”。文件权限语义由JuiceFS及相应内核检查处理；本方案没有在TiKV增加文件用户鉴权。

### 2.4 客户端如何登记、重连和退役

`client_id`是运维为受管客户端分配的持久管理编号，例如UUID，用于关联该机配置和审计。主机名、管理IP属于可更新的联系信息。数据库内部主键只承担记录关联，不再另外定义一套供文件权限使用的“稳定用户身份”。

| 情况 | 处理方式 |
|---|---|
| 首次纳管 | 运维登记机器，生成并保存client_id，在该机受保护目录部署客户端记录及专属配置 |
| 网络断开重连、机器重启或正常重挂载 | 使用本地持久保存的原client_id和映射；不重新注册，不自动分配新的存储UID |
| IP或主机名变化 | 核对受管机器后更新联系信息，保留client_id和映射 |
| 证书轮换 | 更新该client_id关联的凭据，保留原存储身份；不能把证书指纹本身当作永不变化的client_id |
| 重装、配置丢失或机器替换 | 由管理员确认恢复原客户端记录还是建立新记录；无论使用哪个client_id，原用户仍对应原存储UID，不能按重装自动改号 |
| 退役 | 停止相关任务、排空并卸载，按后端实际能力撤销该机接入；记录标记retired，client_id不再分配给其他机器，保留必要审计 |

断线恢复是客户端重新连接后端，不需要Portal重新判断每个IO属于哪台机器。**文件归属由存储UID/GID维持，client_id变化本身不会改变文件owner。** 如果丢失映射而无法可靠恢复，应暂停该挂载，不能猜测身份或回退为本地UID直接访问。

若后续实现客户端自动获取配置，可在首次受控登记时注册公钥、签发客户端证书，并由管理服务将证书身份关联到client_id；换证时更新该关联。P0～P3由可信运维通过已核验的主机连接人工部署，不为了原型先开发注册代理或CA服务。

证书只能证明请求者持有相应私钥；复制私钥的两台机器可能表现为同一身份，不能据此保证物理客户端绝对唯一。管理服务使用的证书与PD/TiKV、Ceph的接入凭据分别说明用途，不默认一张证书同时适用。删除Portal记录或本机密钥也不等于后端已经拒绝旧凭据；实际撤销方式和已有连接行为需随后端接入方案验证。

### 2.5 谁分配存储ID，如何避免客户端之间串号

**各客户端不自行分配存储ID，也不互相同步映射。** 运维维护一份跨JuiceFS卷通用的权威身份台账，记录用户、组、客户端及映射；各机只持有从该台账生成的本机配置。管理员负责确认不同机器上的账号是否属于同一人。

- 一个存储UID在当前受管身份域内只能代表一个用户，并在不同JuiceFS卷中保持相同含义；同一用户可以在多台客户端映射到该UID。A和B的Alice都映射到50001是预期行为，不能把它误判为重复错误。
- 用户映射以`client_id、本地UID`定位，不把卷UUID作为映射键；同一客户端配置内须能唯一反向查找。不同客户端可以各有本地UID 10001，但分别指向50001、60001。同一客户端获准挂载多个卷时复用同一套身份映射。
- 哪个客户端或用户可以挂载、访问哪个卷及目录属于资源授权，由后端接入凭据、受控挂载和POSIX权限/ACL单独管理；不能通过在不同卷给同一人分配不同存储UID实现。
- 组单独登记和分配存储GID，用户可共享业务组；本地组到存储组的转换与用户转换分别校验。不得仅凭同名组自动合并。
- 原始目录owner、已有映射与历史分配必须纳入检查。停用用户后不立即回收存储ID；如果存量数据已混用同一ID，新增映射不能自动恢复真实归属。
- 本地账号删除后又用相同UID创建他人账号时，必须先撤销旧映射。仅核对UID数字无法发现“使用者已经换人”，这需要客户端开户流程配合。

P0～P3可用一份受控的集中登记文件和离线校验/配置生成工具完成上述管理，配置输出应由同一份一致记录生成，避免逐机手写目标UID。后续Portal集成复用已有规划中的存储管理SQLite：用事务及唯一约束防止并发分配冲突，增加客户端映射记录，不另起一套身份数据库。Portal中的记录与实际部署版本分开保存；客户端不按每次IO查询该库。

## 三、首期范围与实现原则

### 3.1 首期做什么、不做什么

| 纳入首期 | 首期不承诺 |
|---|---|
| 固定Linux/JuiceFS构建版本上的原生FUSE挂载 | 所有内核、所有JuiceFS版本及其他操作系统通用支持 |
| 集中登记的离线校验/配置生成、本地静态映射、双向UID/GID转换 | 在线热更新、正在运行任务的身份即时切换 |
| POSIX权限、附加组、创建/修改属主、目录配额兼容 | 完整ACL、SELinux及file capability身份语义兼容 |
| 日志标识客户端、本地身份、存储身份和映射版本，运维人工部署 | Portal映射页面、自动开户、证书注册代理及自动分发平台 |
| 独立测试卷验证和受控试点 | 改造现有数据owner、直接替换业务挂载 |

若首期不实现ACL等高级权限能力，只能在确认没有相应依赖的测试卷或试点范围使用；对不支持的配置、操作必须明确拒绝，不能默默忽略或取消已有安全约束。实际业务若依赖这些功能，必须扩展实现与验收范围，重新估算工期。

### 3.2 代码改动集中在客户端边界

尽量让JuiceFS内部元数据和缓存一直使用存储ID，只在FUSE输入、输出边界转换，不改变TiKV/Ceph接口及元数据格式，也不引入第二层FUSE或网络代理。

| 处理位置 | 开发要求 |
|---|---|
| 挂载初始化 | 加载本地受保护配置，核对预期client_id、配置格式版本、发布版本/哈希、数字范围、重复目标及反向映射；实际卷UUID作为挂载资源信息单独记录，不参与用户映射匹配；显式启用映射时配置错误必须失败，不能回退成未映射挂载 |
| 请求身份 | 转换UID、主GID及参与检查的附加组；核对root分支、请求身份缓存和组缓存，不能只改两个请求头字段 |
| 文件属性返回 | 覆盖lookup/getattr/readdirplus等路径；在返回副本上转换，禁止就地污染内部共享属性缓存 |
| 文件属性修改 | 处理setattr/chown中的目标ID、创建owner和setgid继承，不能遗漏请求载荷中的ID |
| 权限与特殊接口 | 核对内核与JuiceFS用户态检查是否一致；审计ACL/xattr及控制接口，不支持的相关行为明确拒绝 |
| 日志与管理操作 | 保留本地和存储身份对应关系，配额等直连元数据的管理入口继续使用存储ID |

映射采用挂载进程内存查找，不在每次IO中调用LDAP、Portal或其他网络服务。未启用特性时保持上游行为，便于回归对照。

首期还必须明确以下规则：

1. **映射模式默认拒绝未登记的普通身份。** UID、主GID或所需组映射缺失时，不得退回数字原样透传；拒绝访问的用户操作应返回明确权限错误。附加组也不得沿用未转换数字，首期要求显式登记参与权限检查的组。任何放宽或忽略组的策略都需单独证明不会扩大权限。
2. **未在本机登记的文件owner不能直接当作本地owner返回。** 例如B上Charlie的本地UID为10001，不能把远端其他人的存储10001原样呈现并意外授权给Charlie。安全的显示方式和权限检查必须在原型中一起验证。
3. **业务挂载的UID 0行为单独定义并测试。** 不把root、服务内部请求或清理请求混作普通未登记用户，也不通过宽泛例外给普通请求放行；管理入口与业务使用方式分开说明。
4. **映射在挂载生命周期内固定。** 新增或调整映射需安排业务停止、写入排空和受控重挂载；已有文件不会因为修改配置自动更换owner。

相关代码依据：[JuiceFS v1.4.1身份上下文](https://github.com/juicedata/juicefs/blob/v1.4.1/pkg/fuse/context.go)、[FUSE操作入口](https://github.com/juicedata/juicefs/blob/v1.4.1/pkg/fuse/fuse.go)。这是设计基线，实际开发前还需核对交付二进制及现有性能补丁对应的源码版本。

### 3.3 客户端配置与实际加载

所有客户端运行同一版本的定制二进制，加载各自配置。以下只说明拟开发的数据结构，不是当前JuiceFS已支持的配置语法或参数：

```yaml
schema_version: 1
client_id: client-b-example
mapping_version: 8
unmapped_user: deny
users:
  10001: 60001   # B上的Charlie
  20001: 50001   # B上的Alice
groups:
  10001: 60001
  20001: 50001
```

UID/GID分表记录，不要求某个用户的主组数字必须等于其UID。客户端A的配置可以是10001映射到50001，与B的配置不同；不需要把所有其他客户端的映射一并加载到本机。

配置及部署清单保存在受保护目录，例如`/etc/juicefs-managed/`，由root或获准服务管理，普通用户不可修改。配置生成工具记录内容哈希及目标client_id；挂载启动时以受控启动配置中的预期值核对，避免把B的文件误用于A。文件只写了client_id却没有独立预期值作比较，不能发现错投；哈希用于一致性核对，也不能单独证明文件来自授权管理端。

卷UUID保存在独立的挂载/资源部署记录中，用于确认某个挂载进程实际连接了哪个JuiceFS卷，不写入身份映射关系。一个客户端挂载多个获准卷时，可以让各挂载进程加载同一份本机身份配置；如需限制某个卷只允许部分用户访问，应另设卷或目录授权策略，而不是改变这些用户的存储UID/GID。

首期由运维通过受控连接部署完整文件，避免半写配置；后续若增加在线分发，再引入证书认证、配置签名及防止未经批准的旧版本覆盖等能力。拟新增的`--id-map`或类似参数需在实现时确定，并明确标记为本项目扩展；不能将讨论中的示意命令当作现有命令执行。

挂载进程分别输出实际加载的client_id、映射版本、配置哈希和实际连接的卷UUID，作为验收证据，不仅核对磁盘文件。其中卷UUID说明挂载资源，不参与决定本地UID映射到哪个存储UID。更新磁盘文件不自动改变已运行进程；Portal或登记工具不可用时，本地有效配置仍可支撑已有授权，新增或变更暂缓，后端本身仍需可用。

### 3.4 开通、变更与撤销何时真正生效

配置发布分别记录以下状态。身份配置由`client_id＋映射版本`标识；实际加载状态还需关联具体挂载实例和卷，以确认每个运行进程是否已经采用该配置，但卷不是身份映射键：

| 状态 | 实际含义 | 对访问的影响 |
|---|---|---|
| 已登记 | 集中台账保存了拟修改关系 | 不改变现有挂载权限 |
| 已部署 | 新配置已经到达客户端磁盘 | 旧进程仍使用已加载版本，不等于新规则已生效 |
| 已加载 | 新挂载已校验并加载该版本 | 新规则开始影响可访问身份；此时就可能允许新增用户，不能声称要等Portal改状态才放行 |
| 已验证 | 正向、越权拒绝、owner及版本核验通过 | 记录验收完成，按部署安排恢复业务；状态字段本身不执行文件权限检查 |

首次开通或变更时，由运维在受控窗口停止受影响挂载上的业务任务并排空写入，部署配置、正常卸载旧挂载后重新挂载，在业务仍停用期间运行验证，通过后恢复业务。若要求验证前普通用户连手工访问都不能进行，还需由运维保持本地挂载入口受限，受控验证后再开放；不能用Portal状态代替这个实际限制。

撤销用户时，停止相关存储任务、移除该客户端上的用户映射，并通过相同流程重挂载及验证拒绝访问。**首期重挂载可能影响同一挂载上的其他用户，新增一个用户也可能需要这一维护窗口。** 全局停用要覆盖所有已授权客户端；某台未完成撤销时，只能记录为待完成，不能宣称全局生效。该用户原本地账号及其他业务不随之删除。

已打开文件、内核缓存和仍存活的旧挂载都必须纳入核验，不能简单把“所有访问都会进入newContext检查”当作假设。尤其lazy unmount可能保留仍被引用的旧FUSE连接，不能作为撤销完成的依据。原型需验证未登记用户通过缓存路径仍无法获取受保护内容，并明确内部释放/清理请求的处理，不能一律拒绝而导致写入排空或卸载失败。[Linux FUSE连接与权限说明](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html)

如果验证失败，保持业务停用并保留现场证据。需要恢复旧版本时，先判断旧版本是否重新授权了刚被撤销的用户；不能自动回退并报告撤销成功。已发布存储ID继续保留，不能靠回收编号解决失败。配置与后端凭据保护、未映射原始入口的封闭也属于验收条件。

## 五、最小验收集

优先验证权限与正确性，不复用此前长时间调优矩阵。P0先验证前四项，后续阶段补齐回归。

| 场景 | 必须验证的结果 |
|---|---|
| 同机两用户、跨机相同本地UID | 各自可读写私有文件，未经授权不能访问他人文件；不是只验证正常读写成功 |
| 同一人跨机使用不同本地UID | 显式登记后使用同一存储身份，创建及stat/readdir返回正确；只读管理视图核对实际存储owner |
| 共享模型 | 获准用户能读，不能写入、截断、删除或通过修改父目录替换模型 |
| 未登记和冲突身份 | 缺失、重复、错误版本等配置按规定失败；远端owner与本地UID碰撞不产生访问授权 |
| 集中分配与多机一致性 | 同一人跨机映射到相同存储UID被允许；不同人占用同一存储UID被拒绝；本地UID可跨机重复；共享组与用户身份区分检查 |
| 客户端生命周期及跨卷一致性 | 重启、断线重连、IP变化后继续原映射访问原文件；恢复配置不重新分配存储ID；另一机器的配置被拒绝；同一用户在两个获准卷中保持相同存储UID，卷访问权另行验证 |
| 配置发布及撤销 | 仅登记/写文件不误报生效；以进程加载版本为准；撤销后所有相关旧挂载、旧句柄按既定流程处理；未完成的客户端不能被标记为全局撤销完成 |
| 组权限及属性操作 | 主组、附加组、setgid继承、umask、chmod/chown没有错配；ACL等未支持能力不能被静默接受 |
| 文件与缓存路径 | 创建、rename、link、删除、属性缓存、目录缓存及已打开文件符合既定权限语义；不能相互污染属主视图 |
| 目录配额 | 用户写入计入正确目录；超限拒绝、删除后用量回收及管理查询符合JuiceFS既有行为，不承诺比上游更严格的即时一致性 |
| 变更、重启与回退 | 映射变更通过排空、停止任务和重挂载生效；不能声称撤销配置会立即收回已打开文件的访问；错误配置不能启动成宽权限挂载 |
| 管理不可用与账号复用 | 管理端不可用不影响后端正常时已有本地配置的使用；本地UID换人前必须撤销旧映射；恢复旧配置不能默默恢复已撤销授权 |
| 训练与性能 | 共享模型读取、检查点写入/重命名及小文件操作正常；相同数据与缓存条件下比较映射开/关，异常下降再做定向复测 |

性能验收阈值在P3执行前结合实测基线约定。本计划不承诺零开销，也不将某个未经确认的百分比设为交付门槛。已有功能测试和基准能复用的就复用，只增加映射相关用例；安全失败不能因“业务暂未使用”而忽略。

## 六、风险与维护成本

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 漏转换或错误映射 | 普通用户获得他人的读写权限，严重时删除他人数据 | 双向映射、拒绝隐式透传、独立审查与负向测试 |
| 写入错误owner/组 | 数据归属或UID/GID配额记账错误，修代码后仍需纠正历史元数据 | 从独立卷起步，核对原始存储ID；不直接处理现有业务数据 |
| 缓存与映射版本不一致 | 修改配置后仍出现旧身份或错误权限 | 挂载内静态版本，输出副本转换，重挂载验证 |
| 配置错投、独立分配或本地UID换人 | 不同人意外对应同一存储身份 | 集中唯一分配、核对目标客户端、记录实际挂载卷和加载证据，并约束开户流程；卷授权单独核验 |
| 静态映射变更需要重挂载 | 新增或停用用户可能中断同挂载其他用户的任务 | 将维护窗口列为首期部署条件；若业务不能接受，另行评估动态更新成本 |
| 增加每次IO的处理开销 | 小IO或元数据密集负载退化 | 内存查表、不新增网络查询、按实际IO模型定向对照 |
| 上游升级改变权限路径 | 补丁虽能编译，但语义已经不兼容 | 小补丁集、固定构建证据、每次升级跑核心权限回归 |
| 回退只换二进制 | 原版看到存储UID而非本地UID，业务权限可能失配 | 永久保留必要映射记录及受控管理入口，回退同时设计身份使用方式 |

维护预算暂按：相关接口不变的小版本升级每次1～3人日；FUSE、权限、ACL或缓存明显变化的升级每次5～10人日，复杂时更多。具体取决于补丁规模和回归自动化程度；冻结版本不等于免维护，还需处理安全修复和内核兼容。

本特性不承诺防范恶意客户端root。若以后需要服务端强制隔离客户端或区分配额管理权限，应作为新的架构需求评估，不能通过扩大客户端映射补丁暗中承接。
