# 第三阶段：客户现场快速部署方案

> 日期：2026-09-22。状态：方案草案，供开发和后续讨论；不代表客户部署参数或任何sudo操作已获批准。
> 开发安排见[开发计划书](CUSTOMER-DEPLOYMENT-DEVELOPMENT-PLAN-20260922.md)。第一、二阶段的功能定义继续由各自文档维护。

## 一、整体方案

**客户指定一台主服务节点，提供服务器、客户端、网络和磁盘信息；运维在该节点启动部署工具，完成环境检查和变更确认后，自动安装JuiceFS＋TiKV＋Ceph、Portal监控及已交付的用户与配额组件，最后验证客户端能够正常使用。**

采用“版本固定的部署包＋配置向导＋主节点执行器”，不新建通用运维平台。界面负责填写配置、展示计划和进度；具有主机管理权限的运维人员在主节点批准计划后，执行器批量完成已批准操作，无需逐条命令人工接力。运行期Portal不因此获得任意SSH或root操作能力。

部署结束后，安装工具可以退出；业务IO仍由客户端JuiceFS直接访问TiKV和Ceph，不经过Portal或部署执行器。

### 1.1 首版范围

| 纳入首版 | 暂不纳入 |
|---|---|
| 一套经过验证的Linux/CPU架构和固定组件版本组合 | 同时兼容所有发行版、跨版本自动升级 |
| 指定新存储节点和空闲磁盘，新建完整存储集群 | 接管、重建或迁移已有Ceph/TiKV集群 |
| 在指定主服务节点部署Portal、监控及第二阶段交付组件 | 管理面自动高可用、跨站点灾备 |
| 经SSH配置指定客户端的JuiceFS、LDAP/SSSD接入和挂载 | 自研客户端常驻助手、任意本地用户管理 |
| LDAP路线A：接入已有目录服务，或安装第二阶段验收过的目录服务模板 | 同时适配多种LDAP/AD产品、B/C用户映射 |
| 整体预检、计划审批、进度查看、失败定位和断点续跑 | 一键清盘重装、删除集群或自动回滚业务数据 |

新建LDAP的前提是第二阶段已确定目录产品、账号分配和恢复机制，并交付可验证模板；尚未具备时，首版只支持客户提供兼容LDAP，不能宣称可从零完成身份系统部署。Portal创建LDAP账号不是第三阶段附带开发的功能。

客户主服务节点允许与一个存储服务节点共用，不强制增加机器；是否适合共置由CPU、内存、持久化空间及故障恢复要求决定。首版不自动改造正在承载其他业务的主机；共用客户端只允许增加明确批准的组件和配置。

## 二、部署结构与职责

```text
运维浏览器 ── SSH隧道 ── 主服务节点上的安装向导（普通Linux账号）
                              │ 填写配置、查看脱敏结果
运维登录主节点 ── 核对并批准计划 ── 部署执行器（仅部署期间运行）
                              ├─ SSH/SFTP → 各存储节点
                              ├─ SSH/SFTP → 获准客户端
                              └─ 本机安装Portal、监控及管理组件

运行阶段：
浏览器 → Portal → 监控/统计查询、第二阶段用户与配额接口
客户端 → JuiceFS → PD/TiKV元数据 + Ceph RADOS文件内容
客户端 → LDAP/SSSD身份查询与登录认证
```

| 位置/主体 | 职责 |
|---|---|
| 客户运维人员 | 提供节点及设备清单、SSH授权和应急入口；确认磁盘用途、变更及业务窗口 |
| 主服务节点 | 保存部署包、配置、执行记录和受保护凭据；运行安装工具及交付后的Portal管理组件 |
| 存储节点 | 运行PD、TiKV、Ceph MON/MGR/OSD；角色由配置决定，不写死150～152 |
| 业务客户端 | 通过标准LDAP客户端获得业务身份，通过JuiceFS访问存储；不承载部署中心 |
| 安装向导 | 配置录入与结果展示；不读取私钥、不接收任意shell、不直接执行sudo |
| 部署执行器 | 按批准的固定步骤执行安装、核验和恢复；权限独立于`jfsweb`，结束后停止 |

主服务节点可以是Ceph bootstrap节点，也可以不同。部署工具使用的SSH凭据与cephadm运行期管理SSH凭据分开；后者属于Ceph组件管理，不是Portal用户或业务用户身份。主服务节点失效会使安装任务及其承载的管理服务不可用，但不是所有IO必经点；若它同时承载PD/OSD/LDAP，业务影响还取决于各组件冗余，不能只以“Portal不在IO路径”保证无影响。

### 2.1 安装入口与首次启动

1. 客户运维把已校验部署包放到主服务节点的持久化目录；通过已有SSH账号登录，不要求提前部署Portal。
2. 启动独立安装向导，默认只监听loopback，通过SSH隧道访问，使用本次安装的一次性访问凭据；不公开无认证安装页面。
3. 填写或导入inventory，运行只读预检，界面展示节点、磁盘和拟执行操作。
4. 运维在主节点的受控命令行确认计划；批准后同一执行器连续完成安装，浏览器关闭不终止任务。
5. 验收后交付正式Portal入口，关闭安装向导和部署执行进程、撤销临时部署授权。后续重新安装或恢复须显式开启，不长期保留root Web服务。

CLI先做成完整入口，再让向导复用相同配置模型和结果，不实现两套部署逻辑。首版允许Web录入草案，但不让普通Portal ADMIN会话单独批准磁盘格式化或主机认证变更。

## 三、客户提供什么，系统检查什么

节点IP不足以决定安全部署。配置统一保存在一个有版本的`inventory.yaml`中，界面和CLI使用同一校验规则；它是数据文件，禁止通过`source`当作shell执行。

| 配置项 | 内容及检查 |
|---|---|
| 集群与主节点 | 集群名称、环境标识、主服务节点、Portal访问域名/IP；避免与已有实例混用 |
| 节点 | 名称、角色、管理地址、SSH端口/账号、主机指纹、可选跳板；配置角色与实际主机一致 |
| 网络 | 管理网、Ceph public/cluster地址、PD/TiKV通告地址、客户端数据网；确认实际端点可达，不以“SSH通”代替数据网通 |
| 磁盘与目录 | 每节点逐盘by-id/序列号、容量、用途、目标挂载点；TiKV数据/日志、OSD data/DB/WAL、可选客户端缓存不得重叠 |
| 软件 | 已签收的release及包/镜像摘要、OS/架构、librados/FUSE依赖；不下载`latest`或现场重新编译 |
| 数据保护 | Ceph副本或EC模板、故障域、容量预留、TiKV副本与节点分布；检查拓扑能否满足模板 |
| LDAP | 服务地址、CA、查询账号引用、用户/组模型、业务UID/GID范围、登录范围；新建模式另需第二阶段模板版本 |
| JuiceFS | 卷名、独立元数据命名空间、对象Pool、format参数、挂载点、安全和性能配置档 |
| root处理 | 全客户端统一的非零root-squash UID/GID，完成LDAP及本地冲突检查；管理挂载另列 |
| 权限与运维 | 运维来源地址、证书/私钥引用、备份位置、日志保留、容量预算、自启策略及停机窗口 |

磁盘信息由只读发现辅助填写，必须由人确认用途，不能自动选择“看起来空闲”的第一块盘。现有UID/GID、系统服务和业务路径只核对，不自动修改以适配部署。

凭据不放入inventory明文、Git、日志或下载报告；配置只保存凭据引用。SSH主机指纹由运维经可信渠道确认，`ssh-keyscan`输出本身不等于已建立信任；不使用关闭主机密钥检查的方式消除连接报错。

### 3.1 预检必须提前发现的问题

- OS/内核与组件依赖不兼容、离线包缺失、端口或目标目录冲突。
- 主机时间/DNS异常、证书SAN不匹配、Ceph通告地址不能从客户端访问。
- 系统盘、在用挂载、LVM/RAID成员、已有文件系统签名或设备身份变化。
- CPU/内存/磁盘预算冲突；尤其同节点Ceph、TiKV、LDAP和Prometheus不能各自按整机容量取默认值。
- LDAP身份范围冲突、普通用户可读后端凭据、拟调整PAM/SSSD但没有应急登录路径。
- 已有Ceph FSID、PD cluster ID、JuiceFS卷或不属于本RUN的目录；不能当作上次失败残留直接删除。

结果分为阻断项、需人工确认项和提示项。阻断项未解决不允许生成可执行计划；“检查通过”不自动授权写入。

## 四、客户交付配置原则

### 4.1 持久化和数据保护

**客户部署不能照搬性能实验环境。** 当前实验脚本有tmpfs DB/WAL、固定盘名和清盘流程；客户数据、TiKV WAL/Raft、Ceph DB/WAL、LDAP、管理库和writeback staging均使用持久化存储。

- 初始候选模板为至少3个存储服务节点，3个PD及3副本TiKV跨主机放置；Ceph采用跨主机的数据保护策略。最终OS、版本与拓扑在开发D0冻结。
- 三节点首版建议使用Ceph三副本作为持久化验证模板，容量和性能另行验证，不将旧EC结果直接当作其性能承诺；该选择在D0由用户确认后实施。
- 如需要EC，按客户节点数、故障域及恢复能力选择并单独验收。普通host级4+2布局需要足够的独立host故障域，不能把三节点实验中的`failure-domain=osd`直接描述为能容忍两台主机故障。[Ceph EC说明](https://docs.ceph.com/en/reef/rados/operations/erasure-code/)
- 没有独立DB/WAL盘时，允许经验证的同盘持久化配置；不得用内存盘冒充生产隔离盘。不同用途的分区/LV必须在计划中明确容量和设备归属。
- 首版不自动修复带签名的盘、不提供清盘按钮；旧盘需要客户另行完成数据处置后重新预检。对明确批准的空白盘初始化，也必须绑定精确设备身份。

“未挂载、未发现签名”不证明盘上没有数据。只有客户明确确认可初始化的指定设备才能进入计划；检查覆盖整盘、分区、holders、LVM/RAID成员及设备别名，并在写入前再次核对身份与占用状态，防止同一设备被不同路径重复分配。

Ceph使用明确的主机及设备清单，禁止`--all-available-devices`及通配整机选盘；新盘替换不自动认领。必须控制cephadm持久化OSD规格的后续作用，避免安装结束后又自动消费后来出现的磁盘。[Ceph OSD部署及声明式状态](https://docs.ceph.com/en/reef/cephadm/services/osd/#declarative-state)

### 4.2 后端认证与服务账号

- 新建PD/TiKV从首次启动即配置双向TLS，服务端和获准客户端使用各自证书/私钥，覆盖PD及所有TiKV端点；先用实际交付JuiceFS和配额适配器验证，不在失败时降级成明文。[TiKV安全配置](https://tikv.org/docs/7.1/deploy/configure/security/)
- 新建集群可采用受控签发流程或客户CA。CA私钥不分发给业务客户端；证书包含实际连接地址，记录到期时间和更新流程。TLS不被描述为TiKV具备目录或配额级RBAC。
- 部署器为每台获准的业务客户端分别配置可识别、可单独轮换的TiKV客户端证书和私钥，并把CA证书、客户端证书和私钥安装到该客户端；仅在批准的客户端清单内分发，不把CA私钥或其他客户端的私钥一起复制过去。挂载配置引用这些文件，由受控的JuiceFS挂载服务使用。
- 客户端私钥及其目录只允许root或指定挂载服务账号读取；普通业务用户只访问挂载点。分发后核对文件属主/权限、证书有效期和实际PD/TiKV握手，并验证没有客户端私钥的进程无法连接。部署计划和日志不包含私钥正文；客户端退出使用时需撤销其接入并处理证书轮换。
- Ceph业务客户端使用目标Pool所需的受限CephX身份，不分发`client.admin`；现有脚本中的管理keyring分发逻辑不能继承。
- 正式Web由`jfsweb`运行，统计组件由`jfsstats`承担，配额服务由`jfsquota`承担，沿用第二阶段验收后的权限关系。Web不持SSH私钥或存储后端凭据；配额服务不需要Ceph keyring。
- 普通业务用户不能直接访问PD/TiKV或读取后端私钥；获准客户端root仍可信。root-squash只减少正常挂载上的误操作，不防御恶意root重挂载。
- 组件端口按实际方向生成白名单；防火墙变更列入计划并保留管理通道，不清空既有规则，不自动重启网卡或修改共享网络参数。

### 4.3 LDAP、挂载和配额

- 复用[路线A](../02-user-quota/features/juicefs-user-quota-management/JUICEFS-LDAP-USER-MANAGEMENT-IMPLEMENTATION-NOTES-20260922.md)确定的LDAP/SSSD模板；不重复`useradd`创建LDAP业务账号，不做客户端UID迁移。
- 客户端SSSD/NSS/PAM改动逐节点执行，备份精确文件，保留已登录运维会话；验证本地应急登录和LDAP新登录后再继续其他节点。
- 所有业务挂载启用冻结的root-squash数字ID。独立管理挂载不启用squash、只允许可信运维使用；统计挂载仍是独立用途，不兼作目录交付入口。
- 卷只在其命名空间和对象空间确认为新建目标时format一次，记录卷UUID。重跑以UUID及配置核验为准，不重复format、不强制覆盖已有卷。
- 性能参数从签收基线生成版本化配置档，区分format参数和mount参数，不复制仍在试验的候选值。新客户硬件上的性能须单独评估，安装成功不等于达到历史最优带宽。
- 读缓存/writeback仅在客户选择并具备获准持久化缓存空间时开启，展示容量、水位、数据排空及故障风险；不自动占用客户端系统盘。
- 回收站期限显式设置，不复制实验中的`trash-days=0`；不固化测试用`noscrub/nodeep-scrub`或未经客户确认的内核调优。
- 安装[第二阶段配额组件](../02-user-quota/features/juicefs-user-quota-management/JUICEFS-QUOTA-MANAGEMENT-DEVELOPMENT-PLAN-20260922.md)及其数据库迁移，不在安装器里另写配额规则、账户分配或管理API。业务账号开通和目录交付沿用第二阶段流程。

### 4.4 主节点资源和可恢复性

主节点预留独立的管理数据目录，明确Prometheus容量/保留期、Portal统计库、LDAP和部署包预算。Ceph与TiKV共置时显式限制各自资源，不能沿用Ceph按整机内存自动估算的默认值。[Ceph共置部署资源提示](https://docs.ceph.com/en/reef/cephadm/install/#enabling-osd-memory-autotuning)

客户交付应明确服务自启、网络和数据盘挂载依赖，验证重启后恢复。新的客户模板可建议开启所需服务自启，但须纳入批准计划；不改变现有150～157环境“新增Portal unit不自启”的约定。

首版主节点不做自动故障切换。其配置、部署记录、LDAP及管理库按各自一致性方法备份到另一持久化位置，并演练恢复；这些备份不替代Ceph业务数据和TiKV元数据备份。

## 五、部署流程

| 步骤 | 实际工作 | 通过条件 |
|---|---|---|
| 1. 导入并检查 | 校验部署包、inventory、SSH主机指纹和只读现场；列出阻断项 | 节点、依赖、设备、网络及容量符合选定模板 |
| 2. 生成并批准计划 | 展示逐节点操作、磁盘身份、配置差异、服务影响及完整提权命令；运维批准固定版本 | 保存计划摘要、审批人、节点/设备清单及允许执行范围 |
| 3. 准备目标主机 | 分发已校验安装包，创建专用目录/服务账号，准备批准的持久化盘和系统依赖 | 只有批准目标发生变化；各节点SSH和原有服务正常 |
| 4. 建立身份及存储服务 | 接入/部署选定LDAP；部署PD/TiKV；通过cephadm建立Ceph、指定OSD、Pool和受限身份 | 认证、PD/TiKV节点状态、Ceph健康和实际设备位置核验通过 |
| 5. 建卷和接入客户端 | format新卷；先接入一个客户端，验证LDAP、挂载及权限，再批量接入其余节点 | 卷UUID一致、业务/管理挂载用途正确、真实用户可读写且相互隔离 |
| 6. 安装Portal管理功能 | 安装监控、采集、Web和第二阶段配额组件，生成实际targets、证书和来源白名单 | 真实数据可见、角色权限正确、配额接口与后端安全条件通过 |
| 7. 验收和交付 | 小数据功能测试、恢复检查、备份与使用说明；关闭安装入口、清理临时授权 | 形成一份结果摘要，全部必要能力可用且不依赖安装器常驻 |

LDAP、TiKV和Ceph是不同依赖，内部可按固定依赖关系调度；首版先串行写操作，校验和无副作用的发现可有限并行。磁盘初始化、认证配置和服务切换必须逐节点验证。无需为每个子步骤另写一份报告。

## 六、执行权限、失败与续跑

### 6.1 一次批准一批操作，不是无限授权

审批绑定inventory、组件包、模块版本、配置及操作清单的摘要。批准对象包含节点指纹、设备身份、路径和变更参数；输入或现场发生关键变化后原审批失效。

执行器只使用经批准、不可被普通Web进程修改的模块和配置副本。远端上传固定文件后执行；不通过嵌套SSH拼接未校验变量，不开放任意命令接口或`sudo bash *`式长期授权。SSH授权可由客户预先准备；需新增或扩大sudo权限时，列入精确审批，不自动配置全局NOPASSWD。

cephadm需要持续的节点管理权限，与部署器临时授权分别列明用途和保存位置，不能在收尾时误删其运行期密钥。官方bootstrap涉及集群管理凭据生成和分发，安装器必须约束其分发范围。[Ceph bootstrap流程](https://docs.ceph.com/en/reef/cephadm/install/#running-the-bootstrap-command)

D0必须确定cephadm使用受控root SSH密钥，还是专用SSH账号及其所需免密sudo；两者都属于持续的主机管理权限，不因使用普通账号就变成低权限。由客户单独批准账号、节点和密钥范围，不接受该权限模型时停止此部署模板，不自动扩大sudo规则。[cephadm SSH账号要求](https://docs.ceph.com/en/reef/cephadm/install/#further-information-about-cephadm-bootstrap)

本仓库后续实施继续遵守[系统安全红线](../../../skills/SYSTEM-SAFETY-SKILL.md)。本文不是当前集群执行授权。

### 6.2 最小执行记录

每次部署有唯一RUN ID，在主节点持久化目录中保存：

| 文件 | 用途 |
|---|---|
| `inventory.yaml`、`plan.json` | 输入及批准计划，不含私钥或密码 |
| `run.json`、`steps.jsonl` | 各步骤状态、节点、开始/结束时间、实际组件ID及错误 |
| `artifacts/` | 配置模板及包摘要；敏感配置只留受保护位置，不进入展示包 |
| `logs/`、`acceptance.md` | 有限保留的脱敏日志和一份验收结论 |

这些是安装执行记录，不新增业务用户数据库，不替代LDAP、配额存储管理库或TiKV。Web只能读取脱敏视图。记录设保留数量和空间上限；失败现场未查明前不自动删除，日志轮转不删除恢复所需状态。

### 6.3 遇到失败怎么办

- 状态至少区分待执行、执行中、成功、失败、结果待确认；非零退出码、健康不达标不能包装为成功。
- 执行超时或SSH断连不代表远端操作没执行。按PID/执行锁及真实对象回读，先确定是否仍运行、是否已经成功，再决定继续；不同节点也要防止第二个RUN同时改同一目标。
- 已完成步骤重跑只核验，不重新format、创建第二个集群或重发覆盖凭据。暂停在安全步骤边界，不强杀正在初始化设备或提交集群变更的操作。
- 写操作前先持久化操作意图及目标。首次安装拒绝的已有对象，仅在resume核对RUN、设备、真实FSID/PD cluster ID/卷UUID及配置能证明属于本次创建时，才接受为本RUN产物；未记录成功不等于没执行，无法确认归属就保留“结果待确认”，不按“存在即跳过”或“清理后重试”处理。
- 配置和Portal静态文件可从本RUN备份精确恢复；已经初始化的存储、已写入的数据和LDAP账号不做自动删除回滚。不能承诺跨多个组件的整体原子回滚。
- 首版只支持保留原计划的恢复；更换主节点、变更设备或改变拓扑时重新核验并批准，不能仅凭步骤文件认定现场正确。

## 七、页面与程序拆分

安装向导保留五个页面即可：**部署输入、环境检查、计划确认、执行进度、验收与交付**。显示真正的阶段结果、失败原因和下一步，不做通用主机命令终端。

| 拟新增模块 | 职责 |
|---|---|
| `deploy/installer/` | inventory schema、版本清单、组件模板及受控节点操作模块 |
| `api/cmd/deployctl/` | 主节点CLI：validate、inspect、plan、apply、status、resume、verify；审批和实际执行由可信运维入口发起 |
| `api/internal/deployment/` | 输入校验、计划生成、状态持久化、有限SSH执行和结果归一化 |
| `web/setup/` | 复用现有前端风格的安装向导；与运行期Portal入口和权限分开 |
| 现有`api/`、`web/`、`deploy/` | 继续提供Portal、监控和第二阶段功能；不按客户复制一套源码 |

组件操作按“发现/校验、生成配置、应用、回读”组织；复用已有安全的模板和检查，不复用整段历史迁移脚本。包安装、磁盘初始化、服务配置分开，方便错误定位；不再按每次失败新建一套脚本。

首版只部署一套监控：Ceph bootstrap不自动安装其附带的Prometheus/Grafana监控栈，使用本项目监控模板并显式接入Ceph指标，避免重复组件、端口和资源占用。离线模式下的本地镜像仓库、CA和拉取权限是Ceph运行期依赖，部署结束后仍须可用；镜像清单覆盖所选Ceph服务实际需要的全部镜像，不能只打包OSD镜像。镜像源恢复纳入主节点恢复说明。[Ceph监控部署](https://docs.ceph.com/en/reef/cephadm/services/monitoring/)、[离线部署要求](https://docs.ceph.com/en/reef/cephadm/install/#deployment-in-an-isolated-environment)

## 九、验收与交付标准

采用小数据、真实路径的功能验证，不复跑性能调优全矩阵。破坏性故障只在隔离环境验证。

计划使用另行提供的三台空白服务节点和两台空白客户端开展本阶段验收；具体主机、磁盘及网络在D0核对后确定，不预先占用现有集群。

1. 在固定支持环境中，新存储节点＋两个客户端可完成部署；断网现场的包、镜像、系统依赖全部由已校验部署包或批准的本地仓库提供。
2. 误选系统盘/在用盘、配置或主机指纹变化、包被篡改、未批准命令均被拒绝；其他业务服务及路径不变。
3. PD/TiKV、Ceph、JuiceFS和Portal使用实际配置；两个客户端看到同一卷。存储数据及元数据重启后仍存在。
4. 两个LDAP用户在两客户端身份一致、私有目录相互隔离、共享模型目录只读；root-squash、独立管理入口和普通用户防后端绕过通过。
5. Portal ADMIN可按第二阶段流程登记目录、设置容量/inode配额；两客户端超限受约束；新增管理接口不对USER或旧自动化凭据开放，第一阶段已有USER只读监控保持正常。个人额度页及个人目录查看授权不作为本阶段验收项。
6. 重复运行、SSH断连和执行器重启均能核对并继续，无重复建卷、覆盖已有数据或虚假成功；Portal停机不改变已有配额和数据面。
7. 隔离环境完成节点逐台重启、主节点安装记录恢复和管理组件备份恢复；记录LDAP单点/缓存等限制，不把单主节点方案写成自动高可用。
8. 交付组件版本/摘要、实际拓扑和端点、卷UUID、磁盘对应、使用方法、备份恢复与证书更新步骤。密码和私钥通过独立安全渠道交付，不进验收报告。

本地开发/试验结果仍按项目要求保存至`/mnt/c/SunRise/test/`；客户现场对应使用其批准的持久化结果目录，不要求存在WSL路径，也不把唯一证据放在`/tmp`。

## 十、开发前需要确认的少量选择

| 选择 | 本方案建议 |
|---|---|
| 首个支持环境 | 先选一套Linux＋x86_64＋systemd环境及固定组件版本，D0核对兼容性和维护状态后冻结 |
| 客户数据保护模板 | 三节点先验证持久化三副本；EC作为有明确拓扑及容量需求时的独立模板，不继承实验故障域 |
| LDAP来源 | 优先复用第二阶段验收结果；已有LDAP可直接接入，无LDAP时必须先具备标准新建模板 |
| 提权批准方式 | 首版主节点运维CLI批准完整计划，向导展示与跟踪；暂不做全网页root授权系统 |
| 自启与恢复要求 | 新客户明确批准服务自启并验证重启恢复；现有测试环境约定不变 |

上述选择不妨碍先完成配置模型和离线预检，但未冻结前不铺开全部安装脚本和页面。
