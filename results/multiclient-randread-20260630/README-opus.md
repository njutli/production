# 多客户端聚合随机读分析（opus 复核）

> 日期：2026-06-30
> 数据来源：本目录 `multiclient-randread-20260630/`（deepseek 采集，opus 对账分析）
> 环境：JuiceFS v1.3.1 / Ceph 17.2.8 EC 4+2 / 1Gbps / `--cache-size 0` / block-size=256K / fio nj=128,bs=256k,direct=1,runtime=60s
> 客户端：tikv-node(.12) / ceph-node1(.11) / ceph-node2(.13)，各自独立挂载跑随机读

## 一、结果

| 阶段 | tikv (.12) | node1 (.11) | node2 (.13) | 聚合 | vs P1 |
|------|-----------|-------------|-------------|------|-------|
| P1 (1 客户端) | 33.8 | — | — | **33.8** | 1.00× |

**聚合天花板 ~51 MiB/s。P2→P3 几乎不涨（50.7→51.3）→ 已饱和。**

## 二、可靠性评估

### 可信 ✓
- **确实是同时并发**（非串行冒充）：P2 两个 fio 完成时刻 19:29:19-20、runtime 均 ~62s → 时间窗完全重叠；P3 三个同理（node2 时钟差 8h 是时区未对齐，runtime 62.9s 正常，不影响并发判定）。
- **数据自洽**：聚合 = 各客户端之和，算术对得上（26.3+24.4=50.7；18.1+18.0+15.2=51.3）。
- **P1 = 33.8** 与冷态基线（final baseline 33.8）完全一致 → 旁证冷态成立。
- 8 分钟测完合理：3 组 × ~62s + 间隔 ≈ 4-5 分钟起停（复用现有 layout，无 128G 重建）。

### 过程留档缺口 ⚠️（标注，不推翻结论）
1. 目录内**无测试脚本、无 drop 日志、无各客户端 mount.log** → 无法证明 node1/node2 是 cache=0、是否每轮 drop。（P1=33.8 旁证冷态，但未直接留证。）
2. node2 系统时钟比主节点慢 8h（时区未对齐）——非数据错误，但提示 node2 环境配置可能与主节点不完全一致，后续多客户端测试建议先对齐时区/确认挂载参数一致。

**判定**：结论（聚合天花板 ~51、加客户端不涨）数据成立且自洽；过程留档需补（下次多客户端测试要有统一脚本 + 各客户端 mount.log + drop 日志）。

## 三、机制：客户端读放大导致聚合天花板

把本结果与已确认的"客户端读放大 3.48×"（见 `seqrand-osd-compare-final-20260629/README-opus.md` §四·补）串起来：

- 每加一个客户端，单客户端带宽被**平分**：33.8 → (26.3+24.4) → (18.1+18.0+15.2)。3 客户端时每个仅 ~17。
- 每个客户端因 3.48× 读放大，要 1 份有效数据就得从后端拉 3.48 份。
- **后端（6 OSD + 网络）总吞吐能力有限**，被 3.48× 放大稀释后，能支撑的**有效**聚合带宽有天花板。
- P3 聚合 51 就是撞到这个天花板：后端总吞吐 ÷ 3.48 放大 ≈ 51 MB/s 有效，再加客户端只是把 51 分得更细。

**结论**：多客户端**救不了**随机读——只要 3.48× 读放大在，后端有效吞吐天花板锁死在 ~51，加客户端只是平分，聚合不涨。

> 这与"客户端读放大"假设完全一致，是一个独立维度的印证：若放大在客户端、且各客户端共享后端，则聚合必然撞天花板（本结果证实）。

---

## 四、战略含义

- 多客户端聚合天花板 51 < 目标 59（差 14%），且不可通过加客户端突破。
- **唯一出路是消除/降低读放大**（3.48×）。这把 readahead sweep 抬成关键路径：
  - 若 `--max-readahead=0` 能把后端放大从 3.48× 降下来 → 不光单客户端随机读上升，**多客户端聚合天花板也会跟着抬高**（后端有效吞吐 = 总能力 / 放大）。
- **待验证闭环**：readahead sweep 确认 ra 能降放大后，应**回来复测多客户端聚合**，验证"降放大 → 抬聚合天花板"。已写入 readahead-sweep 任务。
