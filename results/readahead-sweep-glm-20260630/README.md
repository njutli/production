# max-readahead sweep + 后端放大测量

> 日期：2026-07-01
> 测试者：GLM
> 任务书：`/tmp/opencode/glm-task-readahead-sweep.md`
> 环境：JuiceFS v1.3.1 / TiKV / Ceph 17.2.8 EC 4+2 (6 OSD) / 1Gbps / mount `--cache-size 0`
> 工作集：128G（128 jobs × 1G），block-size=256K，layout 复用
> fio 口径：nj=128 / bs=256k / direct=1 / iodepth=128 / runtime=60s

## 一、配置说明

### max-readahead 值

| 标记 | 挂载参数 | 实际值 | 来源 |
|------|---------|--------|------|
| ra=0 | `--max-readahead 0` | 0 (禁用) | `mount.go:410-411` |
| ra=4 | `--max-readahead 4` | 4 MiB | 同上 |
| default | 不传 `--max-readahead` | **2 MiB** (= 8 × BlockSize 256K) | `mount.go:412-413` |

> 源码 `pkg/vfs/reader.go:714`: `readAheadMax := min(conf.Chunk.Readahead, readAheadTotal)`。
> ra=0 时 readAheadMax=0，`checkReadahead` 条件 `blockSize <= readAheadMax` 永不成立，预读完全关闭。

### OSD 映射

| OSD | 节点 |
|-----|------|
| 0, 1 | node1 (192.168.11.11) |
| 2, 3 | node2 (192.168.11.13) |
| 4, 5 | node3 (192.168.11.14) |

### 采集方法

- **BW**: fio 输出 `READ: bw=...MiB/s` / `WRITE: bw=...MiB/s`（无 strace，干净带宽）
- **NIC RX**: fio 前后读 `/proc/net/dev` eno1 rx_bytes，算增量
- **OSD op_r_out_bytes / op_r**: `sudo cephadm shell -- ceph daemon osd.X perf dump osd`，before 在 fio 起来前、after 在 fio 运行至 50s 时（fio 仍在运行）
- **drop_all**: 每个 fio 前，客户端 + 3 OSD 逐台 `sync && echo 3 > /proc/sys/vm/drop_caches`，每台回显 OK 失败即中止
- **mount.log**: 每个 ra 值重挂载，均确认 `cache-size is 0, writeback and prefetch will be disabled`

## 二、主表 1：后端放大 vs readahead（randread）

> 后端放大 = Σ(6 OSD op_r_out_bytes 增量) / fio io(MiB × 1048576)
> NIC 放大 = NIC RX 增量 / fio io(MiB × 1048576)
> 每个数为 3 轮均值；三轮原始值见 §五

| max-readahead | randread BW (MiB/s) | fio io (MiB) | NIC RX (MiB) | Σop_r_out_bytes (MiB) | **后端放大** | NIC 放大 | IO depth>=64 | OSD op_r 延迟 (ms) |
|---------------|---------------------|--------------|--------------|----------------------|-------------|---------|--------------|-------------------|
| **0** | **51.8** | 3139 | 7313 | **6807** | **2.17×** | 2.33× | 35.6% | 11.4 |
| 4 | 34.2 | 2086 | 7501 | 6902 | 3.31× | 3.60× | 8.8% | 15.0 |
| default(2MiB) | 34.3 | 2091 | 7486 | 6886 | 3.29× | 3.58× | 8.7% | 16.5 |

**关键发现**：
1. **ra=0 将后端放大从 3.30× 降到 2.17×**——readahead 贡献了约 1/3 的放大（3.30→2.17），但不是全部。
2. **残余 2.17× 放大不是 readahead**——ra=0 已完全关闭预读，仍有 2.17× 后端放大。**残余放大的原因不明**：deepseek 的副本池对照实验（任务书 §1.2）已在 default ra 下排除 EC 作为主因（3 副本池随机读照样 3.2× 放大），但本次未做 ra=0 + 副本池对照，无法判断残余 2.17× 是否含 EC 成分。当前指向：放大发生在客户端多读（JuiceFS 客户端逻辑），具体机制未定位。
3. **OSD 吐出量几乎不随 ra 变化**（~6800-6900 MiB）——readahead 不增加 OSD 总吐出量，只是让 fio 的有效利用率从 30% 升到 46%。
4. **ra=4 与 default 完全一致**——4MiB 和 2MiB 的预读窗口在随机读场景下行为相同，证实之前 sweep 的"中间值无差别"结论。
5. **ra=0 下 OSD 延迟更低**（11.4ms vs 15-16ms）——更少的 op 排队，但延迟降幅不足以让带宽翻倍。

## 三、主表 2：三类负载 BW vs readahead（验收视角）

| max-readahead | randread (MiB/s) | randwrite (MiB/s) | randrw R (MiB/s) | randrw W (MiB/s) | **randrw 总计** |
|---------------|-----------------|-------------------|------------------|------------------|----------------|
| **0** | **51.8** | **54.3** | 25.1 | 24.7 | 49.8 |
| 4 | 34.2 | 49.0 | 25.0 | 24.6 | 49.7 |
| default(2MiB) | 34.3 | 49.9 | 25.5 | 25.2 | **50.7** |

**关键发现**：
1. **没有一个 ra 值让 randrw 达标 59**——三档总计都在 49.7-50.7，距 59 差 ~8-9 MiB/s。
2. **ra=0 对纯随机读有大幅提升**（51.8 vs 34.3，+51%），但对 randrw 无提升（49.8 vs 50.7，反而略低）。
3. **ra=0 randrw 方差极大**（r1=15.1/14.8 vs r2=28.3/28.0 vs r3=31.8/31.4），r1 异常低。
4. **ra=4/default randrw 更稳定**（21.8-27.5），且 default 总计最高（50.7）。

## 七、判读要点回答

> 采集阶段只报数据，以下为基于数据的客观判读。

1. **后端放大是否随 ra 减小而降、趋近 1×？**
   是。ra=0 → 2.17×，ra=4/default → 3.30×。但 **未趋近 1×**，停在 2.17×。

2. **ra=0 下后端放大降到多少？若没到接近 1×（如停在 2×）→ 还有非 readahead 的第二个放大源。**
   停在 **2.17×**。残余放大来源**不明**：deepseek 的副本池对照（任务书 §1.2）已在 default ra 下排除 EC 作为主因（3 副本池照样 3.2× 放大），且 OSD 侧对随机/顺序读行为相同（每 op 吐 ~127 KiB，请求长度 256K）。本次未做 ra=0 + 副本池对照，无法判断残余 2.17× 中是否含 EC 成分。当前已知指向：放大在客户端多读（JuiceFS 客户端逻辑），但具体机制（chunk 粒度、并发模型、对象映射等）未定位，需后续实验。

3. **randrw（验收口径）：ra=0 时 randrw 达标吗？**
   **不达标。** ra=0 randrw 均值总计 49.8 MiB/s < 59。且方差大（r1=29.9, r2=56.3, r3=63.2）。ra=0 对 randrw 无改善（与 default 50.7 相当）。

4. **有没有一个 ra 值让 randrw 尽量高？**
   **default (2MiB)** 总计最高 (50.7)，且方差最小（42.7-54.7）。ra=0 虽有 r3=63.2 的峰值，但 r1 仅 29.9，不可靠。

5. **若某 ra 降了放大，多客户端聚合能否破 51、接近 59？**
   ra=0 明显降了后端放大（3.30→2.17）。**步骤 B 已验证：3 客户端聚合 ~76 MiB/s，远超 51 天花板，超过 59 目标。** 详见 §八。

## 八、步骤 B：多客户端聚合 @ ra=0

> 条件满足：步骤 A 确认 ra=0 将后端放大从 3.30× 降到 2.17×（§二），执行步骤 B。
> 3 客户端：tikv(.12) / node1(.11) / node2(.13)，各自 `--cache-size 0 --max-readahead 0` 挂载。
> 测试前修复 node2 时区（UTC→Asia/Shanghai），三客户端时区一致。
> 每轮 drop 客户端 + 3 OSD（逐台验证 OK），三客户端同时跑 randread 60s。

### 主表 3：多客户端聚合

| 轮次 | tikv (MiB/s) | node1 (MiB/s) | node2 (MiB/s) | **聚合 (MiB/s)** |
|------|-------------|--------------|--------------|-----------------|
| 1 | 26.2 | 29.8 | 19.2 | **75.2** |
| 2 | 23.9 | 28.5 | 24.0 | **76.4** |
| 3 | 27.3 | 26.6 | 23.0 | **76.9** |
| 均值 | 25.8 | 28.3 | 22.1 | **76.2** |

> 对比 deepseek default ra 多客户端：P1=33.8 / P2=50.7 / P3=51.3（天花板 ~51）
> ra=0 多客户端：P1=75.2 / P2=76.4 / P3=76.9（天花板 ~76）
> **聚合从 51 提升到 76（+49%），超过 59 目标。**
> 数据来源：`stepB-multiclient/p{1,2,3}-{tikv,node1,node2}.txt` 的 `READ: bw=` 行。

### 机制解释

| 指标 | default ra (deepseek) | ra=0 (本次) |
|------|----------------------|------------|
| 单客户端 randread | 33.8 MiB/s | 51.8 MiB/s |
| 后端放大 | 3.48× | 2.17× |
| 3 客户端聚合 | 51.3 MiB/s | 76.2 MiB/s |
| 聚合 / 单客户端 | 1.52× | 1.47× |

- 聚合 / 单客户端 ≈ 1.5×，说明 3 客户端没有线性扩展（后端带宽是共享瓶颈）。
- default ra 后端负载 = 51.3 × 3.48 = 178.5 MiB/s；ra=0 后端负载 = 76.2 × 2.17 = 165.3 MiB/s。
- 两者后端负载接近（~165-180 MiB/s），说明 **后端总能力（网络 + OSD 磁盘）是物理瓶颈**，降低放大让更多后端带宽转化为有效数据。
- 若后端能力 ~170 MiB/s、ra=0 放大 2.17×，则理论聚合天花板 ≈ 170/2.17 = 78 MiB/s，与实测 76 吻合。

### 注意

- 步骤 B 只测了 randread（任务书要求）。randrw 的验收达标问题仍未解决——ra=0 对 randrw 无提升（§三）。
- 多客户端 randrw 是否能达标，需要额外测试（不在本任务范围内）。
