## 一、可靠性评估

### 采集过程可信 ✓
- 冷态 mount.log 确认 `cache-size is 0`；暖态无此行（= cache=100G），与标称一致。
- patched 二进制、EC 4+2、结构完整（commands.sh / mount.log / summary / 三轮原始齐全）。
- 暖态数值这次合理（不再有上一批 seqread=5.9 那种荒谬失效值）。
- randrw 全口径原始数据齐全，可逐项核对。

### 但汇总表的取值方法有系统性错误 ❌（表里数字大部分不能直接用）
原 `results-table.md` 表头写"**随机取3轮最大值**"。这是错的：

1. **冷态**：cache=0 客户端无缓存，但 OSD 侧 page cache 随轮次预热。冷态**应认 r1**（唯一真冷）。取 MAX 会挑到被 OSD 缓存污染的轮次。例：T1 randread 三轮 37.2/45.4/35.1，表填 45.4，**应为 r1=37.2**。
2. **暖态**：三轮是**单调递增的自我预热曲线**（说明没有独立预热阶段，靠这 3 轮自己填 cache）：
   - warm randread：36.9 → 72.4 → **101**
   - warm ra0：70.1 → 118 → **156**
   取 MAX = 取"cache 填得最满的最后一轮"。
3. **违反缓存红线**：warm ra0 的 r2=118、r3=156 **均 >124 MiB/s，是缓存命中虚高**（千兆物理上限 ~118，>124 必是命中缓存，不能作后端能力/达标依据）。原表"randread ra=0 达标(暖态156)"的结论**不成立**。

**结论**：采集数据可靠、无需重测；但**汇总表须按正确口径重算**（冷态用 r1、暖态高值标缓存命中、不以 MAX 判达标）。下节给出干净版本。

## 三、关键结论（每条有数据依据）

### 结论1：patch 确实提升了纯随机读（冷态，客户端读放大被修）
- 冷态 cache=0：patched randread r1 = **37.2**（原版 33.6，+11%）。
- 冷态 cache=0 + ra=0：patched randread r1 = **53.4**（原版无此项；对比 patch 前 ra=0 的 49.6，略升）。
- 数据来源：`full-bs256k-cold-cache0*/randread-r1.txt`。
- 与专项 patch-verify（单跑 98.3）的差异：那次是独立单测、OSD 预热态更有利；本轮全量矩阵里冷态更严格，故 37-53。**patch 有效这个定性结论一致，绝对值以本轮全量冷态 r1 为准（37-53）。**

### 结论2：⚠️ randrw（验收口径）全口径惨败，patch/ra/mu 都救不动
r1 冷态口径，所有配置的 randrw：

| 配置 | randrw R/W | 距目标 59 |
|------|-----------|-----------|
| 冷态 cache=0 | 14.3 / 14.0 | 差 4× |
| 冷态 cache=0 ra=0 | 10.2 / 10.1 | **更差** |
| 暖态 cache=100G | 13.9 / 13.6 | 差 4× |
| 暖态 ra=0 | 18.0 / 17.6 | 差 3× |
| 暖态 mu=150 | 25.8 / 25.4 | 差 2×（最好） |

数据来源：各目录 `randrw-r1.txt` 的 read/write BW 行。
- **patch 修好了纯随机读，但对 randrw 几乎无用**（冷态 14/14 与原版相当）。
- **ra=0 甚至砸 randrw**（10/10，比不开还差）——与历史"ra=0 救纯读、砸 randrw"结论一致。
- mu=150 最高（25.8）但仍差 2×。
- **randrw 是与纯随机读完全不同的瓶颈：读写竞争，至今未定位。**

### 结论3：ra=0 对纯随机读救、对顺序读/randrw 砸（一致的旧结论再验证）
- ra=0：冷态 randread 37→53（救），但 seqread 79→52（砸）、randrw 14→10（砸）。
- 按负载分挂载点的老结论不变，且 patch 不改变这个权衡。

### 结论4：暖态随机读高值是缓存命中，无验收意义
warm ra0 r3=156 等 >124 值是 OSD/客户端缓存命中。生产随机负载不命中，这些值不能作达标依据。暖态测试因缺独立预热阶段，仅能定性看趋势。

## 四、对项目主线的意义

1. **"随机读 2.5× 放大"根因已确认并修复验证**：不是 EC/网络/messenger，而是 v1.3.1 `loadRange` 条件 bug（`cached_store.go:153` 的 `len(p)<=blockSize/4=64K` 挡住 128K FUSE 半块 → 全量读 → 2×）。patch 后放大 2.17×→1.11×、纯随机读翻倍（专项验证 98.3）。这推翻了 10 阶段"2.5× 放大来自 EC 取片/messenger"的归因。
2. **但这不解决验收**：验收口径是 randrw，randrw 全口径 10-26、差 2-4×，patch 无改善。**randrw 读写竞争是当前唯一未定位、且决定验收成败的瓶颈。**
3. **修复落地**：patch 是验证手段，生产落地需走正规版本评估（升级到含 eaf3d21f 的 v1.4.x 或向 release-1.3 backport），不是直接上 patched 二进制。需重估 v1.4（之前"v1.4 单客户端 -3.3%"要对比随机读修复收益）。
