## 二、用例缺陷修复

### 2.1 容器运行时修复（docker → podman）

**问题**：`fault_inject.sh` 的 `stop_osd` 和 `FT-001` 内联 kill 命令用 `docker ps`/`docker kill` 查杀 OSD 容器，但集群用 podman（cephadm 默认），`docker ps` 返回空，SIGKILL 未送达容器。

**影响**：OSD 只走 `systemctl stop`（SIGTERM），不走 SIGKILL，OSD 停止慢 ~10s。测试能过但故障注入不精确。

**修复**：`fault_inject.sh` 的 `stop_osd` 和 `FT-001` 内联 kill 统一改为 `podman`。

### 2.2 OSD LV 路径解析修复（OPS-001）

**问题**：`_get_osd_data_lv` 从 OSD metadata 取到 `bluestore_bdev_partition_path`（如 `/dev/dm-3`），但 `ceph orch daemon add` 需要 LV 路径（如 `/dev/ceph-vg-ceph-node1/osd_2`）。`lvs` 不认 dm 路径，传入后 `ceph-volume` 报 `IndexError: list index out of range`。

**修复**：增加 dm → mapper → LV 两步解析：

```bash
# 1. dm 路径 → mapper 名（ls /dev/mapper/ | grep dm-3）
mapper_name=$(ls -la /dev/mapper/ | grep 'dm-3' | awk '{print $9}')
# 2. mapper 路径 → VG/LV（lvs /dev/mapper/<mapper_name>）
lv_path=$(sudo lvs --noheadings -o vg_name,lv_name /dev/mapper/$mapper_name)
# 3. 拼接 LV 路径
echo "/dev/${lv_path}"
```

### 2.3 LVM 标签清理修复（OPS-001）

**问题**：Phase 1 用 `wipefs -af` 清除旧签名，但 `wipefs` 不清 LVM 标签（`ceph.osd_id`、`ceph.db_device` 等）。`ceph orch daemon add` 检测到残留标签后报 `already created?`，拒绝部署新 OSD。

**修复**：`_zap_lv` 改用 `lvremove + lvcreate` 重建 LV（彻底清除所有 LVM 元数据），替代 `wipefs`。

### 2.4 fsck 权限修复（OPS-002 / FT-003 / FT-005）

**问题**：三处 `juicefs fsck` 命令返回 exit 1。

**根因**：直连 RADOS 模式下 fsck 通过 librados 读 Ceph 对象，需要 keyring 认证。`ceph.client.admin.keyring` 权限 600 root:root，turboai 用户读不到。之前用 S3/RGW 时 fsck 走 HTTP 不需要 keyring，故未暴露。

**修复**：三处 fsck 命令统一加 `sudo CEPH_CONF=/etc/ceph/ceph.conf` 前缀。

### 2.5 FT-003 md5sum 超时修复

**问题**：FT-003 断电 .14 后，I/O 探测报"读取成功 但 MD5 不一致"，但恢复后 MD5 又一致。

**定位过程**：

1. 在 .14 只 kill OSD（不整节点断电）+ fio 并发 + turboai 用户无 sudo 等多种条件下复现，MD5 均一致。排除 EC 重构错误、fio 干扰、权限问题。
2. 发现关键差异：整节点断电时 TCP 连接 hang（无 RST），librados 要等 `rados_osd_op_timeout=30` 超时；kill 进程时 TCP 立即 RST，快速重试。
3. `dd iflag=direct`（O_DIRECT）在 FUSE 上不填 page cache → `md5sum` 需重新从 Ceph 读 100MB → 整节点断电时读取慢（TCP hang + 30s 超时）→ `timeout 15` 杀死 md5sum → 输出为空 → "MD5 不一致"。

**修复**：`timeout 15` → `timeout 75`。加 `break` 在首次 MD5 一致后跳出循环，避免冗余探测。

### 2.6 OPS-002 reboot 目标固定

**问题**：OPS-002 随机选 `.11`/`.13`/`.14` 之一作为重启目标，每次重跑目标不确定，不利于问题复现和调试。

**修复**：固定选 `.14`（ceph-node3）。

## 三、I/O 行为分析

### 3.1 故障场景对 I/O 的影响程度

| 故障场景 | 影响层面 | I/O 影响 | 恢复时间 |
|---------|---------|---------|---------|
| 1 OSD SIGKILL（FT-001） | 数据面 | 写延迟 692~2565ms，100% 成功 | PG ~2s peering + rerouting |
| 1 OSD EIO（FT-002） | 数据面 | 写延迟 2227~4685ms，100% 成功 | EIO-to-crash 0~3.5s + 同 FT-001 |
| 节点断电（FT-003） | 数据+元数据 | 读 ~22s 恢复（新读）/ ~32s（旧读最坏），写不可用 | 心跳 20s + peering 2s + map 传播 |
| 1 TiKV freeze（FT-004） | 元数据面 | 元数据阻塞 ~15.5s，数据 I/O 不受影响 | gRPC keepalive 13s + 重连 4s |
| 2 TiKV down（FT-005） | 元数据面 | 元数据完全阻塞，数据 I/O 不受影响 | 恢复 TiKV 后立即恢复 |
| 1 MON down（FT-006） | 管理面 | 无影响（MON 不在数据路径） | — |
| 2 MON down（FT-007） | 管理面 | 稳态 -8% IOPS（monc_lock 竞争，非卡死） | MON 恢复后立即正常 |
| 1 PD freeze（FT-008） | 元数据面 | 元数据阻塞 ~21s，数据 I/O 不受影响 | gRPC keepalive 13s + 选举 3s + 重连 5s |
| 2 PD down（FT-009） | 元数据面 | 元数据完全阻塞（TSO 不可用） | 恢复 PD 后立即恢复 |
| FUSE crash（FT-010） | 客户端接入 | mount 不可用，已 close 数据完整 | remount 后立即恢复 |

### 3.2 FT-001/FT-002 延迟波动来源

**FT-001（692~2565ms）**：kill 时机相对于 dd 写入进度的随机性。1GB dd 写 ~9s，kill 发生在写入中途某随机时刻。若 dd 当前正好写 killed OSD 的 chunk → 立即失败 → 低延迟；若在写其他 OSD 的 chunk → 延迟到后续 chunk 命中 killed OSD 才触发 rerouting → 高延迟。

**FT-002（2227~4685ms）**：FT-001 的全部随机性 + EIO-to-crash 间隔（0~3.5s 随机）。EIO 注入后 OSD 不立即 crash，要等磁盘 I/O 才碰到 EIO。命中 BlueStore 缓存 → crash 慢 → 高延迟；立即做磁盘 I/O → crash 快 → 低延迟。

| 因素 | FT-001 | FT-002 |
|------|--------|--------|
| kill 时机 vs dd 进度 | 0~2s 随机 | 同左 |
| EIO-to-crash 间隔 | — | 0~3.5s 随机 |
| PG peering + map 更新 | ~1-2s（相对固定） | 同左 |
| **波动范围** | **692~2565ms** | **2227~4685ms** |

### 3.3 FT-003 新读 vs 旧读

整节点断电（不回 TCP RST）导致两种 I/O 恢复路径：

- **新读**（心跳超时后发起）：客户端已拿到新 OSD map → 直接路由到 up OSD → ~22s 恢复（heartbeat 20s + peering 2s + map 传播）
- **旧读**（心跳超时前发起，命中 down OSD）：TCP hang → `rados_osd_op_timeout=30` 超时 → ETIMEDOUT → 重试到 up OSD → 最坏 ~32s

关键区别：旧读要等 30s 超时才知道 OSD 不可达，新读不需要（OSD map 已更新）。

### 3.4 FT-004 元数据恢复延迟分解

实测元数据最大延迟 15.5s，经逐层分析，延迟来源不是 Raft 选举（1-2s 完成），而是客户端检测链：

| 层 | 机制 | 默认耗时 |
|----|------|---------|
| 1 | gRPC keepalive（检测连接无响应） | 13s |
| 2 | batch recvLoop waitConnReady（硬编码） | 5s |
| 3 | checkLiveness（HealthCheck 探测） | 1s |
| 4 | 连接新 leader + RPC | ~3s |
| **总计** | | **~17s** |

Raft 选举对总延迟无影响——选举 1-2s 完成，但客户端要 13s 才检测到连接死亡，之后还要等 waitConnReady 5s。层 2-4 共 ~9s 硬编码不可调，是理论最低值。
