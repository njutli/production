# 192 长稳环境旧数据回收评估（只读）

范围：仅客户端 `192.168.11.12` 的 JuiceFS 卷 `juicefs-prod`、Ceph 池 `juicefs-data`；存储节点为 `.11/.13/.14`。本评估未删除文件、未执行 GC、未改配置，也未访问 157/150～152。

## 结论

这组环境只承载长稳测试，因此不需要保留旧测试文件的 PG/OSD 布局以维持性能调优可比性；**可以在确认精确归属和证据归档后清理旧 RUN 的数据文件**。但“可以清理”不等于“容量已经回升”：JuiceFS 逻辑删除、后台 slice 删除和 Ceph 对象释放是不同阶段，必须以 `juicefs-data` 的 `max_avail` 实际回升作为下轮写入准入依据。

2026-09-23 的只读核对如下：

| RUN_ID | 当前数据子目录 | 文件/逻辑大小 | 结果状态 | 处置判断 |
|---|---|---:|---|---|
| `20260921-173701` | `reliability-lt-data/<RUN_ID>/LT-002/randrw256k` | 0 / 0 | 无完成标志及清单 | 空目录；删除也不回收可见数据，先保留或另行清理空目录 |
| `20260921-174543` | 同上 | 0 / 0 | 无完成标志及清单 | 同上 |
| `20260921-175201` | 同上 | 0 / 0 | 无完成标志及清单 | 同上 |
| `20260921-175359` | 同上 | 128 × 1 GiB = 128 GiB | `COMPLETE`、`controller.done`、`manifest.sha256`、`verdict.json` 均在；本地完整归档可关联 | 精确清理候选；先核对归档 SHA256 |
| `20260922-144100` | 同上 | 128 × 1 GiB = 128 GiB | `COMPLETE`、上述三项均在；本地有对应归档包 | 精确清理候选；先核对归档包完整性 |

两个完整 RUN 合计 **256 GiB 逻辑文件**，不是可承诺的 Ceph 物理回收量。读侧未发现运行中的 LT/fio 负载；卷 `TrashDays=0`。检查时 Ceph 池 `max_avail=537,945,407,488 B`（约 501.0 GiB）、`stored=668,525,993,388 B`、对象数 2,593,040。它与项0的容量基本一致；0.4 TiB 停止线以上仅约 91 GiB，而历史同负载 2 小时曾下降 107.1 GiB，因此**仍不得启动下一轮 2 小时写入长测**。

## 分批回收顺序与安全门

1. 在 192 客户端对上述两个完整 RUN 的精确数据路径、文件名模式、归档 SHA256、卷 UUID 再核对；确认无活动写者、JuiceFS staging/upload 已排空。其余挂载内容和结果目录 `/data/reliability-lt-results` 不在清理范围。
2. 获得精确目标授权后，每次只删除**一个**已归档 RUN 的 128 个 `lt.<job>.0` 文件及其空数据目录，不使用卷根/池根通配符，不碰其他文件、卷、pool 或 OSD。记录删除前后 `max_avail/stored/objects`、卷后台待删状态，观察至稳定或超时；若无回升，先查异步删除状态，不直接叠加下一 RUN。
3. 只在容量实测足以覆盖已观察 107.1 GiB 的 2 小时下降量、0.4 TiB 停止线及合理缓冲，且健康门通过后，才允许新 2 小时筛查。24/72 小时不能用这一次回收量直接担保；仍须按每个窗口实测趋势推进并在停止线自动停写。

本评估**不授权** `juicefs gc --delete`、强制清空回收站、手工 compact、Ceph 对象/池删除、OSD 操作或扩大卷范围。若普通文件删除后仍不回收，先形成只读归因和单独计划，再申请相应授权。清理旧 RUN 属于新测试前的容量恢复，不得计入原生长稳测试的“自动收敛”结果。
