## 一、缺陷一句话

**写请求尺寸 = 数据块大小时，新 slice 的编号登记异步执行，首写检查 `id>0` 必然失败、上传被跳过（插桩实测 99.2%）；数据滞留 → 缓冲节流 → 纯随机写吞吐崩塌。** 竞态代码（`go s.prepareID(...)` + `if s.id > 0` 守卫）在 **v1.3.1 与最新 main（edabf9c2）完全同款**。

### 2.2 未证 / 未闭合

- **main 在新鲜高吞吐（3815）时竞态滞留为何不抬升缓冲**（按 dwell 算术应为 GiB 级，实测 10MiB）——`usedBufferSize`/`AllocMemory` 实现两版本完全相同，微观账目仍有缺口。**不影响任何判决**（模式 B 签名已把"补丁对 main 无效"钉死），但不建议在文档外宣称完全理解。
- **补丁的质量保证未完成**：单元测试、数据完整性（fio --verify）、长稳 soak 均未跑；上游 PR 路线已放弃（main 不受影响 ⇒ 维护者无动机，用户裁定）。

### 2.3 待决策 / 待做

1. **生产路线**：v1.3.1 + eaf3d21f + 本补丁（`/tmp/juicefs-03-8`，md5 `1f60618c…`，已 8+ 轮实测 2970~3583）。代价 = 与上游分叉，每次升级需重新适配复验；备选 = 退回 128K 挂载（放弃读侧 +115.6%）。**最终拍板在项目方。**
2. 补丁 QA（内部三层）：`go test ./pkg/vfs/...` → 隔离目录 `fio --verify` 完整性 → 夜间 soak。**全部在隔离目录（patch_qa/）进行，共享布局零写入，结束后 gc --delete + compact cooldown 恢复环境。**
   - ✅ 已完成：`go test -race ./pkg/vfs/`（补丁应用于 v1.3.1 树，78s 执行）——**补丁路径（writeChunk）零数据竞争**；唯一 race 警告在 `fill.go` 的 sliceIterator（cache warmup 测试路径，上游预存，与补丁无关）。测试整体 FAIL 的原因是 TestFill 该处 race + 一处 Redis 环境依赖（127.0.0.1:6379 不可达），均非补丁引入。
   - ⚑ 锁纪律声明（2026-08-18 审查补遗）：补丁在 writeChunk 内同步 `NewSlice`——该函数在 `fileWriter.Write` 的 `f.Lock` 保护下执行（唯一调用方），`s.id`/`SetID` 均在锁内、slice 尚未发布无并发访问；但**偏离了原 prepareID"打 meta 前先释放 f.Lock"的锁序**（每 4096 次 NewSlice 一次 TiKV 往返在持锁时发生，健康时无感、TiKV 降级时是短暂停顿点），且正确性依赖"调用方持锁"的隐式约定。已写入补丁注释。
3. 若未来重新考虑上游：issue 只报事实（竞态代码在 main 仍在、性能影响仅 1.3 线可见），不报"main 有性能问题"。

## 四、机理模型（最终版）

```
写路径正常链：写满 slice → FlushTo 立即上传
竞态：首写检查 id==0 → 跳过 → 数据滞留（fallback：flushAll 1s / 冻结链 / 10s 强制刷）
节流：缓冲>300MB → 每次写睡 10/100ms（通用内存保护）

v1.3.1：竞态滞留 ⇒ 缓冲过阈 ⇒ 节流自锁（550，与排水无关）⇒ 补丁消除滞留 ⇒ 恢复
main：  竞态滞留被兜底排水吸收（排水≥写率时缓冲不涨）；塌态 = 排水<写率时上传队列
        自身过阈 ⇒ 节流 ⇒ 补丁不改变排水 ⇒ 无效
历史假象：pre-#6336 的"main 健康"= 旗标失效（实际 128K 挂载，竞态不触发）
```

**一句话**：同一个竞态代码，v1.3.1 上它维持自锁塌态（补丁是解药）；main 上它是旁观者（补丁无药可医）。**病根不同，同一副药只对前者有效。**
