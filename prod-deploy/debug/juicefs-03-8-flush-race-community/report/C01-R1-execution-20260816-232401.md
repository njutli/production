## C01/C01-R1 结论解释与证据边界

> 追加日期：2026-08-17  
> 本节用于澄清“问题在 main 上复现”和“补丁解决 main 上的问题”分别指什么，避免把源码级漏派发、v1.3.1 的 randwrite 塌速以及 main 的宏观性能表现混为同一结论。它不改变前述 `TECHNICAL PASS / AUDIT NON-COMPLIANT` 裁定。

### 1. 原始 C01 与 C01-R1 不能合并记为两次成功复现

原始 C01 在注入测试和应用补丁前即被全包基线门禁阻塞，正式裁定为：

~~~text
C01-REVIEWED = BLOCKED-BASELINE / NO DEFECT OR PATCH VERDICT
~~~

因此，原始 C01 只能说明首版执行方案的基线和审计设计需要修订，不能用于证明 main 存在缺陷，也不能用于证明补丁有效。C01/C01-R1 这一阶段中，真正产生源码级技术结论的是本次 C01-R1。

### 2. C01-R1 复现的是确定性的源码级 I/O 派发行为，不是 fio 塌速

C01-R1 没有运行 fio、挂载、Redis、Ceph、TiKV 或真实对象存储，也没有测量吞吐、缓冲增长和节流。测试使用纯内存 metadata/chunk writer，运行真实的 `writeChunk`、`sliceWriter.write` 和 `prepareID` 状态机，并记录是否调用 `FlushTo`。

测试 helper 显式持有 `fileWriter` 的文件锁后调用 `writeChunk`，复现生产 `fileWriter.Write` 调用该函数时的锁约束。stock main 的确定性顺序如下：

~~~text
fileWriter 持有文件锁
  -> 创建新 slice，初始 s.id == 0
  -> 启动异步 prepareID；prepareID 首先要取得同一把文件锁，因此此时不能设置 ID
  -> 首笔写入恰好 256 KiB，s.slen 达到 blockSize
  -> 执行 s.id > 0 检查，结果必定为 false
  -> 跳过 FlushTo(256 KiB)
fileWriter 释放文件锁
  -> prepareID 才能分配并设置 slice ID
  -> stock 代码没有补发刚才错过的 FlushTo
~~~

所以这里不是未受同步保护的 Go data race，也不是依赖调度概率的“偶现读到 0”，而是由锁顺序决定的 missed flush dispatch / ordering bug。测试中的可控 `NewSlice` 只用于确定地观察 ID 就绪边界，并没有凭空制造生产代码中不存在的顺序。

正负控精确定义了本轮直接证明的行为：

#### 做了什么

测试通过 mock 阻塞 `NewSlice` 的返回，强制制造一个确定性的时序窗口：`writeChunk` 持有文件锁写入数据 → 写路径检查 `s.id > 0` → 此时 `NewSlice` 仍被阻塞、`s.id == 0` → 跳过 `FlushTo` → 释放文件锁 → `NewSlice` 返回、`SetID` 被调用。在这个窗口下分别投入两种写入量：

- **正控**：写入恰好一个完整 block（256 KiB）
- **负控**：写入半个 block（128 KiB）

#### 预期

派发不变式 I：当且仅当一个非 frozen slice 在 ID 就绪时已包含至少一个完整 block，必须对该 block 派发恰好一次 `FlushTo(blockSize)`；不足一个完整 block 时不得派发。

- **正控**（完整 block）：ID 就绪后 1 秒内 `FlushTo(256 KiB)` 必须被调用，且 offset 精确等于 blockSize；随后 100ms 内不得出现第二次 `FlushTo`（不重复派发）。正控同时约束"必须派发"和"恰好一次"。
- **负控**（半 block）：ID 就绪后 250ms 内 `FlushTo` 不得被调用。250ms 窗口兼顾两端——足够长以排除异步调度延迟导致的假阴性，足够短以确认补丁没有走"ID 就绪即无条件 FlushTo"的错误路径。

两组控制缺一不可：没有正控，无法证明 bug 存在或补丁修复了它；没有负控，一个"ID 就绪后无条件 FlushTo"的坏补丁也能通过正控——它会错误地对不完整 block 提前派发，改变上传粒度和写语义。

#### 实际

stock main 在 Go 1.25.7 和 Go 1.26.0 下各 10 个独立进程、合计 20/20 次：

- **正控**：全部 FAIL，每次恰好命中一次 `C01_MISSED_DISPATCH`（`FlushTo` 在 1 秒窗口内未被调用）。负控全部 PASS（半 block 未被派发）。
- A-sync：正控 PASS（`FlushTo` 被调用且 offset 正确），负控 PASS，100ms 内无重复。`count=100` 和 `-race count=20` 均通过。
- B-async-catchup：正控 PASS，负控 PASS，100ms 内无重复。`count=100` 和 `-race count=20` 均通过。

#### 说明了什么

stock 违反了不变式 I 的前半（完整 block → 必须派发一次）——首个完整 block 在异步 ID 就绪后仍未补派发。A 和 B 都恢复了不变式 I 的完整定义（正控 PASS + 负控 PASS + 不重复）。

本轮直接证明的是**派发状态机在 ID 就绪边界的行为正确性**，不是数据持久化的端到端完整性。被漏掉的是正常写路径上的即时上传派发，不应表述为数据已永久丢失——数据仍可能由 freeze、`flushAll` 等后续兜底路径刷出；C01-R1 不验证这些兜底路径的速度或最终持久化结果。

### 3. A/B 在 C01-R1 中分别纠正了什么

#### A-sync：v1.3.1 自维护补丁在 main 上的适配臂

A 在创建新 slice 时同步执行 `NewSlice`，成功后先设置 `s.id` 和 writer ID，再执行首笔数据写。于是完整 block 到达 `s.id > 0` 检查点时 ID 已经有效，正常路径会调用一次 `FlushTo(256 KiB)`。

C01-R1 中 A 的正控、负控、`count=100`、`-race count=20` 和纯内存回归均通过。因此本轮直接证明：**v1.3.1 同步 ID 补丁采用的机制，适配到固定 main 后可以纠正这个最小漏派发行为。**

该结论的严格边界是：

- C01-R1 测试的是 main 上的 A 适配补丁，不是直接 checkout v1.3.1 源码执行同一单测；
- 它证明正常成功分配 ID 时的派发行为，不单独覆盖全部 metadata 错误、重试、freeze、多 block 和并发状态；
- v1.3.1 上约 551 MiB/s 恢复到 2970--3583 MiB/s 的结论来自此前独立的实际 fio 插桩和 ABBA 性能证据，不是由 C01-R1 产生。

#### B-async-catchup：保留异步边界的补派发臂

B 保留异步 `NewSlice`。首笔完整 block 仍可能在 ID 为 0 时跳过原检查，但 `prepareID` 设置 writer ID 后，会在同一文件锁保护下检查已经积累的完整 block 并补调用 `FlushTo(s.slen)`。

因此 A 与 B 达到了相同的 C01-R1 外部可观察结果，但修复位置不同：

~~~text
A：先让 ID 就绪，再进入首次完整 block 的正常 FlushTo 路径
B：保留首次写与 ID 分配的异步关系，在 ID 就绪后补回错过的 FlushTo
~~~

C01-R1 只足以确认两者都覆盖最小行为，不足以据此选择社区方案。后续 C02 扩展错误、阻塞、重试、freeze、多 block 和并发矩阵后，确认 A 会把 metadata 延迟带入首次写路径并改变部分调用/错误语义，而 B 能保留 stock 的异步边界；因此 B 才进入后续社区化验证，A 保留为已有 v1.3.1 性能实证的自维护兜底。

### 4. “修正 main 的漏派发”不等于“修复 main 的 randwrite 塌速”

本轮必须按下表使用结论：

| 命题 | C01-R1 裁定 |
|---|---|
| 固定 main 存在首个完整 block 漏派发 | 已证明 |
| A-sync 能纠正该最小派发行为 | 已证明 |
| B-async-catchup 能纠正该最小派发行为 | 已证明 |
| v1.3.1 与 main 的相关源码顺序属于同一类问题 | 由源码对照和 A 的 main 适配结果支持 |
| C01-R1 直接测试了 v1.3.1 补丁二进制 | 未证明；本轮没有修改或运行 v1.3.1 |
| main 在本轮复现约 550 MiB/s randwrite 塌速 | 未证明；本轮没有运行宏观 I/O |
| A 或 B 能恢复 main 的宏观 randwrite 吞吐 | 未证明 |
| v1.3.1 自维护补丁能恢复 v1.3.1 的 randwrite 吞吐 | 已由此前独立的生产式 ABBA/插桩证据证明，不属于 C01-R1 证据 |

main 上的漏派发可以被 A/B 修正，但 main 的系统级塌速还可能由后端上传队列和排水能力主导。因而历史测试中“main ± 同步补丁吞吐曲线无明显差异”与 C01-R1 的结论并不冲突：前者说明漏派发不是那些 main 系统测试中的主导吞吐瓶颈，后者说明源码中的错误派发状态确实存在且可以被补丁消除。
