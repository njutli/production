3. C02 十项语义测试在双工具链下通过 `count=100` 和 `-race count=20`。

这些结果足以支持“执行时冻结的 main 仍存在最小漏派发行为，B 值得继续社区化验证”，但不等于本轮已经达到可提交 PR 的状态。

### 为什么不能接受原报告的 PR-ready 状态

1. `candidate-gates.tsv` 明确记录 `B_lint=PENDING`，但最终状态仍写成 `PASS-B-PR-READY-LOCAL`；硬门未通过时不得输出 PR-ready。
2. runner 将若干 gate 默认或硬编码为 YES，最终状态没有机械检查 lint、tidy、vet、build、search 等全部要求项，因而“其余 gate 全 YES”不能替代逐门证据。
3. runner 在两次失败后原地修改；旧 OUT 没有完整保留，`pre-run-adaptations.md` 也没有指名历史失败、旧新 runner 和修改原因，破坏不可变执行边界。
4. anchor 检查通过 grep xtrace 识别字符串，匹配到了检查命令自身；`PACKAGE` 在真实打包发生前也可能被错误判定为已出现。
5. GitHub 查询缺少 HTTP status、headers、timestamp 等请求有效性证据，也没有冻结仓库的本地 history 查重。
6. Redis 只证明容器命令整体完成，缺少 inspect、容器日志和销毁后的不存在证明。
7. build 只有 make 返回码，缺少二进制 `version` 输出、冻结 revision 和产物 SHA256，不能证明交付物对应被测源码。
8. Q-semantic 只跑了聚合 `count=100`/race 集合，没有按要求保存十项逐项结果。
9. PR 草稿把实际未运行的 golangci-lint 写成已通过，草稿真实性门不成立。

技术测试通过不能豁免上述执行与交付缺口，尤其不能把 `PENDING` 解释成“留给 GitHub Actions 后仍可本地 PR-ready”。
