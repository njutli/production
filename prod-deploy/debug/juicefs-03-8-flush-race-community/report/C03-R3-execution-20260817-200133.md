### 原报告所称“消除全部审计缺陷”不成立

1. 正式 input 内的 `runner-static-review.txt` 明确写着 `Launcher if/else rc capture: NO` 和 `VERIFY not deleted: NO`，但 formal run 仍被启动。任务书规定 static review 任一 NO 都不得启动，因此正式 attempt 在测试前已经不合规。实际 launcher 后来确有 if/else 捕获，但这只说明 static checker 本身失真；`run-c03-r3.sh` 则确实执行了 `rm -rf "$VERIFY"`。
2. 任务书要求统一 14 列结果 schema，末列为 `expectation_matched`。四张正式结果表实际只有 13 列；数据把日志路径写进 `bad` 字段、真正的 `log` 为空，也没有 `expectation_matched`。因此报告中的“精确行数匹配”不能证明每行期望匹配。
3. B/Q 的 count/race gate 仍主要根据组合进程 rc 判定，没有逐行要求 exact PASS/FAIL/marker/bad/log；预飞也没有留下任务书要求的 100/99/no-tests 三个 result parser 可执行反例。
4. Redis lifecycle 仍是“七列表头、三列数据”：其余六个语义字段被装入冒号串。报告所称“七列 TSV 记录每步真实 rc”与实际文件不符。
5. `input.expected-files` 只列 15 个 basename，而任务书要求精确列出包括三个 manifest 在内的 18 个；因此 `input_integrity=YES` 没有证明任务书规定的完整 input 集合。
6. B-candidate clone 留有未登记文件 `pkg/vfs/?_journal=WAL&_timeout=5000&cache=shared`，但 source/path guard 仍为 YES，说明未跟踪文件未被纳入最终源码守卫。
7. `meta/archive-members.expected` 含两行相同的 `meta/archive-members.expected`；tar 中同一路径也出现两次，其中第二项为 hard-link entry。runner 用集合/sha 成功近似代替多重集比较，仍把 `member_set_exact` 写成 YES。
8. runner 并未真实比较 expected、manifest、tar、extract 四组成员：`member_set_exact` 和 `manifest_coverage_exact` 仅由 manifest checksum rc=0 推导。三个要求始终存在的 diff sidecar均缺失。
9. `meta/final-compliance-review.md` 在 manifest、tar 和 extract 之后才写回 OUT，形成 payload freeze 后修改；该文件既不在 expected 中，也不受 archive manifest 覆盖。
10. archive set 合成反例没有按任务书执行；terminal 8-case 只覆盖 finalizer，无法发现结果列错位、Redis 冒号打包、重复 tar member、未跟踪源码和 post-freeze mutation。
11. 因此，外置十项 `YES` 和 `PASS-B-PR-READY-LOCAL` 是同一套有缺陷 producer/finalizer 的自报结果，不能作为独立终态证明。
