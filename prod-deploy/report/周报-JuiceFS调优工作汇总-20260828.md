# 周报-JuiceFS调优工作汇总-20260828

## 一、进展概要

本周围绕上周遗留的“元数据引擎为什么会从快态进入慢态”和“剩余随机写瓶颈能否解决”两个问题，完成了从客户端 inode 队列、TiKV 同步事务、RocksDB compaction、物理 NVMe 到 WAL/Raft 隔离的完整归因闭环，并完成了 JuiceFS 1.4.1 版本能否替换当前交付基座的前期评估。

核心结论：**将 TiKV WAL/Raft 与 KV/compaction 的物理 I/O 路径分离，能够明确改善随机写稳定性，并带来小幅带宽收益。** 8 轮正式对照测试结果一致：分离后均优于分离前，256-inode randwrite 中位带宽由 `3607.63 MiB/s` 提升至 `3756.51 MiB/s`，配对中位收益 `+5.05%`；分离后逐秒带宽的波动幅度（变异系数）由 `8.60%~12.19%` 降至 `6.30%~7.55%`，最大值降幅约 `38%`；测试后段带宽保持率（160 秒统计窗口均分四段，取末段与首段中位带宽之比）由最低 `0.81` 提升至 `0.95~0.99`。

该收益目前不能直接固化到生产：验证测试将 WAL/Raft 存放在内存中，不具备持久化条件；现有三台 TiKV 节点也没有对称空闲 NVMe。其生产意义是：**后续如能为三台 TiKV 各提供一块独立、持久、低延迟的空闲盘，应优先考虑把 WAL/Raft 与 KV 分离。** 不能用同一 NVMe 上的目录、分区或 loop 代替真实物理隔离。

同时，本周在将历史生产 TiKV 切换为临时新建 TiKV 时观察到 randwrite 带宽提高约 `25%~30%`。该差值同时改变了元数据规模、集群起点及底层存储形态等多个变量，无法固化到单一因素，但其量级远大于本周测出的介质影响（`+0.26%`）和 WAL/Raft 分离收益（`+5.05%`），是剩余未拆分因素中最大的一项，后续需逐一隔离确认收益来源。

此外三项对后续决策有直接作用的结论：**存储介质本身不是随机写主因**（见 3.2）、**JuiceFS 1.4.1 必须携带随机写补丁才能使用**（见第四节）、以及**六个调优方向被正式排除**（见第五节）。

## 二、JuiceFS 方案完成元数据引擎波动原因定位

### 2.1 上周遗留问题

上周已经观察到随机写性能随元数据 `Write` 延迟从约 `138 ms` 上升至约 `187 ms` 而下降，但当时只能确认退化位于元数据引擎侧，尚不清楚是跨日 TiKV RocksDB 状态积累、单次事务延迟变化，还是运行中的共享资源竞争造成。

本周按“客户端排队 → TiKV 事务 → compaction → 物理设备 → 存储隔离”的顺序完成递进定位。

### 2.2 客户端逻辑延迟与 TiKV 事务周期拆分

- 客户端观测到约 `186--201 ms` 的 meta `Write` 不是一次 TiKV 请求的服务时间，而是包含同 inode 前序请求等待的端到端时间。
- JuiceFS 同一 inode 内的 meta `Write` 受 open-file lock 串行约束；实际 TiKV 同步事务周期约为 `10--13 ms`，客户端深队列把该周期放大为约 `190 ms` 的逻辑延迟。
- 128 个活跃 inode 时，随机写首先受“每 inode 串行通道数 × 同步事务周期”约束；增加到 256 inode 后，收益很快被 TiKV 共享服务率限制，不能继续按 inode 数线性扩展。

### 2.3 轮内波动的直接机制

256-inode randwrite 在每轮开始前 pending compaction 可以接近 0，但负载启动后会在本轮重新建立压缩积压。后续正式对照测试中，三节点 TiKV 的 pending compaction 到测试末段均增长至约 `11--16 GiB`；WAL/Raft 与 KV 共用同一 NVMe 时，Raft sync 延迟由测试起始段的约 `0.22--0.23 ms` 上升到测试末段的约 `0.74--0.80 ms`，同时物理 NVMe `w_await` 和带宽低谷共同增大。

三节点 RocksDB hard write-stall 全程为 0，因此这不是达到硬阈值后的停写，而是以下软排队链：

```text
按 inode 串行的同步元数据事务持续进入 TiKV
        ↓
前台 KV/WAL/Raft 写与后台 compaction 共用服务能力
        ↓
pending compaction、设备队列和同步提交延迟在轮内积累
        ↓
客户端可完成的元数据事务减少，上传管线供给下降
        ↓
随机写后段出现低谷，波动幅度上升
```

### 2.4 对“跨日状态积累”和主动清理的结论

每轮正式测试都使用全新 TiKV、全新本地文件系统和相同数据集起点，仍然重复出现本轮内的 pending compaction 增长。因此：

1. 跨日 RocksDB 状态和历史介质起点会影响一轮开始时的性能水平，但不是轮内波动成立的必要条件；
2. 主动清理可以统一测试起点、消除跨轮污染，却不能阻止高强度 randwrite 在本轮重新建立压缩积压；
3. 原先“通过清理即可消除元数据引擎波动”的方向可以关闭，稳定性优化必须处理同步日志与 KV/compaction 的共享延迟路径。

至此，上周遗留的“元数据引擎双态/波动原因”已从环境现象收敛为可重复的运行时机制。

## 三、JuiceFS 方案完成剩余瓶颈分析及解决路径收口

### 3.1 WAL/Raft 与 KV 分离的正式验证

最终验证使用同一全新临时 TiKV、同一数据集、相同 KV 文件系统、相同配置和相同 256-inode 负载，只改变 WAL/Raft 的底层存储介质：

| 测试组 | KV | WAL/Raft | 含义 |
|---|---|---|---|
| 分离前 | NVMe | 与 KV 共用同一物理 NVMe | WAL/Raft 与 KV 共盘 |
| 分离后 | 与分离前相同的 NVMe | 内存 | 移除日志介质延迟及其与 KV 的共享盘竞争 |

正式顺序采用 8 轮测试、4 组相邻对照，避免时间漂移被误判成调优收益。结果如下：

| 指标 | 分离前 | 分离后 | 正式结论 |
|---|---:|---:|---|
| 四组中位带宽 | `3607.63 MiB/s` | `3756.51 MiB/s` | 4/4 配对提高，配对中位 `+5.05%` |
| 逐秒带宽波动幅度（变异系数） | `8.60%~12.19%` | `6.30%~7.55%` | 4/4 改善，最大值降幅约 `38%` |
| 后段带宽保持率（末段/首段） | 最低 `0.810` | `0.946--0.994` | 4/4 改善 |
| Raft sync | 起始段约 `0.22--0.23 ms`，末段约 `0.74--0.80 ms` | 起始/末段均约 `0.074--0.083 ms` | 同步日志尾延迟得到稳定 |
| 6250 目标达成率 | `57.72%` | `60.10%` | 均未达标 |

正式结论是：**WAL/Raft 与 KV/compaction 共用物理盘是尾部波动的放大因素；分离后稳定性收益明确，带宽收益存在但幅度有限。** 带宽 `+5.05%` 幅度较小，不能把日志盘描述为平均吞吐的主瓶颈。

### 3.2 存储介质本身不是随机写主因，`+5.05%` 是分离收益的上界

本周另有一组对照说明介质的作用远小于预期。在完全相同的“KV、WAL、Raft 共盘”拓扑和相同负载下，只把 TiKV 的**全部本地存储**从 NVMe 换成内存：

| 对照 | TiKV 本地存储介质 | 中位带宽 MiB/s | 差异 |
|---|---|---:|---:|
| 全部本地存储在内存 | 内存 | `3699.30` | — |
| 全部本地存储在 NVMe | NVMe | `3709.03` | `+0.26%` |

即**把 TiKV 全部本地存储放进内存，相对放在 NVMe 上只差 `0.26%`**。这条对照有两个直接后果：

1. **随机写的主要约束不在存储介质**，而在同步元数据事务与 KV/compaction 的服务率；
2. **`+5.05%` 应理解为真实第二块盘的带宽收益上界，而不是点估计。** 分离后测试将日志放在内存中，其介质延迟严格优于任何持久化 NVMe，因此实际新增一块 NVMe 的带宽收益不会超过 `+5.05%`。

因此，存储介质本身对随机写带宽的影响极小（仅 `0.26%`）。分离测试中 `+5.05%` 的收益主要来自消除日志 I/O 与 KV I/O 对同一物理设备的共享争用，而非介质本身的速度差异。

### 3.3 为什么分离改善稳定性，但不能解决全部吞吐

分离后 WAL/Raft 的 Raft sync 延迟保持稳定，但 KV 侧 pending compaction 仍增长到 `11--16 GiB`，KV 所在物理 NVMe 的 `w_await` 也没有消失。这说明分离保护了延迟敏感的同步日志路径，使 compaction 高压时不再同时放大 Raft 提交尾延迟；但它没有提高 KV/compaction 的根本消化能力，也没有改变 JuiceFS 每 inode 同步提交的事务模型。

因此当前瓶颈应分为两层：

1. **可通过设备隔离改善的稳定性因素**：WAL/Raft 与 KV/compaction 共用物理盘；
2. **设备隔离后仍存在的吞吐主墙**：按 inode 串行的同步元数据事务，以及 TiKV KV/compaction 的共享服务率。

## 四、JuiceFS 1.4.1 版本替换评估

当前交付基座是打补丁的 JuiceFS 1.3.1。本周对 1.4.1 是否可以替代它做了前期评估，得到一项明确的版本使用结论。

### 4.1 1.4.1 原版存在同样的随机写缺陷，必须携带补丁

在同一集群、同一挂载参数、同一数据集下对比 1.4.1 原版与 1.4.1 加随机写补丁：

| 版本 | 随机写逐轮 MiB/s | 轮间波动 |
|---|---|---|
| 1.4.1 原版 | `551 / 552 / 551` | `0.10%` |
| 1.4.1 + 随机写补丁 | `2754 / 2726 / 2679` | `1.39%` |

`551 MiB/s` 与上周在 1.3.1 原版上观测到的崩塌值完全一致，说明该缺陷在 1.4.1 中同样存在，并未被上游修复。

该结论的可靠性还有一条独立支撑：1.4.1 原版三轮分别在 `6.33M`、`6.33M` 和 `2.43M` 三个相差 `2.6` 倍的存储池对象数下运行，带宽仍恒为 `551/552/551`。这排除了池状态、缓存状态和测试时段等环境因素，崩塌完全来自代码路径。

**生产含义：若将来升级到 1.4.1，必须同时携带随机写补丁，否则随机写会直接降到约五分之一。**

### 4.2 元数据格式双向兼容，回滚可行

评估过程中 1.3.1 与 1.4.1 在同一生产卷上多次交替挂载，均成功，卷设置未发生不可逆变化。这说明两个版本之间可以双向切换，升级具备回滚条件。该项将在正式判定中作为独立验收门再次确认。

### 4.3 版本替换判定尚未闭合

本周两次全量七项对比均因测试设计问题不能作为正式判定依据：一次因为存储池对象数在测试过程中单向累积，使版本效应与池状态无法分离；另一次因为两个版本各自占据连续时段，纯读项在两个时段之间出现 `5.25%` 的系统性偏差，而版本替换需要分辨的正是 `3%--6%` 量级的差异。

正式判定已另立任务，采用轮级交替顺序把两个版本的时间间隔从小时级压缩到十分钟级，并在矩阵内保留同版本相邻对以直接测出噪声底，使判定边界由实测数据决定而不是预先设定。完成后才决定是否更换交付基座。

## 五、本周确认无效的调优方向

以下六个方向本周均有正式证据支持“无效”或“不应作为主解法”。它们不提升性能，但明确缩小了后续工作范围，避免继续投入。

| 方向 | 排除依据 |
|---|---|
| 继续提高 `max-uploads` | 带宽最差的后半程上传槽位占用远低于上限（最低降至接近 0），瓶颈在上游供给不足，不是槽位不够 |
| 继续增加活跃 inode 数 | 128 到 256 的实测增益仅 `10%--13%`，远低于理想 2 倍；继续增加只会更快建立 TiKV 写压力 |
| 增加 compaction worker | worker 单线程 CPU 占用最高仅约 `12%`，且在带宽最差窗口反而下降；增加 worker 只会把更多后台 I/O 送入同一设备 |
| 对 compaction 限速或暂停 | 会把债务推迟到后续窗口，制造短时高值和更大的后续波动，不构成稳定收益 |
| 同一物理盘上的逻辑分离 | 目录、分区、双 loop 三种形式均无材料收益，底层控制器、队列与介质尾延迟仍共享 |
| 通过主动清理消除波动 | 每轮测试均为全新状态起点，轮内仍会重新建立压缩积压 |
