# 周报-JuiceFS调优工作汇总-20260828

## 一、进展概要

本周围绕上周遗留的“元数据引擎为什么会从快态进入慢态”和“剩余随机写瓶颈能否解决”两个问题，完成了从客户端 inode 队列、TiKV 同步事务、RocksDB compaction、物理 NVMe 到 WAL/Raft 隔离的完整归因闭环，并完成了 JuiceFS 1.4.1 版本能否替换当前交付基座的前期评估。

本周最值得体现的生产结论是：**将 TiKV WAL/Raft 与 KV/compaction 的物理 I/O 路径分离，能够明确改善随机写稳定性，并带来小幅带宽收益。**正式 4 组配对全部同向，256-inode randwrite 中位带宽由 `3607.63 MiB/s` 提升至 `3756.51 MiB/s`，配对中位收益 `+5.05%`；逐秒带宽 CV 配对中位改善 `2.36` 个百分点，`W4/W1` 配对中位改善 `0.0694`。

该收益目前不能直接固化到生产：验证臂把 WAL/Raft 放在 RAM backing 上，不具备持久化条件；现有三台 TiKV 节点也没有对称空闲 NVMe。其生产意义是：**后续如能为三台 TiKV 各提供一块独立、持久、低延迟的空闲盘，应优先考虑把 WAL/Raft 与 KV 分离，并以同口径 A/B 验证后上线。**不能用同一 NVMe 上的目录、分区或 loop 代替真实物理隔离。

同时，本周确认 WAL/Raft 隔离不是剩余吞吐缺口的完整答案：最佳 D1 方案中位带宽仍只有 `3756.51 MiB/s`，达到 `6250 MiB/s` 目标的 `60.10%`，仍差 `2493.49 MiB/s`。剩余瓶颈已经收窄到 JuiceFS 按 inode 串行完成的同步元数据事务，以及 TiKV KV/compaction 的共享服务率，后续需要走事务批量化/异步化、inode 并行模型调整或元数据层扩展等架构路径，而不是继续扫描局部参数。

本周还产出三项不提升性能、但对后续决策有直接作用的可靠结论：**存储介质本身不是随机写主因**（见 3.2）、**JuiceFS 1.4.1 必须携带随机写补丁才能使用**（见第四节）、以及**六个调优方向被正式排除**（见第六节）。读侧现状与仅剩的集群布局余量见第五节。

## 二、JuiceFS 方案完成元数据引擎波动原因定位

### 2.1 上周遗留问题

上周已经观察到随机写性能随元数据 `Write` 延迟从约 `138 ms` 上升至约 `187 ms` 而下降，但当时只能确认退化位于元数据引擎侧，尚不清楚是跨日 TiKV RocksDB 状态积累、单次事务延迟变化，还是运行中的共享资源竞争造成。

本周按“客户端排队 → TiKV 事务 → compaction → 物理设备 → 存储隔离”的顺序完成递进定位，没有直接通过修改参数猜测原因。

### 2.2 客户端逻辑延迟与 TiKV 事务周期拆分

- 客户端观测到约 `186--201 ms` 的 meta `Write` 不是一次 TiKV 请求的服务时间，而是包含同 inode 前序请求等待的端到端时间。
- JuiceFS 同一 inode 内的 meta `Write` 受 open-file lock 串行约束；实际 TiKV 同步事务周期约为 `10--13 ms`，客户端深队列把该周期放大为约 `190 ms` 的逻辑延迟。
- 128 个活跃 inode 时，随机写首先受“每 inode 串行通道数 × 同步事务周期”约束；增加到 256 inode 后，收益很快被 TiKV 共享服务率限制，不能继续按 inode 数线性扩展。

### 2.3 轮内波动的直接机制

256-inode randwrite 在每轮开始前 pending compaction 可以接近 0，但负载启动后会在本轮重新建立 compaction debt。后续正式对照中，三节点 TiKV 的 pending compaction 到 W4 均增长至约 `11--16 GiB`；共享盘控制臂 B1c 的 Raft sync 延迟由 W1 的约 `0.22--0.23 ms` 上升到 W4 的约 `0.74--0.80 ms`，同时物理 NVMe `w_await` 和带宽低谷共同增大。

三节点 RocksDB hard write-stall 全程为 0，因此这不是达到硬阈值后的停写，而是以下软排队链：

```text
按 inode 串行的同步元数据事务持续进入 TiKV
        ↓
前台 KV/WAL/Raft 写与后台 compaction 共用服务能力
        ↓
pending compaction、设备队列和同步提交延迟在轮内积累
        ↓
客户端可完成的元数据事务减少，上传管线供给下降
        ↓
随机写后段出现低谷，CV 上升
```

### 2.4 对“跨日状态积累”和主动清理的结论

每个正式 arm 都使用 fresh TiKV、fresh 本地文件系统和相同数据集起点，仍然重复出现本轮内的 pending compaction 增长。因此：

1. 跨日 RocksDB 状态和历史介质起点会影响一轮开始时的性能水平，但不是轮内波动成立的必要条件；
2. 主动清理可以统一测试起点、消除跨轮污染，却不能阻止高强度 randwrite 在本轮重新建立 compaction debt；
3. 原先“通过清理即可消除元数据引擎波动”的方向可以关闭，稳定性优化必须处理同步日志与 KV/compaction 的共享延迟路径。

至此，上周遗留的“元数据引擎双态/波动原因”已从环境现象收敛为可重复的运行时机制。

## 三、JuiceFS 方案完成剩余瓶颈分析及解决路径收口

### 3.1 WAL/Raft 与 KV 分离的正式验证

最终验证使用同一 fresh 临时 TiKV、同一数据集、相同 KV 文件系统、相同配置和相同 256-inode 负载，只改变 WAL/Raft backing 的底层介质：

| 测试臂 | KV | WAL/Raft | 含义 |
|---|---|---|---|
| B1c | NVMe | 与 KV 共用同一物理 NVMe | 共享盘控制臂 |
| D1 | 与 B1c 相同的 NVMe | RAM backing | 移除日志介质延迟及其与 KV 的共享盘竞争 |

正式顺序采用 8 个 arm、4 组相邻配对，避免时间漂移被误判成调优收益。结果如下：

| 指标 | B1c / 分离前 | D1 / 分离后 | 正式结论 |
|---|---:|---:|---|
| 四臂中位带宽 | `3607.63 MiB/s` | `3756.51 MiB/s` | 4/4 配对提高，配对中位 `+5.05%` |
| 逐秒带宽 CV | 个别 arm 达 `12.19%` | 4 个 arm 均为 `6.30%--7.55%` | 4/4 改善，配对中位改善 `2.36 pp` |
| `W4/W1` | 最低 `0.810` | `0.946--0.994` | 4/4 改善，配对中位提高 `0.0694` |
| Raft sync | W1 约 `0.22--0.23 ms`，W4 约 `0.74--0.80 ms` | W1/W4 均约 `0.074--0.083 ms` | 同步日志尾延迟得到稳定 |
| 6250 目标达成率 | `57.72%` | `60.10%` | 均未达标 |

正式结论是：**WAL/Raft 与 KV/compaction 共用物理盘是尾部波动的放大因素；分离后稳定性收益明确，带宽收益存在但幅度有限。**带宽 `+5.05%` 没有达到预注册的 `15%` 材料收益门，不能把日志盘描述为平均吞吐的主瓶颈。

### 3.2 存储介质本身不是随机写主因，`+5.05%` 是分离收益的上界

本周另有一组对照说明介质的作用远小于预期。在完全相同的“KV、WAL、Raft 共盘”拓扑和相同负载下，只把 TiKV 的**全部本地存储**从 NVMe 换成内存：

| 对照 | TiKV 本地存储介质 | 中位带宽 MiB/s | 差异 |
|---|---|---:|---:|
| 全部本地存储在内存 | RAM | `3699.30` | — |
| 全部本地存储在 NVMe | NVMe | `3709.03` | `+0.26%` |

即**把 TiKV 全部本地存储放进内存，相对放在 NVMe 上只差 `0.26%`**。这条对照有两个直接后果：

1. **随机写的主要约束不在存储介质**，而在同步元数据事务与 KV/compaction 的服务率；
2. **`+5.05%` 应理解为真实第二块盘的带宽收益上界，而不是点估计。**D1 把日志放在内存里，其介质延迟严格优于任何持久化 NVMe，因此实际新增一块 NVMe 的带宽收益不会超过 `+5.05%`。

因此，为 WAL/Raft 增加独立盘的理由应落在**稳定性**（CV 与 `W4/W1` 的 4/4 改善），而不是补齐带宽缺口。以“填补剩余约 40% 带宽”为由申请该硬件是不成立的。

### 3.3 为什么分离改善稳定性，但不能解决全部吞吐

D1 中 WAL/Raft 的 Raft sync 延迟保持稳定，但 KV 侧 pending compaction 仍增长到 `11--16 GiB`，KV 所在物理 NVMe 的 `w_await` 也没有消失。这说明分离保护了延迟敏感的同步日志路径，使 compaction 高压时不再同时放大 Raft 提交尾延迟；但它没有提高 KV/compaction 的根本消化能力，也没有改变 JuiceFS 每 inode 同步提交的事务模型。

因此当前瓶颈应分为两层：

1. **可通过设备隔离改善的稳定性因素**：WAL/Raft 与 KV/compaction 共用物理盘；
2. **设备隔离后仍存在的吞吐主墙**：按 inode 串行的同步元数据事务，以及 TiKV KV/compaction 的共享服务率。

### 3.4 对生产环境的建议

如后续具备三节点对称空闲盘，建议：

1. 每个 TiKV 节点为 WAL/Raft 提供独立、持久、低尾延迟设备，KV SST/compaction 继续使用原设备；
2. 三节点同时采用相同拓扑，避免只有部分 Raft quorum 获得低延迟路径；
3. 迁移前设计精确的备份、回滚和磁盘容量门，以生产等价介质重新做共享盘/独立盘 A/B；
4. 验收同时观察带宽、CV、`W4/W1`、Raft sync、KV pending compaction 和两类设备的 `await/queue`，不能只看 fio 汇总值；
5. 预期收益按 3.2 的上界评估：带宽不超过 `+5.05%`，主要收益是稳定性。

当前测试使用 RAM 是为了完成因果确认，不是生产方案。如果没有新增物理盘，不建议在同一 NVMe 上通过目录、分区或两个 loop 做“逻辑分离”，因为底层控制器、队列和介质尾延迟仍然共享。

### 3.5 剩余约 40% 带宽缺口的解决方向

最佳 D1 中位带宽为 `3756.51 MiB/s`，相对目标仍缺 `2493.49 MiB/s`。按 `6250 MiB/s`、`256 KiB` 写入换算，需要约 `25000` 次逻辑写/秒，而当前稳定的元数据提交能力约在 `12K/s` 量级，缺口接近 2 倍，不是局部参数可以填补的幅度。

若必须继续追求 `6250 MiB/s`，应转入架构方案评估：

- 减少每个数据写入触发的同步元数据事务次数，研究批量/合并提交；
- 在保持一致性和顺序语义的前提下，对同 inode 元数据更新做有序流水或并行化；
- 扩展或分片 TiKV 元数据服务，降低单组 TiKV KV/compaction 的共享压力；
- 评估更适合该同步小事务模型的元数据架构或组件。

这意味着 03 阶段的参数调优空间已基本收口：**能够低风险落地的生产优化是有独立盘时分离 WAL/Raft；要补齐剩余约 40% 带宽，必须改变元数据提交或扩展架构。**

## 四、JuiceFS 1.4.1 版本替换评估

当前交付基座是打补丁的 JuiceFS 1.3.1。本周对 1.4.1 是否可以替代它做了前期评估，得到一项明确的版本使用结论。

### 4.1 1.4.1 原版存在同样的随机写缺陷，必须携带补丁

在同一集群、同一挂载参数、同一数据集下对比 1.4.1 原版与 1.4.1 加随机写补丁：

| 版本 | 随机写逐轮 MiB/s | 轮间波动 |
|---|---|---|
| 1.4.1 原版 | `551 / 552 / 551` | `0.10%` |
| 1.4.1 + 随机写补丁 | `2754 / 2726 / 2679` | `1.39%` |

`551 MiB/s` 与上周在 1.3.1 原版上观测到的崩塌值完全一致，说明该缺陷在 1.4.1 中同样存在，并未被上游修复。

该结论的可靠性还有一条独立支撑：1.4.1 原版三轮分别在 `6.33M`、`6.33M` 和 `2.43M` 三个相差 `2.6` 倍的存储池对象数下运行，带宽仍恒为 `551/552/551`。这排除了池状态、缓存状态和测试时段等环境因素，崩塌完全来自代码路径。

**生产含义：若将来升级到 1.4.1，必须同时携带随机写补丁，否则随机写会直接降到约五分之一。**

### 4.2 元数据格式双向兼容，回滚可行

评估过程中 1.3.1 与 1.4.1 在同一生产卷上多次交替挂载，均成功，卷设置未发生不可逆变化。这说明两个版本之间可以双向切换，升级具备回滚条件。该项将在正式判定中作为独立验收门再次确认。

### 4.3 版本替换判定尚未闭合

本周两次全量七项对比均因测试设计问题不能作为正式判定依据：一次因为存储池对象数在测试过程中单向累积，使版本效应与池状态无法分离；另一次因为两个版本各自占据连续时段，纯读项在两个时段之间出现 `5.25%` 的系统性偏差，而版本替换需要分辨的正是 `3%--6%` 量级的差异。

正式判定已另立任务，采用轮级交替顺序把两个版本的时间间隔从小时级压缩到十分钟级，并在矩阵内保留同版本相邻对以直接测出噪声底，使判定边界由实测数据决定而不是预先设定。该判定作为 04 阶段的前置项执行，完成后才决定是否更换交付基座。

## 五、读侧现状与仅剩的集群布局余量

本周工作集中在写侧，此处补充读侧的完整状态，避免用写侧达成率代表整体水平。

| 测试项 | 交付中位 MiB/s | 目标达成率 |
|---|---:|---:|
| 随机读 | `5544` | `88.7%` |
| 多流顺序读 | `5366` | `85.9%` |
| 混合读写（读向） | `1870` | `29.9%` |
| 单流顺序读 | `1449` | `23.2%` |

随机读是并发读的最佳可固化值。进一步分析显示：

- 提高并发后客户端线程、CPU 和 100GbE 均有余量，但 OSD 读操作服务率增长趋缓，单挂载渐近上限约 `6280 MiB/s`，即目标 `6250` 已经是该上限的 `99.5%`；
- 六个 OSD 的主 PG 与操作分布长期固定为约 `6:6:5:6:5:4`，最热与平均之比约 `1.136`；按最热 OSD 约束推算，完全均衡后的理论值约 `6267 MiB/s`，与客户端侧拟合上限相互验证。

因此读侧的结论是：**距离目标只差 PG 布局这一步，且余量刚好够，没有第二处可挖。**继续增加下载并发或客户端线程数已无收益，后续只能通过在隔离测试池上验证更均衡的 PG 分布、或增加 OSD 与调整池布局来推进，不能直接热改当前生产池。

单流顺序读的 `23.2%` 属于架构限制：单请求完成周期决定吞吐，`6250 MiB/s` 在 `256 KiB` 请求下要求约 `41 µs` 的等效周期，而一次跨网往返本身已超过 `200 µs`。

## 六、本周确认无效的调优方向

以下六个方向本周均有正式证据支持“无效”或“不应作为主解法”。它们不提升性能，但明确缩小了后续工作范围，避免继续投入。

| 方向 | 排除依据 |
|---|---|
| 继续提高 `max-uploads` | 带宽最差的后半程上传槽位占用远低于上限（最低降至接近 0），瓶颈在上游供给不足，不是槽位不够 |
| 继续增加活跃 inode 数 | 128 到 256 的实测增益仅 `10%--13%`，远低于理想 2 倍；继续增加只会更快建立 TiKV 写压力 |
| 增加 compaction worker | worker 单线程 CPU 占用最高仅约 `12%`，且在带宽最差窗口反而下降；增加 worker 只会把更多后台 I/O 送入同一设备 |
| 对 compaction 限速或暂停 | 会把债务推迟到后续窗口，制造短时高值和更大的后续波动，不构成稳定收益 |
| 同一物理盘上的逻辑分离 | 目录、分区、双 loop 三种形式均无材料收益，底层控制器、队列与介质尾延迟仍共享 |
| 通过主动清理消除波动 | 每个 arm 均为全新状态起点，轮内仍会重新建立 compaction 债务 |

此外，三节点 RocksDB 硬写停顿全程为 0、L0 文件数低于触发阈值、限速器未生效，说明当前不存在“调高某个 RocksDB 阈值即可解决”的入口。

### 7.2 为保证结论可信完成的测试工程

本周建立了一套可复用的隔离测试与证据校验链，用于避免重新铺数据、旧状态残留和对象累积制造假收益，并已在本周的正式结论中生效。

其中三项已固化为后续同类测试的强制要求：以实际 I/O 起点而不是进程启动时刻划分统计窗口；证据完整性门与性能稳定性指标分离，不因结果不佳删除完整样本；多臂实验采用平衡顺序与同轮配对，禁止跨时段直接相减。本周有两个探索性矩阵因触及上述要求而按无效处理并完成资源清理，没有把不完整数据包装成正式结论，最终以完整重跑签收正式效应量。
