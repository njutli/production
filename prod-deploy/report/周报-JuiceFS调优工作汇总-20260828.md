# 周报-JuiceFS调优工作汇总-20260828

## 0、进展概要

本周围绕上周遗留的“元数据引擎为什么会从快态进入慢态”和“剩余随机写瓶颈能否解决”两个问题，完成了从客户端 inode 队列、TiKV 同步事务、RocksDB compaction、物理 NVMe 到 WAL/Raft 隔离的完整归因闭环。

本周最值得体现的生产结论是：**将 TiKV WAL/Raft 与 KV/compaction 的物理 I/O 路径分离，能够明确改善随机写稳定性，并带来小幅带宽收益。**正式 4 组配对全部同向，256-inode randwrite 中位带宽由 `3607.63 MiB/s` 提升至 `3756.51 MiB/s`，配对中位收益 `+5.05%`；逐秒带宽 CV 配对中位改善 `2.36` 个百分点，`W4/W1` 配对中位改善 `0.0694`。

该收益目前不能直接固化到生产：验证臂把 WAL/Raft 放在 RAM backing 上，不具备持久化条件；现有三台 TiKV 节点也没有对称空闲 NVMe。其生产意义是：**后续如能为三台 TiKV 各提供一块独立、持久、低延迟的空闲盘，应优先考虑把 WAL/Raft 与 KV 分离，并以同口径 A/B 验证后上线。**不能用同一 NVMe 上的目录、分区或 loop 代替真实物理隔离。

同时，本周确认 WAL/Raft 隔离不是剩余吞吐缺口的完整答案：最佳 D1 方案中位带宽仍只有 `3756.51 MiB/s`，达到 `6250 MiB/s` 目标的 `60.10%`，仍差 `2493.49 MiB/s`。剩余瓶颈已经收窄到 JuiceFS 按 inode 串行完成的同步元数据事务，以及 TiKV KV/compaction 的共享服务率，后续需要走事务批量化/异步化、inode 并行模型调整或元数据层扩展等架构路径，而不是继续扫描局部参数。

## 1、JuiceFS 方案完成元数据引擎波动原因定位

### 1.1 上周遗留问题

上周已经观察到随机写性能随元数据 `Write` 延迟从约 `138 ms` 上升至约 `187 ms` 而下降，但当时只能确认退化位于元数据引擎侧，尚不清楚是跨日 TiKV RocksDB 状态积累、单次事务延迟变化，还是运行中的共享资源竞争造成。

本周按“客户端排队 → TiKV 事务 → compaction → 物理设备 → 存储隔离”的顺序完成递进定位，没有直接通过修改参数猜测原因。

### 1.2 客户端逻辑延迟与 TiKV 事务周期拆分

- 客户端观测到约 `186--201 ms` 的 meta `Write` 不是一次 TiKV 请求的服务时间，而是包含同 inode 前序请求等待的端到端时间。
- JuiceFS 同一 inode 内的 meta `Write` 受 open-file lock 串行约束；实际 TiKV 同步事务周期约为 `10--13 ms`，客户端深队列把该周期放大为约 `190 ms` 的逻辑延迟。
- 128 个活跃 inode 时，随机写首先受“每 inode 串行通道数 × 同步事务周期”约束；增加到 256 inode 后，收益很快被 TiKV 共享服务率限制，不能继续按 inode 数线性扩展。

### 1.3 轮内波动的直接机制

256-inode randwrite 在每轮开始前 pending compaction 可以接近 0，但负载启动后会在本轮重新建立 compaction debt。后续正式对照中，三节点 TiKV 的 pending compaction 到 W4 均增长至约 `11--16 GiB`；共享盘控制臂 B1c 的 Raft sync 延迟由 W1 的约 `0.22--0.23 ms` 上升到 W4 的约 `0.74--0.80 ms`，同时物理 NVMe `w_await` 和带宽低谷共同增大。

三节点 RocksDB hard write-stall 全程为 0，因此这不是达到硬阈值后的停写，而是以下软排队链：

```text
按 inode 串行的同步元数据事务持续进入 TiKV
        ↓
前台 KV/WAL/Raft 写与后台 compaction 共用服务能力
        ↓
pending compaction、设备队列和同步提交延迟在轮内积累
        ↓
客户端可完成的元数据事务减少，上传管线供给下降
        ↓
随机写后段出现低谷，CV 上升
```

### 1.4 对“跨日状态积累”和主动清理的结论

每个正式 arm 都使用 fresh TiKV、fresh 本地文件系统和相同 immutable seed，仍然重复出现本轮内的 pending compaction 增长。因此：

1. 跨日 RocksDB 状态和历史介质起点会影响一轮开始时的性能水平，但不是轮内波动成立的必要条件；
2. 主动清理可以统一测试起点、消除跨轮污染，却不能阻止高强度 randwrite 在本轮重新建立 compaction debt；
3. 原先“通过清理即可消除元数据引擎波动”的方向可以关闭，稳定性优化必须处理同步日志与 KV/compaction 的共享延迟路径。

至此，上周遗留的“元数据引擎双态/波动原因”已从环境现象收敛为可重复的运行时机制。

## 2、JuiceFS 方案完成剩余瓶颈分析及解决路径收口

### 2.1 WAL/Raft 与 KV 分离的正式验证

最终 03-22c 使用同一 fresh 临时 TiKV、同一 seed、相同 KV 文件系统、相同配置和相同 256-inode 负载，只改变 WAL/Raft backing 的底层介质：

| 测试臂 | KV | WAL/Raft | 含义 |
|---|---|---|---|
| B1c | NVMe | 与 KV 共用同一物理 NVMe | 共享盘控制臂 |
| D1 | 与 B1c 相同的 NVMe | RAM backing | 移除日志介质延迟及其与 KV 的共享盘竞争 |

正式顺序采用 8 个 arm、4 组相邻配对，避免时间漂移被误判成调优收益。结果如下：

| 指标 | B1c / 分离前 | D1 / 分离后 | 正式结论 |
|---|---:|---:|---|
| 四臂中位带宽 | `3607.63 MiB/s` | `3756.51 MiB/s` | 4/4 配对提高，配对中位 `+5.05%` |
| 逐秒带宽 CV | 个别 arm 达 `12.19%` | 4 个 arm 均为 `6.30%--7.55%` | 4/4 改善，配对中位改善 `2.36 pp` |
| `W4/W1` | 最低 `0.810` | `0.946--0.994` | 4/4 改善，配对中位提高 `0.0694` |
| Raft sync | W1 约 `0.22--0.23 ms`，W4 约 `0.74--0.80 ms` | W1/W4 均约 `0.074--0.083 ms` | 同步日志尾延迟得到稳定 |
| 6250 目标达成率 | `57.72%` | `60.10%` | 均未达标 |

正式结论是：**WAL/Raft 与 KV/compaction 共用物理盘是尾部波动的放大因素；分离后稳定性收益明确，带宽收益存在但幅度有限。**带宽 `+5.05%` 没有达到预注册的 `15%` 材料收益门，不能把日志盘描述为平均吞吐的主瓶颈。

### 2.2 为什么分离改善稳定性，但不能解决全部吞吐

D1 中 WAL/Raft 的 Raft sync 延迟保持稳定，但 KV 侧 pending compaction 仍增长到 `11--16 GiB`，KV 所在物理 NVMe 的 `w_await` 也没有消失。这说明分离保护了延迟敏感的同步日志路径，使 compaction 高压时不再同时放大 Raft 提交尾延迟；但它没有提高 KV/compaction 的根本消化能力，也没有改变 JuiceFS 每 inode 同步提交的事务模型。

因此当前瓶颈应分为两层：

1. **可通过设备隔离改善的稳定性因素**：WAL/Raft 与 KV/compaction 共用物理盘；
2. **设备隔离后仍存在的吞吐主墙**：按 inode 串行的同步元数据事务，以及 TiKV KV/compaction 的共享服务率。

### 2.3 对生产环境的建议

如后续具备三节点对称空闲盘，建议：

1. 每个 TiKV 节点为 WAL/Raft 提供独立、持久、低尾延迟设备，KV SST/compaction 继续使用原设备；
2. 三节点同时采用相同拓扑，避免只有部分 Raft quorum 获得低延迟路径；
3. 迁移前设计精确的备份、回滚和磁盘容量门，以生产等价介质重新做共享盘/独立盘 A/B；
4. 验收同时观察带宽、CV、`W4/W1`、Raft sync、KV pending compaction 和两类设备的 `await/queue`，不能只看 fio 汇总值。

当前测试使用 RAM 是为了完成因果确认，不是生产方案；实际第二块 NVMe 的收益方向有证据支持，但不能直接承诺等于本次 `+5.05%`。如果没有新增物理盘，不建议在同一 NVMe 上通过目录、分区或两个 loop 做“逻辑分离”，因为底层控制器、队列和介质尾延迟仍然共享。

### 2.4 剩余约 40% 带宽缺口的解决方向

最佳 D1 中位带宽为 `3756.51 MiB/s`，相对目标仍缺 `2493.49 MiB/s`。本周测试已经排除以下方向作为主要解法：继续提高 `max-uploads`、继续增加 inode、增加 compaction worker、主动清理、同盘逻辑分区以及只隔离 WAL/Raft。

若必须继续追求 `6250 MiB/s`，应转入架构方案评估：

- 减少每个数据写入触发的同步元数据事务次数，研究批量/合并提交；
- 在保持一致性和顺序语义的前提下，对同 inode 元数据更新做有序流水或并行化；
- 扩展或分片 TiKV 元数据服务，降低单组 TiKV KV/compaction 的共享压力；
- 评估更适合该同步小事务模型的元数据架构或组件。

这意味着 03 阶段的参数调优空间已基本收口：**能够低风险落地的生产优化是有独立盘时分离 WAL/Raft；要补齐剩余约 40% 带宽，必须改变元数据提交或扩展架构。**

- 建立一次 immutable seed，后续每个 arm 从同一 metadata dump 恢复并 clone，避免重复 layout；

- 正式 03-22c 保存 256 份 fio 带宽日志、三节点 TiKV/iostat、6 个 OSD 指标及完整执行授权记录；归档内 `9973` 项 SHA-256 全部通过。
