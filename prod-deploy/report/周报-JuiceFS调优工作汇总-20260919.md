## 2、有方 BS 曲线的断层分析

### 2.1 现象

聚合带宽（读+写，MiB/s；JuiceFS 取 B256/FUSE256K/buffer300 同配置系列，有方取 12 格 sweep 正式窗）：

| BS | JuiceFS | ×倍 | 有方 | ×倍 | 有方/JFS |
|---|---:|---:|---:|---:|---:|
| 4K | 42.4 | — | 62.6 | — | 1.48 |
| 16K | 175.1 | ×4.13 | 257.5 | ×4.12 | 1.47 |
| 64K | 990.4 | ×5.66 | 807.6 | ×3.14 | **0.82** |
| 256K | 3462.8 | ×3.50 | 3640.7 | ×4.51 | 1.05 |
| 1M | 3290.0 | **×0.95** | 28802.0 | **×7.91** | **8.75** |
| 4M | 4200.4 | ×1.28 | 29258.2 | ×1.02 | 6.97 |

两点：**≤256K 全程两家同量级（0.82×–1.48×）且互有胜负**；**一个 BS 台阶内比值从 1.05 跳到 8.75，且有方 ×7.91 是超线性**（BS 只 ×4）。

判据核心：`×4` 的输入只能给出 `≤×4` 的线性响应；出现 `×7.91` 说明接入了新资源，**即路径变了**。真实的架构能力差异不会在整个 ≤256K 区间隐身、再在某一个块大小边界上不连续出现 7–9 倍。

### 2.2 ≤256K 两边都线性的原因

同一个**形式**：都受 ops/s 限制而非 bytes/s 限制。
- 有方 ops/s 在 4K–256K 稳定 `13k–18k`（按 `QD16384/clat` 反推与实测 ops 一致，误差 2% 内）。
- JuiceFS 实测到具体限流器：4K 格元数据事务在途 `74–92`（贴 ~128 inode 串行上限）、读写放大 `8.2×`、`uploading` p95 仅 42、buffer 仅用 10.8 MiB ⇒ **上传槽未参与，瓶颈在元数据事务速率**。

⚠️ 形式相同但限流器不同，不可读成"同因"。有方的具体限流器我方未测。

### 2.3 JuiceFS 恰在 256K 之后走平的原因（实测，非推断）

`put_avg_size_KiB = 256.0`（精确值）—— **256 KiB 就是该卷的对象块大小**。于是：

- BS ≤ 256K：一次应用 I/O ≤ 1 个对象，加大 BS 即加大对象 ⇒ 带宽涨。
- BS > 256K：**加大 BS 不再改变对象大小，只增加每请求的对象个数**（1M=4 PUT，4M=16 PUT）；对象完成率钉住（§1.2 的 6.25% 极差）⇒ 字节率不变。
- `≈9000 ops/s × 256 KiB ≈ 2.2 GB/s` 即平台线，与实测 `2.0–2.2 GB/s` 吻合。

**拐点落在 BS = 块大小不是巧合，是格式化参数。** 旁证：改对象大小有限有效（B1M `2593–2614`，×1.5；B4M `2226`）；改并发无效（05-2）。

### 2.4 有方跳一个数量级：三条证据指向"不再测持久化写路径"

**证据 A —— 那条 ~29 GB/s 的顶，它自己在 256K 纯读上就已摸到：**

| 工况 | 聚合 |
|---|---:|
| 有方 randread @256K（纯读） | 29,010 MiB/s |
| 有方 randrw @1M | 28,802 MiB/s |
| 有方 randrw @4M | 29,258 MiB/s |

三个不同工况落在同一顶，且纯读在 256K 即可达到 ⇒ 它是读/内存路径的顶，**不是被大块解锁的新能力**。

**证据 B —— >256K 的 randrw 写侧超过它自己最好的专用写：**

| 工况 | 写带宽 |
|---|---:|
| randrw @4M 写侧（本轮） | **14,629 MiB/s** |
| 它自己 mseqwrite @4M（16 流、`direct=1`、`end_fsync=1`） | 13,210 MiB/s |
| 它自己 randwrite @256K | 2,744 MiB/s |

50/50 随机混合写得比纯多流顺序写还快，对持久化写路径不成立。

**证据 C —— 拐点位置对应负载几何，不对应任何存储参数：**

每 job 在途窗口 `iodepth × bs` 对 1 GiB 文件的占比：

```
4K 0.05%  16K 0.20%  64K 0.78%  256K 3.12%  |  1M 12.50%  4M 50.00%
                                             ↑ 拐点在此
```

fio randrw 对同一文件同时读写。一旦两位数百分比落在在途窗口内，读的一半大量命中写的一半刚产生的数据 ⇒ 可由客户端内存直接供给。**跳变正好在该比值穿过 ~10% 处**；存储设备与网络在这个位置没有拐点，客户端缓存有。

**量级反证**：我方客户端 100GbE 单向理论 `≈11,900 MiB/s`（05-1b 实测峰值 `3,220 MiB/s`，占 27%）。有方 4M **单向**写 `14,629 MiB/s` 已超 100GbE 线速，双向 29 GB/s = 234 Gbps。若其客户端同为 100GbE 级别，则 ≥1M 的数字不可能在过网络。

### 2.5 保留的另一种良性解释

**H-array：hpfs 前端就是一组大号本地 NVMe。** 20T 容量、GPU 节点、scratch 文件系统，8 片 PCIe4 NVMe 裸带宽 ~50 GB/s，29 GB/s 可由器件提供，无需缓存。因 D4 缺口（`MemTotal`/CPU/NIC/缓存配置全无记录）**无法排除**。

两种解释导向同一结论：**≥1M 的 7–9 倍不是 JuiceFS 软件层面的差距，而是"本地 NVMe 阵列 / 客户端缓存"对"6-OSD Ceph + 100GbE"的架构与状态差距。**

### 2.6 该结论已永久无法验证 —— 处置变更

原计划向有方补测三项（≥1M 纯 randwrite、>180 s 长窗、后端字节计数）以判定 A/B/C 三条证据。**对方环境不再可用，该路径关闭。**

因此：

1. **≥1M 对比行永久标记 `NOT_COMPARABLE`**，不是"证据待补"。不得写"我们慢 7 倍"，也不得写"对方数不实"。只保留 §2.1 区间与 §2.4 三条观测，并附 §2.5 两种未排除解释。
2. **05-6"导入有方数据"的口径需改写**：只能导入已归档的 12 格 sweep（`MATRIX_DRIFTED / VALID_RANGE_ONLY`，SHA256 `7b805c24…`）与七项数据，且七项运行的主机名**未记录**，归到 `c2-gpu-node4` 仍是 `推断`。
3. **几何假设（证据 C）可以在我方环境自证**：固定 BS、只改 filesize/iodepth 使 `iodepth×bs/filesize` 扫过 3% → 12.5% → 50%，在缓存开启下看我方是否也出现同样的跳变。这是唯一还能做的验证，且成本低。⚠️ 改 filesize/iodepth 违反冻结负载合同，必须作**诊断 RUN**单独标记、不进对比矩阵（先例：05-1b `20260914-221613`）。

## 3、JuiceFS 1.4 源码调查：randrw 为何吃不到缓存

源码：`/mnt/c/SunRise/github/juicefs`，`v1.4.0-dev-467-g44dd412a`。

### 3.1 M1｜每次 read 强制 flush 整个 inode 的写缓冲（主因，不可配置）

`pkg/vfs/vfs.go:787`，在 `reader.Read` 之前无条件执行：

```go
_ = v.writer.Flush(ctx, ino)      // 全 inode，非 range
n, err = h.reader.Read(ctx, off, buf)
```

`fileWriter.flush()`（`pkg/vfs/writer.go:386`）**持有整个 fileWriter 锁**，并遍历该文件**所有** chunk/slice 等其全部完成：

```go
f.Lock()
for len(f.chunks) > 0 && err == 0 {
    for _, c := range f.chunks {        // 全部 chunk
        for _, s := range c.slices { s.freezed = true; go s.flushData() }
    }
    f.flushcond.WaitWithTimeout(time.Second*3)
}
```

而"完成"在非 writeback 模式下 = **对象 PUT 返回**（`pkg/chunk/cached_store.go:400`，`s.store.currentUpload <- struct{}{}` 即 `--max-uploads` 信号量，完成信号在 PUT 之后才发出）。

`meta.ChunkSize = 64 MiB`（`pkg/meta/interface.go:41`），1 GiB 文件 = 16 chunk，随机写散布全部 16 个，一次 ≤1 MiB 的读只碰 1 个。

⇒ **randrw 读延迟由"等对象 PUT"支配，不由"取读数据"支配；读缓存命中率再高也移不掉这段等待。** randread 无写 ⇒ flush 空操作 ⇒ 缓存收益全额释放。**这就是"randread 提升明显、randrw 基本无提升"的根因。**

**顺带闭合 05-2**：flush 一次性 freeze 所有 slice 并并发拉起上传，形成突发而非平滑流水；128 文件同时如此 ⇒ `currentUpload` 打满 ⇒ 在途量钉在 150。放到 300 后 mean 只到 193.87、延迟 +25.28%、吞吐 +1.62%。**05-2 的"膝点"在代码里就是这个 flush 突发模式撞上已到完成率上限的后端。**

### 3.2 M2｜新写的整块默认不进读缓存

`pkg/chunk/cached_store.go:368`：

```go
if sync && (blen < store.conf.BlockSize || store.conf.CacheLargeWrite) {
    store.bcache.cache(key, block, false, false)
}
```

`--cache-large-write`（`cmd/flags.go:259`，BoolFlag）**默认 false** ⇒ 满 256 KiB 块上传后不入读缓存。randrw 读的正是自己刚写的文件 ⇒ 结构性 miss。

**⚠️ 重要限定（后续修正）：该条仅在非 writeback 模式成立**，见 §3.5。

### 3.3 M3｜slice 级 COW，覆盖写不失效旧缓存块，只让它变垃圾

`flushData` 中 `prepareID` 取新 slice ID ⇒ 新 object key ⇒ 从不原地修改。旧 key 的缓存块不被标记失效，但再也读不到，只占容量等淘汰。**与 M2 叠加：旧块变垃圾、新块不入缓存 ⇒ randrw 下读缓存对"当前数据"的命中率单调衰减。** 与 0912 周报 line 64–66 的观察一致。

### 3.4 M4｜`cache-size=0` 连带强制关掉 writeback 与 prefetch

`Config.SelfCheck`：

```go
if !c.CacheEnabled() {
    logger.Warnf("cache-size is 0, writeback and prefetch will be disabled")
    c.Writeback = false; c.Prefetch = 0
}
```

05-1 / 05-1b / 05-2 全程 `cache-size=0` ⇒ **无读缓存、无 writeback、无 prefetch**，最保守配置。代码确认，非推断。

### 3.5 writeback 模式下暂存块会被硬链接进读缓存（关键，推翻 M2 的适用范围）

`pkg/chunk/disk_cache.go:773` `stage()`：

```go
err := cache.flushPage(stagingPath, data, false, tierID)   // 写 rawstaging/
if err == nil && cache.enabled() {
    path := cache.cachePath(key)
    os.Link(stagingPath, path)                  // ← 硬链接进读缓存 raw/
    cache.add(key, -int32(len(data)), ...)      // 负 size 标记"已暂存未上传"
}
```

⇒ **writeback 模式下，暂存块立即在读缓存中注册并本地可读；M2 自动消失，无需 `--cache-large-write`。** 因此 `--cache-large-write` 从"首选杠杆"降级为"仅非 writeback 模式下需要"。

### 3.6 读路径与写路径在结构上互不可见

`grep -cE 'writer|Writer' pkg/vfs/reader.go` = **0**。`dataReader` 字段只有 `m meta.Meta` 与 `store chunk.ChunkStore`。

数据变可读的顺序是硬的（`pkg/vfs/writer.go:186` `chunkWriter.commitThread`）：

```
flushData() → writer.Finish()  // 等对象 PUT 完成
  → s.done → f.w.m.Write(...)  // 才提交 slice 到元数据引擎
  → f.w.reader.Invalidate(...) // 才对读路径可见
```

且**按创建顺序 FIFO 提交**（`s := c.slices[0]`，外加 `for s.dep != nil && !s.dep.committed`）⇒ 同一 chunk 内一个慢 PUT **队头阻塞**其后所有 slice 的提交。

## 4、M1 的性质辨析：不是多客户端一致性，不能删

本周一个重要纠错。

**M1 不是为跨客户端一致性设计的。** 依据：flush 的是**本客户端自己**的写缓冲，这对其他客户端的读毫无帮助；而 §3.6 证明读路径在结构上看不见写缓冲。⇒ **M1 的作用是让单客户端、甚至单进程能读回自己刚写的数据，是 POSIX 强制语义，只有一个客户端时也必须有。**

⇒ 因此"我们场景不需要跨客户端一致，可以删掉 M1"的思路**不成立**：删掉会给我们自己的负载引入读到旧数据/空洞的正确性 bug（fio randrw 本身就在同 offset 上先写后读）。**该方向否掉。**

**三层缓存关系（澄清 COW 与 page cache 的区别）：**

| 层 | 内容 | 读回自己刚写的数据 |
|---|---|---|
| L1 内核 page cache（FUSE） | 缓冲 I/O 的页 | **由内核满足，不下到 JuiceFS** |
| L2 JuiceFS 写缓冲（`buffer-size`，RAM） | 未提交 slice | **看不见**（§3.6） |
| L3 元数据 slice + 对象/本地缓存 | 已提交数据 | 仅 `upload→m.Write→Invalidate` 之后 |

JuiceFS 是 COW/log-structured、不原地改（§3.3），这与 Linux page cache 的原地语义不同；但"立刻回读会读到旧数据"**当前不会发生**，正因为有 M1。

**安全的改法：把 whole-inode flush 改为 range-scoped。**

- 语义**完全等价**，read-your-own-writes 一字不差保留
- `f.chunks` 本就是按 chunk index 的 map，改动约 30–40 行
- 1 GiB 文件下 flush 范围从 16/16 chunk 降到 ~1/16
- **可上游化**：小、语义等价、有测量支撑，是上游会认真看的那类
- 即使不合并，**社区 review 记录本身就把"私有分叉"降级为"已知且被第三方检视过的差异"**，是有效的维护风险对冲
- 我方本已维护 patched 构建（`/tmp/juicefs-1.4.1-patched`，MD5 `24fae0852051c80ca571cb2f20275d46`），增量成本低

提交上游时应带：range-scoped 前后 randrw A/B、语义不变回归（写后立即读同 offset 校验）、M1 的 profile 证据。

## 5、一致性轴与持久性轴要分开（对有方机制的判断修正）

一个易混的点：**"从自己的脏缓存供自己的读"与"强跨客户端一致"可以同时成立**，前提是客户端持有该 extent 的锁/租约且服务端能回收（callback/revocation）。Lustre 的 LDLM、GPFS token manager、WekaFS、NFSv4 delegation 都如此。**那是更多机制，不是更少保证。**

JuiceFS 恰恰**没有**文件数据的 DLM / 缓存回收协议 ⇒ 没有"别人要这个区间了"的通知通道 ⇒ 唯一安全设计就是"本地绝不保留可读但未提交的状态" ⇒ 必须 flush。**M1 是 JuiceFS 架构更简单的代价，不是它保证更强的产物。** 这条限制无法通过我方小改弥补。

因此对有方的机制判断修正为：

| 轴 | 有方 | 我方 |
|---|---|---|
| 一致性 / 缓存一致 | **可能更强**（锁/租约驱动的客户端脏数据缓存） | 无 DLM，只能 flush-on-read |
| 持久性 | **很可能妥协**（ack 先于持久化；证据见 §2.4 A/B） | 非 writeback 模式下严格持久化 |

即：有方让掉的**很可能是持久性，不是一致性**；而这两者正交。

## 6、天花板算术：三层修订（含本周自我纠错）

### 6.1 持久化模式（`cache-size=0`）：⛔ 原"已达上限 95%--100%"结论已撤销

**成立的部分**：fio randrw 50/50 **按发起数强制读写比例**（实测 READ `2015.89` vs WRITE `2012.15`，差 0.19%），故恒等式成立：

```
randrw 聚合 ≈ 2 × 应用写速率
```

**⛔ 已撤销的错误论证（GPT 评审 §二.1，属循环计算）**：此前用"05-2 最好格 C2 的应用写 `2120.09 MiB/s` × 2 = `4240.18 MiB/s`"当作架构上限，再拿同轮实测与它比得出"达成 `95.0%--100.1%`"。**该"上限"直接来自被评价样本自身**，命题退化为"最差格与最好格相差 5%"，只是**离散度**，不能证明该模式已达不可突破的上限。

**准确结论**：05-2 的正式裁决是 `RESOLUTION_INSUFFICIENT / SCREEN_CONTINUE=FAIL` —— U300 未形成一致收益，当前没有继续扫描上传并发的依据；⛔ 但不得把现有带宽定义为架构上限。

**替代的独立证据（非循环，来自 04-tmp3j 直接 RADOS，绕过 TiKV/FUSE）**：

| 口径 | 值 |
|---|---:|
| 直接 RADOS 256 KiB 写 QD32 / QD64 / QD128 | `3271` / `3660` / **`3949 MiB/s`**（**未饱和**） |
| JuiceFS 在 05-2 randrw 中达成的对象 PUT 字节吞吐 | `2177 -- 2275 MiB/s` |

⇒ **直接 RADOS 只证明 PUT 没有在 `2.2 GiB/s` 处形成独立的**纯写**硬上限；randrw 的剩余约束**可能位于客户端路径，也可能来自 GET/PUT 混合服务关系**，需 06 阶段继续区分。** 这条把「该模式无空间」这一错误结论替换为一个**待区分的开放问题**（⛔ 不是替换成「瓶颈已定位在客户端」），因而**加强** 06 阶段的立项。

⚠️ 必带限定（⛔ 不得省略）：① 04-tmp3j 是**纯写、无并发 GET**，而 05-2 中后端同时承担约 `2.0 GB/s` GET、对象层总量约 `4.2 GB/s`，已接近 RADOS 纯写的 `3.95 GB/s`；② 04-tmp3j 自述 `3948.86 MiB/s`"只是本次最高观测点，不得写成 Ceph 写服务的最终上限"；③ ⇒ 只能得出"后端未在 2.2 GB/s 硬封顶"，⛔ **不得推出"PUT 可达 3.9 GB/s"**。

**一条探索性假设（⛔ 不作预设结论，GPT 评审 §二.8）**：GET `≈8064 ops/s` + PUT `≈8711 ops/s` ≈ `16.8k object ops/s`；若读改由本地供给使 GET 预算释放，PUT 可能上升（乐观 `×1.9`）。限定：该数只是**某一轮混合负载的观测和**，不是独立测得的对象层容量；B1M 字节吞吐更高也不能单独证明 B256 受固定 op 预算限制（BS/对象大小/放大/队列形态均已变）；且 **writeback 下前台与后台已解耦**，"前台涨而 PUT 不变"既可能是积压增加也可能是读路径改善，**无法直接区分**。⇒ `16.8k`/`×1.9` 只作探索性预测，验证须用同 RUN、同基座的 **paired U150/U300**。

### 6.2 缓存 + writeback 模式：⛔ 原"只用到本地能力 4%"口径已撤销

**⛔ 已撤销的错误口径（GPT 评审 §二.2）**：此前用 `1393.98 MiB/s ÷ 34.83 GiB/s ≈ 4%` 表述"只利用了本地能力的 4%"。该比较有**双重错配** —— 分子是 randrw 的**单方向**均值（聚合约 `2788 MiB/s`），分母是热缓存下的**纯 mseqread/randread** 结果。

**可成立的定性表述**：热数据完整容纳时多流顺序读/随机读实测 `34.83 / 36.53 GiB/s`（0912 周报 §3.4.2），**只能证明客户端本地读缓存路径本身具备充足读能力**。M2'（`disk_cache.go:773` 暂存块 `os.Link` 进读缓存）说明 writeback 下刚写的块天然本地可读。

**⛔ 不可成立的表述**：⛔ "randrw 只利用了 4% 的缓存能力"；⛔ "cache+writeback 的上限就是本地介质带宽"。
理由：randrw 混合路径还包含本地缓存读、staging 写、元数据提交、后台对象上传、FUSE、CPU、锁等待与远端未命中读取，**纯读结果不构成 randrw 的上限**。

**现状唯一数据点**：读缓存+writeback randrw `1393.98 MiB/s`（单方向均值，聚合约 `2788`），相对无缓存 **−16.88%**，排空 `57 s`，且该格 `cache-size` **仅为热集 25%**。

⇒ **缓存模式对 randrw 的上限目前未知，需在容量与本地并行度改善后重测（06-1）**；⛔ 不预设结论、⛔ 不预告幅度。

−16.88% 的四条**候选**原因（⚠️ 均为候选，未逐项实测归因）：

1. **同盘竞争（不可通过分盘消除，机制已核实）** —— `cachePath = cache.dir/raw/key`、`stagePath = cache.dir/rawstaging/key`（`disk_cache.go:718/722`），两者**必然同盘**；且 §3.5 的 `os.Link` 硬链接优化**要求同一文件系统**，所以"读缓存与 staging 分盘"**在设计上不可实现**。可做的是把 `--cache-dir` 配成**多路径跨多块设备**：每块盘各自持有 `raw/`+`rawstaging/`，块按一致性哈希（`consistenthash.New(100, murmur3.Sum32)`）分布，`dirCacheSize = CacheSize / len(dirs)` ⇒ **提高本地并行能力的候选配置**，是唯一的配置手段。⚠️ 但源码只证"同属一个 cache store"，**未实测**原测试的本地盘是否在带宽/IOPS/时延上饱和 ⇒ ⛔ 不得称"已核实混杂"，须用 iostat 补证。
2. **缓存容量只给了 25%，但机制不是 `stageFull`** —— `stageFull = 设备可用空间比 < free-space-ratio/2`（默认 `<5%`，`disk_cache.go:344`），**与 `--cache-size` 无关**。小 `cache-size` 的真实后果是读缓存命中率低（实测 25.71%）与淘汰压力大。**静默回落同步 PUT 只在 `stage()` 出错（`stageFull` / `errStageConcurrency` / 超时）时发生（`cached_store.go:441` 之后），小 `cache-size` 不直接导致。**
3. **`--upload-delay` 默认 `0s`** ⇒ 暂存刚完成即内联发起上传并占用 `currentUpload` 槽（`cached_store.go:443`），本地盘 / 网络 / 读缓存三者同抢。
4. **M1 仍是全 inode 且持 `f.Lock()`** ⇒ 即使 flush 降到本地盘延迟，对写侧的锁串行仍在。

⇒ 结论：**那个 −16.88% 不足以证明"writeback 对 randrw 无效"**（配置存在已识别的容量与本地并行度缺陷）；但同样⛔ **不得据此预言修正后必然为正**。06-1 以**组合包**筛选给出答案，且其结果⛔ 不可归因到单项。

### 6.2.1 暂存块在缓存中的记账与淘汰（补充核实）

- `add()` 中 `if size > 0 { cache.used += ... }` ⇒ **暂存块以 `size<0` 记录，不占 `--cache-size` 预算**。
- `cleanupExpire()` 遇 `v.size < 0` 直接 `continue // staging` ⇒ **过期淘汰不会淘汰未上传的暂存块**。
- 即使 `raw/` 侧条目被淘汰，`rawstaging/` 的硬链接仍在 ⇒ 淘汰不会破坏暂存数据的持久化路径。
- ⚠️ `stagedBlockCooldown = CacheExpire / 2`，暂存块入读缓存时 atime 被**人为回拨**（`time.Now().Add(-stagedBlockCooldown)`）⇒ 淘汰时优先被清。但 `--cache-expire` 默认 `0s`（永不过期）⇒ 回拨量为 0，默认配置下该效应不存在。**推论：randrw 场景下不应设置 `--cache-expire`**，否则刚写的块会被优先逐出读缓存。

### 6.3 长期稳态

writeback 是**突发吸收**，不是稳态吞吐 —— 排空 57 s 即证据；0912 周报 line 132 已述"缓存容量增加只能吸收更多暂存数据，不能提高长期持久化服务率"。

- ⚠️ 稳态排空率的**保证值未知**：05-2 观测到的 `≈2.2 GB/s` 来自 `cache-size=0` 配置，**不是 writeback 配置下的保证值**，⛔ 不得直接用于 writeback 场景的容量估算。空间门须改用既有 writeback 实测的保守下界（04-tmp2f 脏峰值 `≈53 GiB`）、按**每个 cache-dir 设备最坏偏斜**分别过门、单位统一 **GiB**。
- 数量级示意（仅示意，⛔ 不作判据）：若以 `14 GiB/s` 写 180 s 而排空按 `2.2 GiB/s` 计，需净暂存约 `2.1 TiB`，不可行。
- **我方吸收介质只能是盘、不能是内存**：`SelfCheck` 明确 `writeback is not supported in memory cache mode`。有方那 29 GB/s 更像 RAM ⇒ 即便"双方都用本地缓存"，**介质仍不对等**（除非把多块 NVMe 拼进 `cache-dir`）。
- 有方是否能长期维持 14 GB/s **已无法验证**（§2.6）。其 1M 的 `W4/W1 = 1.04–1.11` 只说明 180 s 内不衰减。

|---|---|---|---|
| 持久化（`cache-size=0`） | **未知**。⛔ 原 `4240 MiB/s` 为循环计算已撤销；独立证据（04-tmp3j 直接 RADOS `3949 MiB/s` 未饱和）表明后端未硬封顶 | 对象 PUT `2177--2275 MiB/s` | 无继续扫上传并发的依据；但⛔ 不得称"无空间" |

## 7、对外口径修正

### 7.1 `direct=1` 那条免责作废（本周纠错）

原拟免责"`direct=1` 绕过 L1 页缓存、双方缓存配置与介质不对等"。核查 `pkg/fuse/fuse.go:250`：JuiceFS **只对内部特殊节点**设 `FOPEN_DIRECT_IO`，普通文件走 `FOPEN_KEEP_CACHE` / `InodeNotify`。

| 说法 | 判定 |
|---|---|
| `direct=1` 双方对称、都绕过内核页缓存 | ✅ 成立 ⇒ **不能作为公平性免责** |
| `direct=1` 会关掉守护进程自身用户态缓存 | ❌ 不会，它只管内核页缓存 |
| 我方客户端缓存被什么关掉 | **`cache-size=0` 这个配置**（并连带关 writeback/prefetch），**不是 `direct=1`** |

⇒ **正确且唯一的公平性免责，责任在我方配置**："双方都用 `direct=1` 绕过内核页缓存；该标志在两侧均不禁用守护进程自身缓存。我方用户态缓存是被 `cache-size=0` 显式关闭的，对方用户态缓存状态未记录（D4）。"

⇒ `direct=1` 那个观察另有一个**成立**的用途，但只针对我方数、与有方无关：**因绕过 L1，每次读都下到 FUSE 从而触发 M1；真实应用走缓冲 I/O 时 L1 吸收大部分"读回刚写数据"，M1 触发频率低得多 ⇒ 该 randrw 数不可外推到缓冲 I/O 应用。**

## 10、06阶段执行收口与独立审计订正（最终口径）

### 10.1 06-1：缓存+writeback没有形成可交付稳态收益

- 四格算术均值中的`+16.32%～+19.56%`经独立复算确认，但treatment从首窗约`3.12 GiB/s`
  单调降至末窗约`1.22～1.30 GiB/s`，末窗低于位置对照；该数是窗长依赖瞬时量，不登记为效应。
- 应用写减设备写与同期Dirty增长在约11%内闭合，强支持“宿主RAM先吸收、脏页逼近限额后内核回压”
  的解释；原“缓存NVMe服务率导致衰减”归因撤销。
- 四分窗中，T1应用最快的W1设备写仅`1406 MiB/s`，较慢的W3反而为`1737 MiB/s`；T2设备写前三窗
  也基本持平。设备不是轮内衰减的变化来源，但四窗util仍为`79.5%～99.2%`，仍可能限制最终稳态平台。
- 命中字节约`1380/1400 MiB/s`，缓存设备读仅`9.07/0.60 MiB/s`，命中几乎全部由宿主页缓存
  供给；本RUN没有测到名义上的NVMe持续读缓存能力。
- 96GiB缓存约`41.3/43.0s`周转一次，并有约`2078/1988 drops/s`；Dirty峰值约
  `112.4/118.5 GiB`，高于rawstaging峰值`71.08/75.30 GiB`，前段确认数据存在仅驻易失RAM的窗口。
- 正式裁决保持`RESOLUTION_INSUFFICIENT / NO_DECISION / NO_CANDIDATE`，不重跑、不交付。

### 10.2 06-2：M1仍是嫌疑，但本次准入门和补丁证据均未闭合

  关键路径。Gate2B由`PASS`回溯为`GATE_INVALID`。
- instrumentation自身使READ/WRITE下降约`23%`，超过沿用材料阈值`14.64%`；当前测量装置不具备
  估计补丁净效应的分辨率。

  损失；两者并非相同二进制，成因未定。该损失大于观测器的`-23.0%`，不得归因环境，也不能只用
  仪表化解释06-2的绝对带宽。

  NOT_FOR_PRODUCTION`。这不证明M1不是瓶颈，只说明本次方法没有证明它是主因，也没有产出可交付改法。
