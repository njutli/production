# JuiceFS 存储方案调优工作周报

> 周期：2026-07-14 ~ 2026-07-18
> 环境：4 机集群（157 客户端 + 150-152 存储节点），Ceph 17.2.8 EC4+2 + TiKV 元数据
> JuiceFS v1.3.1+e0032b2（含 loadRange 修复），100GbE 双网 + 1Gbps TBF 限速双口径

---

## 一、工作介绍

### 1.1 基于老集群架构的适配调整

从老集群（千兆单网 + SSD RAID）迁移到新集群（100GbE 双网 + NVMe 直通），架构层面做了以下关键调整：

**存储后端：**
- EC4+2 池 failure_domain 从 `host` 改为 `osd`，故障容忍粒度从节点级降到 OSD 级，数据分布更灵活，单个 OSD 故障时只需重建该 OSD 的数据而非整个节点
- DB/WAL 与 DATA 分介质存储：DB/WAL 放 tmpfs 内存盘，DATA 在 NVMe SSD 上，避免元数据 I/O 与数据 I/O 争抢同一存储带宽

**网络：**
- 100GbE 双网分离（public + cluster 独立网卡），EC 取片走 cluster 网不挤占 public 带宽
- 限速测试用 eno12409 10GbE + TBF 1Gbps，TBF 在 3 个存储节点 egress，客户端 ingress 不受限，聚合读上限 3×118=354 MiB/s

**客户端：**
- `--openfiles=128`（= numjobs），修复历史 `--openfiles=100` 导致的 fio 自限假瓶颈

### 1.2 测试方法调整

测试过程中发现单轮数据波动过大、多轮测试偏差过大，定位原因后对测试方法做了以下调整，确保测得的数据更准确：

**数据采集规范：**
- fio 默认生成 128 份 per-job 带宽日志文件，全部保留并按时间戳对齐求和后取稳态中位数。旧方法只拷回 1 份合并文件再用"单文件值 × numjobs"外推，历史数据显示该外推方法曾导致 65 倍失真
- 定量写项（seqwrite/mseqwrite/layout）取 fio 聚合行（总数据量/总时间），不用稳态中位数

**集群状态管理：**
- 卷清理改用 `juicefs destroy`（删除存储池对象 + 元数据），不用 `juicefs format`（只重置元数据，不删对象，导致多轮测试数据累积污染）
- OSD compaction 状态检查（三指标 + get_latency），三指标全绿不保证 LSM tree 最优，膨胀的 SST 在三指标全绿时仍拖慢高并发读
- 写项间强制 compaction 冷却，防止上轮写入的 RocksDB 积压污染下轮
- 覆写随机写（randwrite-ow）轮间重建存储池，单次 compaction 不够

**多轮测试规范：**
- REPEAT=3 严格取中位数（第 2 大值），禁止取平均、禁止挑轮次
- 每轮跑前 drop_caches（客户端 + 3 个存储节点全部执行）
- 覆写随机写每轮重启 JuiceFS 挂载（fresh Go 进程，消除 Go 运行时状态累积导致的性能波动）

### 1.3 其他工作

- CephFS 内核态对照实验（同后端、同并发、绕过 FUSE）：用于区分瓶颈在 FUSE 用户态还是在后端
- BeeGFS 对齐口径双口径对比（不限速 + 限速）：横向对比 JuiceFS 与内核态方案的带宽差距
- Go runtime pprof 热点分析：定位 JuiceFS 进程 CPU 热点分布，确认 FUSE dispatch 串行入口为主要消耗
- 限速网络部署（Ceph 集群级重部署到 eno12409 + TBF 1Gbps）：支撑限速口径测试，验证千兆网络下 JuiceFS 达标情况

## 三、关键发现

### 3.1 后端裸能力不达标

rados bench 测得 EC4+2 后端随机读天花板 ~4400 MiB/s，低于不限速口径达标线 6250 MiB/s（100GbE 网卡半速）。即使完全绕过 JuiceFS/FUSE（CephFS 内核态对照），后端带宽仍为 4608 MiB/s。EC4+2 读取需跨节点取片重建，4+2 的 fan-in 开销可能是后端侧的限制因素。如需更高带宽，可考虑副本池（CephFS Rep 测得 6718 MiB/s）或更换存储后端（BeeGFS 9045 MiB/s）。

### 3.2 JuiceFS 可能存在 FUSE 用户态瓶颈

不限速口径下单客户端单项均未达 6250 线。CPU 饱和曲线显示 JuiceFS 进程 CPU 在 ~6 核附近趋于饱和（并发从 32 增至 16384，CPU 仅从 566% 升至 595%）。pprof 分析热点集中在 FUSE dispatch 串行入口。该限制可能是 FUSE 架构的 per-mount 特性，多 mount 实例初步验证可线性扩展（N=4 达 5013 MiB/s）。进一步的根因确认（Go GC/heap/goroutine 分析）可提供更准确的判断。

### 3.3 覆写随机写性能波动与定位

覆写随机写（randwrite-ow，复用已有文件进行随机覆盖写）在不限速口径下存在轮间波动（22-83%）。通过逐秒采集 + OSD 指标 + iostat + juicefs stats 四路对齐分析，确认后端指标跨轮稳定，波动来自 JuiceFS Go 进程状态累积。每轮重启挂载后重测，波动降至 13%（R1=4102/R2=3562/R3=3651，中位数 3651），可接受。限速口径无波动（1Gbps 撞墙，所有轮次 117 MiB/s）。
