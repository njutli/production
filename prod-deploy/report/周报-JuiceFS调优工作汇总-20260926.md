## 二、确认上周约 21% 的混合读写缓存收益来自何种条件

这次不只是改变了带宽统计窗口，也调整了实际缓存配置：此前同时开启读缓存与 writeback 的有效测试使用 **128 GiB 的 loop 限容文件系统**，缓存 I/O 经过“loop 上的 ext4 → loop 设备 → NVMe 原生 ext4 中的 backing file → NVMe”，读缓存预算约 **31 GiB**（128 GiB 热集的约 **24%**）；本轮直接使用“NVMe 原生 ext4 → NVMe”的缓存目录，文件系统约 **834 GiB 可用**，读缓存预算提高到 **96 GiB**（热集的 **75%**）。`--cache-size` 只约束读缓存，不是 writeback 暂存的硬上限；因此读缓存预算、物理空间上限与 I/O 路径同时发生变化，不能把新旧结果之差单独归因于去掉 loop。

对存储规格重点关注的 `randrw`（256K、128 任务、QD128、128 GiB 热数据集、180 秒）重新进行无缓存、96 GiB 普通读缓存、96 GiB 普通缓存加 writeback 三组对照。普通缓存加 writeback 相对无缓存，**两次配对的完整测试时长平均带宽**分别提高：读 **21.23%/20.73%**，写 **21.13%/20.68%**；历史约 21% 的组合收益得到重复验证。此前 loop 限容、31 GiB 读预算的混合缓存格在其正式窗相对无缓存为 **−16.88%**，但两轮的缓存条件和统计窗口均不同，不能把二者相减当作去掉 loop 的单项收益。普通缓存单独的配对变化为约 **−1.1%/+8.6%**，不足以解释本轮约 21% 的收益。

开启 writeback 后，读缓存命中字节占比约 **53%**，本地暂存峰值约 **49～52 GiB**，宿主脏页峰值约 **94～95 GiB**，正式负载结束仍需 **37～39 秒**排空。证据符合“本地缓存和脏页吸收 180 秒内的突发写入，使前台平均带宽提高；后段因回刷压力回落”的机制。这个前台收益对当前测试目标有效，但不等于后端持续落盘速率提高。由于普通缓存组自身漂移超过预设分辨率门，目前**不能精确分摊 writeback 的独立贡献**；断电、故障和长时负载语义也未完成交付验收，暂不列为生产配置。

同一 inode 的读操作仍须等待相关写入完成和元数据提交；writeback 暂存成功时，这不一定意味着等待远端上传，因此前台带宽收益不能等同于远端持久化保证。

## 三、完成两条源码改动方向的正确性与性能筛选

源码分析定位到同一 inode 读前需要等待写缓冲排空及元数据提交，且当前读前 flush 覆盖整个 inode。为减少这一等待，本周分别验证了两种不绕过上传、提交及一致性顺序的最小修改：

| 源码候选 | 做法 | 正确性 | 180 秒混合读写性能结果 |
|---|---|---|---|
| 缩小读前 flush 范围并修复等待通知 | 避免无关范围也参与排空 | 定向、race 与真实 FUSE 测试通过 | 两组读/写配对约 `+0.5%` 与 `+11.4%`，未达到重复收益门 |
| 对完整对齐覆盖写提前冻结 slice | 将可提前完成的上传/提交移出后续读前等待 | 定向、race、FUSE 及无缓存读回通过 | 两组读/写配对约 `−5.6%` 与 `+2.5%`，方向不一致；前段更快但后段更慢、排空更久 |

两项改动都没有证明能提高上传和元数据提交的下游服务率，但也不能据此断言其他源码方向没有空间。另用 `direct=0` 测试页缓存路径，两次配对读写均未提升，当前 256K 混合负载仍以 `direct=1` 为基线。
