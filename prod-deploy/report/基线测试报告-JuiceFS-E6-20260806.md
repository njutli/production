## 三、测试方法

### 3.1 执行协议

**阶段 1 — 门控**。性能档位属于 JuiceFS 挂载实例（实测：同实例内轮间差异 ≤1.1%，跨实例 median 极差 29.9%，高档命中率约 49%），故先用短探针判档，只在高档实例上开测。

```bash
ITEMS="randread" bash FULLBASELINE_V4.sh GATE1 75 1
```

判定：randread 逐秒均值落入 **[1830, 1930] MiB/s** 即命中，停手留用该实例；未命中则换实例重抽，最多 5 次。本次首次即命中 **1882 MiB/s**。

**阶段 2 — 同实例连跑 3 次全量**。全程 `SKIP_REMOUNT=1` 复用门控留下的实例，使跨运行比较（L3）成立；`REF_LABEL` 链式指向前一次运行。

```bash
nohup bash -c '
  SKIP_REMOUNT=1                bash FULLBASELINE_V4.sh W2P1 180 5 &&
  SKIP_REMOUNT=1 REF_LABEL=W2P1 bash FULLBASELINE_V4.sh W2P2 180 5 &&
  SKIP_REMOUNT=1 REF_LABEL=W2P2 bash FULLBASELINE_V4.sh W2P3 180 5
' > /tmp/w2base.log 2>&1 &
```

`SKIP_REMOUNT=1` 语义：`reset_state()` 仍执行 `juicefs gc --compact` + `compact_cooldown` + `drop_caches`，仅跳过 remount。

**阶段 3 — 实例同一性校验**。四次运行的 `jfs-instance-*.txt` 中 pid 与 starttime_ticks 必须完全一致，且日志中 `forced-mount` 出现 0 次；否则档位已变，L3 全部作废。

**阶段 4 — 独立复核**。由第二方从各轮 `*_bw.*.log` 按 §4 公式重算，不采信脚本或执行方的自算值。

### 3.2 七个测试项 fio 规格

### 3.3 每轮状态复位动作

| 动作 | 内容 | 触发点 |
|---|---|---|
| `drop_caches()` | 157 本地 + 经 sshpass 到 3 个 OSD 节点执行 `sync; echo 3 > /proc/sys/vm/drop_caches`；清空 `/tmp/jfs-bw/*_bw.*.log` | 每轮 fio 前 |
| `compact_cooldown()` | 6 个 OSD 各执行 `ceph tell osd.N compact`，随后轮询 `perf dump` 的 `rocksdb.compact_running` 与 `compact_queue_len` 归零（上限 300s） | 每写轮后 |
| `aggressive_cleanup()` | `compact_cooldown` → sleep 30 → `compact_cooldown` → `juicefs gc --compact` → `drop_caches` | randrw / randwrite 每轮后、mseqwrite 项末 |
| `reset_state()` | `juicefs gc --compact` → `compact_cooldown` → `drop_caches` →（remount 或跳过） | 每次运行开始 |
| `pg_gate()` | 校验 `pg_num=32` / `pgp_num=32` / 全 active+clean，未 clean 则等待至多 1800s，仍不满足则整跑作废 | 每轮 fio 前 |

`juicefs gc --compact` 为本方法的关键动作。E6 与 E6C 对照实测：引入每轮 compact 后 randrw 轮间极差由 23.0% 降至 3.0%，randwrite 由"3056 单调衰减至 794"变为"2896 → 2814 平稳"。

### 3.4 稳定性判据

| 层 | 含义 | 阈值 | 说明 |
|---|---|---|---|
| L1 | 单轮清洁度 | 读项 stall ≤1% 且逐秒 CV <6% | 写项因 FUSE flush/sync 天生双模（实测 stall 1.2-22.3%），只记录不判定 |
| L2 | 同一运行内轮间稳定 | 极差幅度 ≤5% | 极差 ≤5% 已蕴含 max_dev ≤5% 且 CV ≤2.5%，故单条即可 |
| L3 | 跨运行稳定 | 与 `REF_LABEL` 的 median 偏差 ≤5% | 仅在同一挂载实例间有意义 |

## 四、指标计算方式

### 4.1 验收口径：逐秒均值（15-175s）

脚本位置：`FULLBASELINE_V4.sh:1017 parse_bwlog_mean()`。fio bw log 行格式：

```
<毫秒时间戳>,<带宽 KiB/s>,<方向位>,<块大小>,...
方向位：0=read  1=write  2=trim
```

算法：

```
1) 读取该轮子目录下所有 *_bw.*.log（128 个 job 各一个文件）
2) 秒对齐：sec = int(field[0]) / 1000
3) 方向过滤：仅保留 field[2] == direction 的行
4) 同秒跨 job 求和：per_sec[sec] += field[1]      ← 128 个 job 带宽相加
5) 取窗口：t0 = min(per_sec.keys())，保留 15 <= sec - t0 <= 175
6) 逐秒均值 = mean(窗口内 per_sec 值) / 1024      ← 单位 MiB/s
```

三点说明：

- 窗口为**相对 t0** 的偏移，非绝对秒，因此 75s 的门控探针同样能正确出值。
- 截去前 15s 用于剔除写缓冲与 ramp 阶段的虚高；采用**均值**而非中位数，因中位数会剔除 stall、掩盖真实抖动。
- 各项使用的方向位（`FULLBASELINE_V4.sh:976`）：

| 项 | direction |
|---|---|
| seqread / mseqread / randread | 0（读） |
| randrw | 0（只取读侧） |
| seqwrite / mseqwrite / randwrite | 1（写） |

fio 汇总值（解析 `fio.txt` 的 `READ:` / `WRITE:` 行）与逐秒中位数（`parse_bwlog()`）并列打印，仅作参考，不作验收。

### 4.2 randrw 的两种口径

randrw 读写各占约一半，因此存在两种算法，数值相差 2 倍，但为同一物理性能：

| 口径 | 算法 | 产出者 |
|---|---|---|
| 读侧 | 只累加 `direction == 0` | `FULLBASELINE_V4.sh`（正式脚本） |
| 读写合计 | 不过滤方向 | `debug/mount-gear-attrib-test.sh` 的 `bw_mean`、复核脚本 `r5chk.py` |

方向拆解验证数据见 §5.6。本报告 randrw 同时给出两个口径值。历史文档中的 randrw 2400 为读写合计口径。

### 4.3 L2 / L3 公式

```
median      = median(该项各轮逐秒均值)
L2 极差幅度 = (max - min) / median × 100%          ← 判定用此条，阈值 5%
max_dev     = max(|v - median|) / median × 100%    ← 参考
CV          = stdev / mean × 100%                  ← 参考
L3 偏差     = (median(本运行) / median(REF_LABEL 运行) - 1) × 100%   阈值 ±5%
```

脚本按 `REF_LABEL` 只计算"与前一次运行"的链式 L3；本报告 §5.4 补算全 pairwise。

### 4.4 首轮（r1）的处理

randrw 与 randwrite 每轮后均执行 `juicefs gc --compact`，故 r1 跑在"刚完成碎片回收的池"上，属受控但不同于后续轮的状态：randrw 的 r1 是历史签收所取的状态，randwrite 的 r1 系统性偏高。本报告对 randwrite 同时给出全 5 轮与剔除 r1 两组 L2 值（§5.5）。

### 4.5 辅助指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| hit% | `collect_hitrate` 于每轮 fio 前后采集，差分求得 | 读项是否命中 BlueStore 缓存 |
| C_amp | NIC 计数器首末差分 ÷ fio 读字节 | 守卫：default 应 2.0±0.1，`--max-readahead 0` 应 1.0±0.1，超范围判该轮无效 |
| gear / stall | 逐秒序列的 stall 占比与 CV | L1 单轮清洁度 |
| compact 成本 | `秒 ≈ 1.95e-4 × 回收对象数`（实测误差 6%） | 预算 `gc --compact` 耗时 |
| 空间放大 | `used 增量 / fio 写入量` | 实测 1.84-1.88× |
| 对象产生率 | 每写入 292 KiB 产生 1 个新对象 | 与 BlockSize 256K 对应 |
