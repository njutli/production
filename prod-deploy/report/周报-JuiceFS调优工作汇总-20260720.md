# JuiceFS 存储方案调优工作周报

> 周期：2026-07-20 ~ 2026-07-24
> 环境：4 机集群（157 客户端 + 150-152 存储节点），Ceph 17.2.8 EC4+2 + TiKV 元数据
> JuiceFS v1.3.1+e0032b2，100GbE 双网（public 10.3.1 + cluster 10.3.2）

## 2026-07-20 关键进展

### 一、架构差异导致的两层瓶颈定位完成

基于前期实验数据（07-18~19 采集）+ 基础设施排查（07-20 执行），JuiceFS 方案与 BeeGFS 方案的带宽差距已分解为两个独立可量化的瓶颈层：

```
BeeGFS 9045 MiB/s（kernel module，同硬件）
    │
    │ ← 瓶颈一：后端软件栈差异（-26%）
    ▼
kernel CephFS+Rep3 6718 MiB/s（前期集群）/ 5359（当前集群）
    │
    │ ← 瓶颈二：FUSE 用户态开销（-42%，修正 max_read 后 -27%）
    ▼
JuiceFS 2404~4096 MiB/s（FUSE + Go + TiKV + librados）
```

两层瓶颈均有直接实验证据和源码级分析支撑，详见下文。

### 二、瓶颈一：FUSE 用户态开销

#### 2.1 实验设计——四栈同后端单变量对照

**实验前提**：同后端（juicefs-data-rep pool, Rep3, 6 OSD）、同数据（kernel CephFS 先 layout 128G，ceph-fuse 复用同份数据）、同 fio 口径（256K bs, 128j×128, direct=1, 180s, REPEAT=3）。

三个客户端栈两两对照，每次只改变一个变量，可隔离 FUSE / Go+TiKV 的独立贡献：

| 客户端栈 | FUSE | Go | TiKV | 作用 |
|----------|:---:|:--:|:---:|------|
| kernel CephFS | ❌ | ❌ | ❌ | baseline（无用户态开销） |
| ceph-fuse（C++） | ✅ | ❌ | ❌ | 隔离 FUSE 变量 |
| JuiceFS+Rep | ✅ | ✅ | ✅ | 叠加 Go+TiKV 变量 |

#### 2.2 实验数据

| 测试 | r1 | r2 | r3 | 中位 (MiB/s) |
|------|----|----|----|:---:|
| kernel CephFS | 4972 | 5001 | 4933 | **4972** |
| ceph-fuse | 2870 | 2884 | 2885 | **2884** |
| JuiceFS+Rep | 2969 | 2965 | 3019 | **2969** |

Per-op 延迟对比（r2 代表性数据）：

| 指标 | kernel CephFS | ceph-fuse | JuiceFS+Rep | ceph-fuse/kernel | JuiceFS/kernel |
|------|:---:|:---:|:---:|:---:|:---:|
| BW (MiB/s) | 5001 | 2884 | 2965 | 0.58× | 0.59× |
| IOPS | 19888 | 11536 | 11876 | 0.58× | 0.60× |
| **slat avg (μs)** | **729** | **11092** | **10787** | **15.2×** | **14.8×** |
| clat avg (ms) | 818 | 1403 | 1365 | 1.72× | 1.67× |
| lat P99.4% | 散布 1-50ms | 99.44% @ 2000ms | 99.45% @ 2000ms | — | — |

#### 2.3 FUSE 损失量化（推理链）

**Step 1 — 隔离 FUSE 变量**：kernel CephFS（4972）vs ceph-fuse（2884）

- 共同点：同后端、同 MDS、同数据、同 Ceph 软件栈、同 cephx 认证
- 唯一差异：mount 方式 = 内核态 `mount -t ceph`（无 FUSE）vs 用户态 `ceph-fuse`（FUSE /dev/fuse）
- ceph-fuse 是 C++ 实现，无 Go runtime、无 TiKV、无 librados cgo——纯 FUSE + CephFS 客户端栈
- **结果：4972 → 2884，损失 42%**

**Step 2 — 隔离 Go+TiKV 变量**：ceph-fuse（2884）vs JuiceFS+Rep（2969）

- 共同点：同后端、同 FUSE 用户态、同 fio 口径
- 唯一差异：ceph-fuse 是 C++（无 Go/TiKV），JuiceFS 是 Go + cgo librados + TiKV 元数据
- **结果：2884 vs 2969，差 3%（统计噪声级别）**

**Step 3 — 交叉验证**：

```
kernel CephFS  4972  (baseline, 无 FUSE/Go/TiKV)
     │
     │ -42%  ← FUSE 单变量损失
     ▼
ceph-fuse      2884  (FUSE, 无 Go/TiKV)
     │
     │ +3%   ← Go+TiKV 变量（统计噪声）
     ▼
JuiceFS+Rep   2969  (FUSE + Go + TiKV)
```

**结论**：FUSE 损失 42%，Go+TiKV 损失 ≤3%（可忽略）。FUSE 是 JuiceFS 的绝对主导瓶颈。

**Step 4 — slat 延迟提供机制证据**：

fio 的 `slat`（submit latency）= fio 提交 I/O 前等待 VFS/设备驱动接受新 I/O 的时间，直接反映客户端 dispatch 路径开销。

- kernel CephFS slat = 729μs：fio → VFS → ceph 内核模块 → 直接提交网络请求，无用户态调度
- ceph-fuse slat = 11092μs：fio → VFS → /dev/fuse 字符设备 → 内核 FUSE 模块排队 → 用户态 ceph-fuse 进程 read() 从 /dev/fuse 取出请求 → 处理 → writev() 写回 /dev/fuse → 内核唤醒 fio
- JuiceFS slat = 10787μs：同 ceph-fuse 路径（/dev/fuse dispatch），差 3%（Go runtime 开销）

ceph-fuse 和 JuiceFS 的 slat 几乎相同（11092 vs 10787，差 3%），都 15× 慢于 kernel。直接证明 **FUSE /dev/fuse dispatch 模型是延迟膨胀的根源**，与语言（C++ vs Go）无关。

#### 2.4 max_read 拆包发现与修正

通过代码级溯源发现 FUSE slat 15× 的一个物理根因：

**根因定位**（代码级溯源链）：
1. `mount | grep juice` 显示 `max_read=131072`（128K）
2. go-fuse 源码 `fuse/server.go:37`：`defaultMaxWrite = 128 * 1024`（128K）
3. go-fuse 源码 `fuse/server.go:339`：`r = append(r, fmt.Sprintf("max_read=%d", o.MaxWrite))` —— go-fuse 设 `max_read = MaxWrite`
4. JuiceFS 源码 `cmd/mount_unix.go:353`：`--max-fuse-io` flag，默认值 `"128K"`
5. JuiceFS 源码 `pkg/fuse/fuse.go:476`：`opt.MaxWrite = conf.FuseOpts.MaxWrite`

**结论**：JuiceFS 默认 `--max-fuse-io 128K` → go-fuse `MaxWrite=128K` → `max_read=128K` → **256K I/O 被 FUSE 内核拆成 2 × 128K dispatch 往返**。

**修正 + 复测**：

| 配置 | max_read | BW (MiB/s) | IOPS | slat avg (μs) | clat avg (ms) |
|------|----------|:---:|:---:|:---:|:---:|
| baseline（默认 128K） | 131072 | 3275 | 13100 | 9765 | 1227 |
| **fixed（--max-fuse-io 1M）** | 1048576 | **4096** | **16400** | **7806** | **983** |
| **变化** | 8× | **+25%** | **+25%** | **-20%** | **-20%** |

修正后 slat 从 9765μs 降到 7806μs（-1959μs），恰好约等于消除 1 次 dispatch 往返（~2ms）。

**FUSE 税变化**：

| 配置 | JuiceFS BW | CephFS BW | FUSE 税 |
|------|:---:|:---:|:---:|
| max_read=128K（默认） | 3275 | 5359 | 38.9% |
| max_read=1M（修正） | 4096 | 5359 | **23.6%** |

#### 2.5 FUSE 配置深度排查

对 JuiceFS / go-fuse 全部源码 + 官方文档排查后，识别出的所有与延迟相关的 FUSE 配置项及实测结果：

| 配置 | 默认值 | 建议 | 实测结果 |
|------|--------|------|---------|
| **`--max-fuse-io`** | "128K" | **1M** | ✅ **+18-25% BW, -10-20% slat** |
| **`-o async_dio`** | 不启用 | ❌ 不推荐 | ❌ **-5~18% BW（有害）** |
| **`MaxBackground`** (sysfs) | 50 | ❌ 不推荐 | ❌ 无收益（同步读不受限）|

**`-o async_dio` 有害的原因**：不启用时 O_DIRECT 读是同步的，128 job = 128 并发 dispatch（不受 max_bg 限制）。启用后 O_DIRECT 读被计入 `max_background`（当前 50），反而被限流；且 async 路径引入 ~1ms kernel-side bookkeeping 开销。

**FUSE 税不可削减部分**（修正 max_read 后仍有 ~27%）：
1. FUSE dispatch 往返：writev → /dev/fuse → go-fuse → librados → OSD → 返回，每 op ~8ms
2. go-fuse goroutine 调度：request pool → goroutine dispatch → cgo 转换
3. librados 用户态 messenger：3 线程 epoll 模型

这是 FUSE 用户态方案的架构固有开销，除非换内核态无法进一步削减。

### 三、瓶颈二：Ceph vs BeeGFS 后端软件栈差异

#### 3.1 同硬件 kernel-mode 对照

两者都是 kernel-mode 客户端（无 FUSE 开销），差距纯粹来自后端软件栈：

| 测试项 | BeeGFS | Ceph Rep3 | Ceph EC4+2 | JuiceFS+EC |
|--------|:---:|:---:|:---:|:---:|
| randread 256K（128j×128） | **9045 ✅** | 6718（前期集群）/ 5359（当前集群） | 4608（前期集群） | 2404 |

> BeeGFS 同硬件 9045 MiB/s 证磁盘 + 网络硬件完全够用。NVMe 单盘可跑 1.5+ GB/s（9045/6），远超 Ceph EC 的 290 MB/s per-OSD。

**核心对比**：CephFS+Rep3 6718 vs BeeGFS 9045（同硬件，均为实测值），差距 **-26%**。差距来自 Ceph 软件栈的 per-op 额外开销。

#### 3.2 Ceph 源码级 per-op 开销分解

从 Ceph 源码追溯一次读操作的完整代码路径和逐层开销：

**读请求完整代码路径**：
```
网络 (epoll) → ms_fast_dispatch → enqueue_op → ShardedOpWQ 线程
→ PG::do_request → PrimaryLogPG::do_op → do_read → BlueStore::read → _do_read
→ RocksDB 查 onode + extent → AIO 磁盘读 → checksum 验证 → 返回
```

**逐层开销分解**（基于源码路径分析的经验估算，非实测值。带宽数据为实测，per-op 各项为估算）：

| 层 | 源码位置 | per-op 估算 | BeeGFS 对应 | 差距来源 |
|----|---------|:---:|---------|---------|
| **① cephx 消息签名（AES ×4）** | `ProtocolV1.cc:960` + `CephxSessionHandler.cc:156` | **40-100μs**（估） | 无 | Ceph 默认 `cephx_sign_messages=true`，每个请求和响应各做一次 AES 加密，每读操作 = 4 次 AES 加密 |
| **② BlueStore RocksDB 查询** | `BlueStore.cc:12744` `get_onode` + `:13141` `fault_range` | **20-40μs**（估） | 内存 inode 缓存 | BlueStore 每次读都查 RocksDB（onode + extent map），即使 cache hit 也有 memtable 查找开销 |
| **③ 线程池切换链** | `OSD.cc:9889` → `:11083` ShardedOpWQ → PG lock | **20-40μs**（估） | 单线程直处理 | messenger worker → ShardedOpWQ → PG mutex，两次上下文切换 + 三把锁（shard_lock + PG lock + collection lock） |
| **④ do_op 验证链** | `PrimaryLogPG.cc:1988` | **10-20μs**（估） | 轻量检查 | 14+ 检查项：PG containment / session backoff / caps parse / blocklist lookup / cluster full check |
| ⑤ epoll + socket 读 | `EventEpoll.cc` + `AsyncConnection.cc:386` | 10-20μs（估） | RDMA <5μs | TCP epoll 边沿触发 + 多次 buffer copy |
| ⑥ BlueStore AIO 磁盘读 | `BlueStore.cc:13176` | 50-100μs（估） | 50-100μs | 两者相同（同一 NVMe 硬件） |
| ⑦ checksum 验证 | `BlueStore.cc:13219` | 5-10μs（估） | 无 | CRC 校验 per blob |
| **软件开销合计（①-⑤+⑦）** | | **~155-330μs**（估） | **~67-127μs**（估） | **Ceph 软件开销是 BeeGFS 的 10-20×** |

**最大单项开销——cephx per-message AES 加密**：

```cpp
// CephxSessionHandler.cc:156
int CephxSessionHandler::check_message_signature(Message *m) {
  if (!conf(cct)->cephx_sign_messages) { return 0; }  // 默认 true
  uint64_t sig;
  int r = _calc_signature(m, &sig);  // 每个 message 做一次 AES 加密
  ...
}
```

每个读操作 = 4 次 AES 加密（请求签名 + 验证 + 响应签名 + 验证），约 40-100μs（估算）。BeeGFS 无任何 per-message 加密。这是**最大的可消除开销**。

#### 3.3 Ceph vs BeeGFS 同硬件逐项对照

| 开销项 | CephFS+Rep3 | BeeGFS | 差值 |
|--------|:---:|:---:|:---:|
| cephx AES ×4/op | 40-100μs（估） | 0μs | **40-100μs** |
| BlueStore RocksDB 查询 | 20-40μs（估） | 0μs（内存 inode） | **20-40μs** |
| 线程池切换 + 3 锁 | 20-40μs（估） | ~5μs（估） | **15-35μs** |
| do_op 14 项验证 | 10-20μs（估） | ~2μs（估） | **8-18μs** |
| TCP epoll（非 RDMA） | 10-20μs（估） | 10-20μs（估） | 0μs |
| checksum CRC | 5-10μs（估） | 0μs | **5-10μs** |
| NVMe 磁盘 AIO | 50-100μs（估） | 50-100μs（估） | 0μs |
| **软件合计** | **155-330μs**（估） | **67-127μs**（估） | **88-203μs** |
| **总 per-op** | **~250μs**（估） | **~167μs**（估） | **~83μs** |

**从实测带宽反推 per-op 延迟差值**（带宽为实测，per-op 为反推导出）：
- CephFS+Rep3 6718 MiB/s（实测）= 26.4K IOPS → per-op = 128×128/26.4K = 0.62ms（含 OSD 排队）
- BeeGFS 9045 MiB/s（实测）= 35.3K IOPS → per-op = 128×128/35.3K = 0.46ms
- 差值 = 0.16ms = 160μs → 与上表估算的软件开销差值 88-203μs 量级一致（粗略佐证，非精确归因）

#### 3.4 可消除 vs 不可消除的开销

| 开销项 | 可否消除 | 方法 | 预期增益（估） |
|--------|:---:|------|:---:|
| cephx AES per-message | ✅ 可消除 | `cephx_sign_messages=false` | +15-30% |
| BlueStore RocksDB 查询 | ⚠️ 部分可消除 | 增大 BlueStore cache（`osd_memory_target`） | +5-10% |
| 线程池切换 | ❌ 架构固有 | 需 Crimson 重写（单线程 OSD） | +5-10% |
| do_op 验证链 | ❌ 架构固有 | 功能需求（caps/blocklist/full check） | 不可消除 |
| checksum CRC | ❌ 数据安全需求 | 不建议关闭 | 不可消除 |
| TCP vs RDMA | ✅ 可消除 | 部署 RoCE/IB + Ceph messenger RDMA（需 Crimson） | +10-20% |

最大可消除项 = cephx 签名关闭（+15-30%，估），但牺牲安全性。即使全部消除可削减项，Ceph 线程池切换 + do_op 验证 ~30-60μs/op（估）仍为架构固有。

#### 3.5 设计目标差异（官方定位）

差距的根源是两个系统的设计哲学不同：

| 维度 | Ceph | BeeGFS |
|------|------|--------|
| 官方定位 | "**scalable unified distributed storage**"（可扩展的统一分布式存储） | "**parallel file system for HPC and AI clusters**"（专为 HPC/AI 设计的并行文件系统） |
| 出处 | `doc/technical-charter.rst` + `doc/architecture.rst` + ceph.io | beegfs.io 首页 + doc.beegfs.io |
| 接口 | object + block + file 三合一（RADOS + RBD + RGW + CephFS） | 仅 POSIX 文件接口 |
| per-op 设计 | 安全/功能验证链（cephx + caps + blocklist + checksum） | per-op 路径最短化（无 cephx/RocksDB/线程池切换） |
| 冗余方式 | EC4+2（1.5× 空间成本）或 Rep3（3×） | Replication（文件级 stripe + replication） |

Ceph 追求"一套系统覆盖所有存储需求"，per-op 需经过安全/功能验证链；BeeGFS 追求"并行文件 I/O 极致性能"，per-op 路径最短化。**这是设计目标的根本差异，不是调优能弥补的**。
