## 一、全路径采集器

基线波动归因过程中开发了三个采集器，用于在 fio 运行期间以 5s 间隔连续采集客户端和 OSD 侧指标，事后与 fio bw_log 时间轴对齐分析。

### 1.1 load-monitor.sh（157 客户端侧）

| 项 | 内容 |
|---|---|
| 路径 | 157: `/tmp/load-monitor.sh`，本地: `/tmp/opencode/load-monitor.sh` |
| 采集方式 | 157 本地 /proc 读取，无外部命令、无 SSH、无跨节点调用 |
| 间隔 | 5s |
| 输出 | CSV（与 fio `_bw.*.log` 同时间轴） |

**字段**：
```
ts, load1, load5, load15, runnable, total, d_state,
cpu_us, cpu_sy, cpu_wa, cpu_id, cpu_st,
rx_bytes, tx_bytes, rx_drop, tx_drop,
memfree_kb, memavail_kb, buffers_kb, cached_kb, dirty_kb,
fuse_ops_total, fuse_ops_sum, obj_get_total, obj_get_sum, txn_total, txn_sum
```

**用途**：
- load/D 态/CPU wa：确认 157 客户端是否饱和（实测 randread 128 jobs 时 idle=82%、wa=0、D=0）
- NIC rx/tx/drop：157 侧网络吞吐和丢包
- JuiceFS .stats（fuse ops + object GET + txn 延迟）：客户端侧 FUSE op 延迟和后端请求延迟

### 1.2 osd-monitor.sh（150-152 OSD 侧）

| 项 | 内容 |
|---|---|
| 路径 | 157: `/tmp/osd-monitor.sh`，本地: `/tmp/opencode/osd-monitor.sh` |
| 采集方式 | 从 157 通过 `ceph tell osd.* perf dump`（6 OSD 串行）+ SSH 到 150-152 采集 /proc + `ss -ti` + `ethtool -S` |
| 间隔 | 5s（每轮迭代约 6s，含 6 次 ceph tell + 3 次 SSH 并行） |
| 输出 | CSV × 4（osd-perf.csv + node-150.csv + node-151.csv + node-152.csv） |

**osd-perf.csv 字段**（33 列，同一 perf dump JSON 多抽）：
```
ts, osd_id,
get_latency_avg, buffer_hit_bytes, buffer_miss_bytes, compact_running, compact_queue_len,
thr_cli_bytes_wait_cnt, thr_cli_bytes_wait_sum, thr_cli_bytes_getfail,
thr_cli_msg_wait_cnt, thr_cli_msg_wait_sum, thr_cli_msg_getfail,
thr_bs_wait_cnt, thr_bs_wait_sum, thr_bs_getfail,
thr_msgr_wait_cnt, thr_msgr_wait_sum, thr_msgr_getfail,
op_r_lat_cnt, op_r_lat_sum, op_r_proc_cnt, op_r_proc_sum,
op_dequeue_cnt, op_dequeue_sum, op_queue_cnt, op_queue_sum,
read_lat_cnt, read_lat_sum, read_wait_aio_cnt, read_wait_aio_sum,
kv_sync_cnt, kv_sync_sum
```

**node-150/151/152.csv 字段**（27 列）：
```
ts, load1, load5, load15, cpu_us, cpu_sy, cpu_wa, cpu_id,
rx_bytes, tx_bytes, rx_drop, tx_drop,
disk_read_sectors, disk_write_sectors, disk_busy_ms,
tcp_cwnd, tcp_rtt, tcp_retrans, tcp_sndq,
nic_tx_dropped, nic_tx_pause, nic_rx_pause, nic_rx_discards
```

**用途**：
- rocksdb get_latency / bluestore hit/miss：OSD 读路径元数据延迟和缓存命中率
- throttle wait/getfail：是否命中限流
- op latency cnt/sum：op 阶段排队等待（须 Δsum/Δavgcount 差分算窗口均值）
- read_lat cnt/sum：BlueStore 读延迟
- TCP cwnd/retrans/rtt + ethtool tx_dropped/pause：网络发送侧是否有拥塞/丢包/流控

### 1.3 historic ops 采集

| 项 | 内容 |
|---|---|
| 命令 | `ceph tell osd.* dump_historic_ops`（串行执行 6 OSD） |
| 输出 | JSON 文本文件（`historic-ops-osd{0-5}.json`），不进 CSV |
| 时机 | 每轮 fio 完成后一次性采集（非 5s 高频） |

**用途**：慢 op 的逐阶段延迟分解，定位 op 处理链中哪个阶段慢。

### 1.4 关键工程教训

1. **累积计数器必须窗口内差分取增量**：NIC tx_bytes、buffer_hit_bytes、retrans、tx_dropped 等均为累积值，严禁看绝对值——十轮报告中因未差分 NIC TX 和 buffer hit_rate 导致误判"好坏轮无差异"。
2. **avgtime 是全局均值被历史稀释**：Ceph perf dump 中的 `avgtime` 是自 OSD 启动以来的全局平均值，被海量历史操作稀释，窗口内变化几乎看不出。必须采集 `avgcount` + `sum`，用 Δsum/Δavgcount 算窗口内真实均值。
3. **dump_historic_ops 采集必须串行**：不能用 `&` + `wait`（bare wait 会等待 osd-monitor 无限循环进程导致死锁），必须用 `for ... do ... done` 串行执行。
4. **采集器 kill bug**：`[ -x "$script" ] && "$script" &` 会把整个 `&&` 表达式放到后台子 shell，kill 杀的是子 shell 不是采集器进程。修复为 `if [ -x ... ]; then "$script" & local pid=$!; fi`。
