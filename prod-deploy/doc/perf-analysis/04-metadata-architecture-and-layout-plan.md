## 一、继承的公理层事实（04 阶段不再重验）

以下全部来自 03 阶段的可正式引用结论。**04 阶段任何任务书不得重新测量这些项**，
除非其前提（硬件、拓扑、版本）发生变化。

### 1.1 交付基座

```text
JuiceFS  /tmp/juicefs-03-8   v1.3.1+2025-12-02.e0032b2a   md5 de93563f11a5ff3bd94dd25a4e0283b1
mount    --max-fuse-io 256K --max-uploads 150 --cache-size 0
ceph     客户端私有 CEPH_CONF: [client] ms_async_op_threads = 8
规则     ms_async_op_threads >= OSD数据连接数 × 1.33（当前 6 OSD → 8）
```

### 1.2 七项基线与达成率（03-17f 交付口径，128 inode）

| 项 | 方向 | MiB/s | 达成率 |
|---|---|---:|---:|
| seqread | 读 | `1449` | `23.2%` |
| mseqread | 读 | `5366` | `85.9%` |
| randread | 读 | `5544` | `88.7%` |
| randrw | 读 | `1870` | `29.9%` |
| randrw | 写 | `1870` | `29.9%` |
| seqwrite | 写 | `1570` | `25.1%` |
| mseqwrite | 写 | `4676` | `74.8%` |
| randwrite | 写 | `2707` | `43.3%` |

### 1.3 已封板的机制结论

| # | 结论 | 关键数字 |
|---|---|---|
| 1 | 读侧墙在 OSD 服务率与主 PG 分布，不在客户端/网卡 | 单挂载渐近上限 ≈`6280`；PG 分布 `6:6:5:6:5:4`，max/mean `1.136`；均衡理论值 ≈`6267` |
| 2 | 写侧墙在按 inode 串行的同步元数据事务 + TiKV KV/compaction 共享服务率 | `6250 MiB/s @256KiB` 需 ≈`25000` 逻辑写/s；当前 meta 提交能力 ≈`12K/s`，缺口近 2 倍 |
| 3 | 轮内衰减是软排队，不是 RocksDB hard stall | stall 计数全程 0，L0 低于 trigger，限速器未生效 |
| 4 | **TiKV 存储介质不是随机写主因** | 全部本地存储 RAM vs NVMe 仅差 `+0.26%`；介质效应量级 `0%--3%` |
| 5 | **WAL/Raft 隔离的带宽收益上界 `≤5.05%`** | D1（logs on RAM）严格优于任何真实 NVMe；稳定性收益真实（CV `+2.36 pp`、`W4/W1` `+0.0694`） |
| 6 | **v1.4.1 原版仍有随机写崩塌，必须携带 B-catchup 补丁** | 原版 `551/552/551`（跨 `2.6` 倍池对象数恒值）；补丁版 `2679--2754` |
| 7 | 三节点无合格 spare NVMe | 12 块 NVMe：3 系统 + 3 TiKV + 6 Ceph OSD，SMART 全绿但**健康≠空闲** |
| 8 | 单流项受单请求完成周期限制，物理不可达 | `6250 @256KiB` 需 ≈`41 µs` 等效周期，一次跨网 librados 往返已 >`200 µs` |

### 1.4 已排除、⛔ 不得重开的方向

提高 `max-uploads` · 继续增加活跃 inode 数 · 增加 compaction worker ·
对 compaction 限速或暂停 · 同一物理盘上的逻辑分离（目录/分区/双 loop）·
通过主动清理消除轮内波动 · 调高某个 RocksDB 阈值

## 五、U1：交付基座版本锁定（P0，可立即开）

### 5.1 命题

> 在同一生产卷、同一挂载参数、同一 Ceph 数据面和同一文件资产上，把二进制从
> `de93563f`（patched v1.3.1）换成 `24fae085`（patched v1.4.1）后，**七项是否每一项都非劣**？

### 5.2 为什么必须重做（03 阶段两次评估均无效）

| 批次 | 失效原因 |
|---|---|
| U141 | mseqwrite 每轮净增 `0.9--1.3M` 对象、`gc --compact` 对活数据无效，池自 `2.4347M` 棘轮到 `5.36M`；**每一项 B 臂平均起点都高于 A 臂** ⇒ 臂效应与对象数共线。randrw `r(obj,BW)=−0.863` |
| V141R/V141P | 序贯非交叉；补丁只改写路径，三个读项是零假设对照（真值 0），实测 `−5.25%/−2.26%/+1.03%` ⇒ 该设计对 `\|Δ\|<5.2%` 无分辨力，而需分辨的正是 `3%--6%` |

### 5.3 设计要点

- 交错粒度降到**轮级**（臂间间隔小时级 → 十分钟级）
- 顺序 `V13 V14 V14 V13 | V14 V13 V13 V14`，两臂占位均值均为 `4.5` ⇒ 单调漂移一阶抵消
- 矩阵内含 2 个**同臂相邻对**（真值恒为 0）直接测噪声底 `ε`，边界 `M = max(3%, 2ε)`
- mseqwrite 移出主矩阵（棘轮源头），单列为条件 phase
- P0 兼容性门：双向挂载 + Setting 对比，出现 `ROLLBACK_BLOCKED` 则强制 `REPLACE_REJECTED`

### 5.4 任务书与排期

| 项 | 值 |
|---|---|
| 任务书 | `doc/perf-tasks/u141b-juicefs-141-replace-131-decision.md`（633 行，含 Gate 0 与 S01--S20） |
| 前置 | Gate 0（离线，零环境接触）+ 三个脚本 fixture 自证 |
| 墙钟 | 第一夜 P0+P1+P2+P3 ≈8 h；第二夜 P4（条件执行） |
| 停点 | 5 个：Gate 0 / 阶段 I / P1+P2 / P3 /（条件）P4 |

### 5.5 结论如何落地

| U1 结论 | 动作 |
|---|---|

## 六、A 线：归因闭合（需生产 TiKV 维护窗口）

### 6.1 为什么这是最高信息价值的一线

| 因子 | 已测？ | 量级 |
|---|---|---|
| TiKV 存储介质（RAM vs NVMe） | ✅ 已测 | `+0.26%`（同拓扑）；`0%--3%`（含分盘对照） |
| logs 隔离（共享盘 → 独立） | ✅ 已测 | `+5.05%`（上界） |
| **历史环境 → 全新环境** | ❌ **从未单独测** | **`+25%--30%`** |

⇒ **未测因子比已测因子大一个数量级。** 03 阶段的 5 个 RUN 全花在了 `0%--3%` 的因子上。

### 6.2 A1：条件 C —— fresh TiKV + 生产 NVMe 原生 ext4

- 对应 `TODO C01`
- 停生产 TiKV，在现有 `/mnt/jfs-tikv` 下建精确临时目录，跑 fresh PD/TiKV，KV/WAL/Raft 共享该**原生 ext4**（不经 nested loop）
- 作用：一次剔除 **nested loop 开销** 与 **介质** 两个因素
- 不需要额外硬件；⛔ 生产 TiKV 与条件 C 绝不能并行使用同一文件系统

### 6.3 A2：元数据规模 / region 数 sweep

- 对应 `TODO C01b`（2026-08-28 新增）
- 固定介质与拓扑，唯一变量 = 临时集群内的**元数据体量 / region 数**
- 先验依据：

| 项 | 生产 TiKV | 临时集群（seed 级） |
|---|---:|---:|
| region 数/store | `2485` | 极少 |
| store used size | `15.42 / 17.53 / 17.54 GiB` | 远小于此 |
| 活对象数 | `2.43M` | `524,288`（少 `4.6` 倍） |
| 元数据 dump | 全量 | ≈`25 KB` |

region 数决定独立 Raft group 数 ⇒ 每事务 fsync 放大与 scheduler 扇出。

- 档位：4--5 档，含 seed 级与 ≈`2485` region/store 两个端点；每档 ≥2 arm 平衡顺序，端点加密

### 6.4 A2 的预注册判据（决定 M 线优先级）

| 结果 | 结论 | M 线动作 |
|---|---|---|
| 带宽随 region 数单调下降，生产量级回落到 ≈`2880` | `+25%--30%` 归因到元数据规模 | **C03（TiKV 扩容/分片）优先** |
| 带宽对 region 数不敏感 | 剩余归于 fresh RocksDB 状态本身 | **C04（事务架构原型）优先**；且"定期重建元数据"不是可持续对策 |
| 非单调或方差过大 | `MECHANISM_PARTIAL` | 先补客户端事务分段插桩，⛔ 不启动 C03/C04 |

## 七、R 线：读侧最后余量（04 唯一达标型实验）

### 7.1 R1：隔离 pool 上验证均衡 PG 分布

- 对应 `TODO C06`
- 依据：6 OSD 主 PG/op 分布长期固定 `6:6:5:6:5:4`，max/mean `1.136`；
  按最热 OSD 约束推算，完全均衡的 randread 理论值 ≈`5516.7 × 1.136 ≈ 6267 MiB/s`，
  与客户端侧拟合的单挂载渐近上限 ≈`6280` 相互验证
- ⇒ **这是全项目唯一还可能真正达到 `6250` 的方向。**

### 7.2 步骤与红线

1. **新建隔离测试 pool**，选择能改善 6 OSD 分布的 PG 数与等价 EC 参数；
2. 在新 pool 重新 layout 同口径数据，做读侧 A/B（旧 pool ↔ 新 pool）；
3. 只有新 pool 验证有稳定材料收益后，才评估生产 pool 迁移。

⛔ **禁止直接提高现有生产 pool 的 `pg_num/pgp_num`**：现有约 `2.43M` 对象会触发大规模重映射/backfill，
性能与稳定性在较长时间内不可比，回退也不简单。

### 7.3 风险与边界

- 新 pool 会占用容量，需先核 `MAX AVAIL`（当前 `26 TiB`）
- 新 pool 改变 pool_id ⇒ CRUSH 重算 PG→OSD 映射，**与旧 pool 的绝对值不可直接比**，
  必须在同一批次内做 A/B，不得跨批相减
- 即使 R1 达标，也只说明"读侧在新布局下达标"，⛔ 不得回溯宣称交付配置已达标

## 八、M 线：写侧架构（不承诺达标）

### 8.1 M1：方案盘点与工作量评估（纸面工作，不占集群）

针对"减少 / 批量化同步元数据事务"，至少评估四个方向：

| 方向 | 机制 | 需要评估的风险 |
|---|---|---|
| 多 slice/extent 更新的批量或合并提交 | 减少每次数据写触发的事务数 | 崩溃一致性窗口变大 |
| 数据写与非关键元数据更新的受控异步化 | 把非关键路径移出同步周期 | 故障恢复语义变化 |
| 同 inode 多请求的有序 pipeline | 替代全程持锁串行等待 | 顺序保证与重试语义 |
| 热点 inode 的元数据分片 | 提高单 inode 并行度 | 一致性与可验证性 |

每个方向必须给出：**预期提交率提升倍数**（当前 ≈`12K/s`，达标需 ≈`25000` 逻辑写/s，即需 ≈2 倍）、
代码改动面、协议兼容性、正确性验证清单、工作量与风险等级。

### 8.2 M2：选中方案的原型验证

- 对应 `TODO C04`
- 必须使用**新测试 volume/namespace**；
- **正确性签收先于性能签收**：崩溃一致性、重放、故障注入、旧版本回滚，全过之后才报性能；
- 性能报告沿用 §二 的全部口径。

### 8.3 与 C03 的关系

C03（TiKV 扩容/分片）需要新增节点与专用 NVMe，属容量项目。
其优先级由 A2（§6.4）决定，**⛔ 在 A2 出结论前不立项**。

## 十一、红线（逐项复核后在报告中打勾）

1. ⛔ 禁改系统 `ceph.conf`（md5 必须恒为 `5b6be34179a64e0a5f9c6d3a9690041f`）、禁 `ceph config set`；
2. ⛔ 禁 `ceph osd pool delete/create` 作为轮间清理；R1 新建 pool 是**实验对象**，需单独授权，且不得删除生产 pool；
3. ⛔ 禁写 `/dev/nvme*`、`/mnt/jfs-tikv`（A1 例外：仅在授权窗口内的精确临时目录）、`/opt`、`/etc`、`/var/lib/ceph`；
4. ⛔ 禁 `pkill`/`killall`/`fuser -k`/模式 kill；⛔ 禁 `fusermount -uz`、`umount -l`、`losetup -D`、`rm -rf`；⛔ 禁 kill mount PID；
5. ⛔ 禁 reboot/shutdown/systemctl 改生产服务（A1 的生产 TiKV 停启需单独授权与回滚计划）；
6. ⛔ 禁动 157 的 WekaIO、K8s、内核、网卡、RoCE、md0；
7. ⛔ 脚本内不得内嵌口令（既有例外 `FULLBASELINE_V4.sh:37` 已登记，建议轮换凭据）；
8. 失败即保留现场：不卸载、不删目录、不清 sampler；`incidents.tsv` 动作前后各一条；
9. ⛔ 禁同 RUN 热修后按正常签收、禁换 RUN_ID 重来、禁补样替换、禁把无效 RUN 点值与有效 RUN 拼接；
10. 执行方只交原始数据 + 逐门 PASS/FAIL + `incidents.tsv`；⛔ 不算效应量、不下结论、不挑轮次；
11. 报告首部必须有机器可读 VERDICT 行；⛔ 订正不得只写在附录。
