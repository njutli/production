## 〇、本计划与 02 计划的关系

02 计划的 A/B/C/D 四条主线是**按"改什么"分类**的（后端 / JuiceFS / OS / 方法论）。经过 02-2 整个稳定性攻坚阶段，我们发现真正决定能不能做的不是"改什么"，而是**"改这个东西要付出什么代价才能测出来"**：

| 旋钮的切换方式 | 噪声代价 | 可用分辨力 | 结论 |
|---|---|---|---|
| `ceph config set`（在线，不 remount 不重启） | 仅剩轮间噪声 | **1.5-7%（逐项）** | ✅ 可做，本阶段主力 |
| 需 remount（JuiceFS 挂载参数） | 重抽档位，跨实例极差 **29.9%** | 需多实例分布比较 | ⚠ 可做但成本 ×4 |
| 需重启 OSD | CV 从 0.27% 升到 **4.5%**，含组合 9.5-13.0% | 效应 3-7% 被噪声吞掉 | ⛔ 本阶段不做 |
| 需重铺 layout（format 级 / EC profile / 新池） | 换 epoch，绝对值不可比；删池重建曾致 PG 落点 100% 改变、漂移 16-37% | σ_layout 未知 | ⛔ 先测 σ_layout |

**因此 03 计划按"切换代价"重新分线**：T1（在线）/ T2（需 remount）/ T3（写侧含对象数预算）/ T4（重铺类）。02 计划的 A/B/C/D 条目全部映射进来，不丢项——映射表见 §十二.3。

## 二、⚑ 03-1 探针交叉验证结论复核（与执行方结论不同，须改判）

> 报告：`doc/perf-report/03-1-probe-cross-validation-20260806.md`
> 执行方结论：`Pearson r = 0.8801 → 相关性高 → 写侧指标可作为读侧参数调优的门控探针；T2 读侧调优难度从"最难"降到与写侧同级`
> **复核结论：该结论不成立。数据本身有效且很有价值，但支撑不了"可作门控探针"。**

### 2.1 r = 0.88 完全由 2 个点支撑

8 个样本是 6:2 的双簇结构（高档 6 个挤在 1861-1886，低档 2 个在 1211/1453）。对双簇数据算 Pearson r，本质是在做**两组均值差检验**，簇间距离提供了全部杠杆：

| 数据子集 | Pearson r |
|---|---|
| 全部 n=8 | **+0.8801** |
| 去掉 X1 | +0.7600 |
| 去掉 X2 | +0.8500 |
| **去掉 X1+X2（只留高档 6 个）** | **−0.1291** |

留一法显示去掉任一低档点 r 就明显掉；去掉两个低档点 r 直接**变负**。这不是"相关性高"，而是"两个簇的中心同向偏移"——后者是真的，前者不是。执行方给出的 Spearman ρ=0.5714 已经在报警，但被解释成"组内排序未完全保留"而放过了。

### 2.2 传导增益 0.22，写侧探针的信噪比比读侧探针差 22 倍

| 指标 | 组间信号（低档均值→高档均值） | 噪声 | SNR |
|---|---|---|---|
| randread（现用探针） | **+40.8%** | 档内极差 1.3% | **31.4** |
| mseqwrite（拟用探针） | **+9.0%** | 轮间极差最大 6.4%，档内跨实例 6.8% | **1.4** |

**传导增益 = 9.0 / 40.8 = 0.221**：档位在读侧动 40.8%，传导到写侧只有 9.0%。

⇒ **最小可判档差**（noise / gain）：
- 用轮间极差 6.4% → 需要档差 ≥ **29.0%**（换算到 randread 口径）
- 用档内跨实例极差 6.8% → ≥ **30.8%**
- 用最乐观的高档组标准差 2.42% → ≥ **11.0%**

也就是说，写侧探针最好情况下也只能分辨 **≥11%** 的档差，现实情况要 **≥29%**。

### 2.3 判据盲区：真正需要拒绝的中档，这次一个都没抽到

按 F3，档位是多档的：1714 / 1750 / 1790 相对高档 1880 只低 **4.8% / 6.9% / 8.8%**。而调优效应量本身就是 3-7%（§1.1）。

⇒ **门控探针必须能分辨的正是这 4.8-8.8% 的中档**，而 §2.2 算出写侧探针的分辨门槛是 11-29%。**中档对写侧探针完全隐形。**

本次 8 次挂载没有抽到任何中档（6 个全在 1861-1886，历史高档命中率只有 55%，这次 75% 且异常紧凑），所以"门控有效"这个结论在**最关键的区间上根本没被测试**。

### 2.4 时序混淆：低档两例恰好是头两次

X1、X2 是**最先跑的两个实例**，也是池对象数最低的两个（2.36M vs X8 的 ~17M）。而 F9 已确认存在**首运行效应**。

⇒ "头两次两个指标都低" 正是时序/首运行共因会产生的图形，与"档位传导"在本设计中**不可区分**（实例序 = 时间序 = 对象数序，三者完全共线）。
⇒ 缓解证据：R1 十组里低档出现在 g4/g6（不在开头），所以低档不**只**是首运行效应；但本次这两个点是否是纯档位，无法判定。

### 2.5 两处数值问题（不影响主结论）

1. §七 "空间放大 ~3.5×"：口径不明且与 R5 的 1.84-1.88× 不是同一指标。按本次数据 `ΔUSED/ΔSTORED = 5.24/3.5 = **1.50×**`，就是 EC 4+2 的 1.5 倍开销，正常。建议删掉或改标口径。
2. §五 "组间 gap 3.9%" 是 `max(低档)→min(高档)` 的**间隙**，不是组间差。两个指标都用间隙口径所以内部一致，但拿 3.9% 与"randread 28.1%" 比较容易被读成"传导只有 1/7"，真实传导增益是 0.22（§2.2）。**间隙 3.9% 的意义在别处**：它 < 单实例轮间噪声 6.4%，说明用单次 mseqwrite 分类高/低档时，判决边界的余量比噪声还小。

### 2.6 改判后的结论与影响

| 项 | 执行方 | 改判 |
|---|---|---|
| 相关性 | r=0.88，高 | **组间同向传导成立（增益 0.22），组内无相关（r=−0.13）** |
| 能否作门控探针 | 能 | **只能拒绝"严重低档"（≥29% 档差，即 1334 那一类），不能认证"同档"** |
| T2 读侧调优难度 | 降到与写侧同级 | **不变，仍是最难**；读侧参数调优不能靠写侧探针门控 |
| 落在任务书三种情形的哪一种 | 第一种（相关性高） | **第三种的变体：结论为"不可用作细粒度门控"，但产出了可量化的传导增益，是有效负结果** |

**这仍然是一次成功的实验**：它把"写侧探针"这条路线用 4.5h 关掉了，避免了在 T2 上按错误前提排数天的实验。同时它意外产出了三个可用副产品：
1. **传导增益 0.221** —— 首个跨侧耦合的定量值；
2. **高档带内极差 1.3%（n=6）** —— 独立复现了 F4，把"探针判为同档"的实际精度钉到 1.3%，这是 T2 路线②的关键参数（见 §七）；
3. **高档命中率 6/8 = 75%**（历史 55%），两次合计 ~11/18 ≈ 61% —— T2 的挂载次数预算依据。

⇒ **T2 定案走"多实例 + 高档带门控 + 分布比较"（原路线②），"换探针"路线（原提议）关闭。** 详见 §七。

### 5.4 集群实查发现的两个异常（新增，非 02 计划已知）

**异常一：osd.3 的 mClock IOPS 容量缺失，比同伴低 3-3.7×**

```
osd.0  osd_mclock_max_capacity_iops_ssd = 78571
osd.1  = 75968      osd.2  = 79983
osd.3  = (config dump 中无此项) → 取默认 21500
osd.4  = 65524      osd.5  = 63911
```

`osd_op_queue = mclock_scheduler`（Quincy 默认），容量值由 OSD 首次启动时自测并写回 mon config store。osd.3 显然**没写回**（benchmark 失败或被跳过），于是用了默认 21500。

- 相关性：这与长期未量化的 **PG 主分布 9:1 倾斜 + straggler（osd.4 延迟 4-5×）** 是同一族现象，且 osd.4/osd.5 的容量本身也比 osd.0-2 低 **18-20%**。
- 诚实的期望值：源码 `mclock_common.h` 显示 `BALANCED` 与 `HIGH_CLIENT_OPS` 的 client `limit` 均为 `0`（= `default_max`，不设上限），所以**空闲集群下 mClock 不会硬性截断客户端 op**，容量值主要影响 reservation 的绝对刻度。⇒ 预期效应**可能很小**。
- 但值得 30min：EC 4+2 的写必须集齐 6 个 shard、读需 4/6，**任何一个 OSD 被结构性压低都会传导到每一个 IO**；而这是一个**免费、在线、可回滚**的不对称修正。
- ⛔ 注意：把 `osd_op_queue` 换成 `wpq`（老调度器）**需要重启** ⇒ parked。

**异常二：`osd_memory_target` 已是 375 GB/OSD，02 计划 A2.2 作废**

```
osd  host:ceph-node1  osd_memory_target = 375831164518   (350 GiB)
osd  host:ceph-node2  = 375831178854
osd  host:ceph-node3  = 377978635264
osd  (默认层)          = 2147483648          ← 被 host 层覆盖
osd  osd_memory_target_autotune = true
```

02 计划 A2.2 写"osd_memory_target 16GB + BlueStore cache"，实际已经是它的 **22 倍**（cephadm autotune 按主机内存分配）。同时 `bluestore_cache_size` 被显式钉在 30 GiB 且 `autotune=false` —— 两者**语义冲突**（显式 cache_size 会让 memory_target 的自动伸缩失效）。⇒ **A2.2 作废**，改为 K2：不动总量，只调 KV/RocksDB 那一份的生效路径。

### 6.1 协议

> ⚑ **2026-08-07 依 03-2 结果重写**：原协议的 `2×|A−A'|` 分母此前 **n=0（无数据）**，T1 无法判定。03-2 已填上（F13），并同时证明该分母**随 A/A' 间隔增长** ⇒ 原"分臂串行"设计会使 T1 全线失效。

```
[前置] 池对象数门禁 ≤3.11M（⚑ 当前已是 2.36M，自动满足；F14）
   ↓

   ↓

   每个 A/B 单元 = 1 个 run，相邻单元必须是异臂
   ↓
判定：|median(B臂) − median(A臂)| ≥ max(该项分辨力, 2×漂移底噪(lag1))
```

**⚑ 判定分母（F13，lag1 口径，唯一可用口径）**

| 项 | 可检出效应量 | 2×漂移底噪(lag1) | 余量 | T1 可用性 |
|---|---|---|---|---|
| `randread` | ≥3.0% | 2×1.30 = **2.59%** | **+0.41 pp** | ✅ 可作判据（余量薄） |
| `mseqread` | ≥1.5% | 2×0.50 = **1.00%** | **+0.50 pp** | ✅ 可作判据（余量薄） |
| `seqread` | ≥4.0% | 2×3.89 = **7.78%** | **−3.78 pp** | ⛔ **不可作判据**，只能作旁证 |

**⚑ 三条由 03-2 新增的硬纪律**

1. **紧邻交错是硬要求，不是优化**。若 A/A' 任意间隔，门槛按全 45 对 max 计算 → `mseqread` 3.38%（>1.5%）、`randread` 3.04%（>3.0%）、`seqread` 9.58%（>4.0%）⇒ **三项全部失效**。分臂串行下 `mseqread` 会被系统性高估约 1%，**足以伪造一个"有效"结论**。

- **疑点（须诚实记录）**：若 H1 成立，`randread` 也应升温，但 `randread` 无趋势（Spearman +0.091）。可能因 randread 为 4K 随机、命中率本就低且已饱和；也可能 H1 本身不对。⇒ **按"待验假设"记录，不得当结论引用。**

## 七、T2：JuiceFS 挂载参数（多实例分布比较）—— P1

### 7.1 定案设计（§2.6 改判后）

```

比较两臂高档子集的 median
```

**为什么这样成立**：F4 + 03-1 独立复现 —— 高档带内极差只有 **1.3%**（n=6）。所以"探针判为高档"这个门控把档位污染压到 1.3% 量级，配合 n≈7 取中位数，残余档位噪声 ≈ 0.5%，足以支撑 3% 级效应判定。

**⚠ 读侧参数（`--max-readahead` 类）仍是最难，且本阶段不建议做**：探针本身就是 randread，改读侧参数会同时改探针，门控失效；写侧探针已被 §2.2 证明分辨力不足（11-29% ≫ 需要的 4.8-8.8%）。
⇒ **读侧挂载参数推迟到 04 阶段**，或等到有人给出一个"与读路径解耦、又能分辨 5% 档差"的第三种探针（目前没有候选）。
⇒ 顺带：`--max-readahead 0`（ra0）口径已在 02 计划 §9.1 由用户拍板锁定，本阶段**不动**。

### 7.2 排期

| 序 | 战役 | 参数 | ITEMS | 挂载次数 | 机器时间 |
|---|---|---|---|---|---|

## 八、T3：写侧战役的对象数预算（贯穿 T1.4-T1.6 / T2.1-T2.3）

这不是一条独立战线，是**所有写侧战役的前置约束**。03-1 的教训（§3.1）必须制度化。

> ⚑ **2026-08-07 依 F14 重写**：原模型是"**累积**总量预算"（假定对象泄漏不可逆），已证错误。正确模型是"**峰值** + **排空窗口**"。

### 8.1 预算算式（⚑ 峰值口径）

| 量 | 值 | 来源 |
|---|---|---|
| 安全上限（轮前） | **3.11M** 对象 | R5 |
| 拐点区间 | (3.78M, 4.40M] | R5 |
| 稳定起点 | **2.36M**（空闲态自动回归此值） | F14 实测，08-06/08-07 三次一致 |
| **单轮峰值预算** | **≈1.42M** 对象 | 3.78 − 2.36 |
| mseqwrite 净增（180s × 2 轮） | **1.83M / 实例**（⚑ **瞬时峰值贡献，非永久**） | 03-1 实测（+14.67M / 8） |
| 每对象数据量 | 292 KiB | R5 |
| ⚑ **排空速率** | **14.67M 对象 / ≤66min ≈ ≥3700 对象/秒** | F14 实测（20:10 → 21:16） |
| compact 耗时 | `1.95e-4 × 回收对象数` 秒 | R5（误差 6%） |

⇒ **单个 mseqwrite 实例的峰值增量（1.83M）就会吃掉 1.29 倍的单轮峰值预算**，即**一轮 mseqwrite 就能把轮前对象数顶过拐点**。这与旧模型的结论一致——**约束依然紧**——但**成因不同**：不是垃圾积累不掉，而是**单轮生成太快、来不及排空**。

⚑ **03-1 就是这么坏掉的**：8 个实例连续跑、中间无排空窗口，X3 起轮前对象数已越过 3.78M，**X3-X8 的 mseqwrite 绝对值全部报废**（§3.1）。

### 8.2 纪律（⚑ 重写，写入 `TUNING-SKILL.md`）

1. **每轮前门禁（不变）**：轮前 `OBJECTS ≤ 3.11M`，超限则等待排空/先 compact，不达标则中止该轮并记 `obj_gate=DIRTY`（不进统计）——与现有 `pg_gate` 同构。见 §十一 `obj_gate()`。
2. ⚑ **每个写侧 run 之后留排空窗口**（替代原"删文件 + compact"）：等待 `OBJECTS` 回落到 ≤2.5M 再起下一个 run。**首选办法是等待**（后台任务自动完成，实测 ≥3700 对象/秒，1.83M 约需 **≤10min**），**不需要删文件、不需要 `gc --delete`**。`gc --compact` 仍可用于加速切片合并，但不是回收的必要条件。
3. ⚑ **排空窗口必须显式计入工期**：不再是"纯 compact 2.3h"，而是"每写侧 run 后 ~10min 等待"。6 run 交错的写侧战役 ≈ **+1h 等待**。
4. ⚑ **禁止"连续多个写侧 run 不看对象数"**——这是 03-1 唯一的实质损失来源。门禁必须逐 run 生效，不是逐战役。
5. **A/B 交错是硬要求（不变，且理由加强）**：即使有门禁，残余对象数漂移仍与时间序共线（§2.4）；且 F13 已证同实例本身存在与时间共线的漂移（mseqread +0.939）。⇒ 见 §6.1。
6. **报数必须附轮前对象数列**，使事后可做 F6 的偏相关校正。⚑ 并附**该 run 的峰值对象数**（不只是轮前值）。

## 九、T4：重铺类（layout / format 级）—— 暂缓，需先测 σ_layout

### 9.1 哪些旋钮属于这一类

JuiceFS **BlockSize**（format 时定，改不了 ⇒ 只能建新卷）、format 级 **compress**、**EC profile / 新池**。

### 9.2 为什么不能直接测

- 重铺 = 换 layout epoch。重铺等价一次超级 compact（把对象数归零）⇒ **跨 epoch 绝对值不可比**。
- ⇒ 两臂都必须重铺、且 **A/B 交错重铺**。
- σ_layout（同参数重铺的批间标准差）**未知**，且有理由认为不小：删池重建曾致 32/32 数据 PG 的 acting set **100% 改变**、randread 漂移 16-37%（`00-baseline-20260723.md:223,250,306`）。
- ⛔ 脚本 `phase0_layout`（`FULLBASELINE_V4.sh:722`）含 `rm -rf ${TEST_DIR}/*`（384 文件，10.5min）。

### 9.3 定案打法

1. **先做 σ_layout 试点**：同参数重铺 K=4，只跑 `randread randrw randwrite`，6-8h。
   - σ_layout ≤2% → 可做随机区组设计（用户提的"多次 layout 取平均"方向正确）；
   - σ_layout >5% → T4 全线关闭到 04 阶段。
2. **BlockSize 当"验证机制预测"而非"精测"**：256K→1M 是"对象数 ÷ 4"的 **300% 级**效应（F6 给了对象数→性能的定量关系），属于验证性实验，K 可压到 2-3，不需要精测分辨力。
3. 用户曾提的"同池两卷交错测"降级为**备选、非首选**：写侧共享池，对象数会被另一卷污染。

## 十三、口径与红线

### 13.1 测试口径（继承，全部已固化在 `skills/FULLBASELINE-SKILL.md`）

- **验收口径**：逐秒均值，窗口 `15 ≤ sec − t0 ≤ 175`（相对起点，非绝对时刻）；取该项**逐轮中位数**。不认 fio 汇总 BW（`rounds.tsv` 的 `BW_MiBs` 列是 fio 汇总值，**不是验收口径**）。
- **方向位**：randrw 必须过滤方向（V4 `:979` 取读侧）；报数标口径（F10）。
- **首轮规则**：`randwrite` / `randrw` 首轮单独记录、不进 L2 统计（F9）。
- **L2**（轮间极差）/ **L3**（跨运行 median 偏差）判据 + 逐项分辨力（§1.1）。
- block size 256K（对齐 EC stripe_width）、openfiles=128、`--max-readahead 0`（ra0，已拍板）、`--cache-size 0`。
- **门控前置**：任何 A/B 对比前必须探针门控并固定实例（F1）。
- **ITEMS 纪律**：子集绝对值 ≠ 全量绝对值；每战役自带同 `ITEMS` 基线臂（F11）。
