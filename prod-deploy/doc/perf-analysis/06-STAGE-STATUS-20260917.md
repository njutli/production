## 0.2 方法术语

| 术语 | 含义 |
|---|---|
| **ε（同臂重复漂移）** | 同一配置在一轮内跑两次，两次自身的差。用来量化"环境噪声有多大" |

## 0.3 缓存目录结构（实测路径）

```
<cache-dir>/<卷UUID>/raw/chunks/873/873183/873183997_0_262144      # 262176 B = 256 KiB + 32 B 校验尾
<cache-dir>/<卷UUID>/rawstaging/chunks/…
```

| 目录 | 内容 | 能否丢弃 |
|---|---|---|
| `raw/` | **读缓存**块。对象存储里已有一份，本地这份是副本 | **可以**，随时淘汰 |
| `rawstaging/` | **写回暂存**块。开 `--writeback` 时先写这里就向应用返回"写完成"，后台再异步上传 | **绝对不能**，上传成功前是数据唯一副本 |

正因"可丢 / 不可丢"的差别，JuiceFS 给两者不同的空间余量线（见 0.5）。

⚠️ **重要计量陷阱**：开 writeback 时 `disk_cache.go:801` 用 `os.Link` 把每个暂存块**硬链接**进 `raw/`，
两个目录**共享 inode**。因此 `du raw + du rawstaging` 是**重复计数**，必须按 inode 去重才是真实占盘。

| 缩写 | 全称与作用 |

## 0.5 `--cache-size` 是总开关

`--cache-size`（MiB）是**读缓存容量额度**，同时是整个缓存子系统的**总开关**
（`cached_store.go:562-570 SelfCheck`）：

```go
if !c.CacheEnabled() {            // CacheEnabled() = CacheSize > 0
    if c.Writeback || c.Prefetch > 0 {
        logger.Warnf("cache-size is 0, writeback and prefetch will be disabled")
        c.Writeback = false       // 强制关写回
        c.Prefetch  = 0           // 强制关预取
    }
    c.CacheDir = "memory"
}
```

⇒ `--cache-size 0` **强制关闭 writeback 与 prefetch**（命令行即使写了 `--writeback` 也会被关）。
这就是为什么我们的 C 臂"无缓存"自动等于"无写回、无预取"。

⚠️ **`--cache-size` 与 `--cache-large-write` 是两个不同开关，不可混称。**
04 阶段**设了** `--cache-size`（见 4.2 各格实测值），**没设** CLW；
CLW 在 04-tmp2i / 04-tmp2j / 06-1 三个归档中**命中数均为 0**，是 **06-3 首次引入**。

06-1 是否开写缓存：T1/T2 有 `--writeback`；C1/C2 因 `--cache-size 0` 被**强制**关闭。

## 0.6 写缓存容量与 `--free-space-ratio`

**没有独立的写缓存容量参数。** 源码核实：

- 暂存目录与读缓存**同目录同盘**，且 **JuiceFS 1.4 不可能分盘**（两条路径都由同一 `cache.dir` 派生）；
  要分散只能配多个 `--cache-dir`
- 暂存块以 `size<0` 记账（`disk_cache.go:802`），**完全不占 `--cache-size`**
  ⇒ `--cache-size 98304` 只约束读缓存
- `--writeback-threshold-size`（`cmd/mount.go:389`）默认 `BlockSize+1`（`cached_store.go:607-608`）
  = 256K+1 ⇒ 256K 块恰好**可以**进暂存
- 实际空间约束来自 `--free-space-ratio`（**可调**，默认 `0.1`，`disk_cache.go:114-115`；本阶段全程设 `0.20`）：

```
isFull(usage, stage=true):   剩余空间比 < freeRatio/2 (=0.10) ⇒ stageFull ⇒ 写回回落为同步 PUT
isFull(usage, stage=false):  剩余空间比 < freeRatio   (=0.20) ⇒ 读缓存停写 / 触发淘汰
（inode 剩余比按相同阈值同时判断）
```

**`--free-space-ratio` 对 randrw 有影响吗？有，但迄今所有已执行测试都未触发它** ⇒ 属"潜在影响，未显现"：

| RUN | 缓存盘可用 | 去重后实占峰 | 剩余比 | 是否触发 |
|---|---|---|---|---|
| 04-tmp2i P25 | 128 GiB（loop） | **59.40 GiB** | 53.6% | 否 |
| 06-1 T | 834.4 GiB | ≈96 GiB | >88% | 否 |
| 06-3 W | 834.4 GiB | ≈96 GiB | >88% | 否 |

一旦触发，`stageFull` 会使 writeback 立即退化为同步 PUT、收益归零 —— 这正是 06-3 任务书把它列为容量硬门的理由。

吸收小 IO、避免频繁 flush**（官方 `zh_cn/guide/cache.md:133`+`:137` 明确页缓存延时微秒级、
吞吐几 GiB/s；`:141` 的 `writeback_cache` 专为 10–100 字节级高频小写而设）。

该口径与06阶段既有数据不可直接混用。06-4最终采用一个新RUN内的`D1/B1/B2/D2`
配对对照，只解释同批应用I/O模型变化，不拿旧历史值充当对照：

| # | 强制条件 |
|---|---|
| ① | 结果必须标注「**缓冲 I/O（`direct=0`）**，数据集 128 GiB < 宿主内存（≥750 GiB），**含宿主 page cache 命中**」 |

| ③ | 记录客户端`MemTotal/MemAvailable`和实际QD，明确128GiB数据集小于宿主内存 |

## C-5 缓存命中全部由宿主页缓存供给，介质读为零

### 为什么 direct IO 还会有宿主页缓存

`--direct=1` 挂在**挂载点**上，绕过的是「内核对**这个 FUSE 文件**的页缓存」。
但**本地读缓存是另一条路径**：juicefs 进程用**普通 buffered 文件读写** `<cache-dir>/<UUID>/raw/<key>`
（ext4 on nvme1n1），**没有 O_DIRECT**：

- **写**缓存块 → 先进宿主页缓存变成脏页
- **读**缓存块 → 若仍在页缓存里就**直接内存命中，根本不碰 NVMe**

本机 `MemAvailable ≈ 916 GiB`、实测 `Cached` 峰 `743 GiB`，缓存额度仅 96 GiB ⇒ 可整体常驻内存。

## C-7 缓存准入的真实作用域（CLW 与 WB 的关系）

### C-7.1 三层作用域必须区分

| 机制 | 控制点 | 与 CLW 的关系 |
|---|---|---|
| 读缓存的**读路径填充**（miss 后 GET 回来的块入缓存） | 读路径，`--cache-size`>0 即生效 | **无关** ⇒ 04-tmp2j C96 无 CLW 仍有 31.55% 命中 |
| 读缓存的**写路径准入**（本地写产生的块入缓存） | `cached_store.go:368` `if sync && (blen < BlockSize \|\| CacheLargeWrite)` | **直接相关**；256K 满块 ⇒ 不开 CLW 就不入 |
| **写回暂存**（rawstaging） | `cached_store.go:424` `if s.writeback && blen < WritebackThresholdSize` | **完全无关** |

⇒ 准确说法是「**新写的满块没进读缓存**」，而不是「写缓存没生效」。

### C-7.2 开 WB 会自动绕过 CLW 门槛

`disk_cache.go:793-806`：stage 成功后，只要读缓存启用，就 `os.Link(stagingPath, path)` 把暂存块
**硬链接**进读缓存，并以 `-int32(len(data))` 负值记账（不占 `cache-size`）。

### C-7.3 四组配置的准入行为与实测命中率

| 来源 | WB | CLW | 新写满块入读缓存？ | 途径 | 命中率 | blockcache 峰 | 读 MiB/s |
|---|---|---|---|---|---:|---:|---:|
| 04-tmp2j C96 | 无 | 无 | **否** | —（命中全来自读路径填充） | **31.55%** | 96.03 GiB | 1743.09 |
| **06-1 T1 / T2** | **有** | **无** | **是** | WB 的 `os.Link` | **41.82% / 42.39%** | 96.05 / 96.03 GiB | 2157.69 / 2080.46 |
| 06-3 S1 / S2 | 无 | **有** | **是** | CLW（`:368`） | 45.26% / 42.38% | ≈96.0 GiB | 616.22 / 526.47 |
| 06-3 W1 / W2 | 有 | 有 | **是** | 两条路都开 | 44.71% / 44.69% | ≈96.0 GiB | 513.68 / 516.07 |

**三条结论**：

1. **命中率确实提升 +11~14 个百分点**（31.55% → 42~45%）⇒ 机制预期实现
2. **WB 或 CLW 任一即可达成，两者叠加无额外增益** ⇒ **CLW 在 W 臂是冗余开关**
   ⇒ 有利副作用：06-3 W 与 S 的真实差异**只有 `--writeback` 一项**，比较设计干净

   ⇒ 「把写数据带进读缓存」这条路 **06-1 已跑通并伴随高带宽**

### C-7.4 与"读前必须固化到集群"的关系

历史讨论中的现象实际包含**两件独立的事**：

| | 现象 | 源码机制 | 谁能解 |
|---|---|---|---|
| (a) | 读之前要先把写的数据"固化到集群" | **M1**：`vfs.go:787` read 前无条件 flush；非 WB 下"完成"= PUT 返回 | **只有 `--writeback`**（"完成"改为落 rawstaging 即返回）。⛔ CLW 无效 |
| (b) | 写入的数据不进读缓存，读要回源 GET | **M2**：`cached_store.go:368` | **CLW**；**或** `--writeback`（`os.Link` 顺带解决） |

⇒ **CLW 只解决 (b)**。上述描述准确对应**不开 writeback** 的情形；
一旦开 writeback，(a)(b) **同时消失**，CLW 变冗余。

### C-7.4b 常见误解订正：「开 WB 会导致读/写缓存不一致，需 CLW 补齐」——不成立

这是一个需要明确否定的模型。JuiceFS 1.4 中**读缓存与写缓存从一开始就是一致的 ——
物理上就是同一个 inode 的两个名字**（`disk_cache.go:798-802`）：

```go
err := cache.flushPage(stagingPath, data, false, tierID)   // 落 rawstaging
if err == nil {
    ...
    if cache.enabled() {
        path := cache.cachePath(key)                        // raw/<key>
        cache.createDir(filepath.Dir(path))
        if err = os.Link(stagingPath, path); err == nil {   // :801 硬链接
            cache.add(key, -int32(len(data)), ...)          // :802 登记进 keys 索引
        }
    }
}
```

且 `add()` 中 `if size > 0` 对负值为假 ⇒ 暂存块**不占 `--cache-size` 额度**，
但**条目已进 `cache.keys` 索引 ⇒ 立即可命中**。

三层独立证据：

| 层次 | 证据 |
|---|---|
| 源码 | `:801 os.Link` + `:802 cache.add(key, -size, …)`；`add()` 负值不计入 `cache.used` 但入 keys |
| 文件系统 | 04-tmp2i P25 归档 `cache-inodes-formal-end.tsv`：122,486 个 rawstaging 文件**全部**在 `raw/` 有硬链接（重复 inode 122,486，**100%**） |
| 性能计数器 | 06-1 T 臂**有 WB、无 CLW**，命中率 **41.82% / 42.39%**（vs 04-tmp2j C96 无 WB 无 CLW：31.55%） |

⇒ **"免除读前 flush 到集群" + "新写数据能本地命中"这两件事，只需 `--writeback` 一个开关即全部达成。**
CLW 的定位是「**不开 writeback，但仍想让本地写的满块进读缓存**」—— 而该场景**免不掉** flush 到集群。

两开关作用域对照：

| 配置 | 读前是否要等数据落集群 | 新写块能否本地命中 |
|---|---|---|
| 无 WB、无 CLW | **要**（等 PUT 返回） | **不能** |
| 无 WB、**有 CLW** | **要** | 能 |
| **有 WB**、无 CLW | **不要**（落 rawstaging 即返回） | 能（`os.Link`） |
| 有 WB、有 CLW | 不要 | 能（**CLW 冗余**） |

### C-7.6 M1 到底在等什么（2026-09-17 源码澄清）

常见疑问：「既然读缓存与写缓存一致，读前完全没必要等数据上传到集群。」
**这个判断是对的，但 M1 等的并不是"上传到集群"。** 逐层澄清：

**① M1 等的是「pending slices 数据落地 + 按序提交元数据」，不是"上传到集群"**

`vfs.go:787` 每次 read 前 `v.writer.Flush(ctx, ino)`；`writer.go` 的 flush 循环：

```go
for len(c.slices) > 0 {
    s := c.slices[0]
    for !s.done {                                    // :201  等数据落地
        if s.notify.WaitWithTimeout(100ms) && !s.freezed && time.Since(s.started) > flushDuration*2 {
            s.freezed = true; go s.flushData()       // :204  超时则强制刷
        }
    }
    for s.dep != nil && !s.dep.committed {           // :207  等依赖 slice 提交
        f.commitcond.WaitWithTimeout(100ms)
    }
    ...
    err = f.w.m.Write(..., ss, s.lastMod)            // :215  提交 slice 到元数据
}
```

「`s.done`」的含义随配置而变（`cached_store.go`）：

| 配置 | "落地"= | 是否要等集群 |
|---|---|---|
| 非 writeback | 对象 PUT 返回（`:368` 路径） | **要** |
| **writeback** | 写入 `rawstaging` 返回（`:424` 路径） | **不要** |

⇒ **开 writeback 后，M1 确实不再等上传到集群，只等本地落盘。** 你的判断成立。

**② 那为什么读必须等？—— 是元数据顺序/可见性，不是缓存一致**

写操作产生一个 **slice**；读路径要先从元数据解析 `offset → slice 列表`，才知道去取哪些块。
**未提交（`:215 m.Write` 未执行）的 slice 对读路径不可见** ⇒ 读会返回**旧数据**。
这就是 POSIX read-your-own-writes 语义，⛔ **不可删除**。
⇒ 与"读/写缓存是否一致"**无关** —— 即使块已经在本地缓存里躺着，元数据不指向它，读也找不到。

**③ 非 writeback 下为什么提交必须先等 PUT？**

因为 slice 一旦提交，就对**该卷所有客户端**可见（该卷当前有 2 个活跃 session，见 C-11.3）。
若数据只在本地 `rawstaging`，其他客户端取不到。
⇒ **writeback 的本质是：用"牺牲跨客户端立即可读性与持久性"换取"提交不必等 PUT"。**
这既是它的收益来源，也是它的风险面。

**④ M1 的真实成本：读前要 flush 该文件的「全部」未完成写**

`vfs.go:787` flush 的是**整个 inode**，不是读请求覆盖的范围。
本阶段几何为每 job 一个 1 GiB 文件、QD128、50/50 ⇒ 单文件随时可有约 64 个未完成写
⇒ **每次读要等这 64 个写全部落地**。
- 非 WB：等 64 次 PUT ⇒ 这就是 06-1 T 臂 `+19.56%` 的来源（WB 把它变成 64 次本地落盘）
- ⇒ 这也正是 `range-flush.patch` 的动机：把 flush 范围收窄到读请求覆盖的 range

**⑤ 修正：假设① 的适用范围收窄（对我方前述表述的更正）**

此前把「约 100 ms 超时轮询」笼统写作 M1 的成本，**不准确**。冻结基座实测：

| 位置 | 覆盖写场景下是否命中 | 说明 |
|---|---|---|
| `:201-206` `s.notify.WaitWithTimeout(100ms)` | **不构成惩罚** | `:112 s.notify.Signal()` 在 slice done 时及时唤醒；100 ms 只是安全超时，用于强制刷长期空闲 slice（`flushDuration = 5 s`，`:32`） |
| `:207-209` `commitcond.WaitWithTimeout(100ms)` | **不进入** | `s.dep` 仅在 `:305-313` 的 `if s.growing` 分支内被赋值；128 个预建满文件**纯覆盖写** ⇒ `s.growing` 恒假 ⇒ `s.dep` 恒 nil ⇒ 循环跳过 |

⇒ **基座代码在覆盖写场景下没有 100 ms 轮询惩罚。**
⇒ 100 ms 轮询是 **`range-flush.patch` 独有的缺陷**：该补丁把 waiter 扩到 `rangeScope`，
而 `:233-234` 的 `Broadcast()` 仅在 `s.growing` 时触发（覆盖写下永不触发）
⇒ waiter 只能靠 100 ms 超时返回。
⇒ 假设① 应重述为「**range-flush.patch 在纯覆盖写下退化为约 100 ms 定时轮询**」，
⛔ 不得表述为"M1 本身有 100 ms 轮询"。这正是 06-2b 要修的对象。

### C-7.7 CLW 带宽收益的实测状态

- 06-3 S/C 两配对 `−3.53% / +7.85%`（读），ABBA `+1.40%`，材料线 `47.16%` ⇒ **不可判**
- 但 06-3 的 C 臂本身只有 638.77（06-1 C 是 1804.72，−64.6%）⇒ **整轮后端状态崩坏**
- ⇒ **判断：机制有效且已实现；带宽收益在 06-1 环境下方向为正（+19.56%，不可判），
  在 06-3 崩坏环境下测不出。真正阻碍下结论的是后端状态漂移（C-9），不是 CLW 本身。**
- ⚠️ 按 C-10.1 的转化率外推，CLW 的预期效应仅 `+3.4~4.3%`
  ⇒ 06-1（M=14.17%）与 06-3（M=47.16%）**都不可能测出**，须靠第 4 步的相邻交错设计

- **06-3 的低带宽不是客户端上传并发不足**（槽位还剩 30%–73%）
- 06-1 与 06-3 处在**性质不同的工作区**（一个上传槽绑定、一个不绑定），进一步说明状态不可比
- 与 05-2 独立发现一致：`150 槽是绑定约束而非吞吐约束`

### C-9.3 06-2/06-3 取消 GC 是有理由的主动选择（非疏漏）

**06 阶段不是从一开始就禁 GC：06-1 执行了 GC，06-2/06-3 才改为默认不主动执行。** 当时的两条理由：

1. **减少额外变量** —— GC 不是轻量清扫。06-1 记录显示每次 compact 约 **50 万 slices / 128 GiB**、
   清理约 **150 万 pending slices**、耗时约 **160–168 s**。测缓存或 flush 改动时，不希望轮间再加一轮重型整理。
2. **限制操作范围** —— GC 作用于**整个共享卷**，不只是本轮 128 个测试文件；主动整理需单独确认范围与影响。
   ⇒ 已由只读验证坐实：该卷当前有**另一个活跃客户端** `sid 995 ceph-node3 /var/lib/juicefs-portal/namespace-mount`。

⚠️ 这是「GC 可能造成混杂」，**不是**已证明 GC 有害或会降低性能。

**须区分三个层次**：

| 层次 | 06-1 | 06-2/06-3 |
|---|---|---|
| JuiceFS GC/compact（回收对象、整理 slice） | 每格执行 | **不再自动执行** |
| 主动 OSD compact（整理 Ceph 自身数据库） | 禁止 | 禁止（阶段计划起即默认禁止，需专项授权） |
| 后台自动回收、TiKV/RocksDB 自动 compaction | 正常运行 | 正常运行（**未关闭**） |

且 06-3 任务书 `:159` 明写：起点不可比时应暂停，单独审批精确恢复方案 ⇒ **不是永久禁止恢复**。

### C-9.4 GC 作为混杂变量高度对称（2026-09-17 实测）

06-1 五次 GC 的实际工作量（`recovery/*/gc.stderr`）：

⇒ 作为混杂变量**高度对称**，且被 ABBA 轮序进一步抵消。
⇒ 这**减弱**（但不排除）「GC 是混杂」的担忧；也说明 06-2/06-3 的取消决定虽有理由，

## C-10 命中率提升为何没转化为带宽（2026-09-17 新增）

### C-10.1 主因可量化：预期效应量只有 +3.4~4.3%，而这一轮的尺子是 47.16%

用 04-tmp2j 容量曲线的**实测**转化率外推（同一负载、同一批 128×1GiB 文件）：

| 22.63% → 31.55% | +8.92pp | +5.87pp | 0.658 |
| 31.55% → 38.16% | +6.61pp | +1.25pp | 0.189 |
| 38.16% → 47.41% | +9.25pp | +3.77pp | 0.408 |
| **C96 → C256 合计** | **+15.86pp** | **+5.02pp** | **0.317** |

按 `0.317` 外推 CLW 的效应：

| 配置 | 命中率 | 相对 C96 | 预期带宽增益 |
|---|---:|---:|---:|
| 06-3 S2 | 42.38% | +10.83pp | **+3.43%** |
| 06-3 S1 | 45.26% | +13.71pp | **+4.34%** |

对比材料线：

| RUN | M | 所需分辨率倍数 |
|---|---:|---:|
| 06-3 | 47.16% | **约 11 倍** |
| 06-1 | 14.17% | **约 3.3 倍** |

⇒ **06-1 与 06-3 都不可能测出 CLW 的预期效应。"没测出来"是必然的，不是异常。**

### C-10.2 根因：`rwmixread=50` 把读带宽与写带宽锁死成 1:1

**这是 randrw 转化率低的结构性原因，不是若干因素的叠加。**

fio 的 `rwmixread=50` 强制维持读写比例 ⇒ **读带宽与写带宽被锁定相等**。全部实测格印证：

| RUN | 格 | READ | WRITE | 差异 |
|---|---|---:|---:|---:|
| 06-1 | C1 | 1804.72 | 1808.10 | 0.19% |
| 06-1 | T1 | 2157.69 | 2161.70 | 0.19% |
| 06-3 | C1 | 638.77 | 639.79 | 0.16% |
| 06-3 | S1 | 616.22 | 617.81 | 0.26% |

⇒ 十格全部在 **0.3% 以内**。

由此推出关键结论：

1. **缓存只能加速读的那一半**；写必须 PUT 到集群，缓存对写侧无直接作用
2. 但 **读带宽不能超过写带宽**（比例锁定）⇒ **读侧的富余能力无法兑现**
3. ⇒ 若写侧是瓶颈（06-1 四格 `object_request_uploading` 全部 150 饱和，C-8），
   把读做到无限快也**换不来任何带宽提升**

**那为什么转化率不是 0 而是 0.317？因为存在一条二阶（间接）通道：**

```
读命中率↑ → 发往 Ceph 的 GET 流量↓ → 同一组 6 个 OSD 腾出能力给 PUT
          → PUT 有效时延↓ → 写带宽↑ → （比例锁定）读带宽也↑
```

两条实测支撑：

| 证据 | 数据 |
|---|---|
| GET 流量确实随命中率下降 | 04-tmp2j：数据网 RX 从 A0 的 `1910–1975` 降到 C256 的 `1150 MiB/s` |

⇒ **缓存对 randrw 的作用是"通过卸载读流量间接给写侧腾空间"，而非"直接加速读"。
这条通道天生是二阶的，所以转化率只有约 0.317。**

### C-10.3 randread 为什么接近 1

| 维度 | randread | randrw 50/50 |
|---|---|---|
| 比例锁定 | 无 —— 读就是全部 | **有** —— `read_bw ≡ write_bw` |
| 缓存作用于关键路径 | **是**，直接缩短 | 否，只作用于非瓶颈的一半 |
| 收益通道 | 一阶（直接） | **二阶（卸载 GET → 腾出 PUT 能力）** |
| M1 读前强制 flush | 无写可 flush ⇒ 无成本 | **每次读要 flush 该文件全部未完成写** |
| 覆盖写使旧读块失效 | 无 | 有：04-tmp2j C96 `W4/W1 = −22.51%`、CV `13.2%`；06-3 S1 `drops 302,759` + `evicts 425,898` |
| 本地缓存写入成本 | 很小（只填充） | 大：S 臂介质写 `600–624 MiB/s`、util 峰 `100.40%`、Dirty `26–28 GiB` |
| 命中读是否碰介质 | 否（宿主页缓存） | 否（同上，C-5） |

⇒ randread 缓存收益近似线性；randrw 的收益被"比例锁定 + 二阶通道 + 三项成本"三重压缩。

## C-12 元数据量、提交顺序与"减少元数据"的收益上限（2026-09-17 新增）

### C-12.1 元数据有多少：每个 256K 写 ≈ 1 次元数据事务

06-1 四格 `cells/*/mechanism/*.prom` 正式窗（约 180 s）增量实测：

| 格 | 元数据事务数 | 事务/s | 事务均值 | 写 ops/s | **事务/写操作** | meta_ops 总数 |
|---|---:|---:|---:|---:|---:|---:|
| C1 | 1,372,122 | 7,640 | 2.59 ms | 7,232 | **1.056** | 3,161,802 |
| T1 | 1,612,800 | 8,955 | 7.47 ms | 8,647 | **1.036** | 3,788,966 |
| T2 | 1,563,181 | 8,713 | 8.32 ms | 8,334 | **1.046** | 3,645,059 |
| C2 | 1,290,467 | 7,185 | 4.55 ms | 6,722 | **1.069** | 2,944,722 |

⇒ **每个 256K 写操作恰好对应约 1.04–1.07 次元数据事务**，与源码 `writer.go:215`
（每提交一个 slice 调一次 `f.w.m.Write(...)`）严格吻合。
⇒ 单格 180 s 产生 **129 万–161 万次元数据事务**、**294 万–379 万次 meta_ops**
（meta_ops / 事务 ≈ 2.3，即一次事务含约 2.3 个元数据操作）。

旁证（06-1 GC 记录，C-9.4）：单格 180 s 覆盖写产生约 **50 万 slices 待 compact + 145~171 万 pending slices 待删**。

⇒ **元数据量确实巨大，且与写操作数严格 1:1 —— 这是 randrw 覆盖写的固有代价（每次覆盖写产生一个新 slice）。**

### C-12.2 "元数据顺序"是什么：同 chunk 内 slices 必须按创建顺序提交

源码 `writer.go:198` 原注释：`// the slices should be committed in the order that are created`。
实现：flush 循环取 `c.slices[0]`，处理完 `c.slices = c.slices[1:]`（`:236`）⇒ **严格 FIFO**。

**为什么必须有序**：slice 是 COW 的，同一 chunk 内的 slices **会重叠**（随机覆盖写必然重叠）。
读路径按提交顺序叠加解析。若乱序提交，后写的数据会被先写的覆盖 ⇒ **返回错误数据**。

**要等元数据保存到元数据引擎吗？—— 要，同步等 TiKV 事务返回。**

`:215 err = f.w.m.Write(meta.Background(), f.inode, c.indx, s.off, ss, s.lastMod)` 是同步调用。
实测事务均值 **2.59–8.32 ms** ⇒ 这是**真实的、位于 M1 关键路径上的等待**。

且**单文件内串行**：`:211 f.Unlock()` → `:215 m.Write` → `:219 f.Lock()`，
虽然释放了锁，但循环仍逐个处理 slices ⇒ 一次读若前面有 N 个未提交 slice，就要**串行等 N 次事务**。

⇒ **元数据事务并发上限 ≈ 文件数（本几何 128）**，因为每个文件的 flush 各自串行。这是结构性上限。
05 阶段独立实测印证：`4K 格元数据事务在途 74–92（贴 ~128 inode 串行上限）`（周报 0919 §2.2）。

### C-12.3 "减少元数据能提升多少"：256K 上收益空间有限（可量化）

用「元数据事务通道利用率」= 事务总耗时 ÷ (窗长 × 128 串行上限) 来界定上限：

| 格 | 事务在途（= 事务耗时/窗长） | 占 128 上限 |
|---|---:|---:|
| C1 | 19.8 | **15.4%** |
| C2 | 32.7 | **25.5%** |
| T1 | 66.9 | **52.3%** |
| T2 | 72.5 | **56.6%** |

对比 05 阶段 4K 格：在途 **74–92**（58%–72%），且 05 判定其为限流器。

⇒ **结论（对 06 阶段有直接规划价值）**：

| BS | 元数据事务在途 | 是否为限流器 | 依据 |
|---|---|---|---|
| 4K | 74–92 / 128（58–72%） | **是** | 05 §2.2 实测：`uploading` p95 仅 42、buffer 仅用 10.8 MiB ⇒ 上传槽未参与，瓶颈在元数据事务速率 |
| **256K（06 阶段固定）** | **19.8–72.5 / 128（15–57%）** | **不是主瓶颈** | 通道未饱和；同期 `uploading` 满 150（C-8）⇒ 绑定约束在对象完成率/上传槽 |
| >256K | — | 不是 | 05 §2.3：对象大小不再变，只增加每请求对象个数，对象完成率钉住 |

⇒ **⛔「减少元数据」不是 06 阶段（固定 256K）的高收益方向。** 这是一条有用的**负面结论**：
可据此排除该方向，把精力集中在已识别的写侧（对象完成率 / 上传槽 / M1 flush 范围）约束上。

⚠️ 但需注意**趋势**：T 臂在途 66.9–72.5 已达上限的 52%–57%，而 C 臂仅 15%–26%
⇒ **带宽提升会把元数据推向绑定**。若后续把 randrw 从约 2.2 GB/s 继续推高，
元数据事务速率会成为**下一个**绑定约束。建议在后续任务中把
「元数据事务在途 / 128」列为常规观测项，用于提前发现该转折。

⛔ 无法给出"元数据变少能提升 X%"的可信数字 —— 现有数据不能把 M1 flush 的等待拆成
"等数据落地"与"等元数据事务"两部分。这正是 06-2 想测而失败的东西（仪表开销 −23% 超过 M=14.64%）。
上述只是**上限约束**，不是效应量估计。

### C-12.4 05 阶段 BS 数据对本分析的支撑与修正

**支撑（三条，05 已独立得出且为实测）**：

1. **「每操作成本主导」成立** —— 我方 JuiceFS BS sweep 实测：

| BS | 聚合 MiB/s | 总 IOPS | 带宽× | IOPS× |
|---|---:|---:|---:|---:|
| 4K | 42.4 | 10,854 | — | — |
| 16K | 175.1 | 11,206 | ×4.13 | ×1.03 |
| 64K | 990.4 | 15,846 | ×5.66 | ×1.41 |
| 256K | 3462.8 | 13,851 | ×3.50 | ×0.87 |
| 1M | 3290.0 | 3,290 | ×0.95 | **×0.24** |
| 4M | 4200.4 | 1,050 | ×1.28 | **×0.32** |

⇒ **4K–256K：IOPS 恒定在 10,854–15,846（均值 12,940，极差 ±19%），而带宽增长 ×81.7**
⇒ 该区间是**每操作成本主导**，不是字节吞吐主导。

⇒ 256K 以上 IOPS 掉到 3,290 / 1,050 而带宽走平 ⇒ 转为对象完成率受限。

2. **4K 的限流器已实测为元数据** —— 周报 0919 §2.2：
   `4K 格元数据事务在途 74–92（贴 ~128 inode 串行上限）、读写放大 8.2×、uploading p95 仅 42、
   buffer 仅用 10.8 MiB ⇒ 上传槽未参与，瓶颈在元数据事务速率`

3. **256K 走平的限流器已实测为对象完成率** —— 周报 0919 §2.3：
   `put_avg_size_KiB = 256.0` 即对象块大小；BS>256K 只增加每请求对象个数（1M=4 PUT、4M=16 PUT），
   对象完成率钉住 ⇒ `≈9000 ops/s × 256 KiB ≈ 2.2 GB/s` 平台线，与实测 `2.0–2.2 GB/s` 吻合。
   旁证：改对象大小有限有效（B1M `2593–2614`，×1.5；B4M `2226`）；**改并发无效**（05-2）。

**修正（两处，须订正我方先前表述）**：

| 编号 | 先前说法 | 订正 |
|---|---|---|
| a | 「上传通道是绑定约束」（据 06-1 四格 uploading 全 150） | **限流器随 BS 变化，不通用**：4K 时 `uploading` p95 仅 **42**（05 §2.2）⇒ 上传槽未参与。上传槽饱和只在 256K 附近出现。今后须写「**在 256K 上**上传槽饱和」 |
| b | 未提及 `direct=1` 对 M1 触发频率的放大 | 周报 0919 §7.1 已指出：`direct=1` 绕过 L1 ⇒ **每次读都下到 FUSE 从而触发 M1**；真实应用走缓冲 I/O 时 L1 吸收大部分"读回刚写数据"，M1 触发频率低得多 ⇒ ⛔ 该 randrw 数不可外推到缓冲 I/O 应用 |

**不能支撑的部分（诚实边界）**：
BS sweep **无法单独把成本归到元数据** —— 因为无论 BS 多大，一次随机写都产生一个 slice、

而非 BS 曲线本身。

## C-14 `--writeback` 的收益本质是「拿耐久性换带宽」（2026-09-18 新增）

### C-14.1 写序在开 WB 后完全反转（源码实证）

| | 默认（无 WB） | 开 `--writeback` |
|---|---|---|
| 顺序 | **数据先落、元数据后提交**（同 ext4 ordered） | **元数据先提交、数据后异步上传** |

| | ext4 元数据先落 | JuiceFS WB |
|---|---|---|

| 可检测性 | 难 | `cmd/fsck.go:167` 扫全部 slice，`:222` 报 `N objects are lost, M broken files` |

### C-14.3 更难看的细节：staging 全程无 fsync

`pkg/chunk/disk_cache.go` 全文搜 `Sync()` / `Fsync` **零命中**（1.4.1 与 1.4.0-dev 两份都是 0）；

⇒ **WB 的不一致窗口连宿主掉电都挡不住**，只能挡 juicefs 进程崩溃。

## C-16 新块洪流单格即超过缓存容量 ⇒ 缓存必然抖动（2026-09-18 新增）

**这是「加大 `--cache-size` 对 randrw 无效」的最根本架构原因。**

```
S/W 臂 --cache-size 98304 MiB = 96 GiB
S1 单格 180 s 产生全新 block：put_count 544,032 × 256 KiB = 132.8 GiB  >  96 GiB
六格新块量区间 113.5 – 147.0 GiB，全部超容
实测 evicts/writes = 79% / 87% / 86% / 81%  ⇒ 写进去的绝大部分同窗口内即被淘汰
```

### C-16.1 机制 = COW 的直接后果

每次覆盖写都生成**新 slice / 新 block / 新对象名**（`chunks/<id/1e6>/<id/1e3>/<id>_<indx>_<size>`，
`cached_store.go:74--79`），slice id 单调分配永不复用。旧 block **内容一个字节都不会变**
（官方 `docs/zh_cn/guide/cache.md:22`：「任何修改操作都将生成新的数据块，原有块保持不变，
所以不用担心数据缓存的一致性问题」）⇒ **缓存永远不会"失效"，只会"变死"**：
旧块在 `buildSlice`（`slice.go:134`，越靠后越赢）中被覆盖而逻辑死亡，却仍占着 `--cache-size` 额度。

### C-16.2 容量记账逐字节吻合（S1）

`add()` 每块记 `size + 4096`（`disk_cache.go:775`）：

```
387,147 块 × (262,144 + 4,096) = 103,074,017,280 B = 实测 juicefs_blockcache_bytes（差 0）
--cache-size 98304 MiB = 103,079,215,104 B ⇒ 可容 387,166 块
实测峰值 387,147 ⇒ 99.995%（只差 19 块）
```

⇒ 整个正式窗都在「填满 → `cleanupFull()` 淘汰到 `capacity×95/100`（`:830`）→ 立刻再填满」
的抖动循环里。⛔ 「缓存只利用了很小一部分」的旧说法在 06-3 上完全不成立。

### C-16.3 死块清理的三条路径，只有一条精确

| 路径 | 触发 | 精确性 | 源码 |
|---|---|---|---|
| **A 显式删除** | 元数据侧真删该 slice（**GC / compaction / 回收站到期**） | ✅ **精确** | `base.go:2985 deleteSlice_` → `newMsg(DeleteSlice)` → `cmd/mount.go:319--321 store.Remove` → `cached_store.go:187 rSlice.Remove` |
| **B 容量淘汰** | `add()` 时 `full()`（`:249`）⇒ `cleanupFull()` 降到 95% | ❌ 近似随机 | `disk_cache.go:777 → :779 → :830` |
| C 过期淘汰 | `--cache-expire` | ❌ 按 atime | `:374 cleanupExpire` |
| D 完整性剔除 | CRC/长度不符 | — | `cached_store.go:147` |

默认策略 **`2-random`**（`cached_store.go:622`/`:625`；`cache_eviction.go:27--29`）：遍历 Go map
（顺序随机）比 atime 取较旧者 ⇒ **近似 LRU，不是精确 LRU**；`if value.size < 0 { continue }`
跳过未上传的暂存块。

★ **A 路径只在执行删除的那个客户端上发生**，其他客户端的同一块永远收不到通知 —— 但**安全**，
因为死条目不可能被误读（没有 slice 列表指向它）。**这正是 JuiceFS 敢完全不做缓存失效协议的
根本原因**，代价是垃圾回收必须由元数据侧驱动 ⇒ 引出 **M-47**。

## 4.2 「固定共享比例」是什么

**不是 JuiceFS 的配置项** —— JuiceFS 没有「读/写缓存比例」参数。它是 04-tmp2h/2i 的**实验设计变量**：
先用 loop 把缓存文件系统锁到总量 T，再把 `--cache-size` 设成 T 的 25/50/75%，名义上把剩余留给 staging。

**而且不是硬分区**：`--cache-size` 只约束 raw；staging 以 `size<0` 记账，只受 `free-space-ratio/2` 约束。
04-tmp2h 原文亦明说「raw 和 rawstaging 会动态争用同一 ext4」。

| A0-pre/post | 0 | — | — | 无 | 无 |

### 第 7 步（2026-09-18 新增）｜`--buffer-size` 单参数格（已转07-1，暂不开展）

**当前性价比最高的候选**（M-44 + C-15）：单参数 `--buffer-size 300 → 2048`。

- **依据**：C-15 已实测 S 臂准入丢弃 **31–36%**，根因是 `pendingPages = 240 块 = 60 MiB`

  `2048 MiB → 1638 块 → 260 ms` 缓冲，从量级上足以吸收 `p95 53.82 ms` 的抖动。
- **成本**：不改代码、不需补丁构建基座、不需仪表 —— 比 range-flush（06-2b）**简单得多**。
- **判据**：主口径仍为活跃写带宽；**必须同时报告 `cache_drops` 与 `evicts/writes`**（R-19 硬门⑥）。
- ⚠️ **前置评估（未做）**：`--buffer-size` 同时是读写缓冲总量，且 `reader.go:629` 有基于它的
  反压逻辑 ⇒ 须先算清对读侧预读与内存占用的影响。
- ⚠️ **注意 C-16 的天花板**：本步只减少"丢弃"，**不改变**「单格新块量 113–147 GiB > 缓存 96 GiB」
  这一结构性事实 ⇒ 命中率上限仍受 C-16 约束，⛔ 不得预期大幅提升命中率。
