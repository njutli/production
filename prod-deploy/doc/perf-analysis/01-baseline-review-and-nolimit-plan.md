双口径（不限速 100GbE / 千兆限速 1Gbps TBF）× 双组（default / ra0）。每组证据链完整：

### 2.1 过程可信度：高
TBF 起止计数器证明全程真实限速；限速态网络迁移正确、HEALTH_OK 贯穿、JuiceFS 含关键 patch。

### 2.2 数据判读三处订正（已回写 STAGE-SUMMARY §9 + results-table.md）

**订正一：限速读类聚合天花板是 354 不是 118。**
TBF 只加在 3 个 Ceph 服务端 eno12409，**客户端 157 不限速**。客户端从 3 节点并行读，
聚合读上限 ≈ 3×118 = 354 MiB/s。因此 mseqread=182、ra0 randread=181、default randread=90.9 **均可信**。
唯一存疑：default 单流 seqread=147（单流理论 ~71），属 default 预读跨 3 节点并行预取放大，
非本地缓存假象，也非"纯单流过网"真值——判读注明即可（ra0 关预读后掉到 56.7 反证此点）。

**订正二：randrw R/W 分列是 fio 队列测量偏差，仅看合计。**
128 job × iodepth 128 = 16384 并发压管道，队列灾难性积压（avg clat 达 26248 秒、`>=2000ms 占 44%`）。
**不限速组同样 R=17.9/W=47.5、同 44% 积压** → 去限速比例不变，证明 R/W 不均衡是 fio 混合队列行为
（写走客户端缓冲先排空），非集群/网络特性。STAGE-SUMMARY §8「R/W 不均衡待分析」为无效结论，关闭。

**订正三：写类撞墙可信。** seqwrite/randwrite/mseqwrite/layout ≈114 = 1Gbps 理论 118，bw_log 稳定。

### 2.3 结论：数据不需要整体重测
仅需修正判读口径。"全内存盘新集群测试"确认**不必做**：限速下写撞网卡墙、读瓶颈在网络/并发不在 DATA 盘，
且 DB/WAL 已在 tmpfs，搬 DATA 进内存盘不动任何指标。

### 3.3 可疑点：randrw R/W 严重不均衡

| 项 | 老集群 ra0 | 新集群 ra0（1gbit）| 新集群 default |
|----|----|----|----|
| randrw R | 76.1 | 21.0 | 18.8 |
| randrw W | 76.1 | 54.0 | 50.4 |
| R/W 比 | **1.00 均衡** | **0.39 偏读低** | 0.37 |

首要解释=fio 队列测量偏差（§2.2 已坐实）。但**老集群同配置却均衡 76/76**，差异候选（不限速重测须排查）：
1. **稳态口径差异（最可能）**：老取稳态中位数、新取 fio 平均，平均把"写缓冲早爆发+读长期饥饿"放大 → 新集群补算稳态中位数后 R/W 可能回归均衡。
2. 老集群客户端也在千兆（读写共享出口天然对等），新集群客户端不限速、读跨 3 节点聚合而写走本地缓冲，路径不对称。
3. 工作集/layout 差异。

> **行动项**：不限速重测 randrw 时 (a) 必须用 bw_log 稳态中位数；(b) 若仍不均衡，降 iodepth/numjobs（如 32×16）复测排除队列测量偏差。
>
> **✅ 已结（01-2b，2026-07-16）**：真凶不是上述任一候选，而是 **§6.3 fresh-volume（create_on_open）冷启动失真**——每档首轮读到未写数据的空洞、W 虚高 R 虚低，被平均/中位数掩盖。改用**方案 A（复用 §5 layout 卷 + §6.4 analysis 版）**后，四档 R/W 比全部回归 **0.99-1.01 均衡**（与老集群 76/76 一致），合计随并发单调（D3=508→D0=2673.8）。原"randrw 断崖 65-72"整体作废。

### 3.4 seqread 单流：新旧共有"未撞墙"现象
老集群 §12.6 已归因单流 seqread 不满速 = 单流 psync 延迟受限 + FUSE/meta 开销（非放大）。
新集群 default seqread=147 靠预读跨节点并行掩盖单流延迟，ra0 关预读后掉到 56.7 暴露真值（同老集群 ~71 量级）。
→ 单流 seqread 是并发度/延迟问题，非软件放大，**不作主战场**。

### 3.5 老集群已排除项（新集群不必重走）
❌ 磁盘调度器/nr_requests/read_ahead ❌ EC→副本（写放大 3×>1.5×反而慢）❌ 增大 pg_num
❌ WAL/DB 迁介质（已在 tmpfs）❌ 全内存盘（RAID/SSD 非瓶颈）❌ throttle/deferred（对吞吐无效）。

### 5.2 主战场与假设

**主线 A — randrw（头号瓶颈 ~65）**
- 假设 A1（首要）：低是 fio 队列测量偏差 + 口径问题，非真实能力。

- 假设 A2（A1 排除后）：读侧走 FUSE→TiKV(查位置)+FUSE→RADOS(取数据) 双往返，IOPS 受限（老集群 `results-table` §二#12 已定位）。验证：`juicefs stats` 看 GET/PUT 放大。

## 七、战略决策：单客户端封顶与换栈评估（2026-07-16 新增）

> 触发：用户指出——若网卡（100GbE）足够强、CPU（64 核仅用 9.1%）也不弱，而有效带宽因**方案本身**上不去，则须考虑换方案；并追问新集群是否值得重试 CephFS。

### 7.1 报告"FUSE CPU 固有限制"结论的可信度审视

| 论点（报告 §93-97）| 数据支撑 | 判定 |
|----|----|----|
| CPU 随吞吐/IOPS 近似线性 | ✅ D0(580%/2890M) vs D2(370%/1790M)：吞吐比 1.61 ≈ CPU 比 1.57，单位成本 26-27%/kops 一致 | **成立** |
| 瓶颈在客户端而非后端（当前 randread）| ⚑ **订正**：~~客户端仅 11% 开销……当前限制其实更像贴后端 90%~~ → 真值 JuiceFS ra0=2404 = 后端裸 ~4300 的 **56%**，**客户端确有额外损耗（非贴后端）**；但**后端 4300 本身 < 6250，是首要瓶颈** | **两层瓶颈：后端首要 + 客户端次级** |
| "FUSE 单进程只能用 ~6 核、无法扩展" | ❌ 无饱和曲线。D0/D2 两点 CPU 都仍随负载**线性上升、未见平台**（CPU 数字待 01-3 用真值复跑） | **证据不足** |
| "线性扩展到 64 核可达 60 GiB/s" | ❌ 纯外推，且与"无法扩展"自相矛盾 | **不可作结论** |

**结论**：报告方向（用户态 FUSE 有税、单客户端难满 100GbE）大概率对，但"6 核硬封顶"当前是**假设**。必须先跑 §5.3.4a 拿到饱和曲线 + 多实例倍增数据，才能区分三种情形：
- (a) 多挂载实例吞吐近倍增 → **单进程封顶属实**，workaround = 多客户端/多实例（JuiceFS 可留，架构上多挂载）。
- (b) 多实例不倍增、CPU 仍不饱和 → 瓶颈在**后端/网络**，换 CephFS 也救不了。
- (c) 单进程能继续吃 CPU 到 KGiB/s → 当前只是参数没调对（5.3.4 解决）。

> **✅ 01-3 实测（现象层，2026-07-16）+ ⚑ 01-2d 基线订正（2026-07-17）**：现象层"6 核封顶"**已证实**——CPU 封顶 ~595%（6.0 核），
> 并发 32→16384（512×）CPU 仅 +5%，S1→S0 bw/CPU 双双饱和（**CPU 数字待 01-3 用真值复跑确认**）；~~bw 封顶 ~2876（后端 90%）~~ → **bw 真值 = ra0 randread 2404，为后端裸 ~4300 的 56%（非后端 90%）**。
> 多实例**可倍增**（N4 ra0=5013=单进程 1.74×）落 (a)，但**业务要求单挂载点，多实例 workaround 不满足需求**，
> 故 (a) 的"多挂载"出路被业务否决。线程级：CPU 分散、最集中是 librados msgr-worker（~60-67%，无单线程锁死）。
> **但"为何只能用 6 核"的根因未定位**（C1 FUSE 管道 / C2 librados / C3 锁未区分）→ 01-4 用 pprof 定位。
> **在根因定位清楚、确认是方案架构限制且无客户端调优空间前，不下"换栈"结论**（用户原则）。

### 7.2 CephFS 是否值得在新集群重试

**先厘清老集群 CephFS 数据的口径陷阱**（`doc/perf-analysis/06_3` + `results-table §14`）：
- 老集群实测 CephFS randread **13.9 MB/s** vs JuiceFS 3.8 MB/s（读 3.6×），CephFS randwrite 13.8 反低于 JuiceFS 38.1。
- **但那是 4K 小块 + 限速小样本口径**，绝对值极低；结论"读 3.6×、无 FUSE 税"是**相对趋势**可信，绝对值不能直接搬到新集群 256K 不限速。
- 老集群后来"移除 CephFS 备选"的理由（`09_deepseek` §87）是"JuiceFS 256K randread 45.9 已是 CephFS 13.9 的 3.3×"——**这是 256K block-size 对齐后 JuiceFS 反超**，说明 JuiceFS 调对 block-size 后随机读并不弱于 CephFS。

**新集群该不该重试 CephFS：结论——有条件地值得，但不是现在。**

| 维度 | 判断 |
|----|----|
| 收益假设 | CephFS 内核态无 FUSE 税，若"FUSE CPU 封顶"属实，读类可能显著更高（用户态→内核态是 BeeGFS 领先 3.5× 的同款机制）|
| 反面证据 1 | 老集群 256K 对齐后 JuiceFS 反超 CephFS 3.3×，**block-size 才是随机读关键**，非 FUSE 层 |
| 反面证据 2 | CephFS + EC4+2 **写触发 overwrite RMW**（就地改写读回旧条带），老集群 CephFS 写 13.8 崩，本集群 EC4+2 生产池同样会中招；须搭副本池才公平，但副本违反 EC 规格 |
| 反面证据 3 | ⚑ **订正后更强**：JuiceFS randread ra0=2404 仅为后端裸 ~4300 的 56%，且**后端 4300 本身 < 6250 验收线**——**瓶颈首要在后端 EC4+2，CephFS 用同一后端也顶不动 4300 上限，达不了标** |
| 触发条件 | **仅当 §5.3.4a 证实"FUSE 单进程封顶且多实例 workaround 不可接受"时**，才启动 §5.3.5a CephFS 同口径对照 |

**执行要求（勿重蹈老集群误判）**：若做，必须 256K bs + 不限速 100GbE + 同规格 fio + 冷态隔离，EC 池与副本池两版都测（隔离 RMW 影响），与 JuiceFS 不限速真值同口径对比。参考老集群 `06_3` 命令骨架 + `results-table §14`。

### 7.4 口径基线复审（01-2c 后新增，待用户拍板）

01-2c 补测 default 口径后，当初「调优基线取 default」的两条主要论据均松动：

| 当初论据 | 01-2c/01-3 后的事实 | 影响 |
|----|----|----|
| randrw 两口径打平 | ❌ 推翻：default randrw 因 **2.01× 读放大**仅为 ra0 的 57-84%（D2=128 验收档 692 vs 919）| 选 default 论据之一失效 |
| 业务"共享读基础文件"偏顺序/多流读 | ⚠️ 01-3 多实例共享读实测 ra0 更优（N4 ra0 5013 vs default 2822）| 选 default 论据之二松动 |
| default 顺序/多流读/写类占优 | ✅ 仍成立（seqread 1268 vs 180、mseqread 3311 vs 1784）| default 唯一确定优势区 |

**待拍板**：调优基线是否由 default 改回 ra0？
- 若业务随机读/randrw 权重高 → 倾向 ra0（随机项全面占优、读放大=1.0 贴后端）。
- 若业务顺序/多流读为主 → 保 default。
- **两口径都测的约定不变**；此复审只影响"调优分析以哪个口径为主叙述"。
