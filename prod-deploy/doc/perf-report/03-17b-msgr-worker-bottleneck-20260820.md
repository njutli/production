## 一、结论先行

1. **H1 成立，且是强结论**：per-mount 读带宽由 librados 的 3 个 `msgr-worker` 线程封顶。8 轮里**每一轮都至少有一个 worker 跑满单核（99%~100%）**，无一例外。
2. **档位波动 = 连接到 worker 的分配抽签**。7 条 OSD 连接数**每轮完全一致**，变的只是它们落在 3 个 worker 上的分布。分布均衡 → 快；偏斜 → 慢。
3. **定量律**：`bw ≈ 1438 MiB/s × (msgr-worker 满载核数)`，8 轮离散仅 **1.2%**，`r = +0.9962`。3 worker 全满载理论上限 **≈4184 MiB/s**，实测最好轮 4101（达上限 98%）。
4. **H2 否**：worker 线程在 35 次采样中跨 **26~33 个不同 CPU** 漂移，无稳定落位；NUMA 组合 `n1n1n0` 同时出现在最好轮与最差轮。**H3 无需启用**，**H4 否**（全程单会话、掩码恒为 `0,17-64,81-127`）。
5. **⚑ 订正 F54**：读侧**不是"双稳态"**，而是**多值抽签**。8 轮 bw 连续分布于 2994~4101，in-flight 连续分布于 77.5~95.2。原"好 97.4 / 坏 80.0"的二分是 2 个样本造成的错觉。**判别器应从 in-flight（r=0.81）换成 msgr-worker CPU 离散度（r=−0.9907）**。
6. **`io_context_pool` 线程 8 轮 CPU 全为 0.00s** ⇒ `librados_thread_count` 维度**零价值**，03-17 应删掉该臂，只扫 `ms_async_op_threads`。
7. **首次出现通往 6250 MiB/s 的机制性路径**：需 ≈**4.3 个**满载 worker。外推 4 worker ≈5579、5 worker ≈6975、6 worker ≈8369 MiB/s。⚠ 但 F51 的机器级上限 6.1~6.4 GiB/s 恰好压在目标线上，须同批验证。

## 三、机制

7 条 OSD 连接（`10.3.1.6:6800/6802/6806`、`10.3.1.7:6800/6804`、`10.3.1.8:6800/6804`）在**每一轮都完全相同**，`ss` 计数 pre=1 / post=7 也每轮一致。所以变量只有一个：**建连时这 7 条连接被轮转分配到 3 个 `msgr-worker` 的分布**。

以最差的 iter7 为例，按未饱和 worker 的单连接开销 66.7 s 折算：

- worker-0 = 66.7 s ⇒ 1 条连接
- worker-1 = 133.0 s ⇒ 2 条（2 × 66.5，吻合）
- worker-2 需求 4 × 66.7 = 267 s，但**被单核截断在 174.2 s** ⇒ 4 条连接被挤在一个核上

即 **1/2/4** 分布。落在 worker-2 后面的 4 个 OSD 每条只拿到 174/4 ≈ 43.5 s 而非 66.7 s，服务速率降 35%；EC 条带需要多个 OSD 的分片才能拼出一次读，**最慢的那条路径直接给整个条带定速**，于是全局 bw 掉到 2994。均衡轮（3/2/2）则三个 worker 一起顶到 95%~97%，取到 3968~4101。

这解释了此前一串悬案：

- **F50**（单挂载 GET ≈16.9K op/s 上限）：即 3 个 worker 满载时的 op 率，机制到位。
- **F52**（第二挂载位稳定慢 8~10%）：同一抽签，与"挂载位"无因果关系。
- **03-16 连续 3 次重挂全败**：抽签独立，连抽 3 次偏斜完全正常（本次 8 轮抽到 4 次偏斜）。
- **03-17 A1 臂（msgr=1）为何不见档位波动**：1 个 worker 没有分配自由度，必然确定性。且 **A1 实测 1495 / 1699 MiB/s，与本律预测的 1×1438 吻合** —— 用 03-17 废弃数据独立验证了 1438 MiB/s/核。
- **iter5 前空转 180 s 无特殊效应**（iter5 属均衡组，但 2/4/8 未空转也均衡）⇒ 档位**不粘连、不自愈**，每次挂载重新抽签。
