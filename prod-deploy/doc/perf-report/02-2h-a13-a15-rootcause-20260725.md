## 三、根因定位

### 3.1 因果链

```
WekaIO 活跃度↑（共享 100GbE）
  → 网络排队延迟↑（无丢包/无重传/无流控，但 RTT +79%）
  → obj_get 延迟↑（11.12→12.36ms，+11.2%）
  → fuse_op 延迟↑（10.83→12.08ms，+11.5%）
  → randread 吞↓（1444→1304，-11.3%）
```

### 3.2 为什么 RTT 升高但无丢包/无重传/无流控？

- **无丢包**（retrans=0, tx_dropped=0）：网络带宽充足，没有拥塞到丢包的程度
- **无流控**（tx_pause=0）：NIC 间的流量控制没有触发
- **RTT 翻倍**（1.94→3.48ms）：数据包在网络路径上**排队等待时间增加**

排队可能发生在：
1. NIC TX/RX 队列（WekaIO 与 Ceph 共享同一 NIC，中断/队列处理争抢）
2. 内核网络栈（socket buffer、TCP 处理、上下文切换）
3. 交换机缓冲（如果 100GbE 链路有中间交换机）

### 3.3 排除项汇总

| 排查项 | 好坏轮差异 | 判定 |
|--------|-----------|------|
| OSD throttle 限流 | 0/0 | ❌ 排除 |
| OSD op 队列排队 | 0.062/0.070ms | ❌ 排除 |
| OSD read 延迟 | 0.043/0.047ms | ❌ 排除 |
| OSD get_latency | ~4μs（A7-A10 已证） | ❌ 排除 |
| 157 CPU idle/wa/D | 82%/0/0 | ❌ 排除 |
| TCP 重传/丢包/流控 | 0/0/0 | ❌ 排除 |
| OSD 节点 CPU idle | ~99% | ❌ 排除 |
| buffer hit_rate | -3.6pp（Opus 差分） | ⚠ 次要因子 |
| **TCP RTT** | **1.94→3.48ms（+79%）** | **★ 根因** |

### 3.4 与 A11/A12 数据一致性

A11（坏轮）vs A12（好轮）的 ss -ti 也显示同样模式：
- 坏轮 cwnd=1605 > 好轮 576-758（TCP 试图补偿高 RTT）
- 坏轮 rtt=2.0-3.0ms > 好轮 1.8-1.9ms（RTT 更高）

A13/A15 数据更精确（取平均），差异更明显（1.94→3.48ms，+79%）。

## 四、判定

### 4.1 根因

**TCP RTT 升高是 randread 双峰波动的直接根因。** 坏轮 RTT 比好轮高 79%（1.94→3.48ms），无丢包/无重传/无流控 → 排队延迟增加 → obj_get 延迟 +11.5% → randread 吞吐 -11.3%。

### 4.2 可控性

- **RTT 升高来自网络排队**，排队来自 WekaIO 与 Ceph 共享 100GbE NIC/网络栈
- WekaIO 是生产业务，不能控制其网络流量模式
- → **不可控**

### 4.3 buffer hit_rate 的角色

Opus 差分发现坏轮 hit_rate 低 3.6pp。hit_rate 低 → 更多读落盘 → OSD 发送数据稍慢 → 但 OSD 内部 read_lat 仅 0.04ms，影响极小。hit_rate 是**次要因子**，不是主因。主因是 RTT（网络排队）。

### 4.4 建议

1. **采纳统计基线**：好轮 randread 8 轮中位 1472 ± CI（CV 1.0%），作为基线推进 B/B2
2. **坏轮标注**：randread <1350 的轮次标注为"WekaIO 网络排队干扰"
3. **不再追打波动**：根因已定位为不可控的网络排队延迟
4. **osd_memory_target 调参**可独立实验验证 hit_rate 可控贡献（次要因子）
