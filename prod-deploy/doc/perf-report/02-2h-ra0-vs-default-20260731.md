# 基线测试方法稳定性验证报告 [2026-07-31]

> 目标：验证 FULLBASELINE_V2 锁定布局方法能否产生稳定基线——包括**单轮内多次 repeat 间的稳定性**（intra-round CV）和**同配置跨轮间的稳定性**（inter-round 一致性）。
> 方法：同一 layout，通过 --remount 切换 mount 参数，4 轮交错测试（ra-default → ra0 → ra-default → ra0）。ra-default vs ra0 的对比是副产品，不是本次测试的主要目的。
> 脚本：`prod-deploy/scripts/FULLBASELINE/FULLBASELINE_V2.sh`
> 数据：`157:/tmp/opencode-fullbaseline-v2/{default,ra0,default2,ra0-2}/`

---

## 一、实验设计

### 1.1 四轮交错测试

```
Round 1: ra-default #1  (JUICEFS_MOUNT_OPTS="--max-uploads 150 --cache-size 0")
Round 2: ra0 #1         (--max-readahead 0)
Round 3: ra-default #2  (remount 回默认)
Round 4: ra0 #2         (remount --max-readahead 0)
```

- 同一 layout 全程不 destroy/format/rm -rf
- 每次 --remount 切换 mount 参数（fusermount -u → juicefs mount -d）
- REPEAT=5，runtime=180s
- 测试顺序：seqread → mseqread → randread → randrw → seqwrite → mseqwrite → randwrite
- 写项轮间清理：seqwrite/mseqwrite 用 compact_cooldown，randrw/randwrite 用 aggressive_cleanup
- mseqwrite 末轮后加 aggressive_cleanup（防 randwrite r1 被残留 compaction 干扰）

交错设计的优势：同一配置出现两轮（#1 和 #2），可以评估同配置跨轮一致性；同轮内 5 次 repeat，可以评估同轮内一致性。

### 1.2 稳态评估口径

- 每轮 fio 加 `--write_bw_log --log_avg_msec=1000`，生成逐秒瞬时带宽日志
- 每轮取**稳态中位数**：读项截前 15s（跳过缓冲暂态），随机写截前 60s + 取末 60s floor_median
- 单轮内 5 轮稳态中位数组成一组样本，计算：
  - **范围** = 5 轮稳态中位数的 min~max
  - **最大偏差** = max(|r_i - median|) / median × 100%（5 个值中偏离中位数最远的那个，占中位数的百分比）
  - **CV** = 标准差 / 均值 × 100%
- 跨轮一致性：同配置两轮（#1 vs #2）的中位数偏差 = |#2 median - #1 median| / #1 median × 100%
  - **仅当跨轮偏差 > 单轮内最大偏差时**，跨轮变化才是有意义的信号；否则淹没在单轮噪声中

### 1.3 集群状态

- 全程 BlueFS spillover（ra0 #2 开始时出现，compact 无法清除，tmpfs DB 盘满）
- ra0 #1 和 ra-default #1/#2 无 spillover
- BlueFS spillover 影响 RocksDB 读延迟（部分读落 NVMe 而非 tmpfs），不影响数据正确性

### 3.3 r1 冷启动现象

多个项的 r1 偏离 r2-r5 稳态值，是系统从"未预热"到"热稳态"的过渡：

| 项 | 轮次 | r1 | r2-r5 范围 | r1 偏离程度 |
|---|---|---|---|---|
| seqread | ra0 #1 | 147 | 165~175 | -14% |
| seqread | ra0 #2 | 147 | 165~168 | -12% |
| randread | default #1 | 1624 | 1640~1696 | -1% (稳态中位数已收敛) |
| randwrite | ra0 #1 | 164 | ~600~651 | -70% |
| randwrite | ra0 #2 | 402 | ~580~649 | -27% |

> 注：r1 值为稳态中位数（bw_log 截首 15s 后取中位数），非 fio 聚合 BW。r2-r5 范围根据稳态评估输出的整体范围推断。

**规律**：r1 偏低是普遍现象。读项 r1 偏低 1-14%（BlueStore 缓存未预热），randwrite r1 偏低 27-70%（JuiceFS 异步删除残留 + compaction 未完全收敛）。r2-r5 稳定后偏差显著降低。

**对策**（已在 V3 实现）：确定性预热（顺序读 128G layout，填充 BlueStore onode 缓存到已知状态），消除 r1 冷启动。

### 3.4 randwrite r1 异常根因

ra0 两轮的 randwrite r1 均极低（164 / 402），而 default #2 的 r1≈571 正常。根因：
- mseqwrite 5 轮覆写产生大量 JuiceFS chunk 创建/删除，异步删除在 compact 后仍持续到达 OSD
- aggressive_cleanup（compact → sleep 30 → compact → drop_caches）能清理 compact 时已存在的 tombstone，但无法阻止 compact 后新到达的异步删除产生新 tombstone
- r2 起恢复（轮间 aggressive_cleanup 重置了状态）

| 轮次 | randwrite r1 (稳态) | r2+ 范围 | 备注 |
|------|---------------------|----------|------|
| default #1 | ~600 | 600~672 | r1 未明显离群 |
| ra0 #1 | 164 | ~600~651 | r1 离群（JuiceFS 异步删除量大） |
| default #2 | 571 | 571~646 | r1 未明显离群 |
| ra0 #2 | 402 | ~580~649 | r1 离群（JuiceFS 异步删除量大 + BlueFS spillover） |

> 注：compact 时间（20-95s）只影响测试总耗时，不影响数据质量——compact_cooldown 保证 compact 完成后才放行下一个 fio。BlueFS spillover 也不影响 compact 清理效果，只是让 compact 更慢。

## 四、跨轮一致性分析

### 4.1 跨轮判定修正

**§2.3 的判定规则**：跨轮偏差 > 单轮内最大偏差时，跨轮变化才是真实信号。

按此规则，只有以下项的跨轮变化有意义：

| 项 | 配置 | 跨轮偏差 | 单轮内最大偏差 | 判定 |
|---|---|---|---|---|
| randread | default | 12.0% | 2.8% | ✅ 真实信号（跨轮波动远大于单轮噪声） |
| randread | ra0 | 10.2% | 1.0% | ✅ 真实信号 |
| mseqread | default | 9.6% | 2.1% | ✅ 真实信号 |

**其余 5 项（seqread/randrw/seqwrite/mseqwrite/randwrite）的跨轮偏差全部 ≤ 单轮内最大偏差**，无法判定跨轮是否稳定——单轮内 5 个 repeat 就散了 6-70%，跨轮 1-4% 的变化只是噪声。

**这意味着**：之前报告中 randrw/seqwrite/randwrite 的"✅ 跨轮稳定"判定**不成立**——不是"稳定"，而是"噪声太大无法判定"。

### 4.2 跨轮波动根因：BlueStore 缓存命中率

**randread 跨轮波动 ±12% 的根因已由 02-2h 和 LC.12 历史数据确证。**

实测配置：
- `osd_memory_target` = 4GB（每 OSD）
- `bluestore_cache_size` = 0（auto，动态管理）
- 实际 buffer_bytes ≈ 2.5GB/OSD（osd.0 perf dump 实测）
- 总缓存 ≈ 2.5GB × 6 OSD = **~15GB**
- layout 数据 = **128G**
- 缓存覆盖率 ≈ 12%（15GB / 128G）

#### 已排除的其他候选

- 157 负载（WekaIO 活动）：LC.12 D 组 D-7（最高 BW=1596）load_pre=25.37 ≈ D-2（最低 BW=1156）load_pre=24.26，负载相近但 BW 差 38%。02-2h A5/A6 实测 157 idle=82%、wa=0、D=0 在好坏轮一致。**排除。**
- 网络/客户端侧：02-2h A11/A12 发送侧假设四项预测全落空（retrans=0、tx_dropped=0、pause 不变、cwnd 坏轮反而更高）。瓶颈被从网络推回 OSD 内部。**排除。**
- Linux 页缓存：每轮 drop_caches 清空，好坏轮清的方式一样。**排除。**

#### BlueStore hit_rate 确认为主因

| 实验 | 轮次 | hit% 范围 | hit% vs randread BW 相关 | 来源 |
|------|------|---------|------------------------|------|
| 02-2h A7-A15 | 9 轮 | 71.7-75.3% | **ρ=1.000** | analysis.md §-STEP1 |
| LC.12 A 组（连续） | 10 轮 | 恒定 83.9%（A-2~A-10） | 无方差 → CV=1.5% | LC.12 报告 §3.6 |
| LC.12 D 组 | 10 轮 | 68.9-77.6% | **ρ=1.0000** | LC.12 报告 §3.6 |
| LC.12 C 组 | 10 轮 | 63.2-73.1% | ρ=0.8788 | LC.12 报告 §3.6 |

**关键反面证实**：A 组 hit% 恒定 83.9% → BW 恒定（CV=1.5%）；其他组 hit% 变化 → BW 变化。**缓存命中稳定时 BW 就稳定。**

#### 影响机制

| 场景 | 影响 | 表现 |
|------|------|------|
| 同轮 r2-r5 | r1 已把热数据加载到缓存，后续轮命中率高且稳定 | 最大偏差 < 3%，极稳 |
| 同轮 r1 | 前面的 seqread/mseqread 加载了不同数据，缓存里是别人的数据 | r1 偏低（冷启动） |
| 跨轮 | 不同轮的前序项不同 + 残余缓存状态不同 → hit% 不同 | ±12% 波动（randread 1670→1469） |

**"锁定 layout"锁的是物理数据落点（CRUSH/UUID 不变），但 BlueStore 缓存命中率是活的——取决于前面跑了什么 + 残余孤立对象。**

#### 无法主动清除 BlueStore 缓存

BlueStore 缓存在 OSD 进程内部，`drop_caches` 只清 Linux 页缓存，清不了 BlueStore 内部缓存。唯一清除方式是重启 OSD → 但重启清空缓存后预热路径随机 → 引入新波动源（CV=13%）。这是"清缓存 vs 保稳定"的悖论：不清则跨轮波动 ±12%，清则引入重启波动 13%。

**V3 的解决方案**：确定性预热（顺序读 128G layout，让 BlueStore 缓存进入已知状态），不重启 OSD，跨轮不再有 ±12% 波动。V3 初步数据见附录。

### 5.2 对比结论的可靠性评估

ra0 对 randread 的提升方向在两轮中一致（1.53x / 1.91x），但比值变化大（+25% 偏差），原因是跨轮绝对值波动：
- default：1670 → 1469（-12%）
- ra0：2549 → 2808（+10%）

randread 的单轮内最大偏差仅 0.6-2.8%（§2.2），而跨轮偏差 10-12%（§2.3），跨轮变化是真实信号。因此：

- **方向性结论可靠**（ra0 > default for randread，两轮一致）
- **精确比值不可靠**（1.53x vs 1.91x，因跨轮 hit% 波动）

其他项（randrw/seqwrite/mseqwrite/randwrite）的单轮内偏差 4-70%，远大于跨轮偏差，比值变化在噪声范围内，无法判定。

## 六、方法稳定性结论

### 6.1 单轮内稳定性

| 评估维度 | 结论 | 证据 |

**结论**：读项（randread/mseqread）在排除 r1 后单轮内极稳（<3%），可作为可靠基线。写项和 randrw 在部分轮次偏差过大，需要改进清理/预热流程才能稳定。

### 6.2 跨轮一致性

| 评估维度 | 结论 | 证据 |
|----------|------|------|
| randread | 跨轮偏差 10-12%，**超过**单轮内偏差（<3%）→ 真实信号 | §2.3 |

| seqread(ra0) | 跨轮偏差 2.3%，**≈**单轮内偏差（1.8%）→ 临界，需更多数据 | §2.3 |
| 其他 4 项 | 跨轮偏差 ≤ 单轮内偏差 → **噪声内，不可判定** | §2.3 |
| 根因（randread） | BlueStore 缓存命中率波动 | §4.2 |
| 方向性结论 | 可靠（ra0 > default 两轮一致） | §5.2 |
| 精确比值 | 不可靠（1.53x vs 1.91x） | §5.2 |

**结论**：randread 的跨轮波动被确认为真实信号（根因 = BlueStore 缓存 hit% 波动）。seqread(ra0) 为临界 case。其余项的跨轮变化无法与单轮噪声区分。

## 七、BlueFS spillover 说明

长时间写测试（~4h × 4 轮 ≈ 累计写入 ~10TiB）导致 RocksDB DB 溢出到数据盘（BlueFS spillover）。

**BlueFS spillover 对测试数据无实质影响**：
- compact 时间从 20-25s 增至 80-95s → 只影响测试总耗时，不影响数据质量（compact_cooldown 保证 compact 完成后才放行）
- compact 能正常清理已有 tombstone（compact_running=0, compact_queue_len=0 确认完成）
