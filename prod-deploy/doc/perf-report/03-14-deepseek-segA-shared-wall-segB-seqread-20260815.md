## 七、DeepSeek 独立复核裁定（2026-08-15 追加）

### 7.1 段A：A2b 共享成立，且把 F42 精化为"librados 总带宽墙"

- 合计 **3920 ≈ F42 墙 4.1 GiB/s**；读侧从单独跑的 3867~4079 被压到 2931（让出 ~1000 给写），写侧仅得 989——**不是"各退各的"（若独立且环境退化，合计应 ~5300），而是总和被钉在 ~4.1**。
- 与 **randrw 合计 3875**（读 1938+写 1937）同数互证：一切读写混合场景合计都封在 ~3.9-4.1 GiB/s。
- ⇒ **F42 升级：客户端 librados 对象层（objecter/messenger）是读写共用的 ~4.1 GiB/s 总带宽墙**——读 GET 与写 PUT 走同一队列。这与 03-13 T1"max-downloads 不破墙"互洽（墙在 librados 层，不在 juicefs 下载信号量）。
- **含义**：randrw 每向 6250 = 合计 12500 = **现有 librados 总容量的 3×**。后续 F42 解法方向 = librados 对象层容量（objecter 并发/消息线程/多 ioctx），而非只读侧。

### 7.2 段B：seqread 转正条件满足，可判转正

3 实例（08:57→09:24 日间窗口）、6 轮全落 week3 平台 [1234,1324]、3 实例中位 ≈1253.5 ⇒ **判转正**（计划书 §3.4 条件达成）。

### 7.3 段A i1 实证（复核 §7.1 的共享结论，来自归档 i1-T44A-t2-rwcon.tsv）

- 写侧 **3.96K slice/s**（=989÷0.25MiB）⇒ 3.96K meta 提交/s ≪ 墙（~12K/s）⇒ **写侧非 meta-bound**——被挤到 989 的机制在 librados 层，不在 meta 管线。
- **总对象 op 率 = 读 11.7K + 写 3.96K ≈ 15.7K/s ≈ randread 单跑时的 16.2K GET/s** ⇒ 墙的等价表述成立：256K 定长下"op 速率 ~16K/s"与"总带宽 ~4.1 GiB/s"不可区分（未来用 128K 读可区分二者）。
- FUSE 混合 op 延迟 16.82ms vs randread 单跑 7.7ms（≈2.2×）⇒ 共享队列下排队深度翻倍，与"读写挤同一资源"一致。
- 缓冲峰 8MiB ⇒ flushfix 正常、写侧无滞留节流——挤占纯粹发生在 librados 层。
- ⚠ 采集缺口：段A 的 i1 未采 meta 计数器（t44 脚本 sample grep 缺 meta 键，DeepSeek 责任），上一条"3.96K meta 提交/s"由写 op 率换算而来，非实测。

## 八、03-15 Gate 0 复核订正（2026-08-17；覆盖 §7.1/§7.3）

### 8.1 保留的结论

- 两个 fio 使用互斥数据集，同一挂载并发时读写分项强反相关；缓冲平稳后的多数写占比分档中，合计约 4038–4198 MiB/s。**“单挂载内存在读写共享容量约束”仍成立。**
- seqread 的 3 实例/6 轮转正不受本次订正影响，但只签 128K 基座。

### 8.2 撤回或降级

1. **窗口失配**：读 fio 约 180s，写 fio 约 219s，原 2931+989=3920 的 fio 汇总不能直接相加。逐秒真并发 0–180s 重算为读 2949、写 1203、合计 4152；写尾部 39s 近乎空转，是收尾 flush，不是独占写能力。
2. **buffer 峰不是 8MiB**：真实 `juicefs_used_buffer_size_bytes` 峰为 **590.4MiB@t2**；8MiB 是 `t>=190s` 的结束后地板。缓冲净变化对长窗平均的修正很小，但“全程无 buffer/throttle 影响”不能成立。
3. **不是固定字节硬顶**：写占比 10%–50% 的平稳秒合计约 4038–4198；写占比大于 50% 的 28 秒达到 4573–4715。共享成本随负载组成/状态变化，不能写成固定 4.1 GiB/s。
4. **不能点名 librados/objecter/messenger**：客户端链路等待证据很强，但 goroutine debug=2 看不到 librados 内部队列；历史旧基座 N4=5013 也已越过 4.1。具体层级待 N1/N2。
5. **写侧绝对值无效**：段A pool objects 从 **7.05M 增至 7.66M**，远超 3.11M 有效性闸门，正处 F45 中间态。i1 又缺 meta 计数器，因此“3.96K meta 提交/s”“写侧非 meta-bound”只是由 write op 换算，不能签字。
6. `env-snapshot-segA-pre` 是候选重挂前的 stock 128K 现场，不是效应轮配置；效应轮本身由 `instances.txt`/mount.log/post snapshot 证明是补丁 256K。仓库脚本已把 pre 快照移动到候选挂载过门后。

统一结论：**F46 = 单挂载内读写共享容量约束（层级和健康态绝对容量待后续划界）。** 这仍解释当前 randrw 为什么远低于每向 6250，但还不足以宣布单挂载架构永久不可达。
