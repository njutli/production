### 1.3 重建过程

**前置**：从 157（client 节点）执行，直接 SSH 到 slave 节点（sshpass），不使用原 rebuild-osds.sh 脚本（3 层 SSH 有转义 bug）。

**Step 1-2：Kill + Purge OSDs**（从 157 直接执行）
```bash
# Kill ceph-osd on all nodes
for ip in 10.20.1.150 10.20.1.151 10.20.1.152; do
  sshpass -p 'Sunrise@801' ssh sunrise@$ip "sudo pkill -9 ceph-osd"
done
# Purge from mon
for osd in $(sudo ceph osd ls); do
  sudo ceph osd destroy $osd --yes-i-really-really-mean-it
  sudo ceph osd crush remove osd.$osd
  sudo ceph osd rm $osd; sudo ceph osd purge $osd --yes-i-really-really-mean-it
  sudo ceph auth del osd.$osd
done
```

**Step 3：全量清理 LVM/dm/PV/VG/loop/tmpfs**（脚本：`/tmp/cleanup-node.sh`，scp 到每个节点后执行）
- 逐节点 detach loop devices → remove LVs/VGs/PVs → dmsetup remove_all → umount+remount tmpfs → wipefs+sgdisk+dd 清盘
- 验证：pvs=0 vgs=0 lvs=0 tmpfs=1

**Step 4-12：准备 LVs + 部署 OSD + 修复 + 建 pool**（脚本：`/tmp/rebuild-step4-12.sh`，在 157 上执行）
- Step 4：逐节点逐盘创建 data LV（nvme2n1/nvme3n1）+ DB/WAL LV（tmpfs loop device）
- Step 5：`ceph orch daemon add osd` 部署 6 个 OSD（部分 "already created?" 走 Step 6 activate）
- Step 6：`ceph-volume lvm activate --all` 激活未启动的 OSD
- Step 7：修复 auth key（`ceph auth add` 从本地 keyring 恢复）+ `systemctl reset-failed + start`
- Step 8：等 PG active+clean
- Step 9：修复 .mgr pool（如有 stale/down：delete .mgr + mgr fail）
- Step 10：Recreate EC pool（`ceph osd pool create juicefs-data 32 32 erasure ec-prod` + `fast_read true` + `allow_ec_overwrites true`）
- Step 11：写 ceph.conf + keyring 到 157（hardcode ceph.conf + `ceph auth get client.juicefs`）
- Step 12：验证（6 OSD up + PG active+clean + fast_read=1 + JuiceFS mount + write test）

**已知问题**（详见 `pre-skills/cluster-rebuild-skill.md`）：
1. LVM/dm 拘留 → Step 3 全量清理
2. ceph orch 竞态 → Step 4 先准备全部 LVs 再部署
3. "already created?" → Step 6 ceph-volume activate
4. auth key 被删 → Step 7 手动 ceph auth add
5. systemd restart limit → Step 7 reset-failed 后 start
6. .mgr pool stuck → Step 9 delete + mgr fail
7. 重建后 cephadm 报 failed daemon → 不影响，health check 允许通过
8. rebuild-osds.sh 的 3 层 SSH 有转义 bug → 改用 157 直连手动执行

**重建耗时**：~3-5 分钟（Steps 1-3 约 2 分钟，Steps 4-12 约 1-3 分钟）

### 1.4 判定标准

- 轮内 CV<5%（3 轮随机项）
- 组间 Δ<5%（同组跨轮次）
- 不收敛时的 contingency：重建 → 跑一组 B → 得到 4 个重建后首次值（A×2: R1A+R3A, B×2: R2B1+R4B）分别收敛判定；若仍不收敛暂停分析

---

### 1.4 测试流程（新策略）

```
R1: 重建 → A → 全量清理 → A2
R2: 重建 → B1 → 全量清理 → B2
R3: 重建 → A（不跑 B）
R4: 重建 → B
```

- **全量清理**（A↔B 或 A↔A2 间）：pool delete+recreate + OSD restart + drop_caches 全节点 + compact_cooldown
- **组内清卷**：juicefs destroy + compact_cooldown
- **REPEAT=3**：所有随机项 3 轮，顺序项 1 轮
- R3 只跑 A、R4 独立重建后只跑 B，目的是得到 4 个重建后首次值：A×2（R1-A + R3-A）、B×2（R2-B1 + R4-B），分别收敛判定
- 不收敛时的 contingency：若仍不收敛暂停分析

### 1.5 判定标准

- 轮内 CV<5%（3 轮随机项）
- 组间 Δ<5%（同组跨轮次）

### 8.3 判定结论

**基线不收敛。** 即使在独立重建后的首次测试之间：

| 收敛项（Δ<5%） | 不收敛项（Δ>5%） |
|----------------|------------------|
| seqread (-2.9%~-3.2%) | randread (A: -12.2%, B: +20.4%) |
| seqwrite (-0.3%~-3.5%) | randwrite-true (A: +4.1% ✅, B: +24.8% ❌) |
| randrw (-3.0%~-4.0% A, +6.5% B ⚠️) | mseqwrite (A: +7.6%, B: +14.8%) |
| randwrite-ow (-3.6%) | layout (A: +8.7%, B: +29.1%) |
| mseqread (A: +13.9% ❌, B: -3.6% ✅) | mseqread (A 组不收敛) |

**核心问题**：
- **randread**：A 组 -12.2%，B 组 +20.4%。轮内 CV<1%（极稳定），但跨重建周期绝对值漂移 12-20%
- **randwrite-true**：A 组 +4.1%（收敛），B 组 +24.8%（不收敛）。同一测试项在不同组别表现不同
- **layout/mseqwrite**：写类多线程项波动大（8-29%）
- **覆写类（randrw, randwrite-ow）**：bw_log 稳态中位数收敛（-3~+6%），但 fio 平均因递减趋势偏高

**根因推测**：
1. OSD 内存分配（osd_memory_target_autotune）每次重建后可能不同，影响 BlueStore 缓存大小
2. PG → OSD 映射在每次重建后不同（crush 算法基于 OSD ID，但 OSD 重建后 ID 可能变化）
3. tmpfs DB/WAL 的内存分配在每次重建后可能有微小差异
4. 写类对 OSD 内部状态更敏感（SST、memtable、WAL buffer），读类对 PG 映射和缓存命中率更敏感

## 九、后续建议

基线不收敛，**暂停测试，需要分析**。可能的方向：
1. 固定 osd_memory_target（关闭 autotune），消除 OSD 内存差异
2. 检查每次重建后 PG → OSD 映射是否一致
3. 考虑用 bw_log 稳态中位数替代 fio 平均值作为基线口径（覆写项递减趋势导致 fio 平均偏高）
4. 对于不收敛的项，考虑增加 REPEAT 到 5-7 轮取中位数，或接受 ±15% 的基线带宽

## 十、波动性质分析与基线锁定策略（opencode 复核，2026-07-22）

> 本节对第八节「基线不收敛」结论做进一步归因。核对了全部 CV / Δ% / bw_log 中位数算术，
> 均无误；问题不在数据准确性，而在于**把三类性质完全不同的波动混为一谈**。
> 按执行时间重排六段数据后，波动可拆为三类，处置方式各异：

### 10.1 三类波动的性质区分

**① randrw 的 r3 骤降 —— 测试方法缺陷（可定位、可消除，非集群波动）**

| 轮次 | r1 | r2 | r3 | r3 跌幅 |
|------|----|----|----|--------|
| R1-A  | 905 | 920 | 905 | 无 |
| R1-A2 | 919 | 929 | 903 | 无 |
| R2-B1 | 1178 | 1201 | 863 | **-28%** |
| R2-B2 | 1410 | 1286 | 824 | **-36%** |
| R3-A  | 875 | 915 | 890 | 无 |
| R4-B  | 1355 | 1282 | 819 | **-39%** |

- r3 崩溃**只在 B 组每一轮发生，A 组六段从不发生**。集群随机波动不可能如此挑组、如此规律。
- 根因（脚本 `baseline-maxfuse1M.sh`）：randread（§3）三轮间**不 remount**、复用 layout → 稳定；
  randrw（§5）**每轮前 `remount_jfs` 且复用同一 layout 目录不重建文件**，`randrw` 的写半程
  在同目录累积（空间放大 / compaction backlog / remount 丢写缓冲），到 r3 累积爆发。
- **结论**：r3 是确定性累积产生的**污染样本**，非系统性能波动。r1/r2 本身收敛。
  基线应**丢弃 r3、取 r1/r2 中位**（或修脚本每轮重建 layout+drop_caches 后重采）。

**② randwrite-ow 逐轮递减 —— 确定性机制，非随机波动**
- 六段**全部** r1>r2>r3 单调递减，是覆写工作集预热 / 空间放大的确定性行为。
- bw_log 稳态中位其实收敛（Δ≈-3.6%），fio 平均被递减尾巴拉高。**非本阶段目标项**（D1 不覆盖）。

**③ randread / 写类多线程跨重建漂移 12~29% —— 真波动，但根因是「重建本身」**
- randread 轮内 CV<1%（极稳），但跨重建绝对值跳变：default 1399/1677/1229，ra0 2393/3173/2882，
  **无时间单调趋势**（不是机器变热），是**离散跳变**。
- 根因（与第八节根因推测一致，此处确认方向）：**重建对读绝对值不是收敛器，而是新随机源**——
  CRUSH 基于 OSD ID 算 PG→OSD 映射，重建后 6 个 OSD 的 ID/映射每次不同；tmpfs DB/WAL 分配每次不同；
  osd_memory_target autotune 未固定使 BlueStore 缓存每次不同。
- **cleanup(OSD restart) 达不到重建冷态**，故 cleanup 值系统性偏高 +17~31%（A/B 两组独立验证一致，
  R1-A→A2 +17.5% / R2-B1→B2 +30.9%），**cleanup 值须剔除，只用 rebuild-first**。

### 10.2 GLM 重建/测试操作审查结论

- 重建流程（§1.3）步骤完整、验证到位，**未发现执行错误**。
- 「两次重建仍波动」符合预期：对读类绝对值，**重建是新随机源而非收敛器**（OSD ID 漂移无法通过重建消除）。
  因此**继续重建无法收敛读绝对值**，只能用区间基线接受。
- 唯一可修的操作缺陷是 randrw（及写 analysis 项）的**每轮 remount+复用 layout** 导致样本污染（见 ①）。

### 10.3 基线锁定策略（不重测，分项分类）

| 项 | 口径 | 锁定值 |
|----|------|--------|
| seqread / seqwrite / mseqread | 现有中位（已收敛 Δ<4%） | 现有值 |
| randrw | 丢弃 r3 污染，取 r1/r2 中位 | 按修正后重采 |
| randwrite-ow | bw_log 稳态中位（非 fio 平均） | 现有值 |
| **randread (default)** | rebuild-first 两值(R1-A/R3-A) 中位 ± 区间 | **~1300 ±10%** |
| **randread (ra0)** | rebuild-first 两值(R2-B1/R4-B) 中位 ± 区间 | **~2600 ±10%** |
| 写类多线程(mseqwrite/layout/randwrite-true) | 现有中位 ± 15% 区间 | 现有值 |

> **不取六段简单平均**：cleanup 值已知系统性偏高 +17~31%，须剔除，只用 rebuild-first 值。
> randread ra0 若含 cleanup 值(3173)误入，会把区间抬偏（3173 vs rebuild-first 2393/2882）。

### 10.4 对 max-fuse-io 256K+buf1024 验证的影响（在波动基线上验证是否有意义）

**有意义，但须改判据 —— 效应量门槛替代全项 CV<5%：**
- max-fuse-io 历史效应量（randread ~2.0×、mseqwrite ~+30%）**远大于**当前 12~29% 漂移带，信号可辨。
- 判据：**同一重建/挂载会话内背靠背对比** 256K+buf1024 vs 128K+buf300，只比 Δ，
  **不跨重建比绝对值**；Δ 须**显著大于 ±15% 噪声带**才算真实效应。
- 前提：randrw 用干净口径（丢 r3 或修脚本），randread 用 rebuild-first 值。
