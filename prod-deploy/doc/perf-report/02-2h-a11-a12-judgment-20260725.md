## 三、判定

### 3.1 发送侧假设：**推翻**

发送侧假设预测坏轮应出现：
- TCP retrans↑（重传）→ **实测 0，未出现** ❌
- TCP cwnd↓（拥塞窗口收缩）→ **实测坏轮反而更高（1605 > 576-758）** ❌
- NIC tx_dropped↑ → **实测 0，未出现** ❌
- NIC tx_pause↑ → **实测不变（2→2，增量 0）** ❌

四个预测全部落空。**发送侧网络路径（TCP/NIC）在好坏轮间无差异**。

### 3.2 为什么坏轮 cwnd 反而更高？

cwnd 是 TCP 拥塞窗口——允许发送的未确认数据量。坏轮 cwnd=1605 > 好轮 cwnd=576-758，说明：
- 坏轮 TCP 窗口大开，但**OSD 产数据不够快，填不满窗口** → 数据产出是瓶颈，不是网络
- 好轮 TCP 窗口较小，因为**数据流动快，ACK 回得快，窗口不必开大**就够用
- cwnd 高低是**吞吐的后果**，不是原因

### 3.3 瓶颈定位（更新）

| 路径环节 | 好坏轮差异 | 判定 |
|----------|-----------|------|
| 157 客户端 CPU/IO | 一致（idle=82%, wa=0, D=0） | ❌ 排除 |
| 157→OSD 网络路径 | 一致（cwnd/retrans/drop/pause 全 0） | **❌ 排除（发送侧假设推翻）** |
| OSD→157 网络路径 | 一致（同上） | ❌ 排除 |
| OSD rocksdb get_latency | 一致（~4μs） | ❌ 排除 |
| **OSD buffer hit_rate** | **坏轮 -3.6pp（Opus 差分）** | **⚠ 最可能但仅解释部分** |
| OSD op queue / messenger | **未采集** | **⚠ 待排查** |
| OSD BlueStore 内部 | **未采集** | **⚠ 待排查** |

**瓶颈在 OSD 内部数据产出路径**（BlueStore 读 → op queue → messenger → NIC），不在网络传输路径。TCP/NIC 路径完全干净，cwnd 高位但填不满 = OSD 产出不够。

### 3.4 下一步方向

发送侧假设推翻后，按 Opus §-1.5 分流：
> 若发送侧指标好坏轮无差异（推翻发送假设）→ 变量在更上游，转排 JuiceFS 客户端侧（go-ceph 连接管理/线程调度/messenger），在 157 采 go-ceph 侧指标。

但实际更可能的是 **OSD 内部路径**（而非 JuiceFS 客户端侧），因为：
1. 157 CPU idle=82% → JuiceFS 客户端有大量算力余量
2. buffer hit_rate 已有 3.6pp 差异（OSD 侧）
3. cwnd 高位填不满 → OSD 产出不够（OSD 侧问题）

建议下一步：
1. **采集 OSD op queue depth**：`ceph tell osd.* dump_op_pq_state` 或 `ceph tell osd.* perf dump` 中的 op queue 相关指标
2. **深入 BlueStore 读路径**：`ceph tell osd.* perf dump` 中的 bluestore_read_latency / bluestore_kv_flush_lat 等
3. **或采纳统计基线**：好轮 randread 5 轮中位 1472±CI，接受波动不可控，推进 B/B2
