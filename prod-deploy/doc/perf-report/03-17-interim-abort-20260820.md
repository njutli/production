## 三、判档失败的归因：不是测量坏了，也不是外部负载

### 3.1 ns/B 与带宽全程线性自洽

同一天、同一脚本形状（`mseqread` / 16 jobs / bs=256k / direct=1 / psync / 180s，t46 与 t47 的判档 fio 逐字符相同，`OPTS` 也逐字符相同）：

| 会话 | 标签 | 判档 bw (MiB/s) | ns/B | dev | bw × ns/B |
|---|---|---|---|---|---|
| 03-16 | A-t1-P-r1 | 4166 | 3.320 | — | 13831 |
| 03-16 | A-t1-P-r2 | 4144 | 3.340 | — | 13841 |
| 03-16 | B-t1-P-r1 | 4161 | 3.326 | — | 13840 |
| 03-16 | B-t2-P-r1 | 2856 | 4.986 | — | 14240 |
| 03-16 | B-t3-P-r1 | 2983 | 4.759 | — | 14196 |
| **03-17** | **A3-p1-P-r1** | **2666** | **5.362** | 63.1% | 14295 |
| **03-17** | **A3-p1-P-r2** | **2697** | **5.297** | 61.1% | 14286 |

乘积从 13831 单调走到 14295（+3.4%，固定开销项），说明 ns/B 与带宽是同一件事的两种表达。**判别器没有坏，5.329 是真实的坏档。**

### 3.2 集群侧反而更快了

A1 臂 `rep1-P64` 在两次会话中配置完全相同（msgr=1、ioctx=2、64 jobs、randread、180s），由 6 个 OSD 的 `perf dump` 前后差算：

| | 客户端 bw | OSD 合计 op_r | OSD 每 op 读延迟 |
|---|---|---|---|
| 第一次 12:xx | 1699.0 MiB/s | 2,569,518 | 0.378 ms |
| 第二次 16:0x | 1495.0 MiB/s | 2,265,046 | **0.335 ms** |
| 变化 | −12.0% | −11.8% | **−11.4%（更快）** |

OSD 变快、客户端要的 op 等比变少 ⇒ **瓶颈 100% 在客户端**，与"157 白天 138 个登录用户 / load 26"无关。这一条正向支持 F50。

### 3.3 客户端逐层拆解：只有两处有差异

判档窗口（179 s）内 `.stats` 指标增量：

| | 03-16 好档 | 03-16 坏档 | 03-17 坏档 |
|---|---|---|---|
| fuse 读出 | 4171.6 MiB/s | 2858.4 | 2668.5 |
| 对象 GET 速率 | **16686 /s** | 11434 | 10674 |
| 每 GET 延迟 | **5.839 ms** | 7.000 | 7.524 |
| **对象层 in-flight**（= GET/s × 延迟） | **97.4** | **80.0** | **80.3** |
| 读放大 | 1.000× | 1.000× | 1.000× |
| GET 块大小 | 256.0 KiB | 256.0 | 256.0 |
| meta | 31.7 /s · 0.352 ms | 32.0 · 0.349 | 32.6 · 0.346 |
| read buffer 峰值 | 52.0 MiB | 51.5 | 51.8 |
| 客户端 CPU | 6.88 core | 4.90 | 4.65 |

**无差异项**（可全部排除）：读放大、GET 块大小、meta 路径、读缓冲区占用、OSD 侧、客户端 CPU 饱和（三档都远未打满 96 核）。

**有差异项**只有两个：每 GET 延迟 +20~29%，对象层 in-flight 97.4 → 80.0 / 80.3。

两次独立会话的坏档 in-flight = 80.0 与 80.3（差 0.4%），落在同一个平台值上 ⇒ 不是连续退化，是**掉进了另一个稳定态**。

### 3.4 两个分量必须分开：A1 臂给出干净的对照

A1 臂 msgr worker 只有 1 个，**结构上不可能出现 worker 之间不均**。同配置跨会话对照：

| A1 rep1 | in-flight | 每 GET 延迟 | bw |
|---|---|---|---|
| 第一次 | **65.1** | 9.116 ms | 1699.0 |
| 第二次 | **65.3** | 10.378 ms（+13.8%） | 1495.0（−12.0%） |

in-flight 纹丝不动（65.1 vs 65.3），只有延迟漂移。据此把现象拆成两个独立分量：

- **分量①「会话间慢漂移」**：每 GET 延迟量级 +13.8%，与 worker 数无关，msgr=1 也有。原因未定，但已知不在 OSD 侧（§3.2）。
- **分量②「好/坏档双稳态」**：in-flight 97.4 ↔ 80.0，跌幅 −17.7%，msgr=1 时不出现。**这是 B8 的本体。**

## 四、对分量②的候选机制（未验证，T48 去验）

**H1｜msgr worker 的连接分配不均**（首选）。librados AsyncMessenger 在**建连时刻**把每条连接轮转绑到某个 `msgr-worker`。3 个 worker 对 6 个 OSD 连接 + mon/mgr，分配结果取决于建连顺序 ⇒ 每次挂载随机、建好后终生不变、重挂不保证修好（与 03-16 重挂 3 次全败吻合）。均匀 2/2/2 = 好档，倾斜 3/2/1 时单个 worker 成瓶颈 = 坏档。也顺带解释 F52 的"第二挂载位慢 8~10%"。
判别信号：坏档时 `msgr-worker-N` 逐线程 CPU 严重不均。

**H2｜线程的 CPU/NUMA 落位**。96 核多 socket，worker 落在跨 NUMA 或与 `io_context_pool` 撞核时延迟升高。msgr=1 时单 worker 的落位同样受影响 ⇒ **H2 还能顺便解释分量①**。
判别信号：坏档与线程所在 CPU / NUMA node 相关，而 worker 间 CPU 均衡。

**H3｜objecter 全局锁**。若 worker 均衡、落位也无差异，则 in-flight 平台值 80 来自客户端对象层的全局串行点。
判别信号：H1/H2 均不成立时的兜底。

已排除：本地缓存盘（`--cache-size 0`，本地缓存本来就关着，根分区 98% 满与本现象无关）、meta、读放大、缓冲区、OSD、客户端 CPU 饱和。

## 五、⚑ 为什么 03-17 不能只修脚本后重跑

如果 H1 成立，**"档位"和"自变量"是同一个东西**：worker 数量是自变量，worker 间连接分配均衡度是档位，后者是前者的函数。此时 ns/B 门槛会系统性地剔掉 A3 臂（msgr=3）的倾斜样本、却保留 A6/A12（worker 多、倾斜相对影响小）的全部样本，**把 A3 人为拔高、把臂间差异抹掉或反转**。这样跑完的 40 个 run 无法回答 F50。

因此 03-17 的正确前置是先定性分量②，再重新设计矩阵（预期方向：取消按 ns/B 剔样，改为每臂多重复 + 把 worker 均衡度作为协变量逐 run 记录）。前置任务 = **03-17b / T48**。
