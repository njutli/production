正确的机制边界是：

1. B1c四臂均复现pending增长、物理NVMe await增长和Raft sync从约0.22--0.23 ms升至0.74--0.80 ms；带宽对pending与await的同窗相关系数分别约`−0.29…−0.63`和`−0.21…−0.54`，与03-22b的尾段软排队链一致。
2. D1没有消除KV compaction或物理NVMe压力；其W4 pending为11.27--15.73 GiB，物理NVMe await反而高于B1c，不能写成“D1通过降低KV/NVMe await而稳定”。
3. D1直接稳定的是Raft sync：四臂W1/W4都约0.074--0.083 ms。它在KV侧pending/await仍增长时保持更好的CV和W4/W1，支持“logs同步路径是尾部波动的放大因素”；但带宽只有5%中位增益，证明它不是平均服务率主墙。
4. OSD kv_sync约0.084--0.095 ms，没有B1c→D1的一致下降。D1对pending/await与BW的同窗相关方向也不完全一致，因此这些相关量不能单独宣告因果。
5. RocksDB hard stall全程为0；观察仍属于软排队、同步提交周期与共享资源耦合，而非硬写停顿。

以上是时间顺序和相关性证据；由于D1同时改变logs介质服务时间和共享NVMe争用，不能继续拆出两者各自贡献。

## 8. 架构结论与下一步

03-18～03-22c形成的写侧链条已经足够清楚：

```text
单inode同步事务周期
        ↓ 增加inode可扩展
TiKV共享KV/compaction与同步logs路径
        ↓ B1c尾段共同排队
D1移除logs同步路径抖动 → 稳定性改善、带宽仅+5%
        ↓
KV compaction/共享事务服务率仍在，3757 MiB/s止步
```

因此不再继续扫描inode数、`max-uploads`、compaction worker或重复A1/B1/D1。要达到6250，D1仍缺`2493.49 MiB/s`，局部logs隔离无法填补。

可选的条件C（fresh临时TiKV直接使用生产`/mnt/jfs-tikv`原生ext4精确目录、无nested loop）只用于拆分“native ext4 vs nested loop”和“fresh临时起点 vs 历史H”的组合差异；它不能推翻本RUN的D1结论，也不直接提供达到6250的调优手段。故降为**可选归因闭环**，仅在需要回答H→fresh差异时另开RUN和维护窗口。真实第二NVMe同样只在硬件可用且确有部署决策需求时再测。

若不做条件C，03阶段写侧可直接收口为：在线参数空间和logs隔离均不足以达标，剩余差距属于TiKV同步元数据事务、KV compaction共享服务率及JuiceFS写架构问题，转入架构改造/组件选型，而不是继续局部参数调优。

### 9.2 五条可交付结论

#### 1. WAL/Raft与KV共享NVMe会放大尾段波动

B1c四臂均出现pending compaction、NVMe await和Raft sync在W3--W4共同增长，并伴随带宽下降。该现象在03-22b首次定位、在有效03-22c中重复出现，因此不是单轮随机噪声。它属于软排队，不是RocksDB hard stall。

#### 2. RAM logs能改善稳定性，但不能解决主带宽问题

03-22c正式结果为4/4配对D1高于B1c，CV和W4/W1也均4/4改善；D1把Raft sync稳定在约`0.074--0.083 ms`。但带宽效应中位只有`+5.05%`，未过`15%`材料门；KV pending compaction和物理NVMe压力仍然存在。故logs路径是尾部波动的放大因素，不是平均吞吐主墙。

#### 3. 同一物理NVMe上的逻辑拆分不是关键优化方向

03-22的RAM逻辑隔离和03-22b的双loop/ext4逻辑隔离都没有形成接近目标的工程幅度；最终更激进的D1也只有约5%正式增益。虽然前两个RUN不能签收其A/B效应，但与正式D1结果合并后，已没有理由继续重复loop、目录、文件系统或同盘WAL/Raft拆分扫描。

#### 4. Fresh状态很重要，但不能解释全部波动

历史H中心约`2880 MiB/s`，fresh临时集群下B1c/D1中位约`3608/3757 MiB/s`，跨阶段组合差约`+25%/+30%`。这说明历史TiKV状态、本地介质起点或临时集群条件确实影响性能，但三者混在一起，不能签成fresh或介质单因素效应。

同时，即使每个arm使用fresh TiKV、fresh本地文件系统和同一seed，B1c仍会在一轮内部随compaction进入尾段下降。因此旧环境波动不能全部归咎于“跨日RocksDB状态积累”；还包含负载运行时必然形成的compaction和同步事务排队。

#### 5. 6250 MiB/s无法靠当前局部调优达到

正式B1c/D1中位为`3607.63/3756.51 MiB/s`；最好方案仍只达到目标`60.10%`，差`2493.49 MiB/s`。logs隔离带来的约5%收益无法解释或填补剩余约40%缺口。

结合03-18/03-19，完整写侧链条为：

```text
低inode并发：单inode同步TiKV事务周期约束
        ↓ 增加inode数可以扩展
较高inode并发：进入TiKV共享KV/compaction及同步提交服务率约束
        ↓ 隔离WAL/Raft到RAM
Raft同步尾部改善，但KV共享路径仍在，吞吐停在约3.76 GiB/s
```

### 9.3 稳定性方法论收益

本系列还形成了一套可复用的稳定性合同：

1. 一次layout生成immutable seed，每arm只restore/clone，避免layout lottery和数据集变化；
2. fresh必须覆盖metadata namespace、本地文件系统容量、旧目录、loop/ext4及可用空间，不能只换data dir名称；
3. 每arm后执行独立GC return，核对`valid=524288`、`leaked=0`和pool回归；
4. 容量、内存、swap、sampler覆盖、UUID/PID/anchor和生产指纹都属于非性能硬门；
5. CV和W4/W1是必须保留的性能端点，不应因结果差而删除arm；
6. 执行失败必须保留现场并使RUN失效，不能在同RUN热修、重试或补样替换。

#### 9.3.1 对数据准确性的实际保障效果

这些合同不是单纯增加日志量，而是在03-22系列中实际阻止了多类错误结论：

| 保障措施 | 实际发现/阻止的问题 | 对结论的影响 |
|---|---|---|
| immutable seed、每arm fresh namespace与fresh local FS | 03-22发现只换namespace但复用logs目录会跨arm累积容量，最终触发TiKV `AlmostFull/AlreadyFull`及EIO | 防止把本地容量污染误判成某个存储臂性能差 |
| 以实际I/O起点对齐、保存256份BW日志并按时间重叠重采样 | 旧流程曾把256个fio进程启动期混入W1，并漏掉真实负载尾段 | 保证CV和`W4/W1`描述的确实是同一段有效I/O，而不是进程启动开销 |
| 4组配对、固定平衡顺序、同批重测B1c/D1 | 03-22部分数据为`+0.47%`，03-22b唯一配对为`-1.55%`，首次无效03-22c为`+2.32%`；这些不完整/无效结果既不同向也不能给出准确效应量 | 最终有效RUN才签收4/4同向、带宽中位`+5.05%`及稳定性4/4改善，避免选择性引用有利样本 |
| 非性能证据门与性能端点分离 | 03-22b把CV同时当证据删除门，控制臂真实不稳定反而使矩阵无法回答稳定性问题 | 最终RUN保留所有完整arm，差CV本身成为正式比较结果，不再因“结果不好”删样本 |
| 容量/内存/身份/采集覆盖硬门，失败保留现场 | 发现tmpfs容量合同、JuiceFS daemon父子PID、Go argv、UUID解析、跨namespace inode合同等实现问题 | 阻止脚本错误、身份错认或容量不足进入性能统计 |
| 每arm独立GC、pool return和最终生产指纹 | 每轮清除约239万--264万个leaked objects，最终均回到`valid=524288, leaked=0`；生产TiKV、Ceph和本地资源闭环 | 保证下一arm不继承对象/本地状态，也证明测试没有以污染生产环境换取数据 |
| 冻结manifest、9973项SHA校验、891行授权账本和独立离线审计 | 独立审核纠正了执行方关于GC数字、授权账本位置、driver计数及“D1降低物理NVMe await”等错误描述 | 结论可由归档重算，不依赖执行者口头摘要；同时避免把相关性写成错误因果 |

如果没有这些门禁，03-22系列很容易在不同阶段分别得到“逻辑分离几乎无效”“分离略有负收益”或“RAM logs约2%收益”等相互冲突的说法。最终正式重跑说明：方向上确有收益，准确效应是带宽配对中位`+5.05%`，主要价值则是CV和`W4/W1`的4/4改善。数据治理因此直接改变了可交付结论的证据等级和精确幅度，而不只是让报告更完整。

#### 9.3.2 时间与token成本

代价同样明显。03-22、03-22b和首次03-22c共三个RUN因容量合同、稳定性门设计或执行协议问题不能签收，直到第四个RUN才形成有效因果结果。最终正式矩阵的纯fio负载时间只有`8 × 180 s = 24 min`，但从03-22准备到03-22c签收跨越8月25日至28日；大部分时间消耗在临时三节点集群、seed/restore/clone/GC、存储create/destroy、canary、脚本现场修复、失败取证和逐阶段授权，而不是负载本身。

正式RUN本身也体现了控制成本：R01--R07各有`46 BEGIN/46 PASS`、R08有`48/48`，授权账本共891行，另有G01--G08八次GC闭环和9973项归档校验。它们不能换算成同等数量的人工操作，但说明一次8-arm实验的控制面规模远大于8条fio命令。

本系列没有保存按任务拆分的模型token用量账本，因此不能编造“每个有效arm消耗多少token”的精确比值。可以确定的是，前期采用“每个小步骤停下、GPT给一句指令、GLM执行后再回传”的方式，产生了大量重复上下文、状态复述和短指令；这部分token主要用于协调和现场调试，边际信息收益偏低。真正高价值的token消耗集中在事前合同审查、无效RUN审计、时间线独立复算和最终跨源归因。

#### 9.3.3 性价比判断

| 评价维度 | 判断 | 原因 |
|---|---|---|
| 防止错误性能结论 | **高性价比** | 三个无效RUN若被直接引用，会得到不完整甚至方向冲突的结论；最终4-pair才具备因果解释能力 |
| 生产与数据安全 | **高性价比** | 测试涉及生产NVMe、临时TiKV、loop/tmpfs、Ceph海量对象和sudo；精确闭环避免了生产目录误删、对象残留和内存/挂载泄漏 |
| 本次一次性交付的时间/token效率 | **中等偏低** | 三个无效RUN和大量逐步交互显著高于24分钟正式负载本身；多项脚本问题本可通过更完整的离线fixture和一次集中review提前发现 |
| 作为后续同类测试基础设施 | **中高，前提是复用和自动化** | seed/clone/GC、真实I/O起点、非性能门、归档审计等可直接复用；若下次仍逐小步人工授权，性价比会再次下降 |

总体上，这次额外投入是必要但偏贵的：对于避免错误生产决策和保证环境安全，收益远高于成本；如果只看“得到一个`+5.05%`数字”，一次性性价比不高。它的长期价值取决于后续是否把已经验证的合同固化成批量自动执行，而不是再次从逐命令指导开始。

后续同类实验建议保留所有高价值准确性门，但压缩协调成本：正式前一次性冻结脚本和manifest；用离线fixture覆盖PID/argv/JSON/容量/partial-destroy等已知分支；只在sudo存储变更、生产停启和失败现场处暂停授权；read-only采集、单arm内部步骤、GC验证和归档由冻结driver自主完成；GLM按“canary一批、正式矩阵一批、最终审计一批”回传。这样不降低数据准确性和生产安全性，同时可显著减少等待、重复上下文和token消耗。

这套协议最终使03-22c能够区分“调优真的改善稳定性”和“环境起点碰巧更好”；其最重要的方法论结论不是“门越多越好”，而是**保留能够改变证据有效性或保护生产的门，自动化已经稳定的机械步骤，删除没有新增信息的逐小步人工往返**。

### 9.4 阶段处置

03-22系列之后，不再继续inode、`max-uploads`、compaction worker、A1/B1、RAM logs或同盘逻辑隔离扫描。条件C只在需要拆分native ext4/nested loop及fresh/历史状态时作为独立可选归因实验；真实第二NVMe只在硬件可用且存在部署决策时测试。

当前正式架构结论是：randwrite剩余瓶颈主要位于JuiceFS按inode组织的同步元数据事务，以及TiKV共享KV/compaction服务率；不在网卡，也不能由单独隔离WAL/Raft解决。若继续追求6250 MiB/s，应转向减少/批量化同步元数据事务、改变inode并行模型、优化或替换元数据架构，而不是继续局部参数扫描。
