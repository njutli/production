### ⚑ 复核方 Q2 判定（2026-08-07）

**⚑ Q2 = 交错有效，且证据比预期更强。**

**① 时序漂移确实存在，而且不小。** 全 6 run 按时间序的 randread median：

```
1862.8 → 1856.7 → 1849.0 → 1830.7 → 1843.7 → 1844.7
  A1       B1       A2       B2       A3       B3
```

Spearman(run 序, 值) = **−0.771**（n=6 的 0.05 双侧临界值 ±0.886 ⇒ **不显著，但方向明确**）；峰谷极差 **1.72%**。

**② 交错把它压掉了 87%。** 时序漂移 1.72%，而臂间残差仅 **0.233%** ⇒ 抵消率 ≈ **1 − 0.233/1.72 = 86.5%**。**这正是紧邻交错要达到的效果，也是 03-2 那三条纪律的直接实证。**

**③ 数值空间上两臂完全交织**（这是交错有效性最直观的判据）。把 6 个 randread median 从小到大排：

| 排序 | 1830.7 | 1843.7 | 1844.7 | 1849.0 | 1856.7 | 1862.8 |
|---|---|---|---|---|---|---|
| 臂 | **B** | **A** | **B** | **A** | **B** | **A** |

**`B A B A B A` 完全交替** —— 两臂在数值空间上无任何分离趋势，这是"无效应"的理想形态。

**④ mseqread 轻微 B 偏高，但不显著。** 排序为 `A(4101.7) B(4122.2) A(4137.0) A(4137.3) B(4142.7) B(4144.5)`，B 占秩 2/5/6。Mann-Whitney **U = 7/9**，而 n₁=n₂=3 时 0.05 双侧要求 U=0 或 9 ⇒ **不显著**。

**⑤ 反过来印证了 03-2 的判断**：如果按"先跑完 A 臂 3 run、再跑完 B 臂 3 run"的常规做法，B 臂会整体落在时序后段。以本次实测的 1.72% 漂移幅度计，**足以凭空造出一个超过 mseqread 门槛（1.5%）的假"收益"**。⇒ **紧邻交错是硬要求，不是优化建议。**

**⚑ 一处与 03-2 的矛盾（重要，见 §十二.3）**：03-2 判定 randread **无 lag 依赖**（Spearman +0.091，纯随机噪声），而本次 4.5h 内 randread 呈 **−0.771 的下行**。差异最可能来自**测量窗口**：03-2 在夜间（低负载），本次在**日间 11:51-16:20**，且最低点 B2（14:07-14:52）正落在午后负载峰。⇒ **randread 的"无趋势"结论只在夜间成立。**

### ⚑ 复核方 Q4 分析（2026-08-07，脚本 `/tmp/h1chk2.py`）

#### 🔴 口径陷阱（先说这个，以后所有 `perf dump` 分析都适用）

`onode_hits` / `buffer_hit_bytes` 等是**累计计数器**（自 OSD 启动起单调累加），**对 run 序天然单调**。直接拿累计值算相关会得到**伪相关**：

| 错误做法（累计值） | 结果 |
|---|---|
| Spearman(run 序, 累计 onode 命中率) | 天然单调，恒 ≈ ±1 |
| Spearman(累计 buf 命中率, mseqread) | **0.371 —— 与 Spearman(run, mseqread) 完全相等** |

第二行那个"完全相等"就是伪相关的指纹：因为累计值对 run 序单调，它的秩就等于 run 序的秩，算出来必然等于 run 序与 mseqread 的自相关。**复核方第一遍就踩了这个坑。**

⇒ **必须取每 run 的 pre/post 增量。** 以下为增量口径结果。

|---|---|---|---|---|
| T10-A1 | 94.251 | 69.085 | 4137.0 | 11320.8 GiB |
| T10-B1 | 94.201 | 69.219 | 4142.7 | 11276.4 GiB |
| T10-A2 | 94.060 | 69.141 | 4101.7 | 11250.3 GiB |
| T10-B2 | 94.169 | 69.259 | 4122.2 | 11209.1 GiB |
| T10-A3 | 93.970 | 69.243 | 4137.3 | 11267.9 GiB |

|---|---|---|

| Spearman(run 序, `d_onode_hit%`) | −0.371 | 不显著 |
| Spearman(`d_buffer_hit%`, mseqread) | **0.486** | **不显著** |

#### ⚑ Q4 判定：部分支持 H1，但不足以判定

**支持的一面**：BlueStore buffer 命中率随 run 序**单调上行**（+0.886，恰在临界值），方向与 H1 预测（数据集 577 GiB 可完全驻留于合计 ~2.1 TiB 的 OSD 内存，`drop_caches` 清不掉 BlueStore 进程内缓存 ⇒ 反复读单调升温）**一致**。

**不支持的一面**：

1. **幅度太小**：69.085 → 69.265，只有 **+0.18 个百分点**。
2. **与目标量的相关不显著**：`d_buffer_hit%` 与 mseqread 的 Spearman 仅 0.486 —— **缓存在升温，但没有证据说它就是 mseqread 漂移的原因**。
3. **onode 层无趋势**（−0.371），若真是元数据缓存升温，onode 命中率也该同步上行。
4. **时间尺度不匹配**：03-2 的 mseqread 漂移是跨 **11h46m** 的 +1.10%，本次仅 **4.5h**，mseqread 自身趋势（+0.371）都不显著 —— **本任务的窗口太短，判不了这件事。**

**⚑ H1 仍是待验假设，不得作为结论引用。**

### 3. ⚑ 对 03-4（写侧底噪）的三点影响（重要）

**① `randread` 锚不能用作中止判据 —— 原设计会误报。**

本任务实测：日间 4.5h 内 randread 从 1862.8 跌到 1830.7（**−1.72%**），而 1830.7 距高档带下界 1830 只剩 **0.04%**。03-4 原写"偏离 WD1 ±2% 即中止"，在 **60h** 尺度上几乎必然误触发，导致周末长跑被无故砍断。

**根因是判据设计混淆了两件事**：F1 已证**档位在挂载时抽签、同实例内 ≤1.1% 不变**，所以"实例是否同一"的硬判据是 **pid + `starttime_ticks`**（03-4 红线 11 已覆盖），锚不该承担这个职责。

⇒ **已订正**：randread 锚改为**协变量记录项**（用于事后把外部负载从写侧离散度里回归掉），中止线放宽到**单 run median <1700**（掉出全部高档、朝 1334 那一档去才算异常）。
⇒ **副作用是好的**：锚从"看门狗"变"协变量"后，03-4 能顺带定量回答"外部租户负载贡献了多少写侧波动"，正好补上"周末口径偏乐观"这个担忧。

**② 03-2 的"randread 无趋势"只在夜间成立。**

03-2（夜间）测得 randread Spearman(run,值) = +0.091（纯噪声），本次（日间 11:51-16:20）测得 **−0.771**，最低点正落在午后负载峰。⇒ **底噪与判据门槛都带"时段"这个隐含前提。** 03-4 跨周末昼夜，测出的写侧底噪会**比 03-2 的夜间读侧口径更保守（更大）**，这是好事，但报告须显式声明时段覆盖。

**③ 单 run 44min 与预估 43min 吻合，读侧工期估算可信；写侧仍未标定。**

本任务 6 run 共 4h29m，与任务书预估 4.5h 误差 <1% ⇒ 读侧任务（03-5/03-6/03-7）的工期估算方法可靠。但 `seqwrite` / `mseqwrite` 的每轮耗时**至今无实测值**（目前只有 `randrw` 8min、`randwrite` 11.3min），仍是 03-4 工期的主要不确定来源，由 03-4 的 `WD1` 校验点补齐。
