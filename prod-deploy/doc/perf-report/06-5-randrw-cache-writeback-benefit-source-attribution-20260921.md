# 06-5：randrw缓存＋writeback历史收益来源确认报告

> 日期：2026-09-21  
> 正式RUN：`20260921-182559`

## 一、结论

统一执行全卷GC/compact并在每格后等待对象数、TiKV pending-compaction和Ceph健康稳定后，历史“96GiB普通缓存＋writeback”相对无缓存的约21.7%增幅在两组位置上均得到复现：读为`+21.23%/+20.73%`，写为`+21.13%/+20.68%`。这说明历史收益不是单个偶然高值，**该组合在当前180秒randrw负载下确实能提高前台平均带宽**。

来源只收窄到“启用writeback后出现的缓存、staging与宿主脏页协同路径”，尚不能按预注册规则精确拆成独立writeback贡献：

- 普通缓存单独相对无缓存为`-1.1%/+8.6%`，没有重复材料收益，不能解释约21%的组合提升；
- writeback相对普通缓存为`+22.5%/+11.2%`，方向一致但第二组低于本RUN材料线约`15.09%`；
- R臂首尾漂移约`+7.55%`，超过预注册5%分辨率门，因此冻结分析器必须给出`RESOLUTION_INSUFFICIENT / PAUSED_INCONCLUSIVE`，不能事后放宽规则改判为`RESOLVED_WRITEBACK_BURST`。

机制证据与“有限突发吸收”一致：W1/W2的缓存命中字节占比约`53%`，staging峰值约`49.4/52.4 GiB`，宿主Dirty峰值约`94.7/94.5 GiB`，正式负载结束后分别需要`37/39s`排空；W格后40秒带宽只有前40秒的约`52%/45%`。因此约21%是完整180秒前台均值收益，但不是Ceph持续落盘能力提高，也不能省略排空和断电风险。

本任务为L1来源筛选，不登记生产配置；06阶段不再为取得更漂亮的来源比例追加同模型样本。若以后要把该组合作为交付候选，须在07阶段按独立任务验证更长负载、故障语义及可重复性。

## 二、合同与执行

- 顺序：`C1 → R1 → W1 → W2 → R2 → C2`。
- C：`cache-size=0`、writeback关；R：`cache-size=98304 MiB`、writeback关；W：同R但writeback开；三臂均关闭CLW。
- fio：`randrw 50/50`、`bs=256K`、`libaio`、128 jobs×QD128、`direct=1`、正式180秒，固定128×1GiB数据集。
- 初始canary及每格后共7次全卷GC/compact；每次等待pool对象/容量稳定、三节点TiKV pending为0和Ceph clean。
- 测试维护窗口内暂停portal namespace与157共享挂载，设置`noscrub/nodeep-scrub`；结束后全部精确恢复。
- 首次RUN `20260921-174705`因driver局部变量同语句展开触发`set -u`退出，尚未设置scrub、执行GC或fio；portal由包装器恢复。该RUN记`EVIDENCE_INVALID_ENGINEERING_PRELOAD`，不进入性能统计。修复并重新通过Gate后以新RUN整套执行。

主值按每格完整`io_bytes / max(read.runtime, write.runtime)`独立复算，不裁剪慢尾。

| 效应 | 读：第1组 / 第2组 | 写：第1组 / 第2组 | 严格判断 |
|---|---:|---:|---|
| R/C：普通缓存路径 | `-1.11% / +8.61%` | `-1.14% / +8.57%` | 无重复材料收益 |
| W/R：writeback增量 | `+22.59% / +11.16%` | `+22.53% / +11.16%` | 同向，但第二组低于M |

同臂漂移为：C读/写`-2.08%/-2.07%`，R`+7.55%/+7.55%`，W`-2.48%/-2.44%`；故`epsilon≈7.55%`、`M=max(5%,2epsilon)≈15.09%`。虽然W/C两组均越过M，预注册规则同时规定任一同臂漂移超过5%即停止来源裁决，所以全局状态仍是`RESOLUTION_INSUFFICIENT`。

1. R臂已实际命中约三分之一读字节并减少远端GET，但带宽没有稳定提高，说明普通缓存命中不是21%历史增幅的主要充分条件。
2. W臂同时提高缓存命中、吸收约50GiB staging并使用约95GiB宿主Dirty，前台完成速率由本地缓冲暂时解耦于远端提交；这解释了其前段高、后段回落和额外排空。
3. W臂PUT字节高于C/R臂，但上传并发仍接近既有上限；本任务不能把前台提升称为后端吞吐提升，也没有把普通缓存、staging和宿主页缓存三者精确分摊。
4. writeback仍遵守同inode读前flush语义；收益来自没有读操作阻断时的暂存与缓存协同，并未改变数据必须最终上传、提交元数据后才能安全读回的设计。
