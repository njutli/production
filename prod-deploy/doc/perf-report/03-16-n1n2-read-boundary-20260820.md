## 一、结论先行

1. **读侧瓶颈在单挂载，不在整机、也不在 Ceph 集群。** 双挂载并发合计 6048.7 MiB/s，比单挂载最好值 4021.3 高 **+50.4%**。若存在整机共享墙，加挂载不可能涨。
2. **单挂载的限制是对象 GET 的 op 速率，不是带宽。** 单挂载稳定在约 **16.9K GET/s**；并发从 j64 加到 j128，GET 速率不变（16866 → 16888/s），延迟精确翻倍（3.875 → 7.812 ms）。16.9K × 256 KiB = 4224 MiB/s，与实测 4101 MiB/s 相符。
3. **集群侧有余量。** 双挂载时 GET 速率到 25.1K/s，是单挂载的 1.49 倍；OSD 侧读延迟只占客户端 GET 延迟的 19%（单挂载）到 40%（双挂载 j128）。
4. **B2 结案**：F42/F46 的约束作用域 = **per-mount（单挂载 / 单 FUSE 实例）**。"整机固定封顶 4.1 GiB/s"证伪。01-3 历史 N4=5013 的反证得到同会话受控数据支持。
5. randread 双挂载已到 **96.8%** 的目标水平（网卡侧 6269.9 MiB/s 已过 6250）。但业务当前为单挂载，**该值只能作为约束归属证据，不能作为 randread 验收值**。

## 四、分析

### 4.1 约束作用域是单挂载

单挂载在 j64 就已饱和：加倍并发后 GET 速率零增长、延迟精确翻倍，这是服务速率封顶的标准形态。而把同样的并发拆到两个挂载进程上，机器级 GET 速率从 16.9K 涨到 25.1K，带宽从 4021 涨到 6049。**同一台机器、同一个 volume、同一个 Ceph 池，只是换成两个客户端进程，吞吐就多出一半**，因此 4.0–4.1 GiB/s 这道墙属于单挂载实例，不属于主机或集群。

### 4.2 瓶颈在客户端对象层，不在 OSD

- FUSE 读延迟与对象 GET 延迟逐配置相差不到 3%，JuiceFS 自身几乎不增加开销；GET 字节率与 fio 带宽相符，**无读放大**。
- OSD 侧读延迟即使按 1 次客户端 GET 折算成 2 次 OSD op，单挂载也只占客户端 GET 延迟的 19%（0.72 / 3.772 ms），C128 时占 40%（3.84 / 9.214 ms）。**剩余 60%–80% 的时间花在 OSD 之外**：客户端对象层处理与排队、网络往返。
- 在飞 GET 数恒等于 fio 的 numjobs（63.6 / 128.9），说明客户端并没有在更高层限流；限制体现为并发升高后单次 GET 服务时间等比恶化。

### 4.3 每挂载约 17K GET/s 的可能来源

librados 客户端默认 `ms_async_op_threads = 3`（157 的 `/etc/ceph/ceph.conf` 为最小配置，未设该项，取默认值）。按此折算：

- 单挂载 16.9K / 3 ≈ **5.6K op/s 每 messenger worker**
- 双挂载 = 2 个独立 librados 客户端 = 6 个 worker，理论 33.7K，实测 25.1K（差额可由 OSD 延迟从 0.362 上升到 1.922 ms 解释）

该折算与观测自洽，但**尚未验证**，是 03-17 要验的假设。它同时说明 B3（`ms_async_op_threads`，被 03-13 脚本缺陷错误跳过）是当前读侧优先级最高的旋钮。

### 4.4 双挂载也接近饱和

C64 合计 24145/s → C128 合计 25110/s，并发翻倍只涨 4.0%，同时 OSD 延迟从 0.958 涨到 1.922 ms。**机器/集群级存在第二道约束，位置约在 25–26K GET/s（6.1–6.4 GiB/s）**。它恰好落在目标 6250 附近，归属未定，候选包括客户端网卡/中断路径与 EC 池放置。注意 EC 池只有 33 个 PG，OSD 间负载不均达 34%，是这道约束的现成嫌疑之一。

### 4.5 P 与 Q 的系统性差异

两个挂载挂的是同一 volume，Q 侧稳定比 P 慢：GET 速率 15.2K vs 16.9K（−10%），判档 ns/B 3.60 vs 3.33（+8%），双挂载下差距扩大到 −21%。挂载序位带来的固定劣势尚无解释，未影响本轮结论（结论基于合计 vs 单挂载的量级差），但会干扰任何以 ns/B 绝对值做通过/失败判定的门。

### 5.1 两处数据缺陷（2026-08-20 在 03-17 前置验证中发现）

1. **`proc-*.tsv` 采到了错误的进程，该项数据不可用。** `juicefs mount -d` 会留下两个进程：ppid=1 的守护父进程（约 34 线程、无 librados 线程）和它的子进程（46~56 线程、持有全部 librados 线程）。t46 的 `mount_pid()` 取了第一个匹配即父进程，因此 `proc-P.tsv` 全程记录 37 线程恒定，而同一时刻真正服务 IO 的进程有 78 线程。**结论影响：无。** 本报告的带宽来自 fio，读路径预算来自挂载点 `.stats`，OSD 与网卡数据独立采集，均不经由 `proc-*.tsv`；受影响的只有 CPU 与线程数这类辅助量。附带一点：`instances.tsv` 冻结的也是父进程，所以"实例身份冻结"实际校验的是守护进程而非工作进程——工作进程若被重建、父进程不变的话不会被这条检查抓到（本轮 `.stats` 计数器全程单调，未出现重建痕迹）。
2. **`background-monitors-count.txt = 2` 是自匹配。** 清点用的 pgrep 模式含 `t4[0-9]-`，会命中 `t46` 脚本自己和它的 wrapper。剔除自身进程树后基线为 **0**，即 08-20 09:01 的清理确实彻底，"背景干净"的判断成立。

两处均已在 `t47` 中修正（正确选取子进程、清点时剔除自身进程树）。

## 六、Pair B 未取到数据的原因

Pair B 三次判档失败（Q 3.636/dev 10.6%，P 4.925/dev 49.8%，P 4.744/dev 44.3%），0 个 fio run。执行现场归因为"环境干扰（高负载）"，**该归因不成立**：

1. Pair A 在 load 29.7–35.2 下全部通过且带宽离散仅 0.30%，负载与判档结果不相关。
2. ns/B 实测呈双峰：好态 3.33（P 位）/ 3.60（Q 位），坏态 4.15 / 4.74 / 4.93 / 4.99。坏档的已知分离度约 27×，1.3–1.5× 的偏离是**第三种状态**，现有判据无法分类。
3. Q 位的正常值 3.595–3.648 正好被 ±10% 门槛（上界 3.616）劈成两半：A-t1 的 Q 以 9.8% 通过、B-t1 的 Q 以 10.3% 失败，**同一总体被边界随机切割**。参考值 3.287 是在单挂载上标定的，未为第二挂载的固定劣势留量。

因此 Pair B 的失败主要是**判档门设计问题**，其次是 ns/B 存在未解释的双峰。判据修订方案见 03-17 §2.3。

Pair A 的独立复现因此缺失。但本报告主结论的效应量为 +50.4%，远大于任何观测噪声（重复性 0.30%），并有网卡侧和 OSD 侧两路独立佐证，**不依赖 Pair B 成立**。复现改为在 03-17 的对照臂中顺带取得。
