## 1. 背景

03-16 确认读侧约束在单挂载（per-mount），单挂载卡在 ~16.9K 对象 GET/s。03-17 原设计因 ns/B 判档双稳态问题中止。03-17b/T48 定性查明：所谓"档位"是 librados 建连时 7 条 OSD 连接分配到 msgr-worker 的抽签，per-mount 读带宽 = 1438 MiB/s × 满载 worker 核数（r=0.9962），io_context_pool 线程 CPU 恒为 0（B8/F57 解除）。

### 11.3 新发现

**F58｜有效 worker 数上限 = OSD 数（6）。** 6 条数据连接轮转落位，`ms_async_op_threads` 超过 6 不再增加并行度：A8 均值仅比 A6 高 5.5%，且最好轮 5374 ≈ A6 最好轮 5412（差 0.7%，在噪声内）。A8 的实际价值**不是更高峰值，而是抽签稳健性**——A6 有 1/4 轮发生落位碰撞（掉到 4178），批内 CV 9.4%；A8 4/4 轮均无碰撞，CV 2.8%。**结论：生产取 `ms_async_op_threads=8` 作为防碰撞余量，收益按 A8 均值 5167 计；再往上（12/16）预测零收益，不建议扫。**

**F59｜≥6 worker 后限制项已换：单挂载读带宽 = 固定在飞并发 × 请求大小 ÷ 单 GET 延迟。** 全 20 轮在飞 GET 数恒为 **63.94 ± 0.69（CV 1.1%）**，即 fio 的 64 条流逐一同步等待；GET 大小恒 249 KB（loadRange 生效，读放大 objbw/fio-bw = **1.024**，无放大）。因此 `bw ~ 1/GET延迟` 的 **r = 0.9999**。延迟随 worker 数下降：9.27 → 3.82 → 3.83 → 3.11 → 2.91 ms，在 ≥6 worker 处触到 **≈2.8 ms 地板**，此时 worker 最忙仅 47–73%、客户端进程总 CPU 8.5 核（可用 96），**msgr-worker 已不是瓶颈**（H1 只在"连接/worker ≥ 2 的 CPU 饱和区"成立）。

**⚑ F56 订正**：`bw ≈ 常数 × 满载 worker 核数` 中的"常数"并非常数。本批 MiB/核 随 worker 数单调下降 **1692 → 1473 → 1395 → 1362 → 1361**；批内回归斜率随子集变化（全批 1243、A1+A3 1349、A6+A8 1408，截距 −170~+474 均显著非零）。⇒ **F56 仅适用于 worker CPU 饱和区（conn/worker ≥ 2）的粗估，不得用于跨 worker 数外推**。原 T48 外推"4≈5579、5≈6975、6≈8369"**作废**：实测 6 worker 为 4898（均值）/5412（最好），比外推低 35–41%。

**H4 复判：否。** 活跃 worker 落在 NUMA node1（奇数 CPU）的比例与 bw 相关性 r = **−0.20**；最好轮（A6-r4，5/6 在 node1）与最差轮（A6-r3，1/5 在 node1）方向相反。掩码与落位子集无偏斜效应。

**⚑ 报告 §5 的 `worker_cv_pct` 口径缺陷**：该列把 0% 的空闲 worker 计入，故 A8 恒显示 CV≈59%、A6-r3 显示 56%，是"存在空闲 worker"的指示器而非失衡指示器。仅取活跃 worker 时，A8 各轮 CV 为 10.9/12.2/11.4/11.3%，A6-r3 为 31.6%。**跨臂比较必须用 active-only CV**；本批内 `bw ~ active-only CV` r = 0.41（弱），`bw ~ 活跃 worker 数` r = 0.951（强）。

### 11.4 6250 MiB/s 可达性判定

- 单挂载 P64 现状：**最好 5412（86.6%）、A8 均值 5167（82.7%）**。
- 按 F59 分解，达 6250 需 25703 GET/s，二者其一：**延迟从 2.77 ms 再降 10.2% 到 2.49 ms**，或**在飞并发从 64 提到 71.2（+11.2%）且延迟不劣化**。
- 延迟侧已无客户端余量（worker ≤73%、CPU 8.5/96 核），2.8 ms 地板由 Ceph 服务时间 + 网络 RTT 构成，属 OSD 侧——两面墙未解除前不动。
- **并发侧是唯一未验证的廉价方向**：03-17c 按设计只跑了 P64，删掉了 P128。F42b"读在 64 并发流饱和"是在 worker 饱和态（msgr=3，加流只加延迟）下得出的，在 msgr=8、worker 有 27–53% 余量的新条件下**该结论必须重测**。
- **F51 交叉约束（最大风险）**：机器级 6.1–6.4 GiB/s = 6246–6554 MiB/s，而单挂载已占 82–87%。若并发侧完全奏效，6250 恰落在机器上限**下沿**，意味着"单挂载达标 = 独占全机读能力"，属**边缘可达**；若 F51 实为 6246，则 6250 不可达，须扩 OSD/PG 或提升单 OSD 读服务率（超出 03 阶段授权）。

**综合判定：03-17c 已把单挂载读从 3985（默认 msgr=3）提到 5167 均值/5412 峰值（+29.7%/+35.8%），但 `ms_async_op_threads` 这条路已走到尽头（有效上限 = OSD 数 6）。6250 的剩余 13–17% 缺口不在 messenger 线程，而在"并发 × 延迟"积，且被 F51 机器墙夹住。**

### 11.5 下一步建议（03-17d，短测，约 30–40 min）

1. 固定 `ms_async_op_threads=8`、独立挂载、256K randread，只扫并发：**P64 / P96 / P128**，各 3 轮，观测 `in-flight GET`、`GET 延迟`、`bw`、active-only worker CPU。
2. 判据：若 in-flight 能越过 64 且延迟保持 ≈2.8 ms ⇒ bw 应线性推进，届时用实测判断是撞 6250 还是撞 F51；若 in-flight 卡在 64 或延迟同比例上升 ⇒ F42b 在新条件下依然成立，**读侧目标在现集群规模下不可达**，应改走结论层（记录上限、转写侧 B1）。
3. 不做：12/16 worker 扫描（F58 预测零收益）；任何 OSD 侧旋钮（两面墙）。
