# 04-tmp2d 交付配置对齐的读缓存容量曲线报告

## 一、结论

RUN `20260903-131428`完成mseqread、randread各7个cell，14/14最终有效，判定：

```text
VERDICT=READ_CACHE_CURVE_COMPLETE
ENVIRONMENT_ASSET_STATE=CLOSED
```

在JuiceFS v1.4.1 patched、客户端私有`ms_async_op_threads=8`、256 KiB FUSE、默认预读条件下，
两项带宽均随缓存容量和实测命中率显著上升：

- 25%容量只有约14%--16%命中，收益约16%--19%；
- 50%容量约40%--42%命中，收益约61%--74%；
- 75%容量约67%--70%命中，收益约173%--233%；
- 100%名义容量仍只有94%--95%命中，因块文件/条目开销仍有淘汰和drop；
- 200%档达到100%命中、Ceph数据网读取接近0，mseqread/randread分别约
  `34.83/36.53 GiB/s`，相对同窗无缓存锚约`+671.8%/+743.6%`。

这证明本地读缓存存在稳定、材料级收益，且75%档补出了容量拐点；但不等于生产必须配置2倍
缓存。工程含义是**有效缓存容量至少要覆盖热工作集并给缓存块/条目开销留余量**。最小余量位于
100%--200%之间，本任务未细扫，不应从C200直接推导生产容量。

## 二、冻结口径

| 项 | 实际口径 |
|---|---|
| JuiceFS | `/tmp/juicefs-1.4.1-patched`，MD5 `24fae0852051c80ca571cb2f20275d46` |
| Ceph客户端 | RUN私有配置MD5 `86351c58848c7e4caaa1bbeccb211730`；实际8个`msgr-worker` |
| mount | `--read-only --max-uploads 150 --max-fuse-io 256K`；默认readahead/prefetch；禁止writeback |
| mseqread | 16×4 GiB，psync，iodepth=1，256 KiB，180秒；64 GiB工作集 |
| randread | 128×1 GiB，libaio，iodepth=128，256 KiB，180秒；128 GiB工作集 |
| 缓存介质 | 157原生ext4 `/mnt/jfs-cache`；每cell独立空目录 |
| 窗口 | 缓存cell预热180秒、正式180秒；性能取正式`[15,175)` |
| 顺序 | 每项`A0-pre→C25→C50→C75→C100→C200→A0-post` |

与04-tmp2c相比，本RUN修正了两处关键口径：不再使用Ceph系统默认3 worker配置，也不再显式
`--prefetch 0`。drops/evicts按产品表现记录，不再错误地作为证据完整性硬门。

## 四、有效性边界

1. 两项A0前后漂移均小于1%，证明本RUN时间漂移很小；14个最终cell的fio、资产、配置、网络、
   mount和健康证据均通过。
2. 每个容量档需要重新挂载。历史已知挂载档位会影响后端读路径，因此C25这类约16%--19%的
   小效应不能当成高精度容量因果点；C50以上60%--744%的材料信号远大于该噪声，方向可靠。
3. 本地缓存接近全命中后的35--37 GiB/s主要体现157内存页缓存+本地NVMe路径，不是Ceph裸盘或
   跨网带宽；生产收益取决于热集可重复性和本地盘容量。
4. 当前同窗无缓存绝对值低于历史最优`mseqread=5366`、`randread=5544 MiB/s`，分别约
   `-13.9%/-20.0%`。由于实际8 worker和A0漂移已受控，这说明历史峰值不能替代本RUN锚点；不影响
   大容量缓存收益方向，但生产canary仍应保留同窗cache=0锚。
5. 本任务完全只读，不提供writeback安全性或写性能结论；写侧由04-tmp2e独立处理。

## 五、工程建议

- 对有独立本地NVMe且读热集明确的生产场景，本地读缓存值得进入独立canary；
- 容量规划应按“热工作集+缓存条目/块开销+文件系统20%空闲保护”，不应只把`cache-size`机械设成
  热集逻辑字节，也不需要默认配到2倍；
- 空间紧张时，50%档已有约61%--74%吞吐收益，75%档约173%--233%，可用于成本/收益估算；
- 不把本报告加入无缓存七项交付基线，也不据此启用writeback；
- 若要固化生产档位，下一步只需小范围补`110%/125%`容量canary定位最小全驻留余量，不重跑本矩阵。
