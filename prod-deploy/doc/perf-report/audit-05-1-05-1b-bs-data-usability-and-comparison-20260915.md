>
> **口径归属的用法**：对外对比表的"JuiceFS 标准配置"列只能填**通用交付**口径值
> （B256 + FUSE256K + buffer300）。⛔ 专用挂载/专用卷口径值只能填入"JuiceFS 该 BS 最优有效
> 配置"列——04-8 已确认把 FUSE1M 全局化会使 256K randwrite 回归，混填会重演该错误。

一句话：**只有 256 KiB 规格点具备"通用交付口径 + 可作单点"的双重资格；4M/1M 的高值都属于
专用口径；4K/16K/64K 目前只能作为区间**。这与 05 计划书 §六"任一 BS 正反向两点差异超过 10%

尺度上同样越线，只是被"同一 RUN 内两点"这个较窄的定义放过了。

对照当前有方数据（周报 20260912）：有方 randrw 三轮 `2663/2177/2175 MiB/s`、均值
`2338.33 MiB/s`，且 R1→R3 自身下降 `18.33%`。**双方在 randrw 上都不稳定**，因此
"JuiceFS 1749.3 = 有方 74.8%" 这一行必须同时标注两侧的轮次离散度，不能作为单点结论；
正式对比须走 §三.1 的三态裁决规则。


## 三、必须先统一的五个口径问题

1. **统计窗口不同会系统性低报我方 4%--9%。**
   本项目主口径是 `[15,175)` 正式窗；有方给出的必然是 fio 180 s summary。复算得到的
   `正式窗 / summary − 1`：256K `-0.83%/-1.02%`、4M `-0.17%~-1.37%`，但
   4K `-4.18%~-8.01%`、16K `-6.88%~-8.89%`、64K `-4.23%~-7.62%`。
   ⇒ **对外比对表必须两栏并列（正式窗 + summary），且与有方比较时用同一栏**；
   ⛔ 不得用我方正式窗对有方 summary。

   **预注册的跨系统裁决规则**（本审计与 GPT 复核共同议定，落在 05 计划书 §三.3）：
   竞品脚本保留 128 份 per-job 逐秒日志，因此两侧的 summary 与正式窗**都能算**，无需二选一。

   ```text
   允许写方向性结论 = 两栏相对方向同号  AND  效应超过预注册的双方漂移/噪声范围
   两栏异号             → STATISTIC_SENSITIVE，只报区间
   两栏同号但未超过噪声 → INCONCLUSIVE，只报区间
   两栏同号且超过噪声   → 才允许写领先/落后方向

   μ_side(BS) = (位置1 + 位置2) / 2
   ε_side(BS) = |位置1 − 位置2| / (2 × μ_side)
              = |位置1 − 位置2| / (位置1 + 位置2)  （相对半幅，各侧分别计算）
   ε_pair(BS) = ε_ours(BS) + ε_theirs(BS)           （无量纲，保守取和）
   判定        = |JuiceFS/竞品 − 1| > ε_pair(BS)
   ```

   内部调优决策继续以正式窗为主口径（指导书 §二.13.4 不变）；summary 只作与公开 fio 命令
   对齐的并列旁证。

2. **≤64 KiB 在 180 s 内根本没到稳态。** 复算 `W4/W1`（末 40 s / 首 40 s）：
   4K `0.44--0.61`、16K `0.41--0.61`、64K `0.43--0.60`；256K `0.79--0.80`；1M `0.92--1.26`；
   4M `0.91--1.08`。⇒ 小 BS 的"均值"是 runtime 的函数。若要与有方比，必须双方同 runtime，
   并同时给出 W1/W4，否则谁 runtime 短谁占便宜。

3. **卷状态是未申报的变量。** 同为 `BlockSize=256K`：老生产卷 4K 只有 `20.2--22.2`，
   而同日新建卷 `24.5--39.6`；16K 为 `84.7--90.4` vs `104.0--124.8`。
   ⇒ 报告不应把生产卷（05-1 Phase A）与新建卷（05-1b）数值放进同一条"标准曲线"叙事；
   对外表格必须逐点标注"卷是新建还是已承载历史写入"。

4. **长矩阵内单调衰减，且已定位到根因。** S 组 12 格中同配置 4K 从 `39.6`（位置 1）降到
   `24.5`（位置 12），`-38.1%`。复算 `juicefs_transaction_durations_*` 得到：事务平均延迟
   `6.54 ms`（位置 1）→ `11.17 ms`（位置 12）；同格内四分位进一步给出
   `3.33 → 5.67 → 8.52 → 12.30 ms`，而**同期对象 GET 延迟从 `2.03 ms` 降到 `0.96 ms`**。
   ⇒ 衰减不是后端变慢，是元数据事务随累计写入变慢。平衡序列只抵消了它，没有消除它；
   小 BS 对外数值必须附"测前状态复位协议"（GC + 静置 + 事务延迟入门槛）。

5. **4M 用 per-job bw log 时逐秒积分比 `io_bytes` 少 `8.19%--9.71%`**
   （Phase A/B 全部 4M 格），改用完成日志的正式补测 RUN 为 `0.00%`。
   ⇒ 4M 绝对值优先引用 summary 或完成日志版本；⛔ 不要把 per-job bw log 的积分值当作 4M 真值。

## 四、订正一：B4M 的 `+17.94%~+18.80%` 不是净收益

把三个同为 `fio bs=4M`、同为 FUSE1M 的端点并列（全部来自 `derived/cells-recompute.tsv`）：

| 端点 | 卷 BlockSize | buffer-size | 正式窗 READ MiB/s |
|---|---:|---:|---:|
| `05-1b-r1/L-1-C1` | 256 KiB | **300** | `2201.56` |
| `05-1b-r2/L-1-C1`、`L-4-C2`（正式对照臂） | 256 KiB | **1024** | `1873.85`、`1886.68` |
| `05-1b-r2/L-2-T1`、`L-3-T2`（登记候选） | **4 MiB** | 1024 | `2226.13`、`2227.25` |
| `05-1-phaseB/4M-T1`、`4M-T2`（生产卷） | 256 KiB | 300 | `2216.14`、`2310.66` |

- 候选 `B4M+FUSE1M+buffer1024 = 2226` 与**现成的** `B256+FUSE1M+buffer300 = 2202/2216/2311`
  在同一水平（差 `+0.4%~-3.7%`，落在该配置自身 `4.3%` 漂移内）。
- 正式 RUN 内 `+18%` 之所以成立，是因为对照臂被 `buffer1024` 压低了约 `15%`
  （`2201.56 → 1873.85`）。机制侧一致：复算得 B256/4M 的读放大（GET 字节 ÷ FUSE 读字节）
  从 buffer300 的 `1.06` 升到 buffer1024 的 `1.37`，即抬 buffer 让 B256 多发了无效读。
- 因此 05-1b 的"4 MiB randrw 专用卷 L1 候选"应改判为
  **`NET_GAIN_UNPROVEN`，并从交付候选中撤出**：B4M 只是抵消了 buffer1024 对 B256 的损失。
- 内部效度并未被否定（同轮、同参数、同臂漂移 ≤0.69%），被否定的是"可交付净收益"的读法。
- **证据不对称原则（复核共同议定）**：本订正基于**跨 RUN** 比较（r1/b300 与 r2/b1024 位于两只
  不同 fresh 卷），这个强度足以**撤销**一个候选（保守方向），但**不足以重新主张**任一方向。
  因此 ⛔ 既不写"B4M 有收益"也不写"B4M 无收益"。
  若未来确有部署 B4M 专用卷的意图，须先做**同 RUN 三臂**
  （`B256/b300`、`B256/b1024`、`B4M/b1024`）；该实验已按复核结论从 05-2 删除，不占当前排期。

## 五、订正二：05-1 标准曲线没有机制证据

Phase A 12 个格的 `metrics-pre/post.prom` 均为空，标记
`METRICS_MISSING_ALLOWED_PHASE_A`（Phase A 复用既有生产挂载 `/mnt/juicefs`，未开 metrics 端口）。
- 影响：那条"4K→4M 标准曲线"只有 fio 端点，**没有对象 GET/PUT、上传在途量、buffer、事务延迟**，
  ⛔ 不得用它做任何机制归因（包括报告 §三"小 I/O 固定开销被摊薄"这类措辞，只能作为假设）。
- 好消息：该挂载参数经 `inventory/reference-mount-process.tsv` 核对确为交付配置
  （`--max-uploads 150 --cache-size 0 --max-fuse-io 256K`，buffer/downloads 取默认 300/200），
  所以曲线的**配置身份**是正确的，只是缺机制层。
- 05-1b 的 A/M/L/S 各格有完整逐秒机制采样，机制结论一律引用 05-1b，不引用 05-1 Phase A。

## 六、机制发现：大 BS 的写向被 `--max-uploads 150` 打满

这是本次复算最有价值的副产物，也是 05-2 的立项依据。

1. **在途上传槽 100% 饱和，12/12 格。** 所有 `fio bs=1M/4M` 且卷为 B256 的格，PUT 在途量
   （Little 定律 `Σlatency/Δt`）都是 `147.6 -- 149.8`，上限 `--max-uploads 150`：
   05-1 Phase B 8 格由 fio 前后 prom 计数器差分得出（`metrics_source=PRE_POST_COUNTER`），
   05-1b 的 `M-1-C1/M-4-C2/L-1-C1(r1)/L-1-C1(r2)/L-4-C2` 由逐秒采样得出
   （`PER_SECOND_TIMESERIES`），其中逐秒 gauge `juicefs_object_request_uploading`
   的 mean = p95 = max = **`150.0`**（全窗恒定，无一次回落）。
2. **写向带宽因此被算术决定**：`150 槽 × 256 KiB ÷ PUT 延迟`
   —— PUT `19.95 ms` → `1880 MiB/s`（`1M-C1` 对象层实测 `1849`）；
   PUT `16.29 ms` → `2302 MiB/s`（`1M-T1` 实测 `2284`）。全部 12 格 PUT 延迟落在
   `15.03--19.95 ms`，对应写向天花板 `1880--2496 MiB/s`。
   ⇒ FUSE1M 在 1M 上的 `+16%~+24%` 主要来自 PUT 延迟 `19.95→16.29 ms`，**槽数始终打满**。
3. **换成 1 MiB / 4 MiB 对象后闸门就松了**：`M-2-T1/M-3-T2`（B1M）PUT 在途 `60.5/59.9`、
   uploading p95 `90/80`，GET 在途 `51.7`（上限 200），带宽升到 `2593/2614`；
   `L-2-T1/L-3-T2`（B4M）PUT 在途仅 `27.1/27.0`。
   ⇒ 限制项是"槽数 × 对象大小"，不是后端能力。
4. **后端与客户端都有余量**：对象层总流量（GET+PUT）B256 各格只有 `4.12--5.15 GiB/s`，
   而 B1M/B4M 达 `6.07--6.15 GiB/s`；直接 RADOS 256 KiB 写 QD128 = `3948.86 MiB/s`
   （04-tmp3j，且未到平台）；客户端 mount 进程在大 BS 只用 `7.75--10.20` 核 / 64 核，
   100GbE名义单向线速约`12500 MiB/s`，但本批没有可用于签收的NIC计数器证据；历史
   `3220 MiB/s`是fio randwrite观测值，不是NIC能力上限，不能据此量化网卡余量。
5. **小 BS 是另一个瓶颈，且后端在闲着**：4K 格 uploading p95 仅 `42`、`used_buffer` p95
   `10.8 MiB`、对象时延 `1.44/1.81 ms`，而读写放大约 `8.2×`
   （正式窗应用 `39.6/39.7` ↔ 对象 `327.2/325.3 MiB/s`）。
   同时元数据事务在途量全窗为 `74.3--91.9`、格内末窗进一步升到 `93.7--101.9`
   （≈128 个 inode 的串行上限，与 04-4 审计的"一 slice 一事务" fan-in、
   03-19 的 inode 并行度 `+24%~26%` 一致）。
   ⇒ 小 BS 不是挂载参数问题，属 04-5 元数据事务批处理与 TiKV 存储隔离方向。
6. **buffer-size 是第二道闸，且全部超配**：`used_buffer_size_bytes` 的 p95 相对配置值为
   B256/1M `334--340 / 300`、B256/4M(buffer300) `597 / 300`、
   B256/4M(buffer1024) `1059--1067 / 1024`、B4M `1225--1234 / 1024`、B1M `482--491 / 300`。
   ⇒ 该参数在所有大 BS 格都处于越限throttle 状态，必须与 `max-uploads` 联动测，
   ⛔ 不能像 05-1b 那样把它当成"两臂公共条件"直接抬高。

7. ⚠️ **256 KiB 规格点是"接近闸门"，不是"顶在闸门"——这是推算，不是实测。**
   上述 12/12 格全部是 `bs=1M/4M`；256K 格没有机制数据（见 §五）。用现有量可以推算其水位：

   ```text
   B256 + FUSE256K 下 fio 的 256 KiB 随机写按 bs 对齐，1 次应用写 = 1 个 256 KiB 对象 PUT
   应用写 1749.3 MiB/s ÷ 0.25 MiB = 6997 PUT/s
   × 同配置实测 PUT 平均延迟 15.03 -- 19.95 ms
   ⇒ Little 在途量 = 105 -- 140 / 150，即 70% -- 93%
   ```

   对比 1M/4M 的实测 `147.6--149.8`（98%--99.9%）与逐秒 gauge 全窗 `= 150.0`。
   ⇒ 因此 05-2 把**主因果验证点放在 1M**（信噪比最好、闸门证据最硬），
   256K 先跑 1 格基线过 `256K_UPLOAD_PROXIMITY_GATE`（`uploading` 正式窗 p95 >= 120，
   沿用 05-1b §2.6 已预注册阈值）才进四格 C/T。
   该门名为 **PROXIMITY（接近）而非 SATURATION（饱和）**：`p95 >= 120` 只代表"接近并发上限、
   值得测试"，⛔ 不得写成"已证明 256K 上传槽饱和"；真正的持续饱和须看到接近 150 的占用比例
   或等价的 Little 在途量证据。
