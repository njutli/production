# 06-1 randrw 缓存与 writeback 组合包筛选报告

> 日期：2026-09-15  
> 有效 RUN：`20260915-204941`  
> 状态：`COMPLETED / RESOLUTION_INSUFFICIENT / NO_CANDIDATE`
> 审计订正：2026-09-16 根据 raw tar、fio bw log、iostat、meminfo 与 `.prom` 独立复算订正机制解释；
> 原始数据与预注册裁决不变，撤销“正式窗均值是有效收益”和“缓存盘饱和导致轮内衰减”两项表述。

## 一、结论

06-1 已完成并安全闭环，**不把 `96 GiB 读缓存 + writeback` 登记为生产候选，也不重跑 06-1**：

1. 两组位置配对的 READ/WRITE 160 秒算术均值高约 `16.3%～19.6%`，但 treatment 在窗内单调
   衰减，末窗已低于位置对照；该数是**依赖窗长的瞬时量，不构成可登记效应或收益**。
2. T1/T2 的秒级 CV 达 `38.0%～42.1%`，READ/WRITE 的 `W4/W1` 仅
   `0.387～0.414`；首窗约 `3.12 GiB/s`，末窗降至约 `1.22～1.30 GiB/s`，末窗已低于
   同位置无缓存对照。前段高带宽主要由宿主脏页吸收：T1 W1 的应用写减设备写约
   `1725 MiB/s`，同期 Dirty 增长约 `1559 MiB/s`，两者在约 `11%` 内闭合；随着脏页逼近限额，
   内核回压写者。该解释有强定量支持，但 `/proc/meminfo` 是宿主全局观测，不能写成唯一已证因果。
3. 同轮噪声底 `ε=7.32%` 超过任务书的 5% 分辨率门，故即使四个窗均值差都超过
   `M=max(5%,2ε)=14.64%`，预注册四态仍必须裁决为 `RESOLUTION_INSUFFICIENT / NO_DECISION`。
4. JuiceFS 报告的读命中约 `1380/1400 MiB/s`，而缓存设备实际读仅约 `9.07/0.60 MiB/s`，
   因而命中数据几乎全部由宿主页缓存供给；本 RUN 没有测到“NVMe 持续读缓存”这一名义被试对象。
   treatment 的设备写入与利用率很高，但它们**不足以证明设备服务率是轮内衰减主因**。
5. 96 GiB 缓存按 evict 速率约每 `41.3/43.0 s` 周转一次，并有约 `2078/1988 次/s` 的 drops；
   treatment 确实改变了缓存/writeback 路径，但当前容量与注入速率下存在持续淘汰和拒绝入缓存。
6. 两格 rawstaging 峰值约 `71.08/75.30 GiB`，均在 47 秒内严格归零；`stageFull`、staging
   errors、对象错误均为 0，无缓存验证挂载读回均 PASS。writeback 生命周期正确，但该短窗前台
   带宽不能解释为同速持久化能力；宿主 Dirty 峰值约 `112.4/118.5 GiB`，表示更多已确认数据一度
   只在易失内存中，宿主掉电时存在丢失风险。

因此 06-1 回答的是：**该组合能借宿主脏页与页缓存制造明显的前段加速，但没有形成可估计的稳态效应，
本轮状态也未对称，不能成为稳定或可交付配置。** 后续不追加“漂亮样本”；06-2 只先进入构建溯源
与动态 profile 门，用直接证据判断 whole-inode flush 是否值得改，尚不实现行为补丁。

以位置配对比较，T1 首窗相对 C1 首窗约高 `67%`，但末窗约低 `30%`；T2 首窗相对 C2
首窗约高 `73%`，末窗约低 `14%`。这不是稳定的平台提升。

同一正式窗内，缓存设备 `nvme1n1` 的四分窗如下：

| Cell | 指标 | W1 | W2 | W3 | W4 |
|---|---|---:|---:|---:|---:|
| T1 | 设备写 MiB/s | 1406 | 1696 | 1737 | 1370 |
| T1 | 设备 %util | 95.7 | 98.3 | 99.0 | 79.5 |
| T1 | w_await ms | 22.74 | 26.35 | 41.00 | 34.28 |
| T2 | 设备写 MiB/s | 1717 | 1704 | 1734 | 1505 |
| T2 | 设备 %util | 98.8 | 98.0 | 99.2 | 87.3 |
| T2 | w_await ms | 31.29 | 30.03 | 45.90 | 38.60 |

T1 在应用最快的 W1，设备写仅 `1406 MiB/s`（四窗最低）；应用较慢的 W3，设备写反而达到
`1737 MiB/s`（四窗最高）。T2也表现为应用带宽持续下降而设备写前三窗基本持平。因此设备写与
应用带宽并非同向变化，设备服务率不是本轮轮内衰减的**变化来源**。

但四窗设备利用率仍为 `79.5%～99.2%`，整体接近饱和；上述结论不等于“设备不是稳态限制”。
当宿主脏页吸收能力耗尽后，稳态前台写仍可能受本地设备排空率约束。这里区分的是：**设备可以限制
最终稳态平台，但不能单独解释应用带宽为何从 W1 到 W4 持续下降。**

| C2 | 0 | 0 | 1963.57/1937.88 | 0/0 | 0.01/0% | 0/0 | 0/0 |

读命中使远端 GET 明显下降，writeback 也改变了 PUT 路径；但命中字节与设备读相差两个数量级，
说明本轮读取几乎都来自宿主页缓存。应用带宽下降 `2.4×` 时，设备写大体持平且 W4 的 util 反而下降，
故不能再把“缓存盘持续饱和”写成衰减原因。T1/T2 的 JuiceFS `blockcache_write_bytes` 约
`2683/2550 MiB/s`，又高于设备写 `1552/1665 MiB/s`；结合 drops、evicts 与 Dirty 才能闭合路径，
设备写单值不能直接解释为持续服务率。

按 256 KiB 块计算，96 GiB 缓存在 T1/T2 约 `41.3/43.0 s` 周转一次，与只有首个 40 秒窗最快的
时间尺度一致。该一致性说明容量压力参与了瞬时曲线，但不得据此推出“增加容量即可获得稳定收益”。

## 五、因果、持久性与能力边界

1. **因果范围**：本轮 treatment 同时改变 96GiB 读缓存和 writeback；只有一条已批准缓存路径，
   `MULTI_DIR_UNAVAILABLE`。不得把结果单独归因于读缓存、writeback 或多路径。
2. **持久性**：writeback 的前台 ack 早于远端持久化；T1/T2 在 fio 后仍需47秒排空，rawstaging
   峰值 71.08/75.30GiB，而宿主 Dirty 峰值更高达112.4/118.5GiB。前台短窗均值不是同速远端
   持久化能力。宿主全局Dirty显示最多约112/119GiB脏数据驻留RAM；结合本轮字节预算，强烈指向
   大量前台已确认写入尚未落本地NVMe或Ceph，但不能把宿主全局Dirty逐字节独占归因给本任务。
3. **读回边界**：独立 `cache-size=0` 挂载只证明远端可读且无 EIO，不构成内容正确性验证。
4. **单盘边界**：单盘 P50/P95 util=100%只证明设备承受高写压，不能证明它是轮内衰减的唯一或主要
   原因；本任务没有第二块独立盘，也不回答多设备是否能消除衰减。
5. **状态不对称**：`ε=7.32%` 由 C1→C2 的方向性下降主导，而 T1↔T2 仅约4.79%；这更像携带/残留
   状态而非可由加样降低的对称随机噪声。任务书禁 `drop_caches` 与“页缓存已成为主导变量”之间存在
   方法张力，原 ABBA 未实现状态对称。
6. **GC混杂**：每格后 GC 实际 compact 约507,597 slices/128GiB并删除约1,537,725 pending slices，
   它有效维持了对象数稳定，但也是重型元数据与对象层改写，属于 C2 衰减的潜在混杂变量；现有数据
   不能证明它就是原因。

## 六、执行异常与分析器修复

首次 RUN `20260915-200000` 在 C1 完成、T1 正式负载前因 PID 门依赖被 Go 进程标题截断的尾部参数而停止。
现场先保留取证，随后只对精确私有挂载优雅卸载并清理仅含 `.lock` 的本 RUN 缓存目录；该 RUN 标为
`EVIDENCE_INVALID_PRELOAD`，包括 C1 在内全部未进入效应量。

修复只把 PID 身份改为“启动前 PID 差集 + exact exe + 每格唯一日志路径 + 唯一父子拓扑”，未改变负载、
挂载、采样或统计。replacement RUN 使用统一冻结脚本整套重跑。

初版离线分析器又把“每自然秒选中的首样本”用于最大间隔检查，约0.82秒的真实采样会人为形成约1.65秒
间隔。四格原始流最大间隔均不超过0.829秒且160个自然秒完整。修复后间隔门改看原始时间戳，仍保留
“每秒必须覆盖 + 原始最大间隔≤1.5秒”双门；self-test、历史回放与完整离线 Gate 均 PASS。Luna 独立
复核同意该修复及结果。
