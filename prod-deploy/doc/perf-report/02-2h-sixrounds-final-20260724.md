## 三、连续负载采集（A5/A6 load-monitor.csv）

### 3.1 采集方式

- 独立脚本 `/tmp/load-monitor.sh`，5s 间隔 CSV
- 字段：ts, load1/5/15, runnable/total, D 状态进程数, CPU us/sy/wa/id/st（差分）, 网卡 rx/tx/drop, 内存 free/dirty
- A5: kill bug 导致孤儿进程，CSV 行数过多（164行/项，含 fio 后数据）
- A6: kill bug 修复（if/then/fi），CSV 行数正确（36-38行/项 = fio 窗口）

### 3.2 randread 128 jobs 负载画像（关键发现）

| 指标 | A5 r1 | A5 r2 | A6 r1 | A6 r2 | 结论 |
|------|-------|-------|-------|-------|------|
| **wa (iowait)** | 0.0 | 0.0 | 0.0 | 0.0 | **CPU 从不等 I/O** |
| **D 状态进程** | 0 | 0 | 0 | 0 | **无进程被 IO 阻塞** |
| **CPU idle** | 82% | 82% | 82% | 82% | **157 大量空闲** |
| **CPU us** | 15% | 15% | 15% | 15% | 中等使用 |
| load1 | 21-24 | 23-24 | 25-26 | 24-25 | 中等（128 线程排队） |

### 3.3 结论：157 客户端不是瓶颈

- **82% CPU idle + wa=0 + D=0** = 157 在 128-job randread 时完全不饱和
- 负载（~23-26）来自 128 个 fio 线程排队，但 CPU 轻松处理
- **randread 的轮间波动（1153-1472, spread 22%）不是来自 157 的 CPU/IO**

### 3.4 波动根因推断

| 可能来源 | 证据 | 可能性 |
|----------|------|--------|
| 157 CPU 饱和 | ❌ idle=82% | 排除 |
| 157 IO 等待 | ❌ wa=0, D=0 | 排除 |
| 网络争抢（WekaIO） | 157 与 OSD 共享 NIC，WekaIO 流量可能影响网络栈处理 | 高 |
| OSD 侧波动 | 无法从 157 观测，需 OSD 节点 perf 采集 | 中 |
| JuiceFS 客户端内部 | go-ceph 连接管理/线程调度 | 低 |

## 六、结论

### 6.1 可复现性判定

- **判据①（变量守卫）**：✅ 六轮全通过
- **判据②（同组复现 <5%）**：
  - 起点 load <20 的轮次（A3/A5/A6）vs A：randread Δ <1.2% ✅，randrw Δ <1.0% ✅
  - 起点 load >20 的轮次（A2/A4）vs A：randread Δ 12-21.5% ❌
  - 读类项在低负载条件下可复现；高负载条件下不可复现

### 6.2 负载采集成果

- A5/A6 的 load-monitor.csv 证明：**randread 128 jobs 时 157 CPU 82% 空闲，wa=0，D=0**
- **157 客户端不是 randread 波动的瓶颈**
- 波动根因在**网络争抢（WekaIO）或 OSD 侧**，需进一步在 OSD 节点采集才能定位

### 6.3 建议下一步

1. **OSD 侧负载采集**：在 150-152 上采 `ceph tell osd.* perf dump`（rocksdb get_latency、bluestore buffer_hit/miss），看 randread 波动是否与 OSD 侧指标相关
2. **网络侧采集**：在 157 采集 NIC 的 per-second throughput + packet drop，与 fio bw_log 对齐
3. **低负载窗口重跑 A2/A4 对比**：等 load <20 时重跑，验证 randread 是否恢复
4. **或直接用 A3/A5/A6 作为基线**：三轮一致（randread 1452-1472），可在此基线上叠加调优
