### 2.3 分析（opencode 从 `run-*/fio-{P,Q}.txt` + `threads-series.tsv` 独立复算，2026-08-21）

复算口径：带宽取 fio `Run status group 0` 的 `READ: bw=` 原文；worker CPU 取 `threads-series.tsv` 中 `comm` 前缀为 `msgr-worker` 的行，按 tid 取窗口首末 `utime+stime` 差分（100 Hz，180 s 窗口 = 18000 ticks）。**12/12 cell 带宽与 §2.2 表逐值一致**。

#### 2.3.1 msgr=3 → msgr=8：+44.3%，且是 CPU 饱和墙而非抽签

| 臂 | r1 / r2 / r3 | 均值 | worker 数 | 最忙 worker 占单核 | 合计核数 | MiB/s per core |
|---|---|---|---|---|---|---|
| CAL3（msgr=3） | 3792 / 3853 / 4047 | **3897.3** | 3（全活跃） | **96.1% – 97.6%** | 2.704 | **1441.5** |
| S128（msgr=8） | 5612 / 5644 / 5613 | **5623.0** | 8（活跃 6） | 76.8% | 4.112 | 1367.6 |

- 增益 **+44.28%**，三轮各自独立挂载（每 cell 重挂），两臂区间零重叠（3792–4047 vs 5612–5644）。
- CAL3 的 3 个 msgr worker **全部打满单核**（17295/17492/17560 ticks ÷ 18000 = 96.1/97.2/97.6%）⇒ msgr=3 在 128 流 randread 下是**真 CPU 饱和上限**，不是坏档抽签。
- 效率复算 **1441.5 MiB/s/核**，与 **F56 的 1438** 只差 **+0.24%** ⇒ F56 在饱和区被独立复现（此前仅 msgr=3 单批标定）。
- ⚑ msgr=8 的单核效率反而低 5.1%（1367.6）——因为它已不在饱和区，多余 worker 只提供余量，不再是效率点。

#### 2.3.3 F51 定案：机器级墙，不是 per-mount

| 配置 | 每挂载 (P / Q) | 合计均值 | 相对 S128 | P/Q 不均衡 |
|---|---|---|---|---|
| S128（1 挂载 128 流） | 5612 / 5644 / 5613 | **5623.0** | — | — |
| D64（2 挂载 × 64 = 128 流） | 2659+3140 / 3299+2561 / 2578+3232 | **5823.0** | **+3.56%** | 1.18–1.29× |
| D128（2 挂载 × 128 = 256 流） | 3075+2823 / 3723+2570 / 2743+3443 | **6125.7**（max 6293） | **+8.94%** | 1.09–1.45× |

- **等流数**下加一个挂载只买到 **+3.56%** ⇒ per-mount 开销不是约束主项。
- 流数翻倍 + 挂载翻倍只买到 **+8.94%**，聚合停在 **6125.7**：
  - = F61 九点 OLS 上限 6265 的 **97.8%**
  - = F61 渐近上限 6280 的 **97.5%**
  - = F62 均衡后理论 6267 的 **97.7%**
  - = 验收目标 6250 的 **98.0%**（仅 D128-r2 单轮 6293 越线，3 轮中 1 轮，不可复现）
- 四个来自不同实验、不同推导路径的估计（F61 拟合 / F62 PG 倾斜反推 / D128 实测 / 目标值）**收敛在 6126–6280 的 2.5% 带内** ⇒ 结论：**约束在机器/集群级，不在挂载实例级**。
- ⚑ 因此 **03-16 的"读侧瓶颈 = per-mount"结论被本批否证**（至少在 ≥128 流区间）：单挂载 5623 与双挂载 5823 只差 3.6%，per-mount 最多解释 3.6 个百分点。
- P/Q 不均衡最高 1.45×（D128-r2 的 3723 vs 2570），与 F62 的主 PG 倾斜 / 连接抽签同源，属批内噪声，不改变合计判决。

### 3.5 Seg B 审计：四条硬伤（opencode，2026-08-21）

🔴 **裁定：Seg B 不可用于固化新基线，也不可用于给 `ms_async_op_threads` 归因。** 逐条证据：

**① 线程数根本没被验证生效（致命）**
`sentinel/threads-series.tsv` 全部 86 个采样 **`msgr_workers=0`**，`sentinel/stop.log` 86 条 `STOP 哨兵: msgr-worker=0 != 3` 被当噪声忽略。哨兵取的 pid 为 2319972 / 2496730，而 **NB3 实际挂载 pid = 2498793**（`nb3.log:36`）⇒ 哨兵 PID 解析错误，抓的是陈旧/无关进程。且该文件时间戳跨度只覆盖 NB3 阶段（首行 ts=1787301744 ≈ 15:42），**NB8 阶段的哨兵数据被同路径覆盖丢失**。结论：`NB8=8` 与 `NB3=3` 两者**都无任何生效证据**，wrapper 只证明了 PATH 注入与 `ceph.conf` 未被改动。

**② 每臂只有一次挂载抽签，3 轮是伪重复**
`nb8.log:920` 全程 `挂载实例=pid=2319972`（21 个 run 共用一个挂载实例），`nb3.log:36` 全程 pid=2498793。V4 自身横幅即写明"**跨实例极差 29.9%**"（`nb8.log:7`）。因此 NB8 与 NB3 各自**有效样本 n=1**，轮间 CV 0.2–0.4% 是同一实例的伪重复精度，不是配置的可复现性。

**③ 对照臂与历史锚点冲突，且两项内部自相矛盾**
NB3 randread median 1179 vs 03-10 同口径 3831 = **−69.2%**、vs E6 1880 = **−37.3%** ⇒ 对照臂本身失效。由 Seg B 反推的 msgr 增益在两项间还互相矛盾：randread **+119.8%**、randrw **+79.1%**，而 Seg A 同一对比（3 独立抽签/臂）只有 **+44.3%** ⇒ 差 1.8–2.7 倍。

**④ 口径设错：Seg B 测的不是交付配置，而是"128K FUSE 口径"（根因在任务书）**
V4 `item_randread`（`FULLBASELINE_V4.sh:897`）与 t50 的 P 侧命令**逐参数相同**（128 jobs / 1G / 256k / iodepth=128 / libaio / direct=1 / openfiles=128），差异仅在 ①Seg A 挂载带 `--max-fuse-io 256K` 而 Seg B 按任务书**明令不加**、②Seg A 加 `--readonly`、③挂载点与抽签。结果 **2591 vs 5623 = 46.1%**，差值 **+117.0%** —— 与 03-6 实测的 `--max-fuse-io 256K` 收益 **+115.6%** 只差 **1.4 pp** ⇒ 该 2.17× 不是未知噪声，而是**已立结论 F39/03-6 的又一次独立复现**，同时证明 **Seg B 实际测的是 128K FUSE 口径**。

🔴 **任务书错误（opencode 自查，非执行方责任）**：03-17e §五 原文写"⛔ 不要加 `--max-fuse-io 256K`，因为要与历史 E6/03-10 同口径"，该指令基于两个错误：
- **事实错误**：**03-10 本身是带 `--max-fuse-io 256K` 跑的**（`doc/perf-tasks/03-10-…md:42`，且要求验 `max_read=262144`；主计划 §2.4d 把"生产候选基座"定义为 `--max-fuse-io 256K --max-uploads 150 --cache-size 0`）。只有 E6 是 128K 出厂基座（卷 BlockSize 亦为 128K）。"E6/03-10 同口径"是把两个不同口径并成一个 ⇒ 去掉该参数后**既不等于 03-10、也不等于 E6**。
- **设计错误**：新基线要固化的是**交付配置**（补丁二进制 + msgr=8 + `--max-fuse-io 256K`），与历史的可比性应靠**加一个历史口径锚点臂**解决，⛔ 不应把主臂降级为历史口径。
- 因此执行方"确保差异只有二进制 + msgr=8 两项"的理解是照任务书执行的；但该表述也不成立 —— Seg B 相对 03-10 至少还差 4 项：**max-fuse-io（03-10 有、Seg B 无）**、挂载抽签数（2 vs 1）、相隔 7 天的集群状态、NB3/NB8 固定先后顺序。

### 7.2 `ms_async_op_threads=8` 是否固化

分成"配置项"与"基线数值"两问，答案不同：

| 问题 | 判决 | 依据 |
|---|---|---|
| 作为**客户端挂载默认配置项** | ✅ **方向成立，可先固化**（限定适用域） | Seg A：+44.3%，3v3 独立抽签零重叠；msgr=3 三 worker 96.1–97.6% 打满 = 真饱和墙；1441.5 MiB/s/核 复现 F56（+0.24%）。立为 **F65** |
| 作为**新的七项基线数值** | ❌ **不可，须重测**（03-17f） | §3.5 四条硬伤（首要 = 口径设错，缺 `--max-fuse-io 256K`）；§3.8 的 5 项劣化因两列口径不同而不可用于归因 |

**F65 适用边界（⛔ 不可外推）**：
1. 只在 **128 流 randread + `--max-fuse-io 256K` + msgr=3 三 worker 全饱和** 区间证实。
2. 低并发项（seqread 1 流、mseqread 16 流）msgr=3 是否饱和**无数据** ⇒ 无收益证据。
3. 写侧七项**完全无有效证据**（Seg B 已否决）。
4. 成本侧：msgr=8 合计占 4.112 核 vs msgr=3 的 2.704 核，**多耗 1.41 个核**；157 为共享机，需计入预算。
5. 落地方式必须是**私有 conf + `CEPH_CONF` 注入挂载封装**，⛔ 不得改全机 `/etc/ceph/ceph.conf`、⛔ 不得 `ceph config set`（B6 未授权）。
