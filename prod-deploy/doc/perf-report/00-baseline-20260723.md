### 1.4 测试流程

```
R1: 重建 → A1 → 全量清理 → A2
R2: 重建 → B1 → 全量清理 → B2
R3: 重建 → A（不跑 B）
R4: 重建 → B
```

- **全量清理**：pool delete+recreate + OSD restart + drop_caches 全节点 + compact_cooldown
- **组内清卷**：juicefs destroy + compact_cooldown
- **REPEAT=3**：所有随机项 3 轮，顺序项 1 轮
- **randrw 变体 Y**：每轮重建 layout + drop_caches（T1 实验验证 CV=2.1% 消除 r3 骤降）
- **randwrite-ow**：不重建 layout（非目标项），用 bw_log 稳态中位

### 1.5 判定标准

- 轮内 CV<5%（3 轮随机项）
- 组间 Δ<5%（同组跨轮次，rebuild-first 值对比）
- 不收敛项用区间基线接受，不追跨重建 <5%

### 9.4 OSD 物理落点变化

R4-B 的 OSD IDs 为 {0,1,2,3,6,7}（OSD 4/5 在 R4 重建时被 purge，新建了 6/7）。
R5-A 的 OSD IDs 为 {0,1,2,3,4,5}（OSD 6/7 在 R5 重建时被 purge，新建了 4/5）。

即使 OSD ID 相同（如 0-3），其底层 LVM/tmpfs 分配在每次重建时也是全新的——`cleanup-node.sh` 清空了所有 LVM/VG/PV/loop/tmpfs 后重建。

### 9.5 因果结论

**因果闭环成立。**

1. CRUSH 规则不变（`ec-prod` profile, k=4 m=2, failure-domain=osd）
2. 唯一变化：重建 purge 了旧 OSD + 创建新 OSD → OSD IDs/weights/positions 改变
3. CRUSH 基于新的 OSD 集合重新计算 PG→OSD 映射 → **32/32 PG 的 acting set 100% 变化**
4. 不同的 acting set = 不同的 primary OSD = 不同的 tmpfs DB/WAL 物理落点 = 不同的 BlueStore 缓存分配
5. 这些物理差异直接影响 RADOS 读写延迟 → JuiceFS 端表现为 randread/randrw/randwrite-true 跨重建漂移 16-37%

**跨重建波动物理上不可通过重测消除，基线只能用区间表达。** 调优测试（P2-P4）须用同周期背靠背对比，不跨重建比绝对值。

### 9.6 第二随机源：pool delete+recreate（同一次重建内也漂移的根因）

> **⚑ 2026-07-23 补充。此前把 R1-A1→R1-A2 偏差归因为"清理达不到重建冷态"是错误归因，此处纠正。**

#### 现象：同一次重建内、OSD 未变，R1-A1→R1-A2 仍漂移 -22~-26%

| 测试项 | R1-A1（重建后首测） | R1-A2（全量清理后） | Δ% |
|--------|-------------------|-------------------|-----|
| randread | 1309.0 | 993.7 | **-24.1%** |
| randrw-R | 922.9 | 686.4 | **-25.6%** |
| mseqwrite | 3792.0 | 2956.0 | **-22.0%** |
| layout | 3699.6 | 2879.5 | **-22.2%** |
| seqwrite | 1460.0 | 1360.0 | -6.8% |
| randwrite-true | 3625.6 | 3580.3 | -1.2% |

A1 与 A2 之间**没有重建 OSD**（OSD 集合不变），中间**唯一操作 = full_cleanup**。

#### 机制：full_cleanup 里的 `pool delete + recreate` = 迷你重建

`full_cleanup`（源自旧 skill §2.5 "轮间清理"）执行：
```
ceph osd pool delete juicefs-data ...     # 删 pool
ceph osd pool create juicefs-data 32 32 ... # 重建 pool → pool_id 变 (90→92)
+ OSD restart
```

**pool_id 是 CRUSH 计算 PG→OSD 映射的 hash 输入之一。** 删掉再建 → pool_id 变 → **即使 OSD 集合完全不变，PG→OSD 映射也全部重算**，等价于一次"迷你重建"，引入与跨重建同量级的随机漂移。OSD restart 另叠加 tmpfs DB/WAL 物理落点 + BlueStore 内存态重置。

#### 结论：波动机制精确化

**波动的真正机制 = CRUSH 重映射**，由两个操作触发：
1. **重建 OSD**（OSD 集合变）——§九已证
2. **pool delete + recreate**（pool_id 变）——本节证实

两者都会重洗 PG→OSD 映射。**方向随机**（0722 cleanup 偏高 +17~31%，0723 偏低 -4~26%）正是"随机重映射"的标志，非任何确定性机制。

#### 对策：soft-clean（保留 pool、不重启 OSD）

轮间清理改用 **soft-clean**：`juicefs destroy`（清对象，保留 pool → pool_id 不变）+ compact cooldown + drop_caches，**不删 pool、不重启 OSD、不动 CRUSH**。映射保持不变 → 同一部署内跨轮次可复现。已固化进 skill §2.5，并由 02-2-G（§十）验证。

#### 可复现的 CRUSH 映射不变量清单（skill 已固化为红线）

| 操作 | 是否重洗映射 | 轮间清理是否可做 |
|------|:-:|:-:|
| `juicefs destroy`（保留 pool） | 否 | ✅ 用它 |
| `pool set fast_read/allow_ec_overwrites/size` | 否 | ✅ 可 |
| 改 `pg_num`/`pgp_num` | 是 | ❌ 禁 |
| `pool delete + recreate` | 是（pool_id 变） | ❌ 禁 |
| 改 CRUSH rule / EC profile | 是 | ❌ 禁 |
| 重建 OSD / OSD restart | 是（最狠） | ❌ 禁（restart 亦禁） |
