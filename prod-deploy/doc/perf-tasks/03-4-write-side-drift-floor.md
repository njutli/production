## 〇、背景（为什么现在必须做，以及为什么难）

**为什么必须做。** 03-2 只测了读侧三项。写侧四项现在用的判定门槛（`randrw` 3%、`randwrite` 4%、`seqwrite` 5%、`mseqwrite` 7%）是从"跨测试 L3 ≤3.7%"那套口径推出来的 —— **那是"3 次独立测试之间"的离散度，不是"同一实例内连续多次"的离散度，两者口径不同、不可互换**。拿它去判交错对照，就是重犯 03-1 的错误：门槛比效应量还大，而自己不知道。

**为什么难（这是本任务的核心矛盾）。** 底噪的定义是"什么都不改、反复测"，但**写测试每轮都在改池内对象数**，而对象数已知会压性能（F6：`r(randrw, objects) = −0.807`，安全上界 3.11M，拐点落在 (3.78M, 4.40M]）。如果放开跑，测出来的离散度是"漂移 + 对象数效应"的混合物，不是纯底噪。

**破法（依据 F14）。** 03-1 之后的四个池快照证明：池被推到 17.03M / 4.1 TiB 后，在 **66 分钟空闲期内自行排空、逐字节回到 2.36M / 576 GiB**，次日两次复查仍保持。机制是 JuiceFS 挂载进程的**小时级后台待删切片回收**（`TrashDays=0`），**既不是 `gc --compact`、也不需要 `gc --delete`**。⇒ 所以可以**在每一轮之后插一个排空等待窗，把每轮的起点对象数都对齐到 ~2.36M**，从而把 F6 的对象数效应从底噪里剥出去。

这也是为什么 `gc --compact` 不解决问题：V4 每轮已经在跑 `gc --compact`（`aggressive_cleanup`，行 163/577），但对象数照样堆到 17M —— **`gc --compact` 合并碎片，不回收待删切片**。别指望它。

**两个已知未知**（本任务顺带测掉）：① 负载下的实际回收速率（F14 的 ≥3700 对象/秒是**空闲期**的下界）；② `seqwrite` / `mseqwrite` 的每轮实测耗时（目前只有 `randrw` 8min、`randwrite` 11.3min 是实测，另两项是拍的）。

## 一之二、`randread` 是协变量，不是看门狗（⚑ 2026-08-07 依 03-3 实测订正）

**原设计**：`randread` median 越出 `[1830,1930]` 或偏离 `WD1` ±2% → 中止全任务。
**订正为**：`randread` 是**协变量记录项**，中止线放宽到**单 run median < 1700**。

**为什么改。** 03-3 实测：日间 4.5h 内 `randread` 从 **1862.8 跌到 1830.7（−1.72%）**，Spearman(run 序, 值) = **−0.771**，最低点正落在午后 14:07-14:52 的外部租户负载峰；而 1830.7 距高档带下界 1830 **只剩 0.04%**。⇒ 原来那个 ±2% 的门槛，在 **60h** 尺度上几乎必然误触发，**周末长跑会被无故砍断,而且是砍在一个根本不存在的故障上**。

**根因是判据混淆了两件事。** F1 已证**档位在挂载时抽签、同实例内 ≤1.1% 不变** ⇒ "实例是否还是同一个"的硬判据是 **pid + `starttime_ticks`**（红线 11 已覆盖），`randread` 不该承担这个职责。它实际在测的是**外部租户负载**，那是环境噪声，不是故障。

**改完之后它更有用。** `randread` 与外部负载同步、且**不产生任何对象**，因此是一个干净的负载代理变量。有了它就能：

- 事后把外部负载从写侧离散度里**回归掉**，得到比"原始极差"更干净的底噪估计
- 定量回答"周末口径到底偏乐观多少"——这是本任务最大的已知弱点（见 §四.3）
- 顺带把 03-2 的读侧底噪时间覆盖从 11h46m 延到 ~60h、且首次覆盖日间

**⚑ 因此报告必须给两个版本的底噪**：① 原始极差（保守，直接可用）② 回归掉 `randread` 之后的残差极差（更接近真实底噪）。**判据门槛取 ① 的那一版**，② 只作参考 —— 宁可门槛偏严。

**中止线为什么定 1700**：F3 已知多档为 `1870 / 1790 / 1750 / 1714 / 1334`。1700 落在 1714 与 1334 之间的空隙，即"掉出全部高档、朝最低档去了"。只有这种量级才可能是真的换了实例或环境剧变。**日间负载波动（本次实测 1.72%）离它还有十倍余量。**

**为什么顺序不许改**：`randread → randrw → seqwrite → mseqwrite → randwrite` 恰好保持 V4 默认 `ITEMS` 的相对先后（默认序 `seqread mseqread randread randrw seqwrite mseqwrite randwrite`），这样任何顺序效应与签收基线一致。

#### 🔴 ⚑ 为什么放弃"把对象数压在安全线以下"（2026-08-07，实测推翻原设计）

**实测依据**（03-1 的 fio 原文 + `ceph df` 反推，非估算）：

```
WRITE: bw=4714MiB/s, io=829GiB, run=180067msec     ← 单个 mseqwrite 轮
WRITE: bw=4835MiB/s, io=850GiB, run=180069msec
每对象大小：576 GiB / 2.36M = 256 KiB（post 快照 4.1 TiB / 17.03M = 258 KiB，一致）
```

> ## 🔴 ⚑ 换算常数订正（2026-08-07，opencode 自查发现用错了量）
>
> 上面用的 **256 KiB** 是「**池内平均对象大小**」= `STORED ÷ objects`。但要回答"写入 N 字节会**新增**多少对象"，该用的是 R5 的**直接实测**：
>
> ```
> 每轮写 211 GiB ⇒ objects +757k   ⇒ 292 KiB / 新增对象
> 出处：doc/perf-report/02-2h-e6-v4-fullbaseline-20260803.md §18.6.1/§18.6.6
> ```
>
> **两个常数都对，但量不同**：292 > 256 说明约 **12% 的写落在已有对象上（覆写）**、不产生新对象。用 256 KiB 换算会把新增对象数**高估 ≈14%**。
>
> ⇒ 下表"单轮生成对象"列**全部高估约 14%**，订正值见括号。**好在方向是偏保守**（高估生成量 ⇒ 门限留得更宽），故 `OBJ_START_MAX` / `OBJ_MAX` 设计**无需改动**。

| 项 | 单轮写入 | ~~单轮生成对象（256 KiB 口径，高估 ≈14%）~~ | ⚑ **订正值（写入量 ÷ 292 KiB）** | 从 2.36M 起 → |
|---|---|---|---|---|
| `randrw` | ~212 GiB | ~~+0.86M~~ | **+0.76M**（R5 直接实测 211 GiB→+757k，吻合） | 3.12M |
| `seqwrite` | ~246 GiB | ~~+0.98M~~ | **+0.88M** | 3.24M |
| `randwrite` | ~503 GiB | ~~+2.01M~~ | **+1.81M** 🔴 | **4.17M** 🔴 |
| `mseqwrite` | **829-850 GiB**（取 840） | ~~+3.32M~~ | **+3.02M** 🔴 | **5.38M** 🔴 |
| **单轮周期合计** | **~1801 GiB** | ~~7.17M~~ | **6.47M** | — |
| **单 run（×5 轮）** | **9005 GiB = 8.79 TiB** | ~~35.85M~~ | **32.3M** | — |

而从 2.36M 到拐点下界 3.78M 的**全部余量只有 1.42M**。⇒ **`randwrite` / `mseqwrite` 的单轮生成量仍是余量的 1.2 倍和 2.0 倍**（按订正值；原按 256 KiB 口径算是 1.4 倍和 2.3 倍）。**结论不变。**

**⇒ "压在安全线以下"物理上不可能**，不是门控实现问题。原 `OBJ_MAX=3.60M` 会在**第一个 `mseqwrite` 轮结束时**触发硬停，起跑约 1.7h 后整个 run 死掉。

**⇒ 退一步，保住更重要的那个条件：每轮起点对齐。**

- 每轮都从 ≤2.50M 出发、走**同一条对象数轨迹** ⇒ 对象数效应成为所有轮、所有 run 的**共同系统项，不构成跨 run 方差**
- 而本任务要测的**正是跨 run 方差** ⇒ 结论仍然成立
- **代价（必须写进报告）**：`mseqwrite` / `randwrite` 的**绝对值不可用**（每轮后半段在拐点之上，与 03-1 同样的局限），**只有相对变异性可用**。本任务只要底噪与门槛、本就不要绝对值，故可接受
- **附带的正当性**：拐点之上恰是**未来写侧调优的真实环境**（T1.4-T1.6 也会这样累积）。在同样环境下测底噪，口径反而一致；硬在"安全线以下"测出来的底噪，反倒不能用于那个环境

**⇒ 因此两个上限各司其职，不要混用：**

| 守什么 | 参数 | 越界后果 |
|---|---|---|
| **每轮起点对齐**（核心前提） | `OBJ_START_MAX = 3.00M`，只在 PLATEAU 退出时检查 | 前提破坏 ⇒ **停止上报**。这是真正要守的东西 |
| **回收是否还活着**（失控保护） | `OBJ_MAX = 8.00M`，每次采样都查 | 回收死了 ⇒ **停止上报** |

**`OBJ_MAX=8.00M` 的安全论证**：8M 对象 ≈ **2.0 TiB STORED / ~3.0 TiB USED**（EC 4+2 约 1.5×），而池 `MAX AVAIL` 有 **22-26 TiB**。更强的证据是 **03-1 已实测到过 17.03M / 4.1 TiB STORED / 6.1 TiB USED / %USED 15.30%，全程 `HEALTH_OK`** ⇒ 8M 只有那次的 **47%**，是已验证安全区内的一半。选 8M 而不是 6M，是因为最坏情形（起点 `OBJ_START_MAX` 3.00M + `mseqwrite` 单轮 **3.02M** = **6.02M**）**已经超过 6M**，会误触发硬停。⚑ 换算常数订正后这个判断**更成立了**（原按 256 KiB 口径算得 6.32M，订正后 6.02M，两种口径都 >6M）⇒ **8M 是正确选择**（余量 33%，且仍只有已验证安全点 17.03M 的 47%）—— 不改。

> 🔴 **⚑ PLATEAU 的两个前置条件为什么必须有**（2026-08-07 补，此前是任务书的规格疏漏）：
> **JuiceFS 的待删切片回收是小时级后台任务，不是连续均匀的** —— F14 的原始曲线就是"先平后陡"：
> `20:10 → 17.03M`、`21:02 → 12.44M`（52min 只降 4.6M）、`21:16 → 2.36M`（14min 暴降 10.1M）。
> 若只看"连续 3 次 Δ<0.03M"，**在回收尚未启动的那段平台上 6 分钟就会误判 PLATEAU**，带着满池进下一轮 ⇒ 起点对象数逐轮抬高 ⇒ 两三轮内撞 `OBJ_MAX` ⇒ **整个 run 报废，且报废前采的数据全部无效**。
> ⇒ 必须同时要求"至少等了 40 分钟"和"确实观察到过在降"。
> ⚑ 另：`Δ` 为负（对象数回升）时**不得**计入 plateau，只在 `0 ≤ Δ < 0.03M` 时累加。

> 🔴 **⚑ 取数失败必须响亮失败，不许当 0 处理**：`ceph df` 或 python 任一失败时**不得**回落成 `objects=0` —— 那会让 `0 > OBJ_TARGET` 判否、**静默跳过整次排空**。真实对象数不可能为 0（池内常驻 577 GiB layout 数据），故 0 可作哨兵值：**取到 0 或空 ⇒ 记日志并返回非 0 停下**。8 run × 20 轮 = 160 次门控调用，瞬时失败概率不可忽略。

> ⚑ **门控在每轮结束后检查，因此无法阻止单轮内越界 —— 这在新设计下是"预期行为"，不是缺陷。** 单轮冲到 5.7M 是设计允许的（见上方"为什么放弃安全线"）。要守的是 `OBJ_START_MAX`（每轮起点）与 `OBJ_MAX`（回收是否还活着）这两条，**不要**因为看到中途出现 4M/5M 就停下来，也**不要**自行调小 `RUNTIME` 或 `REPEAT`。
