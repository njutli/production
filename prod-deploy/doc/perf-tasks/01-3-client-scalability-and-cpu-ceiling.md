### 🔑 前置闸门：后端裸能力必须先达标（逻辑上游，优先级最高）

**后端裸能力（rados bench，不经 FUSE）是 JuiceFS 性能的物理天花板。** JuiceFS 客户端读写最终都要落到后端，
**后端读不上去，客户端侧无论怎么调（并发、buffer、readahead、多实例）都不可能达标**。因此在做本任务（客户端可扩展性）之前，必须先确认后端裸能力这一关：

- **判据**：01-2d §3.3 的 rados bench 后端随机读，在**低方差稳态**下（不是挑波动大的高点，见 01-2d-1）能否达到验收线所需量级
  （不限速目标 6250 MiB/s；且需对照 BeeGFS randread 9045~10752 —— 当前后端 4000+ 量级明显偏低）。
- **若后端裸能力达标** → 继续本任务，验证客户端侧是否是瓶颈。
- **若后端裸能力不达标（大概率）** → **停止本任务，转入后端诊断**，先回答一个二选一：
  1. **可提高**：后端 EC4+2 随机读还有优化空间（如 EC→副本、OSD 扩容、bluestore/rocksdb 调参、fan-in 尾延迟治理）→ 先立后端调优任务，提上去后再回本任务；
  2. **架构受限、无法提高**：EC4+2 fan-in 是架构固有上限 → 那么 JuiceFS 冷态测试再怎么调也不会达标，
     此时问题定性为**后端架构限制**（非 FUSE 客户端问题），本任务的"FUSE 封顶"命题已无意义，直接进决策链（换后端池型 / 换栈评估）。

> **✅ 闸门判定（2026-07-17，01-2d 真值就位后）**：后端随机读裸能力实测 **~4300–4400 MB/s（低方差稳态）**，
> **明显不达标**（验收线 6250 的 ~69%，仅 BeeGFS 9045 的 ~48%）→ 落"不达标"分支。
> 但**同时** JuiceFS randread ra0=2404 仅为后端 4300 的 ~56% → **客户端侧也有明显差距**。
> 即：**后端与客户端是两层叠加的瓶颈**，后端（EC4+2 随机读 4300 < 6250）是**首要**、更根本的一层。
> 波动主因已定性为脏 pool RocksDB bloat（**可消除**，非架构固有）——即后端还未坐实为"架构受限无法提高"，
> 需 01-2d-1 之后进一步判 EC4+2 是否有优化空间（EC→副本对照 / OSD 扩容）。
> **本任务（客户端可扩展性）仍有意义**：即便后端是首瓶颈，也需查清客户端只发挥后端 56% 的原因（FUSE 封顶 or 参数），
> 二者是并行的两条优化线。**故本任务从"条件触发"转为"可激活"**，与后端诊断并行推进。

> 一句话：**先证明后端裸能力达标或可达标，本任务才有意义。** 否则 01-3 测出来的任何"客户端封顶"都是被后端拖累的假象。
> 这个闸门优先于上面三条数据回填项——若后端诊断结论是"架构受限无法提高"，本任务可直接跳过。

> 说明：**本任务的核心判据（单挂载 CPU 饱和曲线趋势、多实例 N=1/2/4 是否倍增）是相对/趋势判据，不依赖上述绝对值**，方法论完全有效。作废的只是当作"背景/已有数据"引用的具体数字。故本任务**不废弃，条件触发**：待 01-2d 真值就位后激活。

## 〇、先读：为什么要做这个测试（背景与当前证据）

01-2 曾报：JuiceFS randread（ra0）单客户端 = **2404**（01-2d A/B 组 §8.3 真值；default=1480），rados 后端裸测随机读 = **~4300–4400 MB/s**（01-2d §3.3 低方差稳态，旧值 3198 作废），
~~客户端开销仅 11%，已贴后端 90%~~（**此结论作废**——真值下 JuiceFS 2404 仅为后端 4300 的 ~56%，客户端离后端有明显差距）。据此调优报告 §93-97 下了三个结论：

1. 瓶颈是"单客户端 FUSE 用户态处理"，CPU 580% 满载；
2. **"CPU 瓶颈是 FUSE 架构固有限制，单进程只能有效利用 ~6 核，无法扩展到更多核"**；
3. "如能线性扩展到 64 核理论上可达 ~60 GiB/s"。

**但这三条目前证据不足**（perf-analysis/01 §7.1 已审）：

- 已有 stats 只有两个负载点：randread **D0（16384 并发）CPU 580%、D2（128 并发）CPU 370%**
  （CPU% 待本任务复核；配套 bw 真值 = 01-2d ra0 randread §8.3 = 2404，default=1480）。
  两点 CPU 都**仍随负载线性上升、没有出现"CPU 卡住不动、吞吐也不再涨"的饱和平台**。
- "6 核封顶 / 60 GiB/s"是**看到 580% 反推的假设**，不是实测到的上限。
- 而且当前 randread 与后端裸上限的真实关系**已由 01-2d 定**：JuiceFS ra0=2404 vs 后端裸 ~4300 → 客户端只发挥 ~56%，
  **且后端 4300 本身 < 6250 验收线** —— **当前限制是"后端 EC4+2 到顶（首要）"+"客户端未榨满后端（次级）"两层叠加**，本任务负责查清第二层。

> 一句话：报告把"贴后端天花板"和"FUSE CPU 封顶"混在一起讲了。本任务要用实验把它们分开。

**这个结论为什么关键**（用户原话意译）：如果网卡（100GbE，当前只用 ~20%）足够强、CPU（64 核只用 9.1%）也不弱，
而有效带宽因**方案本身（FUSE 单进程）**上不去，那就要认真考虑换方案（多客户端 / CephFS 内核态）。
所以必须先拿到硬证据，再决定 JuiceFS 留不留。

## 一、目标（三件事，按序，缺一不可）

1. **画出单挂载 CPU 饱和曲线**：找到"再加并发 → 客户端进程 CPU 不再上升、吞吐也不再上升"的拐点（或证明没有拐点）。
2. **线程级归因**：`pidstat -t` 看 CPU 是否卡在少数几个线程 / go pprof 看是否卡在少数 goroutine / 锁竞争。
3. **多实例倍增测试**：1 vs 2 vs 4 个挂载实例并行跑，看 157 单机总吞吐是否近似倍增。

**这三件事联合判定**（写进 summary 的核心结论）：

| 现象组合 | 判定 | 后续动作 |
|----|----|----|
| 单挂载 CPU 到某值后卡住不涨、吞吐也卡住；**多实例吞吐近倍增** | ✅ **单进程封顶属实**，workaround = 多挂载 | JuiceFS 可留（多挂载架构）；如运维不接受多挂载 → 触发 CephFS 换栈评估（01-4） |
| 多实例吞吐**不倍增**、且单机总 CPU / NIC 仍不饱和 | ❌ 瓶颈在**后端/网络**，非 FUSE | 换栈无益；优化后端（EC→副本诊断、扩 OSD）或接受架构上限 |
| 单挂载 CPU **仍能随并发继续涨**、吞吐也涨 | ⚠️ 当前只是**参数没调对** | 回到 §四客户端参数扫描继续调，暂不换栈 |

## 四、步骤 2：线程级归因 + 客户端参数扫描

### 4.1 线程级 CPU（证实/证伪"~6 核有效"）

在 S0（16384 并发）稳态期间：
```
pidstat -t -p <juicefs_pid> 1 30       # 线程级 CPU，看是否少数线程吃满
```
- 若少数几个线程各 ~100%、其余空闲 → 支持"少数核封顶"（FUSE /dev/fuse 分发 / Go 调度 / 锁竞争）。
- 若 CPU 均匀分布在很多线程 → "6 核封顶"不成立。
- **可选**：JuiceFS 若开了 pprof 端口，抓 `go tool pprof` CPU profile 30s，看热点是否集中在 FUSE 读路径 / 锁。

### 4.2 客户端参数扫描（perf-analysis/01 §5.3.4）

固定 S0 档，单独扫以下参数，各跑 REPEAT=3 看 randread bw + CPU 是否变：
- `--max-uploads`（当前 150）
- `--buffer-size`（默认 300M，试 1G/2G）
- `--max-readahead`（当前 0，本任务保持 ra0；仅记录，不作为随机读调项）
- 挂载 `-o max_background=` / `-o congestion_threshold=`（FUSE 队列深度）

> 目的：确认 randread 是否还有客户端参数红利。若都无效 → 支持"已到客户端上限"。

## 五、步骤 3：多实例倍增测试（定生死）

**这是最直接的判据**：单进程封顶，多进程就该近似倍增；若不倍增说明瓶颈在共享资源（后端/网络）。

### 5.1 方法

在 157 上挂 N 个独立 JuiceFS 实例（同一卷、不同挂载点即可；如担心互相干扰可建独立子目录数据集）：
```
juicefs mount -d ... /mnt/juicefs-1
juicefs mount -d ... /mnt/juicefs-2      # N=2
juicefs mount -d ... /mnt/juicefs-3
juicefs mount -d ... /mnt/juicefs-4      # N=4
```
每个实例上**同时**起一份 randread fio（各自中等并发，如 32×32，避免单实例已把后端压满导致看不出倍增），同步开始、同步结束。

> **贴业务变体（必做）**：让 N 个实例**读同一批基础文件**（复用同一 layout 卷/同一组文件），
> 模拟"多客户端共享读一堆基础文件"的 AI 训练画像——这既测可扩展性，又暴露共享读时后端/缓存行为。
> **default 与 ra0 各跑一轮**（default 是调优主线基线口径，ra0 作对照），结果并列入报告。

### 5.2 采集与判读

- 采：每个 juicefs 进程的 CPU（pidstat）、每份 fio 的 bw、**157 总 NIC RX**、slave 端 NIC/OSD。
- 算 **单机总吞吐 = Σ 各实例 bw**，对比 N=1/2/4：

| N | 单机总 bw | 相对 N=1 | 总 juicefs CPU | 157 NIC RX | 判定 |
|----|----|----|----|----|----|
| 1 | | 1.0× | | | 基准 |
| 2 | | ? | | | 近 2× = 单进程曾封顶 |
| 4 | | ? | | | 近 4× = 单进程封顶且后端仍有余量 |

- **近倍增** → 单进程 FUSE 确实封顶，且后端/网络仍有余量 → **报告 §94-97 方向证实**，workaround = 多挂载。
- **不倍增**（总 bw 撞某个墙、总 NIC RX 或后端 OSD 饱和）→ 瓶颈在**共享后端/网络**，非 FUSE 单进程 → 换栈（CephFS）也无益，报告结论需大改。

> 停机点：N=4 时若 157 内存吃紧或 WekaIO 受影响，立即降到 N=2 并记录，**红线优先**。
