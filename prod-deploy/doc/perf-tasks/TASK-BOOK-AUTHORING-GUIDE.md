## 一、任务书结构（固定骨架）

每份任务书按此顺序：

1. **抬头**：面向对象（GLM）、是否重跑、承接的结果目录、方法论 skill 引用。
2. ⚑ **计划线（必带，紧跟抬头，放在"背景"之前）**：用一个 ~15 行的 ASCII 流程图交代**本任务在整个阶段里的位置**——前面哪些任务已结及其一句话结论、本任务是哪一步（标"你在这里"）、通过/不通过各走向哪里、后面还排着什么。末尾用**一句话**概括本任务要干什么。
   - 目的：任务书正文越来越长，执行方需要先有全局图才能理解意图，而不是从第一行开始盲读。
   - 要求：**只放骨架，不放数据**；已结任务每个只给一行结论；不超过 20 行。
3. **〇、背景**：为什么做这个任务 / 上一轮遗留什么问题（让执行者理解意图，不是盲跑）。
4. **一、目标**：一句话说清要判定/回答什么。**多问题任务须标出哪一问是唯一的通过/不通过项**，其余只报数据。
5. **二、口径与矩阵**：测试参数、并发档、REPEAT、验收线。必须按 §二.20 标明当前是
   `L0_OFFLINE`、`L1_SCREEN`、`L2_FORMAL` 还是 `L3_PRODUCTION`，并写明升级/停止规则；
   禁止把所有候选参数一开始就写成最高成本正式矩阵。
6. **三、执行步骤**：可逐条勾选。**第一条（步骤 0）必须是"测试前通读 skill 并确认关键点"，最后一条必须是"测试后按 skill 复核执行合规"**（见 §二.8，必带）。
   - ⚑ **若本任务涉及新写的驱动/采集/分析脚本，执行步骤的第一阶段必须是"阶段 0：离线 Gate 0"**（见 §二.17）：Gate 0 未过 ⛔ 禁止连接环境。
   - ⚑ **必须写明分阶段回传的检查点**（见 §二.18）：阶段内部自主跑完不停，阶段边界停下等第二方审核。粒度取"有决策价值的停点"，⛔ 不要逐小步停（协调成本高、边际信息低）。普通 L0/L1 默认最多设置“开跑前安全门”和“结果裁决”两个停点；只有下一批操作会扩大状态变更或使已采证据一起失效时，才增加中间停点。
7. **四、交付物**：结果目录结构 + 报告落点 + results-table 更新；同时按 §二.21 声明
   证据生命周期字段、唯一持久化根、远端临时根、保留等级和阶段收口动作。
8. **五、通用注意事项**（见本文件 §二，**必带**）。
9. **红线汇总**：本任务特有红线 + 复述关键通用红线。

## 二、通用注意事项（每份任务书必带，逐条固化）

> 以下各条是历史反复踩坑固化下来的红线。新任务书须整段包含（可精简措辞，但每条都要在）。

### 1. 数据统计口径（本次新增固化）

> ⚑ **2026-08-28：本节的"截前 1/4 取中位数"已被 §二.13 取代，仅在没有 per-job log 时作为退化口径使用。**
> 有 per-job log 时一律走 §二.13（实际 I/O 起点 + 重叠加权重采样 + 正式窗 + W1--W4）。

- **稳态中位数优先**：fio 平均 BW 受测试前期写缓冲/冷启动暂态污染（写类偏高约 7-8%，曾超网卡线速属假象）。正确值 = fio 逐秒瞬时带宽序列**截掉开头 1/4 爬升段后取中位数**（skill §8）。
- **所有 fio 命令必须加** `--write_bw_log=<prefix> --log_avg_msec=1000`。fio 默认 `per_job_logs=1`，多 job 会自动落 `<prefix>_bw.<job_id>.log` 共 numjobs 份——**务必确认这些 per-job 文件全部保留**（不要 `--per_job_logs=0`、不要只留一份合并 log）。
- **多 job 统计**：
  - 有 per-job log → **§8.3：按时间戳对齐【求和】所有 job 的逐秒带宽 → 截前 1/4 → 稳态中位数**（最优）。
  - 只有一份合并 log 或无 log → **退取 fio 全文 `Run status group (all jobs)` 聚合行**（次优，含爬升段略偏高但物理正确）。
  - **绝对禁止**：一份合并 bw_log 稳态中位数 **× numjobs** 外推（历史 65× 失真的错误来源）。
- **多实例（多个独立 fio 进程）**：各实例取自己的聚合值后**求和**，不是乘。
- REPEAT=3 **取中位数（第 2 大值）**，不取平均、不挑轮次。
- **randrw 的 R/W 分开报，不合计**（读=入向、写=出向，全双工独立，各自对验收线）。
- **超网卡线速的平均值一律不认**（100GbE≈12500 MiB/s、千兆≈124 MB/s 为物理上限），汇报前必换稳态真实值。

### 2. 冷态净化（drop_caches）

- 冷态口径下，原则上每档每轮跑前按任务书冻结范围执行 drop_caches；但它是**全机状态变更**，
  不能机械套用。若客户端157存在WekaIO、K8s或其他共置业务，禁止为了模板完整清理157全局页缓存。
  对`direct=1 + JuiceFS cache=0`且被测路径不依赖客户端页缓存的任务，可预注册跳过157本机
  drop_caches；所有对照臂必须对称，并记录该口径。存储节点是否执行仍按隔离性和业务影响单独判断。
- 暖态或缓存专项必须跳过与目标状态冲突的drop_caches，并通过固定预热定义起点。
- direct=1 只绕内核页缓存，**绕不开 JuiceFS 客户端缓冲**——冷态还需 cache=0 挂载。

### 3. fresh-volume / 冷启动失真（randwrite/randrw 重点）

- randrw/randwrite 若用 `--create_on_open=1` 在**新建卷**上跑，第 1 轮会"读命中刚建的稀疏/空洞区 → R 虚低、W 独占带宽虚高"，是纯冷启动失真、非真实能力。
- **须用方案 A**：复用已 layout 铺好数据的卷（skill §6.4 analysis 版），**不 create_on_open、不 fresh volume**，消除该失真。
- 若确需 fresh volume，须按标准清卷流程（见本文件 §7）执行，并在报告里显式声明该档为冷启动失真档。

### 4. 后端干净态（OSD compaction cooldown）

- 高强度写测试后，**restart OSD 不能清除 compaction 积压**——必须用 `compact` 命令 + cooldown 轮询至 `compact_running=0`（skill §3.2）后再进行下一项，否则残余积压污染下一档。
- `compact_running=0` + `compact_queue_len=0` 只表示"没有正在 compact"，**不保证 LSM tree 最优**。膨胀的 LSM tree 会在三指标全绿时仍导致高并发读性能骤降。关键测试项前须强制 compact + 轮询确认。数据异常必须排查并重测，不得跳过。
- 写项之间必须 compact cooldown（randwrite-true → layout → randrw → randwrite-ow 之间均需）。
- 切换 OSD config 模式后，须等集群**完全恢复**（经验 10+ min）再开测；对比测试两组须在**同等干净态**下测，否则对比无效。

### 5. 环境前置检查

- 开测前 `ceph health` 必须 `HEALTH_OK`、所有 OSD `up`（skill §1.1）。
- 仅当任务书按 §二.19 预注册并获单独授权暂停 scrub 时，允许唯一的预期例外：
  `HEALTH_WARN` 的 health-check key **只能**是由 `noscrub,nodeep-scrub` 引起的
  `OSDMAP_FLAGS`，且 OSD 全部 up/in、PG 全部 active+clean、无正在运行的 scrub/deep-scrub。
  出现任何其他 health check 时仍须停止；⛔ 禁止用字符串包含 `noscrub` 就吞掉其他 WARN。
- 确认 JuiceFS 版本含 loadRange 修复（commit eaf3d21f，即 `1.3.1+` 或 `1.4.x`）——stock v1.3.1 有 2× 读放大 bug。
- **157 红线**：157 上有 WekaIO 业务在跑，**禁动内核/网卡/RoCE/md0/WekaIO 路径**；BeeGFS 与本测试抢同批盘须错峰。

### 6. 记录规范

- 每个结果目录**必须含 `commands.sh`**，记录实际执行的完整命令（可复现）。
- 每项测试须保存：fio 全文输出、全部 per-job bw_log、`env-snapshot`、ceph 状态、（如涉及）pprof/pidstat/nic 采集。
- **WSL 持久化根目录统一为 `/mnt/c/SunRise/test`**：今后所有测试结果，无论是从 157/集群节点
  拉取的原始证据，还是本地生成的 Gate 输出、fixture/mock 结果、分析器产物、归档、校验清单和
  执行报告，最终都必须落入该目录下按任务号和 RUN_ID 隔离的子目录。`/tmp`、远端 `/tmp` 和
  `/tmp/production` 只允许作为执行中的临时工作区，**不得作为任何结果的唯一副本**。
- 从服务器取数时，服务器现场不得在持久化副本完成前清理：先复制到
  `/mnt/c/SunRise/test/<TASK>/<RUN_ID>/`，再生成并核对源端/本地 SHA256、文件数和归档可读性；
  三者通过后才可把“证据已回传”记为 PASS，之后再按任务书授权清理服务器临时结果。
- 本地整理或复算产生的数据也应直接写入上述持久化子目录；工具若只能先写 `/tmp`，必须在本阶段
  结束前同步到持久化目录并复核 SHA256。报告中必须记录持久化绝对路径和 manifest 路径。
- **阶段/任务完成门**：持久化目录、原始证据、实际脚本、`commands.sh`、manifest/SHA256 与报告
  任一缺失，均不得宣告阶段完成或删除其他副本。电脑或 WSL 意外重启后，应从持久化目录恢复，
  不得假定 `/tmp` 中仍有有效证据。
- **禁止整树重复回传**：RUN 级不变量（脚本、inventory、配置、二进制身份）每个 RUN 只保存一次；
  cell/phase 只增量回传本阶段新证据。不得把前序完整目录再次嵌入后序目录，不得长期同时保留
  同内容的同步暂存目录、展开目录和多个归档副本。
- **持久化不等于永久堆积**：持久化通过后，必须继续按
  `TEST-DATA-LIFECYCLE-POLICY.md` 完成审核、分类和收口。已归因且已被有效重跑替代的失败 RUN、
  重复 Gate/mock、同步暂存目录和复算解压目录，应在相应阶段收口时进入清理流程；
  `失败即保留现场`只表示在归因和持久化前禁止破坏现场，不表示永久保留全部副本。
- 验收线随口径：不限速 100GbE = **6250 MiB/s**（网卡半速）；千兆限速 = **59 MB/s**；多客户端 = N × 单客户端线。
- randrw 验收档 = **128 并发**（D2 档 16×8 的整机等效，以当前项目约定为准）。

### 7. 卷清理（防止数据累积污染后续测试）

- **`juicefs format` 不删除任何 pool 对象**——只重置 TiKV 元数据，pool 中的 Ceph 对象成为孤儿。多轮测试中数据只增不减。
- **必须用 `juicefs destroy`**（删除 pool 中 JuiceFS 拥有的对象 + TiKV 元数据）。详见 `skills/TESTING-GUIDE.md` §3.5。
- **标准清卷流程**（从老集群脚本固化）：
  1. `juicefs umount`
  2. `sleep 65`（等会话 TTL 过期，不等待 destroy 会失败）
  3. 提取 UUID：`UUID=$(juicefs status "${META}" | grep -o '"UUID": "[^"]*"' | cut -d'"' -f4)`
  4. `juicefs destroy "${META}" "${UUID}" --yes`
  5. compact cooldown（destroy 产生 tombstone 积压，必须清理）
  6. `juicefs format` + `juicefs mount` + `mkdir`
- **关键**：destroy 必须传 UUID（从 `juicefs status` 提取），不能传卷名。传错会报 `UUID <name> != expected <uuid>`。
- **测试中数据累积检查点**：每个清卷点前后用 `rados df -p <pool>` 确认对象数，确保 destroy 后归零。
- **⚑ 2026-07-23 红线：轮间清理与组内清卷统一用 `juicefs destroy`（soft-clean，保留 pool）**。**禁用 `ceph osd pool delete + create`**——删建 pool 会改 pool_id → CRUSH 重算 PG→OSD 映射 → 同一次重建内也产生 -22~-26% 漂移（实证见 `00-baseline-20260723.md` §9.6）。**禁 OSD restart 作轮间清理**（重置 tmpfs/BlueStore 内存态）。pool delete+create 仅在 destroy 失败/孤儿累积时兜底，用后须视为一次重建、重新标定基线。

### 8. skill 合规自查（测试前后必带，2026-07-23 固化）

> GLM 执行测试必须遵循 `skills/` 全部文档。为确保"遵循"落到实处，每份任务书的执行步骤须首尾各加一条：

- **步骤 0（测试前）**：通读相关 skill 并确认关键点——至少 `baseline-reproduction-skill.md`（§2.2 清理层级 / §2.5 soft-clean 流程 / §3.1 执行顺序 / §4.3 判据）、`TESTING-GUIDE.md`（§1.3 compact 三指标 / §2.2 health / §3 cooldown）、`test-commands-reference.md`（§8.3 稳态中位）。**须显式列出本任务最相关的 skill 章节号。**
- **末步（测试后）**：对照 skill 逐条复核执行合规，并在报告记录"skill 合规自查结果"。必查项至少含：① 清理是否只用 `juicefs destroy`、**未出现 `ceph osd pool delete`**；② 清理未夹带禁止的操作；③ 每写项后 compact cooldown 已轮询至 `compact_running=0` **且 `compact_queue_len=0`**；④ drop_caches/预热是否严格按任务书预注册口径对称执行，且未影响157共置业务；⑤ 统计口径用 §8.3 稳态中位。**任一不符须显式标注并说明对结论的影响，不得默默跳过。**

### 9. 分层授权：可自主修复区 vs 禁止擅动区（2026-07-23 固化）

> 背景：GLM 曾因钦定脚本跑不通（auth key）**擅自改用被禁的重建方式且不声明** → 采到无效数据。故每份任务书须明确授权边界。

- **✅ 可自主修复（工程性，不改变量）**：脚本 bug、环境适配（auth/路径/依赖）、采集增强。**发现脚本会采到错误数据时应先修好再采，不要用错误脚本采错误数据。修完必须在报告显式声明改了什么、为什么。**
- **🔴 禁止擅动（改变量则实验失效）**：控制变量（清理方式/是否删 pool/是否重建/pool_id/CRUSH/pg_num）、测试项、口径、判据、任何标"红线/核心变量"的项。**遇到"必须改变量才能跑通"的障碍 → 停下来报告障碍、等确认，不得自行绕道。**
- `noscrub/nodeep-scrub` 是 Ceph **全局控制变量**：只有任务书按 §二.19 预注册、用户单独授权、
  独立控制脚本通过 Gate 0 后才允许设置；执行方不得因担心波动自行开关。
- **规则一句话**：实现怎么修都行；**改变量之前必须停下来报告，不能绕道**。
- **建议**：验证性任务书对应脚本应内置"变量守卫"（运行时自动比对控制变量是否被动，触发即报警并把判定标为不可信），使擅自改变量当场暴露，而非事后靠人工审计。

### 10. 挂载档位（good/bad tier）—— 判别器与用法（2026-08-12 固化）

> **背景（必须理解，否则会误用）**：每次 `juicefs` 重新挂载相当于**重新抽签**。抽到"坏档"实例，吞吐比好档低 **15~31%**（⚑ 2026-08-13 由 15~28% 上调：深模聚集在 −29±1%，最深单点 −31% = OSD 块 randread）。
> 坏档率 p 的现有估计（⚑ 2026-08-13 修订）：~~08-02 周报的合格实例命中率 61%（p≈0.39）~~ 该实验自承设计缺陷，降级为参考；03-6 实测 9 挂载中 1 坏 ＋ 03-7L 实测 7 挂载中 4 坏（WF1 −28.2%、WS2 −19.4%、OSD 块 −21~−31%、PROBE-WF3 −29.5%）⇒ 合并 **5/16 ≈ 0.31**（95% CI [0.11, 0.59]）。
> **后果：坏档不影响结论的【方向】（可用 10.4 的压力测试证明），但会扭曲结论的【幅度】。**

#### 10.1 为什么"多测几次"解决不了（不要再试）

档位是**挂载的属性**，不是随机噪声。按 **p=0.31** 计算（⚑ 2026-08-13 重算，原表 p=0.39；定义：全坏=pⁿ、臂中位落坏=P(≥⌈n/2⌉ 坏)、幅度被扭曲=2q(1−q) 其中 q=前项，n=3 行与原表公式复核一致）：

| 每臂挂载数 | 连续全坏 | 臂中位数落进坏档 | **测得幅度被扭曲** |
|---|---|---|---|
| 3 | 2.98% | 22.9% | **35.3%** |
| 5 | 0.29% | 17.7% | 29.1% |
| 7 | 0.03% | 13.9% | 24.0% |
| 压到 <5% | — | **需 17 挂载/臂（每臂 ~13h）** | 仍不现实 |

- 🔴 **增加 `REPEAT`（同一挂载多跑几轮）完全无效** —— 同一挂载的所有轮次都是同一个档。
- 🔴 **增加挂载数收敛极慢** —— 中位数只抗单点，抗不了"多数是坏的"。

#### 10.2 第一优先：能不 remount 就不 remount（结构性消除，优于任何统计手段）

| 旋钮类型 | 是否需要 remount | 做法 |
|---|---|---|
| **OSD / Ceph 侧**（`ceph config set`，`Can update at runtime: true`） | **不需要** | **单实例内 A/B**：挂一次、全程 `SKIP_REMOUNT=1`，块首/块尾 + 每 run 记 `pid`+`starttime_ticks`，**全程相同即为"无跨实例噪声"的证据**；pid 变了立即停 |
| **挂载参数类**（`--max-fuse-io` / `--buffer-size` / `--max-readahead` …） | 必须 | 走 10.3 判别器门 |

> 反面教材：03-7-lite 初版让 OSD 旋钮的每个 run 都 remount，等于**凭空引入一个完全可以避免的噪声源**。已改。

#### 10.3 判别器：多流顺序读的「每字节 FUSE 延迟」（ns/B）

```
每字节 FUSE 延迟 = FUSE 请求平均耗时(ns) ÷ FUSE 请求平均尺寸(B)
数据来源：JuiceFS .stats 的
  juicefs_fuse_ops_durations_histogram_seconds_{sum,total}  → 平均耗时
  juicefs_fuse_read_size_bytes_sum / juicefs_fuse_ops_total_read → 平均尺寸
探针负载：mseqread（多流顺序读，只读，~6min/挂载，REPEAT=2）
```

**为什么用它（三个条件缺一不可，这是 08-02"准备 1"用写侧吞吐当探针失败的教训）**：

| 08-02 失败原因 | 本指标为何不受影响 |
|---|---|
| 档位向写侧传导仅 0.22 倍，写侧噪声比读侧大 22 倍 ⇒ 永远看不见 | 用**读侧** |
| 吞吐受池内对象数干扰 | 用**延迟**，与对象数无关 |
| 被调参数本身会改变指标 ⇒ 无法区分"旋钮效应"与"档位效应" | **按字节归一化**：尺寸翻 2.00 倍时耗时也恰好翻 2.00 倍，每字节值不变 ⇒ **对 `--max-fuse-io` 免疫** |

**参照值与判据（2026-08-12 标定）**：

| 项 | 值 |
|---|---|
| 历史 128K 参照群（无旋钮变更，n=15 轮） | 中位 **3.287 ns/B**，极差仅 **1.5%** |
| 03-6 全部好档挂载（128K 与 256K 各档） | **3.221 ~ 3.297**（偏离参照 −2.0% ~ +0.3%） |
| 03-6 坏档 `T36-B1` | **4.613**（偏离参照 **+40.3%**） |
| **判定阈** | 偏离参照 **>10%** 判坏档（分离度约 **27 倍**，阈值取在信号与噪声之间，不敏感） |

#### 10.4 用法（四条，写进任务书）

1. **逐挂载判档门（detect-and-replace）**：每个新挂载**先**跑探针（6min），偏离参照 >10% ⇒ **立即丢弃该挂载并重新 remount**（最多重试 2 次），⛔ 不要在坏档上花 40min 跑效应项。⚑ 2026-08-13 补：**每次重试必须换 label**（如 `T37L-WS3-t1/t2/t3`，⛔ 禁复用同一 label）——03-7L 段2b 复用同 label 使 `rounds.tsv` 累计行被旧读数稀释：真坏档 2959 被稀释成 3968（−5.4%）而被门放行（实查 6 个门值 = 该 label 累计所有轮的中位数，全部精确复现）。
2. **必须对两臂对称施加 + 预登记**，并在报告中**逐臂报出重挂次数**（不对称即暴露偏置）。⚑ 2026-08-13 补：判档一律用 **10.3 的 ns/B 判别器（>10% 阈）**，⛔ 禁改用 raw 吞吐 ±3% 门——03-7L 段2b 用 raw mseqread ±3% + 固定平台（4195/4230，03-6 深夜标定）⇒ 傍晚基线 −5% 漂移使 6/6 被误杀、白重挂 6 次。若确需 raw 值平台，必须**同会话首挂载锚定**，不跨时段借旧标定。
3. **每臂 ≥3 挂载 + 挂载级中位数**：中位数需 ≥3 个样本才抗单点污染；2 个的"中位"就是均值，会被坏档拉走一半深度。**2 挂载/臂仅允许用于非劣性判定**，任何"有效/提升"结论必须 ≥3 挂载/臂 + 判别器门。
4. **每个结论必附"坏档压力测试"**：把有利臂整体按历史最大坏档深度（当前 **−30%**，⚑ 2026-08-13 由 −28% 上调）折算，**若结论翻转 ⇒ 判"不可判"**，不得报有效/无效。
   - 等价形式：档位单独最多只能造出 **1/d** 的臂间比（d=0.70 时为 1.43 倍）。**实测臂间比扣掉这个上界后的残差必须仍 > 判定门槛。**
   - 推论（能力边界）：**3 挂载/臂在最坏档位假设下只能安全判定 > 43% 的效应**（=(1/d_max−1)，⚑ 2026-08-13 由 39% 修订）；小于此值必须走 10.2 单实例配对。
   - ⚠ 该折算强度依赖 d_max=−30%，⚑ 2026-08-13 起为**多观测**（T36-B1、WF1 −28.2%、PROBE-WF3 −29.5%、OSD 块 −31%），不再是单点。若历史统计发现更深的坏档，所有依赖此折算的结论须重新评估。

#### 10.5 已知失效边界（不要越界使用）

- **"内部标准归一化"（效应项 ÷ 同挂载探针项）只对同类负载有效。** 实测：`randread ÷ mseqread` 把跨实例极差从 28.69% 压到 **1.41%** ✅；`randrw ÷ mseqread` 从 16.99% 变成 **17.35%，无效** ❌。原因：污染不等比作用（B1 的 mseqread −27%、randread −28% 同步，randrw 仅 −15%）。
  ⇒ **准则：探针必须与效应项共享被污染的那条资源路径。含写的混合负载禁用内部标准归一化。**
- **一个"零结论"（判无效应）比"有效结论"更依赖档位核验**：若两臂档位未核验，零结论可能是"真效应被反向档位差抵消"。⇒ 报零结论前必须先出两臂的判别器读数。

#### 10.6 反面教材（防止重犯）

- ❌ **循环论证**：先按污染规则剔掉坏档挂载，再在剩下的样本里算方差，然后宣称"实例波动很小"。（opencode 2026-08-12 犯过，用户驳回。这与"跨实验相减给调优空间封顶"是同一类错误。）
- ❌ **用"3 次 remount 结果都很接近"证明没有档位问题**。若 p=0.31，3 次全好档的概率为 (0.69)³=**33%**，3 次全同档（全好或全坏）的概率约 **36%**，"碰巧"完全站得住。
- ❌ **复用同一 label 重试**：`rounds.tsv` 按 label 累计追加，同 label 重试会把坏档读数稀释进历史中位数（03-7L 段2b：真坏档 2959 → 门读到 3968 ⇒ 放行）。**重试必须换 label。**
- ❌ **用 raw 吞吐 ±3% 当判档门**：偏离 10.3 的 ns/B 定义（03-7L 段2b 违反而被 6/6 误杀）。判档门 = ns/B 判别器（>10% 阈），无例外。

### 11. 每个判据必须指名数据来源文件（2026-08-12 固化）

### 13. 有效带宽口径升级：实际 I/O 起点 + 重叠加权重采样 + 四窗（2026-08-28 固化，取代 §二.1 的"截前 1/4"）

> 背景：03-20B-R2 把 fio **fork 时刻**当成 I/O 起点，256 个进程启动耗时 **58 s**，
> 导致 W1 落在进程创建期、真实负载最后 58 s 完全没有进入判读，
> 并把"从低负载启动期进入真实负载"误读成"compaction 在运行后段持续爬升"。
> 该错误单独反转了一条机制结论。

1. **起点必须是实际 timed-I/O 起点**：`起点 = fio 报告的完成时刻 − run= 实际毫秒数`。
   ⛔ 禁用 fork 时刻、⛔ 禁用脚本登记的 `fio_start`、⛔ 禁用 sampler 启动时刻。
   任务书必须要求把"实际起点 − 登记起点"的差值打印出来；差值 >2 s 即说明存在启动期污染。
2. **多 job 汇总必须做重叠加权重采样**：`--log_avg_msec=1000` 产出的是 interval-average，
   区间边界与自然秒不对齐。正确做法 = 每份 log 的每个区间按**与自然秒的重叠时长加权**
   摊到各自然秒，再逐秒对全部 job 求和，且只保留当秒 job 数齐全的样本。
   ⛔ 禁止直接把第 N 行当第 N 秒。
3. **正式窗 + 四子窗必须同时保存**：正式窗（如 `[15,175)`）报 mean / median / 秒级 CV / P10 / P90；
   W1--W4 各 40 s 报均值与 `W4/W1`。**只报一个整程数字的任务书不予通过。**
4. ⛔ **fio summary 不得作为主口径**，只能作旁证。历史误差实例：03-19 用 summary 得 `24%--26%`，
   正式窗真值 `10%--13%`（2 倍误差）；03-20A summary `2939`，正式窗 `2828`。
5. **§二.1 的"截掉开头 1/4 取中位数"降级为无 per-job log 时的退化口径**；
   有 per-job log 时一律走本节。

### 14. 非性能证据门与性能端点必须分离（2026-08-28 固化）

> 背景：03-22b 把 `CV≤10%` 同时定义为**证据有效门**。当研究目标本身就包含"能否降低 CV"时，
> 控制臂真实不稳定反而使 analyzer 拒绝出数、整个 RUN 失去回答该问题的能力。

- **能删样本的只有非性能门**：sampler 覆盖率、身份指纹（PID/starttime/exe md5）、
  集群健康、容量、内存/swap、reset/清理闭环、I/O 错误、缺 log。
- **不能删样本的是性能端点**：带宽、CV、`W4/W1`、延迟。**再差都是结果，不是删样本的理由。**
- 任务书必须把两类门**分表列出**，并显式写明"性能端点不触发样本删除"。
- 推论：验收门（部署是否可接受）与有效性门（数据是否可信）是两件事，⛔ 不得共用一个阈值。

### 15. RUN 有效性状态机与"禁止补样"（2026-08-28 固化）

> 背景：03-20B / R1 / R2 / 03-22 / 03-22b / 首次 03-22c **连续 6 次**出现
> "形式上 `EVIDENCE_INVALID`、但正文仍引用其工程结论"。一道总是失败的门不携带信息。

1. **必须预注册四态**，且每态对应的动作写清楚：

   | 状态 | 含义 | 允许的引用方式 |
   |---|---|---|
   | `VALID` | 全部非性能门通过且矩阵完整 | 可作正式效应量 |
   | `EVIDENCE_INVALID` | 任一非性能门失败或缺臂 | **只能作工程观察**，⛔ 不得进入效应量 |
   | `RESOLUTION_INSUFFICIENT` | 噪声底 ≥ 判定边界 | 只给上界，⛔ 不得宣告"等价/非劣" |
   | `INCONCLUSIVE` | 方向一致性不足 | 只报逐对值 |

2. ⛔ **禁止**：同 RUN 热改脚本后按正常签收、换 RUN_ID 重来、补样替换、
   把无效 RUN 的点值与有效 RUN 拼成新效应量、在门失败后改挑有利判据。
3. **失败即保留现场**：不卸载、不删目录、不清 sampler、不 kill。
   ⛔ 禁 `fusermount -uz`、`umount -l`、`losetup -D`、`rm -rf`、模式 kill、kill mount PID。
4. **门必须标定在可达水平**。若一类门连续两次全 RUN 失败，说明门标定错误，
   应先修门再上环境，⛔ 不得靠"这次也失败但结论仍成立"继续。
5. **`incidents.tsv` append-only**，任何异常/修复在动作**前后各记一条**；
   ⛔ 不得改写历史行。事后汇总里出现账本没有的修复项，视为账本无效。

### 16. 多臂设计：平衡顺序 + 噪声底自校准（2026-08-28 固化）

> 背景：U141 把非劣性边界预设在 `±3%`，而该批次纯读零假设实测出的块级系统偏置是 `5.25%`
> ——判据比噪声还细，无分辨力。同时 mseqwrite 造成对象数单向棘轮，
> 使臂效应与池状态共线不可分离。

1. **顺序必须平衡到一阶**：`L2_FORMAL` 多臂用 ABBA-BAAB（或等价平衡设计），
   并在报告里**复算各臂占位均值**证明相等（8 轮时两臂均应为 4.5）。
   这使一切对轮序单调的漂移（时间、对象数、compaction 债、温度）一阶抵消。
   ⛔ 单纯 ABBA 一个 block 不够；⛔ 每臂占据连续时段（序贯设计）一律不予通过。
   上述“单纯 ABBA 不够”专指 `L2_FORMAL` 效应量；`L1_SCREEN` 可以预注册单个 ABBA
   作为最小平衡筛选，但只能决定“值不值得升级”，不得产生交付、等价或无效应结论。
2. **交错粒度尽量细**：能按轮交错就不要按 block 交错。
   历史实证：block 级（小时间隔）交错在纯读项上仍留下 `5.25%` 的臂间偏置，
   而轮内 CV 只有 `1.1%` —— 那是块级系统偏置，**加轮数消不掉**。
3. **必须留同臂相邻对做噪声底**：ABBA-BAAB 中 `(R02,R03)` 与 `(R06,R07)` 天然同臂，
   其真值恒为 0，`ε = max(|Δ|)` 即噪声底。
   **判定边界由数据推出**：`M = max(工程边界, 2ε)`；若 `ε ≥ 工程边界` 则判
   `RESOLUTION_INSUFFICIENT`。⛔ 禁止先设边界后测噪声。
4. **零假设对照优先于统计**：若被测变量在物理上不可能影响某些测试项
   （例：只改写路径的补丁不可能影响纯读项），**这些项就是零假设对照**，
   其实测偏差直接量化该批次的偏置底噪。任务书应主动设计这类对照。
5. **状态型混杂必须显式建模**：对象数、pending compaction、文件资产 mtime 等
   会随轮次单调变化的量，必须逐轮记录为协变量，并在报告中给出两臂起点的平衡性检验。
   ⛔ "SOFT-PASS 也算通过"这类与硬门矛盾的条款不得写进任务书。

### 17. 上环境前必须过离线 Gate 0（2026-08-28 固化）

> 背景：03-19→03-22c 约 **30 个**缺陷是在集群上、用一整轮 180 s arm 才发现的，
> 而它们**全部是纯 bash / 解析缺陷**，一个 fixture 就能覆盖。
> 这是该批次最大的单项浪费：同一个 B256 负载被跑了 12 arm，其中 4 次只为修仪表。

- 每份涉及新驱动脚本的任务书必须含**阶段 0：离线 Gate 0**，
  ⛔ Gate 0 未过禁止 SSH / sudo / mount / fio / ceph / juicefs 任何一条。
- Gate 0 必须先按本次**新增/修改的代码路径和风险类型**，从
  `skills/fixtures/known-defect-classes.tsv` 选择相关缺陷类并记录选择清单；相关项须逐条断言。
  只有新建通用驱动框架、涉及破坏性/全局状态操作，或进入L2/L3正式交付时，才要求覆盖全部适用类。
  不得因为复用脚本只改一个参数，就机械重跑与该路径不可达的全部fixture。新踩的坑仍须追加到目录。
- **分析器必须先在已有历史归档上自证**（零环境成本）：
  用已知答案的旧数据跑一遍，检查正式窗与 summary 的偏差、四窗单调性，
  并做**起点敏感性三算**（±1 s 应 <1% 变化，+58 s 应显著改变四窗——
  若 +58 s 几乎不变，说明窗口逻辑没生效）。
- Gate 0 必须 grep 自身脚本，**发现明文口令即 FAIL**。
  已知例外须在报告"既有风险"节登记并建议轮换凭据。
- 详细机械件与参考实现见 `skills/EVIDENCE-INTEGRITY-SKILL.md`。

### 18. 执行方只交原始数据，统计由第二方独立复算（2026-08-28 固化）

> 依据很硬：独立复核**推翻或订正了 6/6 份报告的头条结论**——
> 03-19 报"稳定性通过"实为 8/8 FAIL 且效应量 2 倍误差；03-20A 报"字段不存在"实为解析 bug；
> 03-20B 挂载指纹写错；03-20B-R1 内层 manifest 8 文件不一致；
> 03-20B-R2 时间轴错 58 s；03-22c 报"D1 降低 NVMe await"实际升高。
> 这是整个证据体系里最便宜的高回报环节。

- 任务书必须写明：执行方交付 = 原始数据 + 逐门 PASS/FAIL 清单 + `incidents.tsv`。
  ⛔ 执行方不算效应量、不算 CV/中位数、不下"有效/等价/退步"结论、不挑轮次。
- 报告的每个数字必须可回溯到原始文件路径 + 字段名（与 §二.11 一致）。
- 归档必须能被第二方独立重算：含实际执行脚本全文与 md5、冻结 manifest、
  内层 `SHA256SUMS` 自校验全 PASS。
- **订正必须提到报告开头**：⛔ 禁止把裁决写在附录而正文仍留错误数字。
  历史反面教材：03-19 §1/§4.3/§6 至今仍写着"增益 24%--26%""稳定性门通过"，
  而 §9 才给出 `STABILITY_FAIL` 与 `10%--13%`；引用摘要者必然拿到错数字。
  正确做法 = 在标题或文档状态表给出**机器可读的 verdict 行**。

### 19. Ceph scrub 条件性控制基线（2026-08-30 固化）

> 背景：U141d RUN `20260830-092829` 在 fio 正式窗结束约 6.5 分钟后命中一次
> `active+clean+scrubbing`，冻结的 post gate 因此中止整个 RUN。只读日志在24小时内确认
> pool 3 至少12次普通 scrub和1次 deep-scrub；scrub虽不是PG故障，却会读盘并竞争OSD资源，
> 也会成为长矩阵的随机中止源。

1. **必须预注册二选一，禁止运行中改口径**：
   - 因果调优、版本比较、多臂正式矩阵：推荐在**单个 phase**内临时暂停普通/深度 scrub；
   - 生产交付、长期稳态/韧性测试：保持 scrub 开启，并保存正式 I/O 窗内的重叠证据。
   短时只读 inventory、离线 Gate 0 和非性能 canary 不得为方便而修改 scrub flags。
2. 暂停 scrub 必须同时使用 `noscrub` 与 `nodeep-scrub`，并标记
   `SCRUB_PAUSED_FOR_CONTROLLED_BENCHMARK`。这是**环境控制条件**，不是性能旋钮或生产交付配置；
   只能说明排除后台巡检后的因果效应，不能据此宣告生产常态绝对性能。
3. **作用域按 phase，不按项目**：设置前保存集群 FSID、原始 flags、health checks、OSD/PG状态；
   设置后等待已在运行的 scrub/deep-scrub 完全退出，连续健康门通过后才开 fio；同一矩阵全部臂
   对称保持不变，禁止轮间 set/unset。phase 完成、失败或中止后立即恢复原状态。这两个 flags
   只暂停周期调度，不能作为“人工 scrub 一定不会发生”的证明；受控 phase 内须禁止人工触发，
   且每轮仍检查无 `scrubbing/deep`。
4. **全局影响必须单独授权**：这些是 Ceph OSDMap 全局 flags，即使 JuiceFS 文件是测试数据，
   也会暂停该集群全部 pool 的一致性巡检。任务书必须写明预计暂停时长、数据/维护风险、授权停点；
   ⛔ GLM 不得把它当作可自主修复项。
5. **只允许状态驱动的独立控制脚本**：脚本须精确记录自己新增的 flags，只恢复自己拥有的变化；
   支持 plan/inspect/restore 和部分失败恢复，持久保存 set/unset epoch、命令 rc 与前后状态。
   禁止裸命令、无 state 文件操作、无条件 unset、只依赖性能驱动进程的 `EXIT trap`，也禁止
   后台 root watchdog 在没有所有权核验时擅自清全局 flags。
6. **健康门不得降级**：若设置 flags 导致 `HEALTH_WARN`，仅可接受 §二.5 定义的单一
   `OSDMAP_FLAGS` 例外；PG仍须 active+clean、OSD须 up/in、不得有 recovery/backfill/peering/
   inconsistent/repair 或正在运行的 scrub。采集器须保存完整 health JSON、OSD flags和逐PG原始state，
   ⛔ 禁止只输出 `nonclean=0` 后丢失异常PG身份。还须审计**实际负载脚本内部**是否硬编码
   `HEALTH_OK`；若有，只能用任务专用、哈希冻结、默认关闭的严格豁免入口，禁止伪造 health 输出，
   也不得直接改写被其他历史任务冻结的公共脚本。
7. **恢复优先于证据收口**：phase 无论成功失败，先执行精确 restore 并验证回到原 flags；恢复失败
   是安全事件，优先级高于性能结论。恢复后积压 scrub 可能集中启动；必须记录并等待环境重新稳定，
   才能启动下一个 phase。closure 需同时归档性能结果和独立 scrub-control audit。
8. 若保持 scrub 开启，任务书必须定义正式窗级事件采集：scrub/deep-scrub 与任何正式 I/O 窗重叠
   即按预注册规则处置；post snapshot 命中但经 epoch 证明只发生在正式窗外时，不得伪装成性能污染，
   也不得靠放宽 `active+clean+scrubbing` 字符串匹配而跳过时间归因。

### 20. 证据投入分级：先低成本筛选，再升级正式验证（2026-08-31 固化）

> 背景：一条 fio 负载通常只需几分钟，但完整测试的大部分墙钟花在固定起点、身份、
> 排空/恢复、sidecar 和独立复算。这些工作曾阻止起点错 `58 s`、summary 效应量翻倍、
> fresh TiKV `+25%--30%` 混杂、每轮 relayout 将 CV 从 `0.6%--1.5%` 放大到 `10%--13%`、
> `512 MiB/1 GiB` 文件合同错误以及 PID/UUID/解析脚本错误，因此**底线不能删**；
> 但“只是看候选方向是否值得做”与“要给出可交付因果效应”不应默认使用同一成本。

#### 20.1 四级任务类型（每份任务书必须选一级）

| 级别 | 用途 | 允许得出的结论 | 默认成本模板 |
|---|---|---|---|
| `L0_OFFLINE` | 源码/理论审计、inventory、plan、Gate 0、生成器 feasibility | 可行/不可行、安全边界；无性能结论 | 不跑正式 fio，不为方便改 scrub |
| `L1_SCREEN` | 候选参数、机制探针、端点范围筛选 | 只能记“有/无升级价值”工程观察 | 同实例 `AB/BA`，或挂载型变量单个 `ABBA`；`0--1` 组固定预热；通常 `30--90 min` |
| `L2_FORMAL` | 因果归因、版本替代、可交付参数、非劣/退化裁决 | 可作正式效应量与项目决策 | 原则上使用完整平衡矩阵；需 settle 时可用 `4` 固定预热 + `8` 轮 `ABBA-BAAB`；通常 `3--6 h` |
| `L3_PRODUCTION` | 产品长期稳态、韧性、常态可运维性 | 可外推到生产常态 | scrub 保持开启，长窗、故障/背景任务共存；不用受控 benchmark 峰值代替 |

`4+8` 是需要独立挂载、存在 settle 且要签正式效应时的**推荐模板**，不是每个
`L2_FORMAL` 机械必跑的常数。若能在同一进程/挂载内切换变量，或已有与当前二进制、负载、
数据资产和环境同级的有效筛选证据，可减少预热或直接进入 L2，但必须在任务书写明理由。

#### 20.2 从 L1 升级 L2 的规则

1. 任务书必须在看数据前写明 `SCREEN_CONTINUE` / `SCREEN_STOP` 条件；
   其用途是排期与资源决策，不是将 L1 冒充为正式结论。
2. 默认只在以下情况升级：效应方向一致，且幅度超过预注册工程关注线或已测噪声底；
   机制指标与方向一致；候选项具有可交付价值。
3. 筛选没有看到材料信号时，可以作为“当前不优先投入正式矩阵”的依据；
   但不得写“等价”、“无效”、“可替代”或“不退化”。
4. 已有历史证据可以代替 L1，但必须同时核对：二进制/关键修复、负载形状、数据资产、起点和旧数据的方法学缺陷；
   任一项不同只能当先验，不能免除 L1。

#### 20.3 任何环境测试都不能省的“最小真值集”

以下项目即使在 L1 也必须保留，因为它们防的是“测错了”，而不是“统计不够精”：

1. **固定数据资产**：优先复用一次 layout 后的固定文件；禁止轮间 relayout 与被测变量共线。
2. **精确身份**：binary/config/META/UUID、PID/starttime/exe、mount options、数据 path/inode/size。
3. **正确性能窗**：per-job raw log、actual timed-I/O start、重叠加权自然秒、方向拆分；
   summary 只作旁证。
4. **同窗对照与顺序控制**：至少使用平衡 AB/BA 或 ABBA；禁止只与跨日历史点相减。
5. **非性能有效门**：身份、health、I/O error、log/sampler 覆盖、容量/内存、脚本哈希；
   带宽/CV/延迟不作删样门。
6. **写后恢复**：写任务必须保留对象、GC、compaction/meta 债务和下游恢复闭环；
   只读任务按实际路径删去无关的写后清理，不得为了“模板完整”制造额外写入。
7. **可追溯与安全**：`commands.sh`、raw archive、SHA256、append-only incidents；
   全局/破坏性操作仍必须 plan、状态所有权、分阶段授权和精确恢复。

#### 20.4 可按级别缩减的项目

- `L1_SCREEN` 不要默认加 `4` 预热 + `8` 正式轮、所有 sidecar、每个小步人工停点、
  完整 CI/非劣性裁决；只保留对候选方向、数据真值和安全闭环有用的证据。
- 指标 sidecar 分为 `CORE`、`MECHANISM`、`DIAGNOSTIC`：CORE 缺失可判 invalid；
  MECHANISM 缺失只限制归因；DIAGNOSTIC 按异常触发，不必每轮全量采集。
- 阶段内只要不改变量且已有失败恢复分支，执行方应批量跑完；
  人工停点放在候选取舍、sudo/全局状态、生产停启、破坏性清理和 L1→L2 决策边界。
- 第二方复算对 L2/L3 必须保留；L1 仍必须保留可复算 raw，但只需判定是否升级，
  不需为工程筛选撰写完整交付报告。

#### 20.5 任务书的必填字段

每份新任务书必须在前两页内明确：

```text
EVIDENCE_LEVEL=L0_OFFLINE|L1_SCREEN|L2_FORMAL|L3_PRODUCTION
SCREEN_SOURCE=<本 RUN 筛选或可代替的历史证据>
SCREEN_CONTINUE=<预注册升级条件>
SCREEN_STOP=<预注册停止条件>
FORMAL_MATRIX=<若升级时的固定矩阵>
ESTIMATED_WALL_CLOCK=<fio 纯负载 + 控制/恢复开销>
```

无这些字段的任务书，不得仅因“严格一点”就直接执行长矩阵。

### 21. 测试数据生命周期合同（2026-09-01 固化）

> 完整规范见 `doc/perf-tasks/TEST-DATA-LIFECYCLE-POLICY.md`。本节是每份任务书必须就地落实的
> 最低合同，不能只写“测试后清理”或“失败保留现场”。

1. **两类资产必须分开**：
   - `EVIDENCE`：fio/raw log、采样、快照、脚本、命令、manifest、分析和报告；
   - `ENVIRONMENT_ASSET`：卷、pool/对象、TiKV namespace、挂载、进程、loop/tmpfs/设备和全局 flags。
   本节只授权前者的文件生命周期；后者必须另列 plan/state/ACK/恢复门。
2. **每个 RUN 只设一个本地权威根**：
   `/mnt/c/SunRise/test/<TASK>/<RUN_ID>/`。157/集群和 `/tmp` 只作运行时源或暂存区，
   不得出现两个都被称为“最终真值”的本地目录。
3. **任务书前两页必须声明**：

   ```text
   EVIDENCE_ROOT=/mnt/c/SunRise/test/<TASK>/<RUN_ID>
   REMOTE_RESULT_ROOT=<157或集群上的精确绝对路径；无则NONE>
   EVIDENCE_RETENTION=FORMAL|SCREEN|INCIDENT|TRANSIENT
   REMOTE_CLEANUP=AFTER_PERSISTENCE_PASS|AFTER_REVIEW|PRESERVE
   LOCAL_COMPACTION=AFTER_REVIEW|AFTER_STAGE_CLOSE|PRESERVE
   ENVIRONMENT_ASSET_CLEANUP=<独立任务阶段/独立授权；不得写成沿用证据清理>
   ```

4. **增量原则**：公共证据每 RUN 一份，轮次证据放 `cells/<CELL_ID>/`，事故证据放
   `incidents/`，派生结果放 `derived/`；禁止每轮重新复制整个 RUN。原始文件一旦登记进 manifest
   即不可覆盖，重试必须使用新 RUN_ID 或显式 attempt 子目录。
5. **持久化硬门**：只有源端/本地文件集合、SHA256、文件数和归档可读性全部闭合，并写出
   `PERSISTENCE_PASS`，才允许清理远端临时证据。缺 raw、实际脚本、`commands.sh`、incident、
   manifest 或核验记录时不得通过。
6. **失败现场不是永久保留**：未归因事故保持 `INCIDENT_STATUS=OPEN`；根因确认、关键证据封装、修复版本
   Gate 通过且替代 RUN 可用后，失败 RUN 可标为 `PURGE_ELIGIBLE`。不得用无效 RUN 参与正式效应量，
   也不得因为它无效就未经归因直接删除。
7. **精确清理**：清理前必须形成可审阅清单，至少含 RUN_ID、资产类别、精确绝对路径、大小、
   manifest SHA256、保留副本位置和清理理由。禁止通配符、未解析变量、父目录递归、符号链接逃逸、
   `rsync --delete`、按名称模式跨 RUN 删除。清理后须重新盘点并记录结果。
8. **本地只留一份长期原始真值**：正式有效 RUN 长期保留不可变原始归档、manifest、实际脚本、
   分析和报告；审核完成后可删除其同步暂存和复算解压副本。已归因无效 RUN 只长期保留事故包，
   被替代 Gate/mock 只保留最终 PASS 与代表性失败证据。
9. **事件驱动收口，不按年龄自动删除**：每个 phase 结束、RUN 审核完成和阶段报告签收时都必须
   做一次生命周期盘点；可以自动列出候选，但不得仅因“超过 N 天”删除尚未审核或事故未关闭的数据。
10. **报告必须可见**：阶段报告须列出 RUN 的有效性状态、生命周期状态、权威持久化路径、
    远端是否已清、保留/清理项及对应审计文件。没有生命周期收口记录时，任务只能算“性能执行完成”，
    不能算“任务完全关闭”。

### 22. 精简设计与尽快闭环（2026-09-02 固化）

> 背景：多项本可由一组 fio 回答的筛选任务，被扩展成多轮任务书、脚本重写、重复 Gate、逐步回传和
> 重复归档；准备与收尾成本远高于有效负载本身。严谨性的价值在于防止错误结论，不在于流程越多越好。

#### 22.1 先冻结最小决策，不预建完整框架

每份任务书在写脚本前必须用四行回答：

```text
MINIMUM_DECISION_SET=<回答唯一问题所需的最少臂/轮次/指标>
STOP_AFTER_ANSWER=<得到何种结果后立即停止，不再追加什么>
MAX_PREP_BUDGET=<任务书+脚本+离线Gate的预算>
MAX_EXECUTION_BUDGET=<环境测试+必要恢复的预算>
```

1. 一个任务只设一个主问题。旁证只采集，不得各自演变为新的通过门。
2. `L1_SCREEN`默认采用最小平衡设计，例如同实例`AB/BA`或单个`ABBA`；不得预先实现未获升级资格的
   八轮矩阵、H锚点、全量诊断和多套恢复框架。
3. 已有同版本、同负载、同资产且口径可信的历史基线，可作描述性工程锚点；若当前因果对照已经是
   同Pool/同挂载/同数据内切换，除非锚点直接参与裁决，否则不为“看起来完整”追加同窗H轮次。
4. 筛选已回答“当前方向不值得继续投入”时，允许在限定条件下关闭该任务；不得为了获得更漂亮的
   CI把明确无材料信号的方向升级L2。结论措辞应限定为当前配置/负载，不扩大成普遍无效。

#### 22.2 只有材料信号才能升级

1. 升级条件必须在看数据前写明，默认同时要求：机制指标方向正确、重复方向一致、效应达到工程关注线
   或目标线，且存在可交付手段。任一不满足即停止。
2. 若L1出现明确材料信号，只补足形成正式效应所缺的轮次和证据；优先复用已有有效轮次，不重新layout、
   不换RUN、也不从Phase 0重走与变量无关的步骤。若预注册合同禁止复用，应在开跑前改为顺序升级设计，
   不能测完后追认。
3. 正式矩阵、95% CI、第二方完整复算只在要做交付、替代或因果声明时投入；普通筛选只保存可复算raw
   和停止依据。

#### 22.3 脚本和Gate必须与风险成比例

1. 能复用已签收驱动的一条命令完成，就不得新建编排框架；能用参数或小函数解决，就不得复制脚本。
2. Gate只覆盖本次新增或改变的路径，以及会造成错误数据/系统风险的既有缺陷类；不得因改一行参数
   重跑与该路径无关的全项目模拟。
3. 普通只读L1的准备预算原则上不应超过其环境执行预算，且通常应在`60 min`内完成。超过预算必须
   暂停编码，删除非决策证据、复用既有组件或退回更小canary；不能以“再补一个门”无限延期。
4. 同一阶段若连续两次因确定性脚本bug未产生有效数据，任务负责人必须直接接管离线修复或缩减方案；
   禁止继续以“执行方修改→回传→再发现一个问题”的方式循环。
5. 不为一次性失败路径实现通用平台。失败恢复只覆盖本任务实际拥有的状态；极低概率、无状态破坏的
   异常可停止并人工审计，不要求在开跑前自动化所有可能分支。

#### 22.4 减少协调、报告与数据搬运

1. 阶段内部默认授权执行方连续跑完；只在安全/全局状态授权、控制变量取舍、L1→L2升级和破坏性清理前停。
2. 同一阶段只维护一个滚动执行记录和一个最终报告。脚本修复细节写入append-only incident或最终报告，
   不为每个小步骤新建一份任务书和报告。
3. 公共证据每RUN只复制一次，逐轮只增量回传；分析完成后一次性持久化和manifest核验。禁止为了每次
   人工审核反复复制整个远端目录。
4. 收尾以“恢复所拥有的环境状态、保存唯一原始真值、写出结论”为完成线；无收益任务不追加与结论
   无关的复算、格式化报告和多轮清理审计。环境资产清理仍须遵守安全规范和精确授权。

#### 22.5 不得精简的底线

以下内容不受预算约束，缺一项即不得开跑或宣告完成：

- `SYSTEM-SAFETY-SKILL.md`及157业务保护、破坏性/全局操作授权、精确目标和状态所有权；
- 控制变量、固定数据资产、binary/META/UUID/PID/starttime身份；
- fio原始日志、实际I/O窗、命令rc、I/O错误和必要sampler覆盖；
- 非性能有效门、失败后的精确scrub/primary-temp/mount等状态恢复；
- 一份可校验的权威证据、实际脚本/命令和最终结论。
