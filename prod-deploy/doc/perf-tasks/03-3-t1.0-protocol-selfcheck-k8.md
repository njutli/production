## 〇、背景（为什么要先做这个）

T1 的判定式是 `|median(B臂) − median(A臂)| ≥ max(该项分辨力, 2×漂移底噪)`。这个式子有两个已知的薄弱处：

1. **余量极薄**。03-2 测出的门槛与可检出效应量只差 0.4-0.5 个百分点（`randread` 判据取 3.0%、`mseqread` 取 1.5%）。
2. **03-2 发现 `mseqread` 存在单调上行漂移**（Spearman(运行序,值)=+0.939，10 运行涨 1.10%）。这个漂移的方向是固定向上的，**如果臂的排列有任何时序偏斜，后跑的臂就会被系统性抬高** —— 足以凭空造出一个"有效"结论。

所以在拿任何真旋钮之前，必须先用一个**已知答案是"0"的旋钮**验一遍框架。K8 就是为此选的：源码 `src/common/mclock_common.h` 显示 `balanced{client .5,1,0}` 与 `high_client_ops{client .6,2,0}` 的 **client `limit` 都是 0（=不限速）**，在空闲集群、无 recovery 的条件下两者对客户端 IO 的实际约束**相同**。⇒ 预期收益 ≈ 0。

**如果这个任务测出 ≥3.0% 的"收益"，说明协议有系统性问题，T1.1-T1.7 全部不能开工。** 这就是本任务的全部价值。

## 一、目标

回答四个问题：

| # | 问题 | 判定方式 |
|---|---|---|
| **Q1** | 判定框架能否正确输出"无收益"？ | `randread` 与 `mseqread` 的 \|median(B)−median(A)\| **均 < 判据门槛** |

| **Q4** | （可选，非必答）H1 假设成立吗？ | BlueStore `onode_hits` / `buffer_hit_bytes` 是否随 run 序单调上升、且与 `mseqread` median 同步 |

⚠ **Q1 是唯一的通过/不通过项**。Q2/Q3/Q4 只报数据，不作为放行条件。

|---|---|
| `ITEMS` | **`"mseqread randread"`**（⚠ **不要加 seqread**，见下） |
| `RUNTIME` | 180 |

| `SKIP_REMOUNT` | 1（全程） |

| 臂序 | **`A B A' B' A'' B''`** —— 6 个 run，严格交替 |
| A 臂旋钮 | `osd_mclock_profile = balanced`（现值） |
| B 臂旋钮 | `osd_mclock_profile = high_client_ops` |
| 单 run 耗时 | ~43min（mseqread 5 轮 ~17min + randread 5 轮 ~14min + gc/warmup ~12min） |

**为什么不加 `seqread`**：03-2 已证 `seqread` 的判据门槛 7.78% > 其可检出效应量 4.0%，**它在 T1 里数学上不可能判定任何事**，只会多花 1.7h。计划书 §6.1 已把它移出判据集。

**判据门槛（03-2/F13 的 lag1 口径，唯一可用口径）**

| 项 | 可检出效应量 | 2×漂移底噪(lag1) | **本任务门槛 = max(两者)** |
|---|---|---|---|
| `randread` | 3.0% | 2×1.30 = 2.59% | **3.0%** |
| `mseqread` | 1.5% | 2×0.50 = 1.00% | **1.5%** |

**Q1 通过条件**：`|median(B臂3个run) − median(A臂3个run)| / median(A臂)` 对 `randread` **< 3.0%**、对 `mseqread` **< 1.5%**。

## 五、通用注意事项（必带，逐条固化）
