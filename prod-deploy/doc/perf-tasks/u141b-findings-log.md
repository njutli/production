## F-U141b-01｜S17 primary map 的口径是「单池」而采集器打印「全池」

**发现批次**：阶段 I preflight（GLM 报告 §4.1 提出）
**现象**：`ceph-preflight.txt` 记 `pg_count=33`、`primary=[0:6 1:6 2:5 3:7 4:5 5:4]`，
与任务书 §6.4 S17 写定的 `[0:6 1:6 2:5 3:6 4:5 5:4]`（32 PG）差 1 个 PG（OSD 3 上 6→7）。

**opencode 独立复算**（2026-08-28，只读 `ceph pg dump pgs_brief`）：

| 范围 | PG 数 | primary 分布 |
|---|---:|---|
| pool 3 `juicefs-data` | 32 | `0:6 1:6 2:5 3:6 4:5 5:4` |
| pool 1 `.mgr` | 1 | 全部落 OSD 3 |
| 全池合计 | 33 | `0:6 1:6 2:5 3:7 4:5 5:4` |

`ceph osd pool ls detail` 确认 `juicefs-data pg_num 32 pgp_num 32 autoscale_mode off`。

**结论**：**集群状态与预期完全一致，无异常**。差异 100% 来自 `u141b-collect.sh:204` 的
`cmd_ceph` 解析 `pg dump pgs_brief` 时**未按池过滤**，把 `.mgr` 的 1 个 PG 也计入。
⇒ 这是采集器的**渲染口径问题**，不是集群问题，不影响证据有效性：
S17 的硬断言是 `nonclean=0`（实测 0），primary map 在实现里只作记录、未参与判定。

**处置**：
- 本任务期内 ⛔ 不改采集器（纯渲染问题，不值得破坏 D27 冻结与 Gate 0 attestation）。
- **后续所有批次的验收口径改为**：`pg_count=33`、`primary=[0:6 1:6 2:5 3:7 4:5 5:4]` 为**恒定期望值**；
  任一批次偏离此值即需解释。等价的单池值仍是 `3:6`。
- 收口后一次性修 `cmd_ceph`，加池过滤并同时打印单池/全池两行。

## F-U141b-02｜⚑ 订正 GLM 报告：P0 的两臂 Setting 不是「identical」，V14 是**超集**

**发现批次**：阶段 I P0（**GLM 报告 §2.6 未发现，opencode 独立复算发现**）
**GLM 原表述**：9 个字段逐一 `✅ 一致` ⇒ `P0_GATE: PASS (settings identical across versions)`。

**opencode 独立复算**（直接读 `closure/p0-status-{1-V14,2-V13}.json` 的 Setting 段做键集合 diff）：

| 项 | 结果 |
|---|---|
| V14 键数 | **16** |
| V13 键数 | **15** |
| `only_in_V14` | **`Tiers`** |
| `only_in_V13` | 无 |
| 共有键的值差异 | **NONE**（全部逐字节相同） |

`Tiers` 实际值：`{"0": {"ID": 0, "StorageClass": "", "Tag": ""}}`
—— 即 v1.4.1 新增的存储分层字段，只有一个默认 tier 0，`StorageClass`/`Tag` 均为空串。

**结论**：准确表述应为 **「V14 的 Setting 是 V13 的超集，新增 `Tiers` 一个字段且取空默认值；
15 个共有字段逐字节相同」**，而非「identical」。
对替换判定的实质影响：**无，且方向有利**——
P0 第 2 步（V14 挂过之后挂 V13）成功、第 3 步（再挂 V14）成功，
说明**新增字段不阻断 v1.3.1 挂载，回滚仍可行**，这正是 P0 要证的事。
⚑ 但「identical」这个词会掩盖「元数据格式确实发生了单向演进」这一事实，
在替换决策文书里不可用，必须按超集表述。

**待补的一个读操作**（成本 <1 min，纳入 P1 批次附带执行）：
区分 `Tiers` 是 **(a) 仅客户端渲染默认值**、还是 **(b) 已被 V14 写入 TiKV 的 setting blob**。
判别法：不挂载、直接 `juicefs config <META_URL>`（无参数即只读回显）看 setting 里有无 `Tiers`。
- 若 (a)：格式未变，结论最干净。
- 若 (b)：格式已单向演进，v1.3.1 靠「JSON 反序列化忽略未知字段」兼容 ⇒
  必须在最终报告写明「回滚可行但元数据已带 v1.4.1 字段」，并确认 V13 重写 setting 时会不会把
  `Tiers` 丢弃（丢弃亦无害，因其为空默认值）。

**处置**：最终报告与 §11 判定表按「超集」表述；P0 结论从
`settings identical` 订正为 `settings compatible (V14 superset, +Tiers default-empty), rollback verified`。

## F-U141b-03｜`closure/*.json` 带 2 行日志前缀，不是合法 JSON（延后为新缺陷类 D33）

**发现批次**：阶段 I P0（opencode 独立复算时被 `json.load` 直接抛异常暴露）
**现象**：`p0-status-*.json` 前两行是 juicefs 的 `<INFO>` 日志
（`Meta address: tikv://...`、`TiKV gc interval is set to 3h0m0s`），第 3 行才是 `{`。
⇒ `json.load(open(f))` 报 `JSONDecodeError: Extra data: line 1 column 5`。
文件行数 V14 69 行 / V13 62 行，其中含 2 行日志。

**根因**：`juicefs status` 把日志写 stdout 而非 stderr，采集时以 `> *.json` 整体重定向，
扩展名承诺了合法 JSON 但内容不是。

**影响评估**：对 U141b 判定**无影响**——这些文件只做人工/脚本比对，
且 P0 的字段比对未走 `json.load`。但任何下游按扩展名直接解析的消费者都会炸。

**规避**：读取前先剥离前缀 —— `sed -n '/^{/,$p' f.json | python3 -c ...`。

**处置（延后）**：U141b 收口后向 `skills/fixtures/known-defect-classes.tsv` 追加
**D33 = 「工具输出含日志前缀却以 `.json` 落盘，下游按扩展名解析即失败」**，
`origin` 填 `u141b-phase1-p0`，`static_check` 填「凡 `> *.json` 的重定向，
须经 `sed -n '/^{/,$p'` 或 `2>/dev/null` 分流后再落盘，且 Gate 0 对产出的 `*.json` 跑一次 `json.load`」。
⛔ 现在不追加：该 tsv 的 md5 `c93b00a6502e…` 已进 U141b provenance，
中途变更会使后续批次的 attestation 与阶段 I 不可比。

## F-U141b-05｜`pgrep fio` 的松匹配会被内核线程 `vfio-irqfd-clea` 命中（驱动实现正确，记为反例）

**发现批次**：opencode 复核阶段 I 环境时自身踩到
**现象**：在 157 上 `pgrep -c fio` 返回 **1**，命中的是内核线程 `vfio-irqfd-clea`（PID 1001），
并非真实 fio 负载。若 S02 用 `pgrep -c fio` 判「有外来 fio」，则**每一轮都会误判失败**。

**驱动实现核对**：`u141b-driver.sh:202` 用的是
`pgrep -c -f '(^|/)fio( |$)'` —— 全命令行锚定匹配，实测 `pgrep -x fio` 与该模式均返回 **0**。
⇒ **驱动实现正确，无需修改**；误报来自我临时用的松模式。

**处置**：记为反例，说明 S02 的模式选择是有意为之。
⛔ 后续任何批次的临时排查 ⛔ 不得用 `pgrep -c fio` 判串行门，必须复用驱动同一模式。

## F-U141b-06｜⚑ 任务书内部冲突：批 1 要「R01 实测 timing」与「phase 内部不停」互斥 ⇒ 正式豁免

**发现批次**：审阅阶段 I 报告时发现（GLM 未提出；GLM 严格停在 preflight 结束，未跑 R01）
**冲突**：
- 任务书 §九 批次表 `批 1 = 阶段 I 全部（S02–S08）+ P0 + **R01 实测 timing.tsv**`，目的是校准单轮时长；
- 任务书 §首部第 9–11 行 `phase 边界是唯一有决策价值的停点`、`phase 内部不停`。

R01 属于 P1。若按批 1 原文在 R01 后停下等审核，则 R01→R02 的间隔变成**小时级**，
而 R02…R08 之间是**十分钟级** ⇒ 直接破坏本任务的核心设计（轮级交错、单调漂移一阶抵消），
正是 U141 与 V141R 被毁掉的同一机制。**两项要求不可同时满足。**

**裁定：豁免「R01 实测 timing」这一项，phase 内部连续性优先。**
理由：交错平衡是本任务证据有效性的**必要条件**，时长校准只是**便利项**，
且时长已有历史 V4 同负载先验（读三项 ≈13 min/轮），且 driver 每轮都会写 `timing.tsv`，
事后即可核对，无需为此牺牲设计。

**替代保障——把「停下问」改成「自动中止」**（不引入时间偏置）：
- P1 的 **R01** 跑完后由 driver/执行者当场比对墙钟；
- 若 `R01 墙钟 > 1.6 × 预估`（读三项即 **>21 min**），**立即中止整个 P1**，
  该 phase 记 `EVIDENCE_INVALID`，回传报告等重新排期；
- ⛔ 不得「继续但压缩后续轮」、⛔ 不得「停下等指示再续跑」——两者都会产生非均匀轮间隔。

**处置**：U141b 收口后修任务书 §九 批次表，删去批 1 的 R01 timing 要求，
改为本条的「1.6× 自动中止」规则，并在 §二 写明「便利项不得与平衡设计冲突」。

## F-U141b-07｜S01 整除截断掩盖了一次真实的硬门失败（driver:425）

`check_timing()` 用 `min=$(( (e - b) / 60 ))` 取整后再与 `PHASE_EXPECT_MAX[P1]=20` 比较。
P1 R01 实测 `1787916191 - 1787914933 = 1258 s = 20.97 min`，**真值 > 20**，
按 `:426-429` 本应 `incident FATAL` + `die`，**整个 P1 会被中止**；
只因 `1258/60` 向下取整成 `20` 才走到 `S01_PASS 20min`。GLM 报告照抄为「20 min ≤ 20 → PASS」。

进一步看：8 轮墙钟 20.95 / 21.05 / 20.97 / 20.95 / 21.07 / 20.97 / 21.22 / 21.05 min，
**极差仅 16 s** ⇒ 这不是异常轮，而是 `PHASE_EXPECT_MIN/MAX=[13,20]` 这个估值本身系统性偏低
（估值只算了 3 项 × 180 s 的 fio 时间，没算每轮 remount / cleanup / 采集开销）。

**处置**：本次按 F-U141b-06 的 `1.6 ×` 规则（读三项阈值 21.6 min）判 **PASS，不追溯**。
收口后修两处：① `check_timing` 改秒级比较（或向上取整），⛔ 不得用整除掩盖越界；
② `PHASE_EXPECT_MIN/MAX[P1]` 改 `[20,24]`，并按实测重估 P2/P3/P4。
收口后追加缺陷类 **D34｜整数除法截断掩盖门限越界**。

## F-U141b-10｜P2 只有 4/8 轮 ⇒ 结构性无效，⛔ 效应量不可引用

**这不是「样本少一半」，是「设计被破坏」。** 半块 `V13 V14 V14 V13` 只能抵消**线性**趋势，
抵消不了**曲率**：二次项对比 V13 占位 `{1,4}` 的 `mean (pos−2.5)²` = **2.25**，
V14 占位 `{2,3}` = **0.25**，失衡 **9 倍**（全 8 轮设计才平衡：V13 = V14 = **5.25**）。

而 P2 恰恰有极强的单调漂移（seqwrite 写载荷 ⇒ 对象数棘轮）：

| 项 | R01..R04 | 线性趋势 | r(objects,BW) | 斜率 |

| randrw 读 | 2018.3 / 1903.8 / 1808.1 / 1780.3 | −81.0 MiB/s per 轮 | **−0.992** | **−458.9** MiB/s per M obj |
| randrw 写 | 2019.9 / 1904.3 / 1808.1 / 1780.2 | −81.5 MiB/s per 轮 | **−0.992** | **−462.1** MiB/s per M obj |
| seqwrite | 1556.0 / 1615.9 / 1583.8 / 1575.7 | +2.7 MiB/s per 轮 | +0.239 | +25.6 MiB/s per M obj |

对象数 1,978,576 → 2,208,720 → 2,386,177 → 2,515,713 单调递增；
randrw 斜率 **−459 MiB/s per M obj**，比 U141 记录的 −33.5 陡一个数量级。
衰减是**凸的**（降幅 −114.5 / −95.7 / −27.8 逐步收窄），凸衰减下占位 `{1,4}` 的均值

## F-U141b-13｜★ 均值 / 中位数口径歧义直接决定最终判定（本任务最重要的发现）

## F-U141b-14｜★ 「同臂相邻对」测到的不是噪声底，是「趋势 + 噪声」
