## 二、现象

`--max-fuse-io 256K` 挂载下，**纯随机覆盖写**（fio `rw=randwrite bs=256k --direct=1`，128 个进程各写 1 个 1 GiB 文件）：

| 场景 | randwrite 吞吐 |
|---|---|
| 128K 挂载（历史基线） | **2942~3258 MiB/s** |
| 256K 挂载（03-7L 实测 14 轮） | **551~552 MiB/s（崩塌 5.8×）** |
| 256K 挂载 + 混合读写 randrw（写的那一半） | 1939 MiB/s（**不受影响**） |

- 同一个 256K 挂载上，混合读写的写半程能到 1939 MiB/s ⇒ **不是网络、OSD、对象存储的写带宽问题**，是"纯写负载"特有的崩塌。
- 14 轮均值稳定到 0.2% ⇒ 是确定性的限速机制，不是随机抖动。
- 崩塌位置在**客户端内部**：写请求在 JuiceFS 客户端进程里平均耗时 **57.7 毫秒**（128K 挂载只有 3.7~4.9 毫秒）；而客户端下游一切正常（上传 5.35ms、元数据操作 6.0ms、仅用 2.4 核 CPU）⇒ 写请求是在客户端里"白等"。

## 三、原理：一次用户写 IO 的预期旅程 vs 实际旅程

### 3.0 前置概念（对照架构文档）

架构文档说 JuiceFS 分三层：**客户端（Client）**、**元数据引擎（Meta Engine）**、**对象存储（Object Storage）**。本 bug 只涉及客户端内部 + 元数据引擎的"发号"环节。需要先建立五个概念：

1. **数据块（block）**：文件在对象存储里的数据单元。本卷格式化时定为 **256 KiB**（官方默认 4 MiB，本卷因 EC 配置切小）。一次"上传"就是往 Ceph 里 PUT 一个 256 KiB 的数据块。
2. **待写块（slice）**：客户端内存里的一个"正在攒数据"的缓冲区，攒满 256 KiB 就应当立刻上传。
3. **编号（slice id）**：每个数据块在元数据引擎里的身份号码。**申请编号非常便宜**——客户端从元数据引擎批量预领一串号码存在本地计数器里，正常申请是纯内存操作、微秒级；只有本地号码用光时才真正找一次元数据引擎（每 4096 个块一次）。
4. **内存缓冲上限（--buffer-size，默认 300 MB）**：客户端允许"已写进内存、还没传到对象存储"的数据总量上限。**超限时客户端会主动降速**（每笔写睡 10ms；超 2 倍上限睡 100ms）——这是 JuiceFS 有意设计的保护机制，防止内存被未上传数据撑爆。正常时这个机制永远不会触发。
5. **兜底清仓**：某个待写块若一直没机会上传，客户端还有两个兜底：同一 4 MiB 区域内堆积超过 4 个待写块时强制上送；以及 10 秒超时强制上送。正常时这些兜底只是保险丝，不该成为主路径。

### 3.1 预期旅程（设计意图，10 步）

一个 256 KiB 随机写从用户侧下发到数据落入对象存储，**应该**是这样的：

| 步 | 位置 | 动作 |
|---|---|---|
| 1 | 应用（fio） | `write()` 下发 256 KiB 数据 + 文件随机偏移 |
| 2 | 内核 | 经 FUSE 把写请求连同数据交给 JuiceFS 客户端进程 |
| 3 | 客户端 | 给该文件加写锁，定位这次写落在文件的哪个 256 KiB 数据块 |
| 4 | 客户端 | 新数据块 ⇒ 创建"待写块"，**向元数据引擎申请编号**（微秒级，本地计数器） |
| 5 | 客户端 | 把 256 KiB 数据拷入待写块（纯内存拷贝） |
| 6 | 客户端 | 块已攒满（256 KiB = 块大小）⇒ **立即把块交给上传队列** |
| 7 | 客户端 | 上传线程领取配额（上限 150 个并发）→ **PUT 到 Ceph**（约 5ms） |
| 8 | 客户端 | 上传完成 → 内存归还缓冲池 → **缓冲水位下降** |
| 9 | 客户端 | 写请求返回成功给内核/应用（全程约 1ms 以内） |
| 10 | 客户端（异步） | 稍后把"块的编号"提交到元数据引擎（TiKV），数据正式对外可见 |

关键点：**第 4 步（登记）和第 6 步（上传）是紧密相连的**——登记是微秒级操作，登记完马上上传，缓冲水位永远很低，节流机制永远不触发，吞吐只受上传能力（~4 GiB/s）限制。

### 3.2 实际旅程（bug 的分叉）

**分叉发生在第 4 步与第 6 步之间——登记被交给了"后台伙计"，而上传检查时伙计还没登记完：**

| 步 | 实际动作 |
|---|---|
| 4' | 创建待写块后，登记编号被丢给**后台 goroutine 异步执行**（`go prepareID(...)`） |
| 5 | 数据拷入待写块（与 4' 同时进行） |
| 6' | 块攒满，上传前**检查"编号到手了吗？"**——后台伙计还没跑完，编号 = 0 ⇒ **判定"未登记"，跳过本次上传** |
| 7' | 代码的设计意图是"没关系，下次再写这个块时补传"——**但纯随机写没有下次**：下一个 256 KiB 写落在别的随机位置，又创建一个新待写块，重复 4'→6' |
| 8' | 数据滞留内存，只能等两个兜底：同一 4 MiB 区域堆够 5 个待写块（随机写下很难），或 **10 秒超时强制刷** |
| 9' | 滞留量 = 写入速率 × 驻留时间（约 0.3~1 秒）⇒ 内存缓冲涨到 **300~600 MB**（逐秒采样实测：均值 144 MB、峰值 609 MB） |
| 10' | 缓冲超限 ⇒ 节流机制启动（每笔写睡 10/100ms）⇒ 写请求平均耗时 57.7ms |
| 11' | 吞吐闭环：128 个进程 × 256 KiB ÷ 57.7ms ≈ **551 MiB/s**（与实测精确吻合） |

一句话：**登记本是微秒级操作，却异步执行，导致上传环节把"还没登记"误判成"不该上传"，每一次上传机会都被错过；数据在内存里越积越多，直到触发了 JuiceFS 自己的内存保护限速——整个崩塌是"自我限速"造成的，而不是任何硬件瓶颈。**

### 3.3 预期 vs 实际 对照表

| 环节 | 预期（设计意图） | 实际（bug 行为） | 差异后果 |
|---|---|---|---|
| 编号登记 | 微秒级、同步完成 | 后台异步，写请求读到时必为"未登记" | 上传误判 |
| 块攒满后 | 立即上传 | 每次都被跳过（纯随机写无第二次机会） | 数据滞留 |
| 数据驻留内存 | 约 5 毫秒（上传耗时） | 约 0.3~1 秒（等兜底清仓） | 缓冲积压 |
| 内存缓冲 | 稳定在几十 MB | 均值 144 MB、峰值 609 MB | 触发保护 |
| 节流机制 | 永不触发 | 持续触发（每写睡 10/100ms） | 写请求 57.7ms |
| 吞吐 | 3~4 GiB/s 量级 | 551 MiB/s | 崩塌 5.8× |

### 3.4 类比（快递驿站）

每收到一个包裹（写请求）本应"登记 → 立刻派送"（申请编号 → 上传）。登记本可在柜台即时完成，但店规却让柜台把登记条丢给一个后台伙计，而打包员看到"登记条还没回来"就认定"这包裹先不派"，放回货架等下次。可下一趟车总是开到别的货架（随机写），这个包裹再也没人来补派。包裹越堆越多，仓库（300 MB 缓冲）爆仓，店主启动"限流令"（每笔写强制休息 10/100ms），全店吞吐崩塌。

对比之下：128K 挂载时，内核会把一个 256K 大包裹**拆成两个连续的小包裹**，第二个小包裹恰好接在第一个后面（顺序相邻），等凑满一箱（256 KiB）时登记条早就回来了 ⇒ 立刻派送 ⇒ 仓库一直很空。混合读写时，读操作插在两次写之间给仓库留出了清仓时间 ⇒ 也不爆仓。

## 四、为什么只有"256K 挂载 + 纯随机写"触发

| 条件 | 256K 挂载 + 纯写 | 128K 挂载 + 纯写 | 256K 挂载 + 混合读写 |
|---|---|---|---|
| 写请求落点 | 随机，每个写都是新数据块 | 内核把 256K 拆成两笔**连续** 128K，第二笔恰好接在第一笔后（同一个块） | 随机，每个写都是新数据块 |
| 块攒满的时刻 | 第一笔写就攒满 | 第二笔续写时攒满 | 第一笔写就攒满 |
| 攒满时编号登记好了吗 | **没有（竞态，必错过）** | 有（登记有足够时间完成） | 没有（同样错过） |
| 结果 | 滞留 → 崩塌 | 及时上传 → 正常 | 错过上传但**读操作给写降速**，兜底清仓来得及排空 → 正常 |

- 128K 挂载幸免的原因不在客户端逻辑，而在**内核拆包**：拆出来的两笔 128K 写是顺序相邻的，第二笔"续写"同一个待写块，攒满时编号已就绪。
- 混合读写幸免的原因：每个进程在两次写之间插一次约 10ms 的读，纯写速率被自然拉低一半以上，兜底机制（同区域堆 5 块 / 10 秒超时）来得及清仓，缓冲始终不超限（实测均值 29.8 MB）。

## 五、修复思路

### 5.1 补丁（≤10 行，已编译为 `1.3.1+2026-08-13.e0032b2a-03-8-ceph`）

把"后台登记"改回"柜台登记"：创建待写块时**同步申请编号**（`NewSlice` 微秒级，本地计数器；只有本地号码用光时才真正找一次元数据引擎，平均每 4096 个块一次），失败时回退原异步路径：

```go
// 原（pkg/vfs/writer.go，writeChunk）：
go s.prepareID(meta.Background(), false)

// 改为：
var id uint64
if st := f.w.m.NewSlice(meta.Background(), &id); st == 0 {
    s.id = id
    s.writer.SetID(id)
} else {
    go s.prepareID(meta.Background(), false)
}
```

修复后：登记即时完成 ⇒ 块攒满时编号必在手 ⇒ **每次写都立即上传** ⇒ 缓冲水位回到几十 MB ⇒ 节流永不触发 ⇒ 写吞吐恢复到上传能力上限（3~4 GiB/s 量级，可能反超 128K 基线）。

**安全性**：`NewSlice` 只碰"发号器"的锁，不碰文件锁；调用点本来就在文件锁保护内，无死锁、无数据竞争；错误路径与原版行为完全一致。

### 5.2 放弃的替代修复（附理由）

| 候选 | 结论 |
|---|---|
| `--buffer-size` 调大（如 4G） | **治标不治本**：节流不触发、写请求不再睡，但数据滞留仍在，内存随速率线性上涨（~速率×1 秒），迟早还是要限（03-8 段2 仅作兜底验证） |
| `--max-uploads` 调大/调小 | **无效**：逐秒采样显示上传信号量（150 容量）全程空转——瓶颈不在上传并发，在**派发被推迟** |
| 升级到上游 1.4/main | 不可行：源码对比确认该竞态在主线**仍未修复** |

### 5.3 补丁适用边界（必须写清，防误用）

- **修复范围**：写尺寸 = 数据块大小（本卷 256 KiB）的完整块随机写——本 bug 的精确触发条件。
- **不覆盖**：写尺寸 < 块大小的纯随机小写（攒不满一个块，上传环节本来就轮不到它，走兜底清仓——**这是预存行为，非本补丁引入**）。预测：bs=128k 直写在任意挂载上仍会塌，待负控验证（可选，10min）。
- 顺序写、混合读写不受影响（本就不触发）。

## 九、影响与后续

- **业务影响**：`--max-fuse-io 256K` 是 randread +115.6%、randrw +52% 的来源；本 bug 使该参数无法固化（randwrite 从 ~3100 跌到 551）。
- **修复价值**：补丁验证通过后，256K 挂载可同时获得读侧 +115.6% 与写侧 ≥128K 基线（可能反超，因上传派发更及时）——全项提升。
- **上游动作**：建议以本报告为素材向 juicedata/juicefs 提交 issue 并附 PR（修复行数与思路见 §五）。
- **遗留**：<块大小的纯随机小写仍走兜底清仓（预存行为），如需覆盖另立专项。

```go
if s.notify.WaitWithTimeout(time.Millisecond*100) && !s.freezed &&
    time.Since(s.started) > flushDuration*2 {    // flushDuration = 5s
    s.freezed = true
    go s.flushData()
}
```

### A.4 上游状态

`git diff e0032b2a..origin/main -- pkg/vfs/writer.go` 显示写路径的节流、FlushTo 守卫、异步 prepareID 均无实质变化 ⇒ v1.4/main 仍含本缺陷。

## 附录 B：历史成因——"异步登记"为什么存在（git 考古）

### B.1 结论一句话

**异步登记不是一开始的设计错误，而是 2022 年一次重构让"登记很贵"的前提失效后，调用方没有跟着改——典型的前提失效遗留代码。**

### B.2 时间线

| 时间 | 提交 | 编号申请的成本 | 异步化是否合理 |
|---|---|---|---|
| 2021-01-08 | `d23762a7`（first public release） | `NewChunk` = `rdb.Incr("nextchunk")`——**每次申请都是一次真实元数据引擎往返**（Redis/TiKV，毫秒级） | ✅ 合理：写路径不该为每个新数据块卡一次元数据往返，异步化是当时正确的取舍 |
| 2022-07-26 | `b38ace2f`（#2397 "refactor: distinguish Slice from Chunk"） | 改为 `NewSlice` = **本地计数器 + 批量预分配**（`sliceIdBatch=4096`，每 4096 个块才真正打一次元数据引擎） | ❌ **前提已失效，但 `go s.prepareID(...)` 与 `if s.id > 0` 原样保留** |

- 2021 年版本里还有一处补偿分支（`else if int(off) <= f.w.blockSize { go s.prepareID(ctx, false) }`），说明当时作者对"第一次写错过上传"有感知，靠"第二笔续写补传"兜住——对顺序写/续写场景这只是 1 个块的延迟，无感。
- #2397 只重构了 `prepareID` 的**实现**（把昂贵的元数据往返换成本地计数器），没有回头审查依赖旧成本模型的**调用方**——异步外壳连同竞态一起留了下来。

### B.3 为什么十年级的维护者也没踩到

1. **触发条件极窄**：写尺寸恰好 = 数据块大小（本卷 256 KiB）的**纯随机**写，且 `max-fuse-io ≥ 256K`（默认 128K 时内核把 256K 应用写拆成连续两笔 128K，第二笔续写时编号早就绪，FlushTo 命中，竞态永远轮空）。
2. **顺序写/续写**：第一次错过只延迟 1 个块，第二笔续写即补传，无感。
3. **混合读写**：读操作给写降速，兜底清仓（同区域堆 5 块 / 10 秒超时）来得及排空积压，缓冲永不超限。
4. 本缺陷是 fio 纯随机覆盖写 + `--max-fuse-io 256K` 组合钉死的——上游与一般用户的典型负载（顺序落盘、append 日志、混合读写）都稳定绕开。

### B.4 教训（供内部复用）

- **优化改了底层成本模型后，必须回头审查依赖旧成本模型的调用方**：异步/批量/缓存类优化最容易留下这类"前提失效"的竞态。
- 本项目同类经验：03-6 的 `--max-fuse-io` 边界、`--max-readahead` 拆包误触发内部 readahead（128K 拆包与 JuiceFS 内部读放大机制的前提冲突）——都属于"参数/实现变了，旧假设没跟着变"。
