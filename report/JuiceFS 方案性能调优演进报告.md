## 二、关键调优突破

### 突破 1：网络基础设施修复（阶段 1）

调优起步时，通过自底向上隔离发现：裸盘 SSD 随机写可达 420 MB/s，但 `rados bench` 后端仅 9.87 MB/s、延迟 17.6 秒——典型的网络拥塞特征。定位到 ceph-node1/node2 网卡仅协商到 100Mb/s（约 12.5 MB/s），是整套系统的头号物理瓶颈。

修复后后端裸能力从 ~10 MB/s 提升到 ~108 MB/s，端到端顺序吞吐从 ~8 MB/s 提升到 ~80 MB/s。

### 突破 2：去 RGW 直连 RADOS（阶段 2）

通过 128G 同口径对照实验，去掉 RGW（S3 网关）HTTP 协议层、改用 JuiceFS librados 直连 Ceph：

- 顺序写 18.6 → 53.8 MB/s（**+189%**）
- 随机读写 4.6 → 15.6 MB/s（**+239%**）

### 突破 3：block-size 4M → 256K（阶段 2，核心突破）

通过白盒实验 + `juicefs stats` 采集 + fio bs-sweep + block-size-sweep 精确定位根因：**JuiceFS 默认 4MB block 对 256K 随机读造成 ~16× 读放大**——客户端拉了一堆用不上的数据，object 层 ~100 MB/s 全浪费，FUSE 有效读仅 ~5 MB/s。

将 block-size 改为 256K 后，经多次重测互证：

- 纯随机读提升约 3.7 倍
- 顺序读写不降反略升
- 存储空间零代价（EC 开销不变）、内存反而更低

### 突破 4：暖态缓存 + 客户端参数调优（阶段 3）

在 256K block 基础上叠加客户端调优：

- **暖态缓存（cache=100G）**：随机读 33.6 → 105 MB/s（+213%），随机读写 +34%
- **--max-uploads 150**：顺序写 +23%、顺序读 +14%、布局写 +39%
- **--max-readahead 0**：写类全面受益（顺序写 +33%、随机写 +8%），但顺序读和随机读写受损，需按负载选配

### 突破 5：loadRange bug 定位与修复（阶段 4，核心突破）

通过 JuiceFS 源码分析，定位到 v1.3.1 版本独有 bug：`cached_store.go:153` 的 `loadRange` 函数中条件 `len(p) <= blockSize/4`（即 64K）错误地阻止了 128K FUSE 半块读取，导致每次随机读都触发完整 256K block 读取，造成 **2× 读放大**。

该 bug 的修复 commit 为 `eaf3d21f`（已在 main 分支，未 backport 到 release-1.3）。应用 patch 后：
- 随机读放大从 2.17× 降至 1.11×（专项验证）

**关键发现：ra 对 randread 无影响**。之前认为"ra=0 显著提升随机读"的结论是带 bug 版本的假象——bug 造成的 2× 放大与预读叠加，ra=0 恰好消除了预读部分。修复 bug 后，ra=0/1/2/4/8 的 randread r1 均为 51-53 MiB/s，无显著差异。因此**无需设置 ra=0**，default（2 MiB）即可。

> ⚠️ **此结论在阶段 5 被环境特定修正**：ra sweep 在**真盘**上执行，后端磁盘是瓶颈（~52 MB/s 上限），掩盖了预读放大的影响。全内存盘去掉后端瓶颈后，默认预读对随机读的 2.02× 投机放大暴露，`--max-readahead 0` 使 randread 从 55.7 飙升至 112.2（+103%）。**生产环境按负载选配**：随机读/混合负载必须 `--max-readahead 0`；顺序单流读为主保留默认预读。详见 §五.4。

**mu=150 冷态全量验证**：将 max-uploads 从默认 20 提升至 150，冷态全量测试结果显示写类指标全面提升：

| 指标 | mu=20（07-03前） | mu=150（07-03） | 涨幅 |
|------|-------------|---------------|------|
| 顺序写 | 50.8 | 57.0 | +12.2% |
| 多线程写 | 41.5 | 43.7 | +5.3% |
| 布局写 | 33.3 | 39.1 | +17.4% |
| 随机写 | 53.5 | 55.7 | +4.1% |
| 随机读写 R | 17.3 | 19.4 | +12.1% |
| 随机读写 W | 17.0 | 19.1 | +12.4% |

mu=150 的作用机制：max-uploads 控制并发上传 goroutine 数。128 个 fio 并发 job 争抢 20 个 upload slot 时写请求排队严重；提升至 150 后排队延迟大幅降低。读操作不走 upload pipeline，故 randread 不受影响（符合预期）。

### 突破 6：全内存盘全项达标 + ra0 根因确认（阶段 5，里程碑）

> 数据：`results/memdisk-fullretest-128g-v3-20260711/` | 详见 `doc/perf-analysis/12-post-diskbottleneck-plan.md` §三

阶段 4 在真盘上穷举排除后，残余瓶颈集中在磁盘/RAID 层。为确认 JuiceFS 软件层能否达到 59 MB/s 全项达标，将 6 OSD 全部替换为 tmpfs（WAL/DB 独立 4G + DATA 独立 45G），排除底层介质干扰，在千兆网络上做全量标准化测试。

**口径校准**：采用 fio `--write_bw_log --log_avg_msec=1000` 逐秒瞬时带宽，截缓冲暂态后取稳态中位数（非全程平均——后者被客户端写缓冲拉高 7-8%，曾报 120-127 MB/s 超千兆物理上限，是假象）。全 180s，A/B 单变量对照，两版（v2/v3）复现互证。

| 项 | A组（默认预读） | B组（+`--max-readahead 0`） | ra0 影响 | 达标(≥59) |
|----|----|----|----|----|
| 顺序写 | 111.8 | 111.5 | 无 | ✅ |
| 多线程写 | 111.6 | 111.8 | 无 | ✅ |
| 顺序读 | 103.0 | 69.1 | -33% | ✅（均过）|
| 多线程读 | 111.6 | 111.6 | 无 | ✅ |
| 随机写 | 111.2 | 111.1 | 无 | ✅ |
| **随机读** | 55.7 ❌ | **112.2** | **+103%** | A✗ / **B✅** |
| **随机读写 R/W** | 48.6/48.6 ❌ | **76.1/76.1** | **+57%** | A✗ / **B✅** |
| 布局(layout) | 112.1 | 112.1 | 无 | ✅ |

**核心结论：全内存盘下 `--max-readahead 0` + patched v1.3.1 使 B 组 8/8 全项达标。**

关键发现：

1. **ra0 是随机读/混合负载达标的关键开关**：默认预读（2 MiB）对随机读造成 2.02× 投机预取放大（object GET 111 MB/s 但 fio 有效仅 55.7），关预读后放大降至 ~1.0×，randread 翻倍（55.7→112.2）、randrw +57%（48.6→76.1）。真盘上 ra sweep 未发现此效果，是因为后端磁盘瓶颈（~52）掩盖了预读浪费。
2. **写类真实吞吐 ~111-112 MB/s（打满千兆 99%）**：fio 全程平均曾报 120-127（>千兆上限）是客户端写缓冲暂态假象；稳态中位数 ~111 是真值。写类不受 ra0 影响（A=B）。
3. **randrw 不再是"硬骨头"**：历史真盘 13-19、全内存盘默认 48，关预读后 76 达标——其瓶颈同样源于随机读放大，ra0 一并解决。
4. **gc --delete 语义厘清**：randwrite 覆盖写产生的 orphan slice 在文件仍存在时 gc 正确 skip（非 bug），删文件后 gc 生效。每轮 rand 后删文件 + gc + 重建 layout 可持续保证净态。
5. **剩余待查**：seqread 单流（A=103，网卡 RX 仅 93% 未撞墙、放大~1.0×却不满速），疑单流 psync 延迟受限/FUSE+meta 开销，非放大问题。

## 三、深度诊断工作（阶段 4）

为定位调优后残余瓶颈，执行了大量诊断实验，形成完整证据链：

### 3.1 瓶颈分层定位

| 诊断层 | 路径 | 放大倍数 | 初步判断 |
|--------|------|---------|------|
| L1 裸 librados（rados bench 256K rand） | 绕过 JuiceFS/FUSE | **1.04×** | EC 取片传输开销仅 4%，后端可能非放大主要来源 |
| L2 JuiceFS FUSE（端到端） | 全链路 | **~2.5×** | ~~放大可能主要在 JuiceFS 内部~~ **已定位：loadRange bug 造成 2× 放大，patch 后降至 1.11×** |

### 3.2 strace 系统调用级追踪

通过 `strace` 追踪 JuiceFS 进程的 Ceph socket 读取行为：

- 每个 fio 256K 读取触发 **139 次 socket read() 调用 ≈ 4 OSD × 35**
- 数量上接近 EC 4+2 四分片，初步排除 slice 碎片化假设
- ~~怀疑残余放大与 Ceph messenger 协议帧开销有关，仍在进一步确认~~
- **已定位**：139 次 socket read 的根因是 loadRange bug 导致全块读取，patch 后每次随机读仅触发 67K 后端读取（1.11× 放大），socket read 次数大幅下降

### 3.3 穷举排除的无效方向

| 方向 | 排除依据 |
|------|---------|
| 磁盘介质（HDD→SSD） | 裸盘实测 4K 随机读 92,500 IOPS，确认为 SSD |
| WAL/DB 换更快介质 | 内存盘测试仅 +4.8%，无效¹ |
| 全内存盘集群 | 纯 RAM 替换 SSD 后吞吐不变（106.6 vs 106.4） |
| BlueStore 引擎参数 | 三组参数全部无效 |
| EC→副本（size=3） | 实测反而慢 16%（写放大 3× > EC 1.5×） |
| 磁盘调度器/IO 合并 | 所有指标纹丝不动 |
| RGW HTTP 层 | 去掉后随机读仅 +22%，非根因 |
| JuiceFS 并发/缓冲/预读参数 | buffer-size 反降，prefetch 无变化 |
| 元数据（TiKV） | 延迟仅 1ms，非瓶颈 |
| FUSE 内核节流 | waiting≈0 全程 50 采样点 |
| FUSE splice/max_read/max_pages | 系统 kernel 5.15 / fusermount 3.10.5 不支持 |
| EC 2+1 / MTU jumbo / overwrites | L1=1.04× 已证 EC/网络非放大源 |
| JuiceFS v1.4 升级 | 单客户端反而 -3.3%（但 v1.4 含 loadRange 修复，需重评随机读净收益） |
| CephFS 内核态对照 | 读 3.6× 但写触发 EC RMW 反降 |

> ¹ **BlueFS stall / 独立 NVMe 的定位订正（2026-07-06，详见 `doc/perf-analysis/11_1-step2-stall-compaction-branch.md`）**：
> 高强度写期间出现的 `DB_DEVICE_STALLED_READ_ALERT` 经 GLM 干净基线复核确认为**可管理现象、非硬瓶颈**——干净态（`compact_queue_len=0`）下 layout 128G + 64G 多 job 写全程零 stall；触发需"单流持续写 + OSD 已有 compaction 积压"两条件同时满足，`compact` 命令可秒级清除积压（restart OSD 不行）。因此**独立 NVMe 做 DB/WAL 从"生产必须"降为"可选优化"**（仅在无法控制写入模式且 compaction 长期跟不上的场景才必要）。此结论与本行"WAL/DB 换介质收益有限"一致。
> 另注：Ceph 因 RAID 卡（PERC H730）不透传介质而将 SSD 误判为 HDD，导致 `bluestore_prefer_deferred_size=65536`（256K 写的 64K 分片走 deferred 双写）。rados 直打池改回 SSD 行为（=0）后端 **+23%**（72.3 vs 58.6），但经 JuiceFS 端到端未显化——**JuiceFS 写路径吞吐才是写侧真实瓶颈，待查（见 11_1 待办 A）**。
| 多客户端聚合 | 有效但验收线同步抬高，治标不治本 |

### 3.4 诊断结论汇总

| 发现 | 依据 |
|------|------|
| 随机读 2.5× 放大根因 = loadRange bug（非 EC/messenger） | 源码分析 + patch 后放大 2.17×→1.11× + randread r1 +10.7% |
| ra 对 randread 无影响（patch 后，真盘上） | ra sweep: ra=0/1/2/4/8 的 randread r1 均为 51-53 MiB/s |
| 之前"ra=0 救随机读"是带 bug 版本的假象 | bug 造成 2× 放大 + ra 预读叠加；ra=0 消除预读部分但 bug 放大仍在 |
| randrw 瓶颈部分来自 upload 并发度不足 | mu=150 冷态 randrw +86%（14.3→26.6），暖态 +30%（18.9→24.6） |
| 全量测试 randread r1 低于稳态值 | 全量测试在 layout 写 128G 后仅 cooldown 120s 即跑随机读，OSD RocksDB compaction 未完成导致 r1=37.2；同配置在 OSD 稳定后（drop OSD cache）r1=52.0 |
| 写类未达标核心 = JuiceFS 写路径吞吐 | rados 直打 EC 池 256K 裸能力均值 52.7，而 JuiceFS multi-seqwrite 仅 40.8（约 -23% JuiceFS 层损耗） |
| BlueFS stall 是可管理现象 | 干净态零 stall，`compact` 命令秒级清除积压，独立 NVMe 降为可选优化 |
| SSD 被 RAID 卡误判为 HDD | `bluestore_prefer_deferred_size` 双写，改回 SSD 行为后端 +23% 但端到端未显化 |

> **阶段 5 补充**：全内存盘测试（去掉磁盘瓶颈）证实上述"写类未达标 = 磁盘/RAID 层瓶颈"判断正确——内存盘下写类全项达标（~111-112）。ra0 在真盘上"无影响"是因为后端磁盘（~52）掩盖了预读放大；内存盘下后端不再瓶颈，预读 2.02× 放大暴露，ra0 使 randread/randrw 达标。

> **关于 B 组 randread（112.2）> seqread（69.1）的说明**：这并非 JuiceFS 特性，而是两项测试的 fio 并发度不同——seqread 为单线程（numjobs=1, psync, iodepth=1），randread 为 128 线程（numjobs=128, libaio, iodepth=128）。单线程顺序读受限于单请求往返延迟（clat 均值 3.6ms → 256K/3.6ms ≈ 71 MB/s，与实测 69 吻合），无法打满千兆网卡（NIC RX 仅 73 MB/s，利用率 62%）；128 线程随机读则充分并发打满网卡（NIC RX=118，利用率 100%）。同口径对照：multi-seqread（16 jobs, ra=0）= 112 MB/s，与 randread 几乎一致——一旦并发足够，顺序读同样打满千兆。此外 ra0 对两者效果相反：顺序读单流受益于预读流水线（103→69，-33%），随机读 128 线程受预读 2.02× 投机放大拖累（55.7→112.2，+103%），两效果叠加造成 B 组 randread > seqread 的表象。

### 5.3 真盘残余瓶颈分析

> 冷态下仅顺序读和多线程读达标。以下为未达标指标的瓶颈定位：

- **随机读写（randrw）是最大缺口**：冷态最优 26.6/26.3，距 59 差 55%。读写混合场景下读被写阻塞，即使 mu=150 提升 upload 并发度（14.3→26.6，+86%），仍有 2.2 倍差距。多客户端聚合测试中 randrw 总带宽可达 76.6（3 客户端），但单客户端仍受限。
- **随机读已大幅改善但仍差 12%**：patch 修复 loadRange bug 后随机读从 33.6 提升至 52.0（+55%）。ra sweep 证实 ra 对 randread 无影响（真盘上后端瓶颈掩盖），无需设 ra=0。剩余 12% 差距可能与 EC 对象读取粒度及客户端并发调度有关。
- **顺序写差 3%、随机写差 6%**：接近达标的两个指标。mu=150 对顺序写提升 12%，对随机写提升 4%。主要瓶颈为 1Gbps 网络带宽限制（单网卡线速 ~118 MB/s，EC 写放大 1.5× 后 net 有效 ~79 MB/s）。
- **写类未达标核心 = JuiceFS 写路径吞吐，不是 mu/buffer 参数**：rados 直打 EC 池 256K 裸能力均值 52.7，而 JuiceFS multi-seqwrite 仅 40.8（约 -23% JuiceFS 层损耗）；顺序写/随机写在 mu=150 是贴 59 上下浮动（运行间方差），扫 mu/buffer 未坐实达标。
- **BlueFS stall 是可管理现象、非硬瓶颈**：干净态零 stall，`compact` 命令秒级清除积压，独立 NVMe 降为可选优化。
- **SSD 被 RAID 卡误判为 HDD**：`bluestore_prefer_deferred_size` 双写，改回 SSD 行为后端 +23% 但端到端未显化。
- **多客户端聚合**：patched + mu=150 + default ra 下，3 客户端冷态聚合 randread 74.2，randrw 总带宽 76.6。后端带宽是共享瓶颈。
- **修复落地路径**：patch 是验证手段，生产落地需升级到含 eaf3d21f 的 v1.4.x 或向 release-1.3 backport。

**ra0 结论的演进与修正：**

阶段 4 在真盘上做 ra sweep，结论是"ra 对 randread 无影响，无需设 ra=0"。该结论在真盘环境下成立——后端磁盘是瓶颈（~52 MB/s），预读放大虽浪费后端带宽但不影响有效吞吐（后端和有效都被同一瓶颈墙限住）。全内存盘去掉后端瓶颈后，默认预读的 2.02× 投机放大暴露：object GET 111 MB/s 但 fio 有效仅 55.7 MB/s，一半带宽浪费在预读上。关预读后有效吞吐翻倍。

**生产挂载参数建议**：按负载选配——随机读/混合负载为主**必须** `--max-readahead 0`；顺序单流读为主保留默认预读（关预读使顺序读 -33%）。

**写类真实吞吐厘清**：fio 全程平均曾报 120-127 MB/s（>千兆物理上限 ~118），是客户端写缓冲暂态假象。达标值一律取 fio bw_log 瞬时带宽稳态中位数（截缓冲暂态，见 `skills/TESTING-GUIDE.md §5.6`）。稳态真值 ~111-112 MB/s。

### 5.5 下一步：生产环境调优

全内存盘达标验证是**阶段性里程碑**——证明了 JuiceFS 软件层（patched v1.3.1 + 正确参数）在千兆网络上能够实现 59 MB/s 全项达标。真盘上未达标项的根因已明确：

| 真盘未达标项 | 根因 | 内存盘验证 | 生产方向 |
|-------------|------|-----------|---------|
| 顺序写（差 3%） | JuiceFS 写路径损耗 ~23% | 内存盘 111 ✅ | 写路径专项优化或接受贴线速 |
| 随机写（差 6%） | 同上 | 内存盘 111 ✅ | 同上 |
| 随机读（差 12%） | 后端磁盘瓶颈 + 预读放大 | 内存盘 ra0=112 ✅ | 生产挂载加 `--max-readahead 0` |
| 多线程写（差 26%） | 同写路径损耗 | 内存盘 111 ✅ | 同上 |
| 随机读写（差 55%） | 随机读放大（同根因） | 内存盘 ra0=76 ✅ | 同上 |

后续工作转为**基于实际生产环境的调优**：
1. **生产挂载参数固化**：`--max-readahead 0` + `--max-uploads 150` + `--cache-size 0`（冷态基线）或 `--cache-size 100G`（暖态缓存，按场景）
2. **patch 落地**：升级到含 eaf3d21f 的 v1.4.x 或向 release-1.3 backport
3. **真盘环境复测**：在真实生产 SSD 上验证内存盘达标结论的可达性（磁盘介质差异可能导致性能低于内存盘参照值）
4. **writeback 模式评估**：生产环境对写入延迟敏感的场景可启用 `--writeback`，利用本地缓存异步刷盘（数据来源：2026-06-29 测试，详见 §四.2 脚注）

> **writeback 参考**：cache=100G + mu=150 + writeback 下，顺序写 346、随机写 688、随机读写 268/270 MB/s（均为本地缓存性能，非后端真实吞吐，NIC 监控证实网络流量 <20 MB/s）。适用于对写入延迟敏感、允许异步持久化的生产场景，但冷态首次读仍需走后端。
